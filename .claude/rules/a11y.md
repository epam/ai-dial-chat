# Accessibility (WCAG 2.1 AAA)

All apps and libs target WCAG 2.1 **AAA** where the criterion has a normal-text/AA-vs-AAA distinction (contrast, focus, help text). Apply these patterns whenever adding or reviewing interactive UI, not only when explicitly asked for an "accessibility pass".

## Decorative icons inside an already-labeled control

When an icon sits inside a button/control that already carries an `aria-label` (or renders next to visible label text), mark the icon `aria-hidden` so assistive tech doesn't get a redundant/competing name.

```tsx
// Correct
<GhostIconButton
  icon={<IconTrashX size={DIAL_ICON_SIZE.SM} aria-hidden />}
  aria-label={labels.deleteMessage ?? 'Delete message'}
  onClick={onDelete}
/>

// Wrong — icon has no aria-hidden
<GhostIconButton icon={<IconTrashX />} aria-label="Delete message" />
```

## Toggle state must be programmatic, not just visual

A button whose only feedback is a CSS class change (color, icon swap) is invisible to screen readers. Expose the state via the matching ARIA attribute:

| Pattern                                     | Attribute                                                                                                                         |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Like/dislike, pressed/active toggle         | `aria-pressed={isActive}`                                                                                                         |
| Expand/collapse ("Show more" / "Show less") | `aria-expanded={!isCollapsed}` + `aria-controls={targetId}` (pair with a real `id` on the controlled element, e.g. via `useId()`) |
| Tab/step/segment selection                  | `aria-selected` / `aria-current`                                                                                                  |

## Focus-trap: closed/hidden panels with focusable descendants

Never set `aria-hidden="true"` on a container while its focusable descendants (inputs, buttons) remain mounted and tabbable — that leaves keyboard focus reachable inside a region hidden from assistive tech. Use the `inert` prop instead (React 19+ supports it natively); `inert` removes the subtree from both the accessibility tree and the tab order.

```tsx
// Wrong — content is aria-hidden but still focusable via Tab
<aside aria-hidden={!isOpen}>{children}</aside>

// Correct
<aside inert={!isOpen}>{children}</aside>
```

## Status feedback for dynamic content

Any action or state change that has no visible, persistent text confirmation (copy-to-clipboard success, search "no results", streaming text, a banner inserted into a feed) needs an `aria-live` announcement:

```tsx
<span role="status" aria-live="polite" className="sr-only">
  {copyStatus}
</span>
```

- Use `aria-live="polite"` for confirmations and status changes; reserve stronger announcement patterns for genuine errors.
- For a group of buttons that mutates a shared visual state (e.g. a copy icon that swaps to a checkmark), keep the `aria-live` region separate from the button's own `aria-label` — the label should stay stable ("Copy response"), the live region carries the transient "Copied!" message.
- For character-limited fields, only announce near/at the limit (e.g. within the last 10 characters), not on every keystroke — a live region that fires on every character is unusable noise.
- For continuously streamed content (chat/assistant text), `aria-live="polite" aria-atomic="false"` on the text container is the standard pattern; don't toggle the `aria-live` value on/off mid-stream.

## Author/role identification in message-like or card-like feeds

When a component renders different visual treatments for different "authors" or "kinds" of item in a list (chat messages from user vs. assistant, notification types, etc.), expose that distinction with `role="group"` + `aria-label` (or an equivalent named region) on each item's root — color/alignment alone is not accessible.

```tsx
<div
  role="group"
  aria-label={labels.assistantMessageAriaLabel ?? 'Assistant message'}
>
  ...
</div>
```

## Contrast fallback colors (AAA: 7:1 for normal text, 4.5:1 for large text)

When writing a `var(--token, var(--fallback-token, #hex))` chain for **real body/content text** (not decorative or disabled-looking secondary text), the `#hex` fallback must itself pass 7:1 against the paired background fallback. Use the established `var(--text-primary, #161b2d)` fallback for primary content text — it resolves to ~15:1 against the standard light background fallbacks used across `libs/*`. Do **not** reach for `var(--text-secondary, #57647A)` (~6.2:1 on light backgrounds) for anything that isn't genuinely secondary/muted UI text, since it fails AAA for normal-size text.

## Heading structure and section grouping

- A reusable field-set or panel embedded inside different host forms should still be discoverable as one named region — expose an optional `ariaLabel` prop that wraps the root in `role="group"` when supplied, rather than assuming the host always renders its own heading above it.
- Don't let a component's own heading level (e.g. an `<h2>` section title) exist with no `<h1>` ancestor anywhere in the tree it's mounted into — a panel/dialog's title bar should render as `<h1>` (or the appropriate level for its nesting), not a styled `<div>`/`<span>`.

## Focus-visible must match hover, not be a lesser version of it

If `:hover`/`:active` change background/border color to communicate interactivity, add the same change to `:focus-visible` (in addition to, not instead of, any outline). Keyboard users should get at least as much visual feedback as mouse users, never less.

```scss
// Correct
&:hover,
&:active,
&:focus-visible {
  background: var(--accent-bg-hover);
  border-color: var(--accent-border-hover);
}
```

## Keyboard parity for hover-only affordances

Any `onMouseEnter` handler that does real work (preloading data/UI, not just a tooltip) needs an `onFocus` counterpart, or keyboard-only users who Tab to the control never get the same benefit mouse users get before they click.

```tsx
<GhostIconButton
  onClick={onEdit}
  onMouseEnter={onEditHover}
  onFocus={onEditHover}
/>
```

## Scope boundary

These patterns apply to code owned by this repo (`apps/*`, `libs/*`). Accessibility gaps that live inside an installed package (`@epam/ai-dial-ui-kit`, `@epam/ai-dial-kit` internals in `node_modules`) are out of scope for a fix here — note them instead of patching generated/vendor output.
