# Tasks

Slicing strategy: **vertical**, one path through the stack working end to end before widening. Slice 1 lands the merge primitive and threads the new `nextRunTime` option through the whole stack inert (no active refresh yet) so every later slice builds on a working, tested plumbing path rather than local logic with no consumer. Slices 2 and 3 then activate each of the two independent triggers on top of that foundation. Slice 4 covers the two app-level call sites' own tests. Slice 5 is integration-only.

## 6. Post-implementation-review fixes

A code-review pass (after slice 5) against the real implementation found four behavior defects the original slices' tests didn't catch, plus one false-positive test and three tasks-claimed tests that didn't actually exist. Fixed in `libs/chat-hooks/src/scheduled-task/use-scheduled-task-runs.ts` and its test file:

- [x] 6.1 **Unbounded polling on repeated failures**: the no-change counter only advanced on a successful-but-unchanged poll, so a poll that errors (e.g. a failing upstream) never counted toward the stop threshold, polling every 15s indefinitely — violating "polling is bounded." Fixed: the counter now advances on both `Unchanged` and `Error` results (an error tells us nothing changed either), resets only on `Changed`. Verified by a new test, "stops polling after 20 consecutive polls that each fail, without polling indefinitely".
- [x] 6.2 **`changed` read after a `setItems` updater**: computing the merge and reading whether it changed inside the `setItems` functional updater relied on React's internal (non-guaranteed) eager-updater timing. Fixed: the merge is now computed directly against a new `itemsRef` (kept in sync at render time and updated eagerly on a real change), with `setItems` called only when something actually changed — deterministic, no reliance on updater-timing internals.
- [x] 6.3 **One-shot `nextRunTime` timer could be silently cancelled**: it shared one `useEffect` (and dependency array, including `hasInProgressRun`) with the poll interval; a `hasInProgressRun` toggle landing inside the `(nextRunTime, nextRunTime+5s)` window tore the effect down and — because `nextRunTime` had already passed by then — never rescheduled it, losing the one-shot refresh. Fixed: split into two independent effects (poll interval; one-shot timeout), each keyed only on the dependencies it actually needs, plus a third shared effect owning the single `visibilitychange` listener and the cross-trigger "at most one catch-up" flag. Verified by a new regression test, "still fires the one-shot nextRunTime refresh even if a poll tick clears the in-progress run inside the waiting window", timed so a poll tick lands exactly inside that window.
- [x] 6.4 **Past-due immediate refresh ignored tab visibility**: an already-past `nextRunTime` fired its immediate refresh even when the tab was hidden at mount, violating "no requests while hidden." Fixed: it now goes through the same `attemptBackgroundRefresh` helper as the other two triggers, deferring to the shared catch-up mechanism when hidden. Verified by a new test, "defers a past-due nextRunTime refresh until the tab becomes visible, when mounted hidden".
- [x] 6.5 **False-positive test removed, three missing tests added**: "does not poll while isLoading or isLoadingMore is true" could not actually fail if that guard were deleted (given `hasInProgressRun` requires loaded `items`, which are always empty during the initial load) — replaced with "does not poll while no run is in progress" (a real assertion of the `hasInProgressRun` gate) plus two tests `tasks.md` had claimed but that didn't exist: "each poll tick's request carries its own AbortController, distinct from the initial fetch's" and "stops the previous schedule's polling and aborts its in-flight background request when scheduleId changes". Coverage of the `isLoadingMore` guard remains via the existing "never overlaps a foreground loadMore request" test.
- [x] 6.6 Converted the internal `BackgroundRefreshResult` result type from a string-literal union to a plain (non-exported) `enum`, per `AGENTS.md`'s TypeScript-enums rule (a named finite set of outcomes, compared in logic and tests) — colocated in `use-scheduled-task-runs.ts` itself, matching this lib's existing precedent for hook-private enums (`SkillPreviewErrorKind` in `useSkillFilePreview.ts`, `FavoriteEntityType` in `useFavoriteEntitiesState.ts`) rather than a separate `types/` file, since nothing outside this file needs it.
- [x] 6.7 Re-ran `npm run test:file -- libs/chat-hooks/src/scheduled-task/tests/useScheduledTaskRuns.spec.ts` (21/21 pass), the two app-consumer test files (unaffected, still pass), and `nx lint`/`nx run …:typecheck` for `@epam/ai-dial-chat-hooks` (0 lint errors after a Prettier auto-format pass, typecheck clean) to confirm the fixes.
- [x] 6.8 Run `npm run verify:changed` once to confirm this slice's lint/typecheck/test pass together, closing out the post-review fix pass. Passed clean: `typecheck:affected`, `lint:affected`, `test:changed` all green.

## 7. Second review pass: five lower-severity fixes

A second, final review (after slice 6) confirmed all eight slice-6 fixes are genuine, then found five smaller remaining issues:

- [x] 7.1 **`itemsRef`/`loadMore` same-batch race**: `backgroundRefresh` only checked `isLoadingRef`/`isLoadingMoreRef` before its network call, not after — so a `loadMore()` invoked while a background request was in flight could have its appended page overwritten by a merge computed from a stale `itemsRef` snapshot. Fixed: the same guard is re-checked immediately after the `await`, before touching `itemsRef`/`setItems`; a foreground fetch that started during the wait now causes the background attempt to defer (`Skipped`) instead of racing it. Verified by a new test, "defers to a loadMore that starts while a poll request is still in flight, instead of clobbering its appended page".
- [x] 7.2 **One-shot refresh didn't claim `handledPastNextRunTime`**: after the one-shot fired, a later `loadMore()`/`refetch()`-driven `isLoading`/`isLoadingMore` toggle could re-run Trigger 3 and fire a redundant extra background refresh for the same already-past `nextRunTime`. Fixed: the one-shot's callback now sets `handledPastNextRunTime.current = nextRunTime` before invoking the refresh. Verified by a new test, "does not trigger a redundant refresh from a later loadMore once the one-shot has already claimed nextRunTime".
- [x] 7.3 **`setTimeout` 32-bit overflow for a far-future `nextRunTime`**: a monthly-or-less-frequent cron schedule's next run can exceed `setTimeout`'s ~24.8-day limit, which silently converts a raw `setTimeout` into an immediate fire. Fixed: added `scheduleAfter`, a chained-`setTimeout` helper that steps through `MAX_SAFE_TIMEOUT_MS`-sized delays for a total beyond the limit, used by the one-shot trigger. Verified by a new test, "schedules a far-future nextRunTime without overflowing setTimeout, firing once at the real target" (30-day `nextRunTime`).
- [x] 7.4 **Stale `{@link useScheduledTaskRuns}` JSDoc reference**: `nextRunTime`'s doc pointed at the hook's own one-line summary, which didn't actually mention background refresh. Fixed: expanded the hook's summary to "Shared, cancellation-safe pagination and background refresh for one schedule's run history."
- [x] 7.5 **Comment-style sweep missed the test file**: slice 6.9 only converted multi-line `//` blocks in the hook source file; four remained in `useScheduledTaskRuns.spec.ts`. Converted all four to `/* ... */`.
- [x] 7.6 Re-verified with `nx lint`/`nx run …:typecheck` for `@epam/ai-dial-chat-hooks` (0 errors after fixing a Prettier formatting issue and an `@typescript-eslint/no-empty-function` violation introduced by 7.3's initial draft) and `npm run test:file` for the hook (23/23 pass) and both app-level consumer test files (unaffected, still pass).
- [x] 7.7 Run `npm run verify:changed` once to close out this fix pass. Passed clean: `typecheck:affected`, `lint:affected`, `test:changed` all green.
