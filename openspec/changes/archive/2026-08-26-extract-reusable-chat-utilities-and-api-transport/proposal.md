## Why

`apps/chat/src/utils/{get-model-id-from-conversation-id,resolve-dial-file-api-path,attachment-types,dial-file-to-attachment}.ts` and `apps/chat/src/server-api/{api-error,api-client,files.api,upload-file-with-progress,chat-stream.api}.ts` implement pure DIAL-protocol parsing and browser API transport that has no dependency on `apps/chat`-specific state, yet every one of them is either duplicated as a private, non-exported mirror inside `libs/chat-hooks` today (`resolve-dial-file-api-path.ts`, `mimeTypesToFileAccept`/`isDialFileAcceptType`/`mimeTypesToDialFileAcceptTypes` inside `useAttachmentValidation.ts`) or has no shared home at all (`get-model-id-from-conversation-id.ts`, `dial-file-to-attachment.ts`, and the five `server-api` transport files). The private mirrors have already drifted from the app copy they were duplicated from — `libs/chat-hooks/src/attachment/useAttachmentValidation/useAttachmentValidation.ts:32-41`'s `mimeTypesToFileAccept` filters out non-accept-type values before joining them, while `apps/chat/src/utils/attachment-types.ts:22-32`'s version of the same function does not, so `DialFileManagerModal.tsx` and `useAttachmentValidation`'s callers can silently disagree on which file types the file picker declares acceptable. Every future client of this codebase that wants to reuse this logic today has no option but to copy the files by hand, reproducing exactly this kind of drift.

The main chat repository should be the single canonical implementation of this pure logic and its transport shell, published as stable, host-agnostic exports from `@epam/ai-dial-chat-hooks`, so any DIAL-Core-backed client can depend on the package instead of hand-copying `apps/chat/src/**` files.

## What Changes

- Consolidate the four pure `apps/chat/src/utils/*.ts` files audited below into host-agnostic exports of `@epam/ai-dial-chat-hooks`, fixing the `mimeTypesToFileAccept` filtering divergence in the process (one behavior, matching `mimeTypesToDialFileAcceptTypes`'s already-documented filtering semantics) — **BREAKING** for any caller currently relying on `apps/chat/src/utils/attachment-types.ts`'s unfiltered `mimeTypesToFileAccept` output.
- Reconcile `apps/chat/src/utils/resolve-dial-file-api-path.ts` with the existing private mirror at `libs/chat-hooks/src/files/resolve-dial-file-api-path.ts`: promote the lib's version to a public barrel export, migrate `DialFileManagerShell.tsx`'s one `getParentFolderPath` call site to it, and delete the now-fully-superseded app file.
- Move `getModelIdFromConversationId` to `@epam/ai-dial-chat-hooks` as-is (zero host dependency, single app call site to migrate).
- Extract `dialFileToAttachment`/`dialFilesToAttachments`/`dialFolderPathToAttachment`'s pure DIAL-file-to-`Attachment` mapping into `@epam/ai-dial-chat-hooks`, replacing the direct `resolveCatalogIconUrl` call with an injected `resolvePreviewUrl?: (url: string) => string | undefined` callback so the host-owned bucket/icon-URL construction stays in `apps/chat/src/utils/icon-path.ts`.
- Extract the CSRF-token and unauthorized-401 middleware behavior of `apps/chat/src/server-api/api-client.ts` into a `@epam/ai-dial-chat-hooks` factory that accepts CSRF getter/setter, an unauthorized callback, an invalid-CSRF classifier, and a CSRF-refresh function as parameters, returning `Middleware` objects the host wires into its own generated-client `Configuration` — **BREAKING** in that `api-client.ts` no longer defines `csrfMiddleware`/`unauthorizedMiddleware` inline.
- Extract `apps/chat/src/server-api/files.api.ts`'s 16 thin wrapper functions into a `@epam/ai-dial-chat-hooks` factory that accepts an already-configured generated `FilesApi` instance and an `uploadFileWithProgress` implementation, returning the same function surface.
- Extract `apps/chat/src/server-api/upload-file-with-progress.ts` into a `@epam/ai-dial-chat-hooks` factory parameterized by an XHR factory, the CSRF getter/setter pair, the unauthorized callback, and the upload base path.
- Extract `apps/chat/src/server-api/chat-stream.api.ts`'s `streamCompletion`/`stopCompletion`/`parseSSELine` into a `@epam/ai-dial-chat-hooks` factory parameterized by a `fetch` implementation, the CSRF getter/setter pair, the unauthorized callback, the completions base path, and a timezone-header resolver.
- Move `apps/chat/src/server-api/api-error.ts`'s already host-agnostic `getApiErrorStatus`/`getApiErrorMessage`/`getApiErrorDetails`/`isConversationNotFoundError` to `@epam/ai-dial-chat-hooks` as-is.
- Migrate `apps/chat` to consume every one of the above through the new `@epam/ai-dial-chat-hooks` exports, deleting the app-owned duplicate implementation in each case once the migration is verified against the existing test suites.
- No change to `apps/chat/src/server-api/base.ts`'s CSRF-token state, `ApiEndpoints` enum, or session/cookie handling — these stay app-owned and are passed into the new factories as plain arguments.
- Extend the same audit-and-extract treatment to the rest of `apps/chat/src/utils/` (58 files not already covered above): move every file with no host-owned import (pure functions over `Conversation`/`Message`/`Attachment`/DTOs/plain strings — conversation/message helpers, catalog-entity/prompt/scheduled-task/skill DTO-to-UI mapping, MIME/date/string formatting) to `@epam/ai-dial-chat-hooks` as-is, and every file that is *mostly* pure but has one or two small host-owned pieces (an `i18n` `t()` call, a hardcoded `/api/...` URL builder, an app-local enum/context type) by extracting the pure majority and injecting the host-owned piece as a parameter/callback — the same `resolvePreviewUrl`-style seam already used for `dialFileToAttachment`. Files that are host-owned throughout (session/localStorage, REST paths, React contexts, routing, OAuth/window flows, or where the translated string *is* the function's entire output) stay in `apps/chat/src/utils/` untouched. `apps/chat/src/utils/request-api-key.ts` is dead code (zero consumers) and is deleted outright, not migrated.

## Capabilities

### New Capabilities

- `chat-hooks-conversation-path-utilities`: host-agnostic `getModelIdFromConversationId` conversation-ID parsing, published from `@epam/ai-dial-chat-hooks`.
- `chat-hooks-attachment-mapping`: host-agnostic DIAL-file-to-`Attachment` mapping (`dialFileToAttachment`/`dialFilesToAttachments`/`dialFolderPathToAttachment`) and MIME/accept-type helpers (`mimeTypesToFileAccept`/`isDialFileAcceptType`/`mimeTypesToDialFileAcceptTypes`/`mimeTypesToAttachmentExtensionLabels`), published from `@epam/ai-dial-chat-hooks` with the icon/preview-URL resolution injected by the host.
- `chat-hooks-api-transport`: host-agnostic factories for CSRF/unauthorized generated-client middleware, a files-API wrapper, upload-with-progress, and streamed-completion transport, plus the already host-agnostic API error/trace parsing helpers, all published from `@epam/ai-dial-chat-hooks`.
- `chat-hooks-domain-utilities`: the bulk of `apps/chat/src/utils/`'s remaining pure and mostly-pure domain utilities — conversation/message helpers, DIAL-file path/URL parsing, attachment-display mapping, catalog entity/prompt/scheduled-task/skill DTO-to-UI mapping, and locale/formatting/string helpers — published from `@epam/ai-dial-chat-hooks`, with every host-owned i18n/URL/context piece injected as a parameter rather than imported.

### Modified Capabilities

- `chat-hooks-file-manager-domain`: `getParentFolderPath`/`virtualPathToApiPath`/`resolveDialFileApiPath` move from private, internal-only helpers to a public `@epam/ai-dial-chat-hooks` barrel export that `apps/chat` itself also consumes.
- `generated-api-client-integration`: the CSRF and unauthorized middleware requirements move from being defined inline in `apps/chat/src/server-api/api-client.ts` to being satisfied by calling a `@epam/ai-dial-chat-hooks` factory with the same observable behavior; `api-client.ts` retains ownership of client configuration, the telemetry middleware, and every domain singleton.
- `api-error-trace-correlation`: `getApiErrorStatus`/`getApiErrorMessage`/`getApiErrorDetails`/`isConversationNotFoundError` move from `apps/chat/src/server-api/api-error.ts` to `@epam/ai-dial-chat-hooks`, with `apps/chat` re-exporting or directly importing the library implementation; the resolution order, W3C trace validation, and single-consumption-safe body reading are unchanged.

## Impact

- **Affected libs**: `libs/chat-hooks/src/index.ts` gains new public exports (files, attachment mapping, conversation-path parsing, API transport factories, API error helpers); its `package.json` peer dependencies gain whatever generated-client/`XMLHttpRequest`-adjacent types the transport factories' signatures require.
- **Affected app code**: `apps/chat/src/utils/{get-model-id-from-conversation-id,resolve-dial-file-api-path,attachment-types,dial-file-to-attachment}.ts`, `apps/chat/src/server-api/{api-error,api-client,files.api,upload-file-with-progress,chat-stream.api}.ts`, and their six call sites (`ConversationPanelView.tsx`, `DialFileManagerShell.tsx`, `DialFileManagerModal.tsx`, `ConversationView.tsx`, `useDialFileManagerState.ts`, plus every one of the 21 `api-error.ts` consumers) are migrated to import from `@epam/ai-dial-chat-hooks` instead; the app files are deleted once migrated.
- **No change** to `apps/chat/src/server-api/base.ts`, CSRF/session cookie policy, `ApiEndpoints` values, or any DIAL Core-facing HTTP contract — this is an internal ownership/packaging change with identical runtime behavior (aside from the one documented `mimeTypesToFileAccept` bug fix).
- **Tests**: every existing Vitest suite for the ten audited files (`apps/chat/src/utils/tests/*.spec.ts`, `apps/chat/src/server-api/tests/*.spec.ts`) moves with its implementation into `libs/chat-hooks`, with a thin app-level smoke test replacing it where a real app call site remains.
- **Extended scope**: ~41 additional `apps/chat/src/utils/*.ts` files move to `@epam/ai-dial-chat-hooks` under `chat-hooks-domain-utilities` (see `design.md` Decision D11 for the full per-file classification and seam list); the ~17 files that are host-owned throughout stay in `apps/chat`.
