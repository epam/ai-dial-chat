## Context

`libs/chat-hooks` already hosts three generations of extraction from `apps/chat` (`2026-08-24-extract-reusable-chat-hooks`, `2026-08-24-extract-conversation-lifecycle-hooks`, `2026-08-25-extract-attachment-citations-file-manager-hooks`, all archived and implemented). Each established the same shape: pure/host-agnostic logic moves into the lib; anything that needs a configured generated-client instance, CSRF/session state, routing, i18n, or an app REST path stays in `apps/chat` and is passed into the lib as a plain parameter, callback, or already-resolved value (AGENTS.md §Library isolation; `chat-hooks-file-manager-domain/spec.md` Requirement "`DialFilesApi` operation port replaces direct `server-api` access").

Ten files remain unmigrated, split into two groups:

**Pure utilities** (`apps/chat/src/utils/`):
- `get-model-id-from-conversation-id.ts:1-106` — `getModelIdFromConversationId`. Zero imports, pure regex/string logic. Single consumer: `ConversationPanelView.tsx:104,451`.
- `resolve-dial-file-api-path.ts:1-88` — `virtualPathToApiPath`, `getParentFolderPath`, `resolveDialFileApiPath`. Already privately duplicated, byte-for-byte, at `libs/chat-hooks/src/files/resolve-dial-file-api-path.ts:1-120` (not exported from `libs/chat-hooks/src/index.ts`), which instead sources `DialFile`/`DialFileNodeType` from `@epam/ai-dial-react-file-manager` while the app file sources the structurally identical types from `@epam/ai-dial-ui-kit`. Only `getParentFolderPath` has a live app consumer: `DialFileManagerShell.tsx:25,384`. `virtualPathToApiPath`/`resolveDialFileApiPath` have no consumer outside this file and its own test.
- `attachment-types.ts:1-50` — `mimeTypesToFileAccept`, `isDialFileAcceptType`, `mimeTypesToDialFileAcceptTypes`, `mimeTypesToAttachmentExtensionLabels`. `mimeTypesToAttachmentExtensionLabels`/`mimeTypesToDialFileAcceptTypes` are consumed by `DialFileManagerModal.tsx:42-43,397,405`. The other two functions have already been privately re-implemented inside `libs/chat-hooks/src/attachment/useAttachmentValidation/useAttachmentValidation.ts:14-41` — with a **behavioral difference**: the app's `mimeTypesToFileAccept` (`attachment-types.ts:22-32`) joins the raw input types unfiltered when no wildcard is present, while the lib's private version composes through `mimeTypesToDialFileAcceptTypes` first, filtering out anything `isDialFileAcceptType` rejects. `attachment-types.spec.ts:29-33` documents the filtering behavior as `mimeTypesToDialFileAcceptTypes`'s intended contract — the app's sibling `mimeTypesToFileAccept` just never applies it.
- `dial-file-to-attachment.ts:1-80` — `dialFileToAttachment`, `dialFilesToAttachments`, `dialFolderPathToAttachment`. Consumed by `ConversationView.tsx:81-82,569,571` and `apps/chat/src/hooks/files/useDialFileManagerState.ts:5-6,35,37` (the one file-manager hook the predecessor design deliberately kept app-owned, `2026-08-25.../design.md:386-393`, precisely because it produces the app's own `Attachment` shape). `dialFileToAttachment`'s only host-owned dependency is one call, `dial-file-to-attachment.ts:50`, to `resolveCatalogIconUrl` (`apps/chat/src/utils/icon-path.ts:32-39`), which branches into two hardcoded app REST paths (`/api/v1/files/download`, `/api/themes/icon`) via `ApiEndpoints`. Everything else in the file — including `dialFolderPathToAttachment`, which is entirely pure — is a straight DIAL-file-shape-to-`Attachment`-shape mapping.

**API transport** (`apps/chat/src/server-api/`):
- `api-error.ts:1-165` — already fully host-agnostic; duck-types both a generated-client `ResponseError` and a raw `base.ts` `ApiRequestError`, no import of `base.ts` or `api-client.ts`. Already specified by `api-error-trace-correlation/spec.md`.
- `api-client.ts:1-193` — builds one shared `Configuration` (`:173`) wiring a CSRF middleware and an unauthorized middleware (imported from `base.ts:24-33`) plus (per `generated-api-client-integration/spec.md`) a telemetry middleware, then exports 18 domain singletons built from that `Configuration`. Already specified by `generated-api-client-integration/spec.md`, whose "CSRF middleware" and "Unauthorized (401) middleware" requirements describe exactly the behavior this design extracts into a factory.
- `files.api.ts:1-167` — 16 thin wrappers around the `filesApi` singleton; already has a `DialFilesApi`-shaped consumer boundary in `apps/chat/src/server-api/dial-files-api.adapter.ts` from the prior file-manager extraction, and is already specified by `chat-hooks-file-manager-domain/spec.md`'s `DialFilesApi` port requirement — but the port's *implementation* (this file) still lives only in the app.
- `upload-file-with-progress.ts:1-91` — a single raw-XHR upload function; needs the CSRF getter/setter, the unauthorized callback, and the hardcoded `/api/v1/files` path (`:9`) injected. The predecessor file-manager design's Open Questions (`2026-08-25.../design.md:534-539`) already flagged this file's XHR/`/api` coupling as the one host-shell assumption baked into `DialFilesApi`'s upload methods, deliberately deferred at the time.
- `chat-stream.api.ts:1-165` — raw-`fetch` SSE streaming for completions/stop; already has an app-owned transport adapter (`apps/chat/src/utils/conversation-stream-transport.ts`) satisfying `libs/chat-hooks`'s `useConversationStream`, per `2026-08-24-extract-conversation-lifecycle-hooks/design.md`. That adapter wraps this file's exports as a parameter to the hook; this file's own implementation still lives only in the app.
- `base.ts:1-287` — CSRF token state, `ApiEndpoints`, `UnauthorizedError`/`ApiRequestError`, `onUnauthorized`/`notifyUnauthorized`, `isInvalidCsrfErrorBody`, `refreshCsrfToken`. Out of scope for extraction (per the proposal and per every precedent design); documented here only as the dependency surface every transport factory in this change receives as constructor arguments.

No consumer beyond `apps/chat` exists in this repository; this design's job is to make the ten files reusable, not to migrate a second consumer.

## Goals / Non-Goals

**Goals:**
- One canonical, host-agnostic implementation of each of the ten audited behaviors, published from `@epam/ai-dial-chat-hooks`.
- Preserve every currently-tested observable behavior of the ten files (see the per-file `describe`/`it` inventories below) with zero regression, migrating each spec file into `libs/chat-hooks` alongside its implementation.
- Resolve the `mimeTypesToFileAccept` divergence in favor of the filtering behavior already documented and already shipped inside `useAttachmentValidation`.
- Reconcile the `resolve-dial-file-api-path.ts` triple-implementation (app copy, private lib copy, and the type-origin split between `@epam/ai-dial-ui-kit` and `@epam/ai-dial-react-file-manager`) down to one public export.
- Keep every host-owned piece (CSRF state, `ApiEndpoints`, bucket/icon URL construction, session cookies) in `apps/chat`, injected into the new lib exports as plain parameters/callbacks — no lib export constructs its own generated-client `Configuration`, reads `apps/chat`'s CSRF token directly, or hardcodes an `/api/...` path.

**Non-Goals:**
- Migrating `apps/chat/src/server-api/base.ts` itself, or any of its CSRF/session/cookie policy, into a lib.
- Introducing a new consumer application in this change — this is a packaging/ownership change with `apps/chat` as its only migrated caller today.
- Changing any DIAL Core-facing HTTP contract, request shape, or response shape.
- Redesigning `upload-file-with-progress.ts`'s XHR-shaped upload contract into a more abstract transport interface — the file-manager predecessor design already deferred that broader question; this change only makes the existing XHR-shaped contract host-configurable, not host-agnostic-by-abstraction.

## Decisions

### D1 — Owning package: `@epam/ai-dial-chat-hooks` for all ten files, not `chat-shared` or `attachment-input`

`libs/chat-shared` is documented as "shared TypeScript interfaces and types only (no logic)" (`openspec/config.yaml`) — none of the ten files are type-only, so `chat-shared` is not a candidate owner for any of them. `libs/attachment-input` is a `type:ui` lib, restricted to importing from `chat-shared` only (module boundary rules), which rules it out for anything touching `DialFile` (sourced from `@epam/ai-dial-ui-kit`/`@epam/ai-dial-react-file-manager`) or a configured generated-client type. `libs/chat-hooks` is already the owner of the file-manager domain layer (`chat-hooks-file-manager-domain`), the conversation-transfer/attachment-validation hooks, and — per AGENTS.md's second `libs/chat-hooks` exception — is explicitly permitted "the thin request/response logic that calling those operations requires (equivalent in shape to today's `apps/chat/src/server-api/*.api.ts` wrappers)". That clause was written for exactly this class of file. All ten files land in `libs/chat-hooks`.

Alternative considered: a new dedicated `libs/chat-api-transport` package for Part B only, keeping Part A inside `chat-hooks`. Rejected — none of Part B's five files have a peer-dependency or module-boundary reason to be separated from `chat-hooks`, and a second lib would duplicate the CSRF/`DialFile`-adjacent typings `chat-hooks` already carries as peer dependencies, with no isolation benefit.

### D2 — `getModelIdFromConversationId` moves as-is

No behavioral change, no injected parameter — it has no host dependency today. `apps/chat` migrates `ConversationPanelView.tsx:104,451` to the `@epam/ai-dial-chat-hooks` import and the app file is deleted; the existing 15-case spec moves with it unchanged.

### D3 — `resolve-dial-file-api-path.ts` consolidates onto the existing private lib copy, exported publicly

The lib's private copy at `libs/chat-hooks/src/files/resolve-dial-file-api-path.ts` is already behavior-identical to the app's version (diffing shows only the `DialFile`/`DialFileNodeType` import source and the private `isDialFileId`/`resolveRelativeDialFilePath` inlining). Rather than write a third implementation, `libs/chat-hooks/src/index.ts` gains `export * from './files/resolve-dial-file-api-path'`. `DialFileManagerShell.tsx:384`'s `getParentFolderPath` call migrates to the new export; `apps/chat/src/utils/resolve-dial-file-api-path.ts` and its spec are deleted (its other two exports, `virtualPathToApiPath`/`resolveDialFileApiPath`, have no live app consumer, so no other call site changes).

The type-origin split (`@epam/ai-dial-ui-kit` vs. `@epam/ai-dial-react-file-manager`) is left as-is rather than unified: diffing the two packages' compiled `.d.ts` declarations shows the two `DialFile`/`DialFileNodeType` shapes are structurally identical, so there is no runtime risk in the lib continuing to type against `@epam/ai-dial-react-file-manager` (its existing peer dependency) while `DialFileManagerShell.tsx` continues to pass a `@epam/ai-dial-ui-kit`-typed value — TypeScript's structural typing accepts it. Unifying the two packages' type source is a separate, unrelated concern and is called out under Open Questions rather than folded into this change's scope.

### D4 — `attachment-types.ts` consolidates onto the filtering semantics, exported publicly, with one bug fix migrated forward

`mimeTypesToFileAccept`/`isDialFileAcceptType`/`mimeTypesToDialFileAcceptTypes` move to `libs/chat-hooks/src/files/attachment-types.ts` (new file, alongside the other file-domain utilities) with the **filtering** behavior — i.e., the semantics `libs/chat-hooks/src/attachment/useAttachmentValidation/useAttachmentValidation.ts:32-41` already ships and `attachment-types.spec.ts:29-33` already documents as `mimeTypesToDialFileAcceptTypes`'s contract. `useAttachmentValidation.ts` is refactored to import the new public export instead of keeping its own private copy (deleting `:14-41`'s duplication). `DialFileManagerModal.tsx` migrates its `mimeTypesToDialFileAcceptTypes` import to the same source. `mimeTypesToAttachmentExtensionLabels` moves alongside them (single consumer, `DialFileManagerModal.tsx:397`, pure `mime-types`-package logic) — kept as a distinctly-named export from `libs/attachment-input/src/utils/attachment.ts`'s `mimeTypesToExtensionLabels`, since the two produce different presentational output (`.pdf` vs `PDF`) for the same input and must not be conflated.

Alternative considered: keep the app's unfiltered `mimeTypesToFileAccept` behavior and treat the lib's filtering version as the bug. Rejected — the filtering behavior is the one `mimeTypesToDialFileAcceptTypes`'s own test already asserts is correct ("filters out values that cannot be passed to DialFileManager"), and `mimeTypesToFileAccept`'s job is to describe the same acceptable-type set in a different string format, so the two should never disagree about which types are acceptable.

### D5 — `dial-file-to-attachment.ts`'s pure mapping moves with an injected preview-URL resolver; the file is not left entirely app-owned

The predecessor file-manager design (`2026-08-25.../design.md:143,159`) concluded `dial-file-to-attachment.ts` stays app-owned, because at the time no seam existed to separate `resolveCatalogIconUrl` from the mapping. This change adds that seam: `dialFileToAttachment(file, bucket, options?: { resolvePreviewUrl?: (url: string) => string | undefined })` moves to `libs/chat-hooks/src/files/dial-file-to-attachment.ts`, calling `options?.resolvePreviewUrl` in place of the direct `resolveCatalogIconUrl` call at the old `:50`. `dialFilesToAttachments`/`dialFolderPathToAttachment` move alongside it unchanged (the latter has zero host dependency already). `apps/chat`'s two call sites (`ConversationView.tsx:569,571`, `useDialFileManagerState.ts:35,37`) pass `{ resolvePreviewUrl: resolveCatalogIconUrl }` explicitly, keeping `resolveCatalogIconUrl`, `ApiEndpoints`, and the two hardcoded REST paths it touches entirely inside `apps/chat/src/utils/icon-path.ts`. This mirrors the exact injected-resolver pattern `useOpenAttachmentCanvas` already uses for ten other resolvers (`2026-08-25.../design.md` Decision D1).

### D6 — CSRF/unauthorized middleware becomes a factory; client configuration and telemetry stay app-owned

`libs/chat-hooks` gains `createCsrfMiddleware(deps: { getCsrfToken, setCsrfToken })` and `createUnauthorizedMiddleware(deps: { notifyUnauthorized, refreshCsrfToken, isInvalidCsrfErrorBody })`, each returning a `Middleware` object matching `@epam/chat-api-client`'s generated-client middleware contract, with behavior identical to `api-client.ts`'s current inline `csrfMiddleware`/`unauthorizedMiddleware` (CSRF header injection on non-GET, rotated-token capture, invalid-CSRF refresh-and-retry-once, 401 → `notifyUnauthorized` + throw `UnauthorizedError`). `api-client.ts` is refactored to call these two factories with `base.ts`'s existing `getCsrfToken`/`setCsrfToken`/`refreshCsrfToken`/`isInvalidCsrfErrorBody`/`notifyUnauthorized` and keeps building its own `Configuration`, telemetry middleware, and all 18 domain singletons unchanged — `generated-api-client-integration/spec.md`'s "Client configuration factory" and "Telemetry middleware" requirements are untouched; only "CSRF middleware" and "Unauthorized (401) middleware" move to describing the factory's behavior instead of inline code.

Alternative considered: move the whole `Configuration`-building `createApiConfiguration()` into the lib too. Rejected — `Configuration`'s `basePath`, telemetry hook, and the set of 18 domain singletons are app-specific composition, not reusable logic; only the two middlewares are pure enough to factor out, matching D6's precedent in `2026-08-24-extract-reusable-chat-hooks` (configured-client-construction never moves).

### D7 — `files.api.ts` becomes a factory over an injected configured `FilesApi` and an injected upload-with-progress function

`libs/chat-hooks/src/files/create-files-api.ts` exports `createFilesApiClient(filesApi: FilesApi, uploadFileWithProgress: UploadFileWithProgressFn): DialFilesApiTransport`, reproducing all 16 of `files.api.ts`'s current wrapper functions 1:1 (including the `downloadFileRaw`/`downloadArchiveRaw` raw-`Response` handling for binary downloads). `apps/chat/src/server-api/files.api.ts` becomes a two-line call to this factory with the app's `filesApi` singleton and `uploadFileWithProgress` (D8) passed in, preserving its existing exported function names and signatures so `dial-files-api.adapter.ts` and `usePublishFolders.ts` need no changes.

### D8 — `upload-file-with-progress.ts` becomes a factory over an injected XHR factory, CSRF pair, unauthorized callback, and base path

`libs/chat-hooks/src/files/create-upload-file-with-progress.ts` exports `createUploadFileWithProgress(deps: { getCsrfToken, setCsrfToken, notifyUnauthorized, uploadUrl, xhrFactory?: () => XMLHttpRequest })`, returning a function with the exact signature and XHR-progress/abort/response-parsing/CSRF-rotation/unauthorized behavior `upload-file-with-progress.ts:19-91` has today. `xhrFactory` defaults to `() => new XMLHttpRequest()`, overridable by tests and by any host without a global `XMLHttpRequest` (matching the pattern the two archived designs used for their own factory-injected browser APIs). `apps/chat/src/server-api/upload-file-with-progress.ts` becomes a call to this factory with `base.ts`'s CSRF/unauthorized exports and the literal `/api/v1/files` path.

### D9 — `chat-stream.api.ts` becomes a factory over an injected `fetch`, CSRF pair, unauthorized callback, base path, and timezone-header resolver

`libs/chat-hooks/src/conversation/create-chat-stream-api.ts` exports `createChatStreamApi(deps: { getCsrfToken, setCsrfToken, completionsBasePath, getTimezone?: () => string | undefined, fetchImpl?: typeof fetch })`, returning `{ streamCompletion, stopCompletion }` with `parseSSELine` kept as an internal, non-exported helper — matching `2026-08-24-extract-conversation-lifecycle-hooks/design.md:559-571`'s reasoning for why `parseSSELine` was never split into its own public export ("would create a library API surface with exactly one real caller"). Unlike D6/D8, this factory takes no `notifyUnauthorized`/unauthorized-error dependency: `chat-stream.api.ts:19-41,89-96` never special-cases a 401 response today, reporting any non-2xx status generically (a thrown `Error` from `stopCompletion`, an `onError` call from `streamCompletion`) — the factory preserves that behavior rather than introducing unauthorized handling the original file never had. `apps/chat/src/server-api/chat-stream.api.ts` becomes a call to this factory with `base.ts`'s CSRF exports, `ApiEndpoints.CONVERSATIONS`, and `getBrowserTimezone`; `apps/chat/src/utils/conversation-stream-transport.ts` (the existing `ConversationStreamTransport` adapter) is updated to wrap the factory's returned functions instead of the raw file's exports — no change to `useConversationStream`'s consumption of that adapter.

### D10 — `api-error.ts` moves as-is; `apps/chat` keeps a re-export

None of `api-error.ts`'s four exports read any host state — they duck-type an `unknown` error/`Response`-shaped value passed in by the caller. The file moves to `libs/chat-hooks/src/api-error/api-error.ts` unchanged, with its 8-scenario spec (`api-error-trace-correlation`) moving alongside it. `apps/chat/src/server-api/api-error.ts` becomes `export * from '@epam/ai-dial-chat-hooks'`'s relevant names (or is deleted, with all 21 consumers repointed directly at `@epam/ai-dial-chat-hooks` — call-site count makes a temporary re-export the lower-risk migration step; the re-export file is removed once every consumer is migrated, tracked as its own task).

Fix: `resolveLocalizedText` gains a required third `primaryLocale: string` parameter (dropping the internal `PRIMARY_LOCALE` read); `buildAdditionalLocaleOptions` gains `additionalLocaleCodes: string[]` and `primaryLocale: string` parameters (dropping the internal `ADDITIONAL_CONTENT_LOCALE_CODES`/`PRIMARY_LOCALE` reads). `PRIMARY_LOCALE` itself, `ADDITIONAL_CONTENT_LOCALE_CODES`, and `buildLocaleFieldLabels` stay in `apps/chat/src/utils/locale.ts`, which wraps both moved functions with `PRIMARY_LOCALE` (and, for the latter, `ADDITIONAL_CONTENT_LOCALE_CODES`) baked in — so all ~36 existing 2-arg/0-arg call sites across `apps/chat` are untouched.
- **`mapToolsetCredentials` naming collision**: `map-deployment-to-catalog-item.ts` and `map-entity-details-to-catalog.ts` each independently export a function named `mapToolsetCredentials`, with different parameter shapes (`DialToolsetAuthSettingsDto` vs. `ToolsetEntityDetails`) — not discovered until both were actually moved. `map-entity-details-to-catalog.ts`'s keeps the name (it has external consumers: `CatalogView.tsx`, `AppEditorIframe.tsx`); `map-deployment-to-catalog-item.ts`'s is renamed to `mapDeploymentToolsetCredentials` (zero external consumers beyond its own test, so a compile-time-checked-only rename).
- **`map-entity-details-to-catalog.ts`'s companion types file**: `mapDeploymentDetailsDtoToEntityDetails`/`mapEntityDetailsToCatalogDetails`'s return/parameter types (`EntitySpecificDetails`, `ModelEntityDetails`, `AgentEntityDetails`, `ToolsetEntityDetails`, etc.) live in `apps/chat/src/types/entity-details.ts` — a second, unannounced (out of the original `utils`-only scope) types file discovered only once the mapping functions were actually moved, since the lib cannot import types back from the app. It is fully pure with zero other consumers, so it moves wholesale into `libs/chat-hooks/src/catalog/entity-details.ts` and the app file is deleted outright (no re-export shim needed). The same pattern recurs for `map-prompt-to-catalog-item.ts` (`apps/chat/src/types/prompt.ts`'s `PromptSource`/`buildPromptResourceUrl`/`parsePromptResourceUrl`, which DOES have two other consumers — `CatalogView.tsx`, `PromptEditor.tsx` — so `types/prompt.ts` becomes a re-export shim instead) and `map-skill-to-catalog-item.ts` (`apps/chat/src/types/skill.ts`'s `SkillSource`/constants/resource-URL helpers, same two-other-consumers situation, becoming a re-export shim; its dead `SkillManifest` interface — zero consumers, structurally identical to the already-moved `parseSkillManifestDocument`'s `SkillManifestDocument` — is dropped rather than duplicated, and its `SkillAboutDetails`/`SKILL_MANIFEST_FILE` duplicate the earlier D-something private mirrors in `skill-manifest.ts`/`skill.ts`, so those become the canonical exports instead of re-declaring a third copy). Unlike `PromptFieldError` (D-earlier) and `entity-details.ts` above, `PromptSource`/`SkillSource` cannot be re-declared as a fresh local `enum` in the lib and relied on structurally: TypeScript string enums are nominal, so a caller's own `SkillSource.Personal` would not type-check against a distinct same-shaped lib enum — the actual enum declaration has to be the single shared one.

Every moved file keeps its exact algorithm and its existing test file (moved, not rewritten), per the same "preserve every currently-tested observable behavior" goal as D2–D10. Files needing an injected seam get one new test case asserting the resolver/callback is invoked with the expected arguments, mirroring D5's `dialFileToAttachment` test additions.

## Risks / Trade-offs

- **[Risk]** `mimeTypesToFileAccept`'s behavior change (D4) is a silent contract change for any code relying on today's unfiltered app behavior. → Mitigation: call it out explicitly as **BREAKING** in the proposal; grep `apps/chat/src` for every `mimeTypesToFileAccept` call site as a task step and assert each one's `allowedTypes` input never actually contains a value `isDialFileAcceptType` would reject (i.e., the fix is behavior-preserving in practice, not just in intent), with a test asserting the fixed behavior.
- **[Risk]** Making `files.api.ts`/`upload-file-with-progress.ts`/`chat-stream.api.ts` factories rather than direct exports adds one layer of indirection to three high-traffic files. → Mitigation: keep the app-side files as call-once composition points (2–5 lines each) so a reader still finds `apps/chat/src/server-api/{files,chat-stream}.api.ts` at their current paths with their current exported names; only the implementation moved.
- **[Risk]** `resolve-dial-file-api-path.ts`'s continued type-origin split between `@epam/ai-dial-ui-kit` and `@epam/ai-dial-react-file-manager` (D3) could diverge if either package changes `DialFile`'s shape independently. → Mitigation: flagged as an Open Question rather than silently accepted; out of this change's scope to fix.
- **[Risk]** Deleting `apps/chat/src/server-api/api-error.ts` outright (rather than keeping the re-export) would require touching all 21 consumer files in one change, raising the diff size and review risk. → Mitigation: D10's re-export step, with removal as a separate follow-up task once every consumer is confirmed migrated.
- **[Trade-off]** This change does not attempt to make `upload-file-with-progress.ts`'s XHR-shaped contract abstract over non-XHR upload transports, per Non-Goals — a future host without `XMLHttpRequest` (e.g., a non-browser runtime) would still need to supply an `XMLHttpRequest`-compatible `xhrFactory`, not a wholly different transport.
- **[Risk]** D11's 41-file bulk move is large enough that a single missed consumer import or a silent behavior change in a rarely-tested helper is more likely than in the four hand-audited files. → Mitigation: migrate and verify in dependency order (foundational files with no intra-`utils` dependents first — `string-utils.ts`, `formatting.ts`, `cron-weekday.ts` — then files that import them), run the full `apps/chat` test suite after each batch rather than only at the end, and treat every cross-file dependency surfaced only during implementation (e.g. `isPublicToolsetId`, the `skill.ts`/`skill-manifest.ts` name collision) as a design decision recorded here, not a silent workaround.
- **[Risk]** Growing `@epam/ai-dial-chat-hooks` to ~41 more exports compounds the "kitchen-sink lib" concern already on record for this package (mixed React hooks, framework-agnostic transport, and now general domain-mapping utilities under one name and one peer-dependency graph). → Mitigation: none applied in this change — accepted as a known trade-off consistent with this repo's established convention (three prior archived changes made the same choice), with a future split into a framework-agnostic package flagged as a candidate follow-up change, not attempted here.
- **[Pre-existing, out of scope]** `locale.ts`'s pure functions depend on `@epam/ai-dial-deployment-creation-form` types (`DeploymentCreationFormLocaleEntry`/`DeploymentCreationFormLocaleOption`), which is added as a new `chat-hooks` peer dependency (D11). That package's own `typecheck` target is currently broken on `development` independent of this change (`DeploymentLocalesField.tsx` passes a `mainButtons` prop the installed `@epam/ai-dial-ui-kit`'s `Popup` no longer accepts — the same latent break also fails `@epam/ai-dial-conversation-panel:typecheck` via `FilterTabs.tsx`'s removed `TagAppearance` export, both from the prior UI-kit-upgrade commit). This was previously invisible to `chat-hooks`' own build/typecheck because nothing in `chat-hooks` depended on that package; adding the peer dependency now makes `nx run chat-hooks:build`/`:typecheck` transitively fail through that pre-existing bug. Verified via `npx vite build` and `npx tsc --build` run directly (bypassing the nx task graph) that `chat-hooks`' own source has no errors — confirmed by inspecting `apps/chat:typecheck` on the unmodified tree hitting the identical two errors. Fixing the UI-kit migration gap is out of scope for this change.

## Migration Plan

1. Land each of D2–D10's new `libs/chat-hooks` exports alongside its migrated spec, verified independently (`npm exec nx test chat-hooks`) before any app call site changes.
2. Migrate each app call site one utility/factory at a time (six call sites for Part A, five files' composition points for Part B), running `npm exec nx test chat`/`npm exec nx lint chat`/`npm exec nx build chat` after each.
3. Delete each superseded `apps/chat/src/utils/*.ts` / `apps/chat/src/server-api/*.ts` file only after its migration step passes and its spec has moved.
4. Update `chat-hooks-file-manager-domain`, `generated-api-client-integration`, and `api-error-trace-correlation` spec deltas to reflect the new public/factory shape (this change's `specs/` deltas).
5. Rollback is per-step: each app file is deleted only after its replacement is verified, so any step can be reverted independently by restoring the deleted file and its import, with no cross-step coupling.

## Open Questions

Left unresolved — the two packages' `DialFile` shapes are structurally identical today, so there is no forcing correctness issue, only a documentation clarity one.
- Should `apps/chat/src/server-api/api-error.ts` be deleted immediately (touching all 21 consumers in this change) or kept as a re-export until a follow-up change removes it (D10)? This design assumes the re-export step; `tasks.md` can be adjusted if the team prefers a single larger migration.
