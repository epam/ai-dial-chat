## 3b. Regression found while testing manually: conversation reload on every message

- [x] 3b.1 User reported: after this change, a spinner appears before each message and the page appears to reload after each message. Root-caused via the dependency chain: `Conversation.tsx`'s `channel` (`useMemo` on `channelId`, among other fields) → `useConversationStream`'s `startStream` (`useCallback` deps include `channel?.channelId`/`channel?.notifyGenerationSettled`) → `loadConversation` (`useCallback` deps include `startStream`) → the mount-load `useEffect` at `[conversationId, loadConversation]`. Idle-disconnect now cycles `channelId` (id → null → id) around every message, so `loadConversation`'s identity churns on that same cadence, and the mount-load effect (previously stable, since `channelId` rarely changed) refired every time — re-fetching the conversation from the server on every message. See design.md's Risks section for the full trace.
- [x] 3b.2 Fixed in `apps/chat/src/pages/Conversation/Conversation.tsx`: the mount-load effect now depends only on `[conversationId]` and calls `loadConversation` through a ref kept current by its own no-dependency effect (the standard "latest callback via ref" pattern), so it no longer re-runs for unrelated churn in any of `loadConversation`'s dependencies.
- [x] 3b.3 Audited the rest of `Conversation.tsx`'s `useEffect` blocks and `AppPreviewChat.tsx` for the same shape (an effect keyed on a callback that transitively depends on `channel`/`startStream`) — none of the others have it; the other effects that depend on `startStream`-derived callbacks are guarded by their own ref/key checks (e.g. `displayNameWatchKeyRef`, `notifiedLoadedConversationIdRef`) and don't re-fetch.
- [x] 3b.4 Verified manually by the user in a real browser — the spinner/reload no longer appears on every message after this fix.
