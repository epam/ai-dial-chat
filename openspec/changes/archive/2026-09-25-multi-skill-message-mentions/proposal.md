## Why

`skill-message-payload` (see `openspec/specs/skill-message-payload/spec.md`) lets a user select **one** skill per message: the selection renders as a `ChatSkill` chip pinned to the very start of the input/message (`inlineStartSlot` / the history bubble's `beforeContent` slot), and `custom_content.skills` carries exactly one `{ url }` entry, cleared after every send. The array shape was chosen deliberately to "future-proof the wire contract" for more than one entry — this change is that follow-up.

Users need to reference several skills in one message, interleaved with free text, e.g. `/abc please summarize this, then run /csd on the result`. Today that is impossible: only one skill can be selected at a time, and it always renders before all typed text regardless of where in the sentence it conceptually belongs. Because two different skills (different resource paths) can share the same display name, the order the mentions appear in the message is the only reliable way to tell which chip corresponds to which `custom_content.skills` entry — order becomes load-bearing the moment a second skill is allowed.

Separately, a small composer usability bug affects this same slash-trigger mechanism: once a user opens the skill/command popup by typing `/`, types more (`/sdf`), and dismisses the popup (Escape/outside click) without selecting anything, backspacing back down to a bare `/` does not reopen the popup — only clearing the textarea to empty and retyping `/` does. Fixing this is small and lives in the same trigger state machine this change already has to touch, so it rides along here.

## What Changes

- **Skill mentions become part of the message text**, not a separate slot. Selecting a skill from the `/` command menu or the Skills add-menu inserts `/{name}` literally into the composer's plain-text value at the caret, instead of clearing the typed query and rendering a chip *before* the textarea. A message can carry any number of mentions, interleaved anywhere with free text.
- **`custom_content.skills` becomes an ordered, N-entry array** reflecting every mention in the message, in left-to-right reading order. Order is the sole disambiguator when two mentions display the same name but resolve to different skills (different `url`).
- **Composing surfaces** (new-conversation composer, existing-conversation composer, edit-message input, AppsEditor/Quick Apps preview composer — all four already share one `useSkillSelectorOverlay` hook and one `ConversationInput`/`EditMessageInput`/`Input` plumbing) track each mention's identity (its resolved `url`) against a live character range in the plain-text draft, so edits, undo, and Backspace-at-a-mention-boundary behave predictably; a mention broken by an in-place text edit reverts to plain text. Live composing renders mentions as **highlighted text runs** (same character width as the underlying text, styled to read as a mention) rather than full interactive chip widgets — a native `<textarea>` cannot host a focusable/hoverable widget at an arbitrary text offset, so the full interactive `ChatSkill` chip (tooltip, "View details") is reserved for read-only rendering.
- **History rendering** (`ConversationMessageItem`'s user-message bubble) replaces the single leading chip with inline chips at each mention's actual position in the flowing text, reconstructed on load by matching the message's ordered `custom_content.skills` urls against `/{name}` occurrences in the text (name resolved from the current skill listing, not the possibly-stale text). Assistant messages, which cannot author text-position mentions, keep today's behavior: every entry in `custom_content.skills` renders as a chip in the bubble's single leading slot, now supporting more than one chip there.
- **Editing an existing message** reconstructs the live mention-tracking state from the same text/url reconciliation, then continues live-tracking edits from that point, so re-sending after further edits carries the correct, possibly-changed set of mentions.
- **Popup reopen-on-backspace-to-slash fix**: `useCommandMenu`'s trigger state machine reopens the command menu whenever the textarea's value becomes exactly the bare trigger character (`/`), whether reached by typing it into an empty box (already supported) or by backspacing back down to it after a prior dismissal (the fix) — without reopening while the user is still typing a query forward.

## Capabilities

### Modified Capabilities

- `skill-message-payload`: multiple ordered skill mentions per message, inline text-position rendering in history, live mention tracking while composing/editing across all four composer surfaces, and the command-menu backspace-to-bare-trigger reopen fix.

## Impact

- **Affected libs**: `libs/skills` (mention data model, matching/reconciliation utility, `ChatSkill` reused for both highlighted-run and full-chip rendering modes, `useSkillSelectorOverlay` reworked from single-selection to an ordered mention list), `libs/conversation-input` (`useCommandMenu` trigger fix; `Input`/`ConversationInput`/`EditMessageInput` gain a mention-aware inline rendering layer replacing the single `inlineStartSlot`/`onInlineStartRemove` pair), `libs/conversation-messages` (`UserMessageBubble` renders text as segments instead of one leading slot; `AssistantMessageBubble`'s existing single slot now renders N chips, no structural change).
- **Affected apps**: `apps/chat` — `NewConversationComposer`, `ConversationView` (existing-conversation composer + edit wiring), `AppsEditor/AppPreviewChat.tsx` (Quick Apps preview composer), `ConversationMessageItem` (history rendering), `apps/chat/src/components/SkillSelector/useSkillSelectorOverlay.tsx` (host wiring), i18n keys for any new labels.
- **No backend/API changes**: `custom_content.skills` stays `RequestSkill[]` (`{ url }[]`) on the wire — this change only removes the "at most one entry" constraint the app-side code enforced; DIAL Core's schema already accepts an arbitrary-length array (Core PR #1956, referenced in the base spec). Confirmed against `ai-dial-quickapps-backend` PR #574 (`docs/skill-invocation.md`, design-doc-only, no code yet): the consuming agent side (QuickApps) already designs against a per-message array of chips (capped at `SKILL_INVOCATION_MAX_PER_MESSAGE`, default 5) and treats `content` as fully opaque — it never parses `/name` out of the text, so the chip array is the only invocation signal it reads. This matches this change's design exactly: the inline `/{name}` text is a client-side-only cosmetic mechanism, and `custom_content.skills`'s order is the real, load-bearing contract.
- **No breaking change to the wire contract or persisted data**: an existing single-skill message (one `custom_content.skills` entry, mention at the very start) continues to render and round-trip exactly as it does today, since it's the N=1 case of the new mechanism.
- **Known limitation, documented in `design.md`**: history/edit-mode reconstruction re-derives mention positions from the text using an in-order name-matching heuristic (no position metadata travels on the wire). A user-typed, non-selected `/word` that happens to exactly match a real skill's current display name and falls in the right reading-order slot can be mis-identified as a mention; this is the accepted, narrow trade-off for keeping `custom_content.skills` schema-compatible with DIAL Core.
