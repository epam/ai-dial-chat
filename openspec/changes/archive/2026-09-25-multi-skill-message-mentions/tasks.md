**Task 2.4 — the finalized `insertMention` call-site API (read this before starting block 3):**

The original sketch ("expose whatever minimal ref/callback `Input.tsx` needs so a `menuOverlays`/`commandMenu` consumer can call `insertMention` and have it actually splice into the live textarea value") is **not** how this ended up working, because forcing every insertion through `Input`'s own imperative DOM pipeline would have meant `Input` needing to know about `insertMention`/`url`/`name` at all — which would leak skill-specific concepts into a lib that must stay generic. Instead, the host (`useSkillSelectorOverlay`, block 3) stays in full control and pushes the result down through the **existing** controlled-value channel:

1. **Caret position for the add-menu path.** `Input` is now `forwardRef<InputHandle, InputProps>`, exposing `getCaretPosition(): number` (reads `textareaRef.current?.selectionStart ?? message.length`). `MenuOverlayConfig.renderOverlay`'s signature gained a second parameter: `renderOverlay: (onClose: () => void, caretPosition: number) => ReactNode` (additive — existing single-arg implementations remain valid under TS's normal function-arity assignability, no other call site needed touching). `AddAttachmentButtonProps` gained `getCaretPosition?: () => number`, threaded into both its desktop-submenu and mobile-bottom-sheet `renderOverlay(...)` calls (defaulting to `0` when absent). `Input.tsx`'s own internal `<AddAttachmentButton>` (footer) passes its own `getCaretPosition`; `EditMessageInput.tsx` holds a `useRef<InputHandle>` on its internal `<Input ref={inputRef}>` and passes `getCaretPosition={() => inputRef.current?.getCaretPosition() ?? 0}` to its **external** `AddAttachmentButton` (the one it renders itself, outside `Input`, since it sets `hideActionBar`).
2. **Caret position for the slash-menu path.** Unchanged/no new plumbing needed: `commandMenu` only ever opens over an empty textarea (per `useCommandMenu`'s existing constraint), so a slash-menu selection's insertion point is always `0` — block 3's `commandMenu.renderMenu`'s `onSelect` can hardcode `0` (or call `close({ consumeQuery: true })` first, which already assumes/enforces this).
3. **Performing the actual insertion.** The host's `onSelect` (in both paths) calls its own `useSkillMentions.insertMention(url, name, caretPosition)` (block 1, unchanged — mutates the host's own `draft`/`anchors` state via string splicing) to get the new full text, **then pushes that text down** by passing it as `message` together with a bumped `messageRevision` and a `caretPositionOverride` set to `caretPosition + 1 + name.length` (the position right after the inserted `/{name} ` run) to whichever of `ConversationInput`/`EditMessageInput` it's driving. This is a plain React-state value push through the **already-public** `message`/`messageRevision` props (not the undo-preserving `execCommand` pipeline `useTextInsertion`/`textInsertion` uses) — accepted deliberately: `design.md` Decision 2 only requires native-undo preservation for the **Backspace removal** gesture (2.5), not for insertion; a plain state-driven insertion matches this codebase's own existing precedent for host-driven text (`NewConversationComposer`'s `message`/`messageRevision` for "populated by a starter selection"). A Ctrl+Z immediately after picking a skill will not specifically "undo just the mention" — the same as picking a starter today — which is an acceptable, non-regressive trade-off (it wasn't undoable before either, since the old mechanism didn't put the skill in `message` at all).
4. **Why `activeMentions` doesn't need updating on the same call.** The host recomputes `activeMentions` from its own `anchors` state (already updated by step 3's `insertMention` call) on the very same render that pushes the new `message`/`messageRevision`/`caretPositionOverride` — all four are just a consistent snapshot of one state update, no extra sequencing needed.

Block 3 should treat this as the contract: `useSkillSelectorOverlay` owns `useSkillMentions`, and on every selection it produces `{ message: draft, messageRevision: <bumped>, activeMentions: <from anchors>, caretPositionOverride: <insertion end> }` for the host composer to spread onto `ConversationInput`/`EditMessageInput`, plus `onChange`/`onDraftChange` wired to keep `draft` in sync with ordinary typing, plus `onBackspaceAtCaret` wired straight to `useSkillMentions.onBackspaceAtCaret`.
