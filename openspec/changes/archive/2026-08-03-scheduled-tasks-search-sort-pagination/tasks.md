## 6. Frontend: infinite scroll and load-more skeletons

- [x] 6.1 Added `ScheduledTaskCardSkeleton` in `libs/scheduled-tasks` using `DialSkeleton` from `@epam/ai-dial-ui-kit`, matching `ScheduledTaskCard`'s footprint (`h-[232px]` `CardShell`), `aria-hidden`. **Bug found via two rounds of user screenshots, actual root cause on the second**: skeleton cards rendered as fully blank white rectangles — no visible title/description/footer bars at all. First hypothesis (a `showTitle`/`paragraph` prop-API version mismatch) was wrong; switching to `variant={DialSkeletonVariant.Rectangular}` still rendered blank. Real cause: `DialSkeleton`'s default color token is `bg-layer-3`, which compiles to `background-color: var(--bg-layer-3, #fcfcfc)` — and this app never overrides `--bg-layer-3`, so it falls back to `#fcfcfc`, a near-white color invisible against the white `CardShell` background. Found the fix by locating the one other skeleton-over-a-card usage in this codebase, `libs/catalog/src/components/CardGrid/CardGrid.tsx:78-84`, which passes `color="var(--bg-layer-4)"` explicitly for exactly this reason (`--bg-layer-4` has real contrast, `#d1dbea` fallback). Added the same explicit `color={SKELETON_COLOR}` (`var(--bg-layer-4)`) to every `DialSkeleton` in `ScheduledTaskCardSkeleton`.
- [x] 6.2 Added `hasMore`, `isLoadingMore`, `skeletonCount` (default 6), `onLoadMore` props to `ScheduledTasks`; renders exactly `skeletonCount` skeletons when `isLoadingMore` is `true`. Also removed the lib's internal `filterScheduledTaskItems` call — `items` are now rendered as received (already server-filtered), only client-side `sortScheduledTaskItems` remains; empty-state vs no-results-state now derives from `items.length === 0` combined with whether `searchQuery` is non-empty. **Bug found via user screenshot, fixed after the skeleton-visibility fix above**: skeletons initially rendered in a separate trailing `<div className="grid ...">` below all `ScheduledTaskSection`s. A separate grid container always starts a new row, so whenever the loaded item count wasn't a multiple of the column count (e.g. 20 items in a 3-column grid), the last real row's empty cell(s) stayed empty and skeletons jumped to a fresh row below — a visible gap. Fixed by adding a `trailingSkeletonCount` prop to `ScheduledTaskCardGrid` that appends `ScheduledTaskCardSkeleton`s as additional children of the *same* grid `<div>` as the real cards (only for the last rendered section), so `grid-auto-flow` continues filling the current row exactly like a real appended card would. Added `ScheduledTaskCardGrid.spec.tsx` asserting skeletons land inside the same single grid container as real cards.
- [x] 6.3 Added a scroll sentinel at the end of the content region using the `findScrollParent`/scroll-listener pattern from `libs/catalog/src/components/ListView/ListView.tsx`; invokes `onLoadMore` when it becomes visible and `hasMore && !isLoadingMore && !isLoading`.

- [x] 7.1a **Bug found via user report (not caught by automated tests)**: after creating a task, `refetch()` fired correctly and the server-side epoch-based cache invalidation was correct, but the newly created task still didn't appear until a hard page reload. Root cause: `GET /api/v1/scheduled-tasks` sent `Cache-Control: private, max-age=30`, which let the **browser's own HTTP cache** serve the prior response for up to 30s on the identical URL (`?limit=20&offset=0`), bypassing the BFF (and its correct invalidation) entirely — the request never even reached the server. Fixed by changing the header to `Cache-Control: private, no-store` in `scheduled-tasks.controller.ts`, since freshness is already fully owned by the server-side `cache-manager` epoch logic; a browser-cacheable response was never correct once list results could change server-side after a create. Added a regression test asserting the header value; documented as a new scenario in the `scheduled-tasks-api` spec delta. `npm exec nx test chat-api -- scheduled-tasks` — 63/63 pass.
