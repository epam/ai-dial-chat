## Why

Both file-manager hosts hardcode which tabs are shown: `DialFileManagerModal.tsx:139` and `DialFileManagerPage.tsx:50` each compute `tabs = allTabs?.filter((tab) => tab.id !== DialFileManagerTabs.Review)`, i.e. "always My files / Shared / Organization, never Review" — baked into app code with no deployment-level control.

**Legacy investigation** (`development:apps/chat/src/components/FileManager/hooks/useFileManager.tsx`, `development:apps/chat/src/utils/app/search.ts`):

- `availableTabs?: Set<string>` was a **host-level React prop**, not deployment- or config-driven — `defaultAvailableTabs` was a hardcoded module constant, exactly like today's hardcoded filter. Legacy never fetched tab visibility from any config/deployment source either. So there is no legacy precedent forcing a specific config source — this change is a genuinely new capability, not a restoration.
- Legacy tab **membership** (which files show up under My files / Shared / Organization) was computed by client-side predicate filters (`defaultMyItemsFilters`, `SharedWithMeFilters`, `PublishedWithMeFilter` in `search.ts`) applied against **file-level boolean flags already present on each item** (`item.sharedWithMe`, `item.publishedWithMe`, `item.isShared`, `item.isPublished`) inside **one merged Redux-stored listing** (`FilesActions.getFilesWithFolders`). This is structurally the opposite of today's architecture, which fetches each tab from its **own separate BFF endpoint** (`/files/list`, `/files/shared`, an organization/public listing) with no file-level provenance flags at all.
- The Review tab used a *third*, different mechanism — bucket equality (`getEntityBucket(f) === reviewBucket`), not a boolean flag — and `availableTabs`/`getInitialTab`'s priority-fallback determined only whether the Review *tab itself* appeared, independent of the flag-based filters above.
- The destination-folder popup (`destinationFolderPopupOptions`, present in legacy too) had **no independent tab selector in legacy either** — it always browsed the tree for whichever tab was already active outside the popup. This matches the current `file-manager-folder-picker` capability exactly ("browsing the same folder tree already loaded for the active tab"), so no popup-level tab-config work is needed by this change.

This is step 18 of the #7505 migration roadmap: introduce deployment-level tab visibility (a genuinely new capability, not a restoration) and resolve the file-level-filter question with a firm, evidence-based answer rather than a placeholder waiver.

**File-level `sharedWithMe`/`publishedWithMe` filters**: `apps/chat-api/src/files/dto/list-files.dto.ts`'s `ListFilesItemDto` carries no such flags today. Critically, **this is not a DIAL Core limitation** — `apps/chat-api/src/conversations/conversation.service.ts:655-777` already implements the exact merge-and-flag pattern legacy used, for conversations: it fetches the user bucket, the public bucket, and `getSharedResources` separately, deduplicates by relative path, and stamps `sharedWithMe`/`publishedWithMe` onto each resulting item. The pattern is proven and portable to files. Adopting it for files, however, would mean replacing the currently-shipped **separate-endpoint-per-tab** design (`file-manager-tabs`'s already-spec'd `my_files`/`shared`/`organization` listing behavior, each independently cached and invalidated) with a **combined, cross-tab listing** — a materially larger architectural change than "which tabs are visible," and one the issue's own acceptance criterion gates on further legacy/Core/BFF confirmation. This change documents the finding and the concrete precedent (so a follow-up doesn't have to rediscover it) and waives implementation here.

## What Changes

- Add a new client-config key `fileManager.availableTabs` to the existing generic config-registry (`apps/chat-api/src/app-config/config-registry/config-registry.constants.ts`), resolved through the already-existing `GET /api/v1/client-config?appId=chat-ui` endpoint (`AppConfigService`/`CompositeConfigProvider`) — no new endpoint is introduced. Backed by a new env var `FILE_MANAGER_AVAILABLE_TABS` (comma-separated tab ids, following the existing `FEATURED_MODEL_IDS`/`HIDDEN_ENTITY_TAGS` CSV-to-`string[]` `@Transform` pattern in `environment.config.ts`). See design.md for the full comparison against the two rejected alternatives (a per-deployment features DTO field, and a config-registry-only static fallback).
- The BFF validates the resolved tab id list against the currently supported set (`my_files`, `shared`, `organization`) and drops any unrecognized id (including `review`, which has no supported tab implementation until — and unless — the separate, PO-gated `add-file-manager-review-tab` change ships). An unset or fully-invalid env var resolves to the default `['my_files', 'shared', 'organization']` — today's exact hardcoded behavior.
- `ClientConfigResponseDto.config` gains `fileManagerTabs: string[]`; `AppConfigContext`'s `AppConfigState.config` gains the matching field, with `INITIAL_STATE` defaulting to the same three-tab array so there is no flash of a different tab set while the config request is in flight.
- New shared hook `useDialFileManagerTabConfig(activeTab, onTabChange, allTabs)` (`apps/chat/src/hooks/files/useDialFileManagerTabConfig.ts`) filters `allTabs` against `useAppConfig().config.fileManagerTabs`, **and** resets the active tab (via the passed `onTabChange`) to the first allowed tab (priority `my_files` → `shared` → `organization`) whenever the currently-active tab is not in the resolved list — covering both the initial-mount case (deployment excludes `my_files`, the usual default) and the async-config-arrives-after-mount race (the config request resolving to a narrower set than `AppConfigContext`'s three-tab `INITIAL_STATE` default). `DialFileManagerModal` and `DialFileManagerPage` both replace their hardcoded `.filter((tab) => tab.id !== DialFileManagerTabs.Review)` with this one hook.
- **Waiver — file-level `sharedWithMe`/`publishedWithMe` filters**: not implemented in this change, for the reasons in Why above. Flagged as a concrete, evidence-backed follow-up rather than an unexplored gap.

## Capabilities

### New Capabilities

- `file-manager-tab-config`: the `fileManager.availableTabs` config-registry key, its BFF-side validation/default behavior, the frontend `AppConfigContext` field, and the shared `useDialFileManagerTabConfig` hook (tab filtering + active-tab-reset) consumed by both hosts.

### Modified Capabilities

- `file-manager-tabs`: the existing "Tab navigation in DialFileManagerModal" requirement states the modal "SHALL display three tabs — My files, Shared with me, and Organization" unconditionally. This becomes conditional on the deployment-driven `fileManagerTabs` config value (defaulting to the same three tabs, so no observable behavior changes for a deployment that does not set `FILE_MANAGER_AVAILABLE_TABS`), and gains an explicit active-tab-reset requirement for when the currently-active tab drops out of the resolved list.

## Impact

- **Modified files (backend)**: `apps/chat-api/src/config/environment.config.ts` (new `FILE_MANAGER_AVAILABLE_TABS` env var), `apps/chat-api/src/app-config/config-registry/config-registry.constants.ts` (new definition), `apps/chat-api/src/app-config/config-registry/env-config.provider.ts` (new special-cased resolution + allow-list validation, following the existing `features.asrEnabled`/`features.llmConversationNaming` inline-branch pattern), `apps/chat-api/src/app-config/app-config.service.ts` (map the resolved value into `config.fileManagerTabs`), `apps/chat-api/src/app-config/dto/client-config-response.dto.ts` (`ClientConfigDto.fileManagerTabs: string[]`).
- **Modified files (frontend)**: `apps/chat/src/context/AppConfigContext.tsx` (new `config.fileManagerTabs` field + default); **new file** `apps/chat/src/hooks/files/useDialFileManagerTabConfig.ts`; `apps/chat/src/components/DialFileManagerModal/DialFileManagerModal.tsx` and `apps/chat/src/pages/DialFileManagerPage/DialFileManagerPage.tsx` (replace hardcoded Review-exclusion filter with the new hook).
- **No change needed** in the destination-folder popup — it has no independent tab UI in either legacy or current code; it inherits whatever tab is active outside it.
- **No new endpoint** — reuses `/api/v1/client-config?appId=chat-ui`, already fetched once per session by `AppConfigProvider`.
- **Generated-client impact**: `ClientConfigDto`/`ClientConfigResponseDto` gain one field; run `npm run openapi`/`npm run openapi:check` and rebuild `chat-api-client` (no new operationId, no new SDK method).
- **Not breaking**: the default value reproduces today's hardcoded 3-tab behavior exactly; a deployment that does not set the new env var observes no change. Rollback is reverting the files above; no data migration.
- **Explicit waiver**: file-level `sharedWithMe`/`publishedWithMe` client-side filters are out of scope for this change; design.md documents the proven `conversation.service.ts` precedent for a future proposal.
