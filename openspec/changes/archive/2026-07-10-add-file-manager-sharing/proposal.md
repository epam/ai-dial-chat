## Why

The standalone DIAL File Manager (#7503, archived) shipped Copy/Move/Duplicate/Download/Delete/Rename on `my_files`, but has no way to share a file/folder with another user, no way to remove access to something the user shared, and no way for a recipient to remove a resource shared with them. `DialFileManagerActions.Unshare`/`.RemoveAccess`/`.ManagePermissions` are already defined in the installed `@epam/ai-dial-ui-kit` (confirmed via `getEntityDetails("component", "DialFileManager")` and `node_modules/@epam/ai-dial-ui-kit/dist/src/types/file-manager.d.ts:7-21`), and `sharedByMePaths`/`onUnshareFiles`/`onRemoveFilesAccess`/`onManagePermissions` are already accepted props on `DialFileManager` — but nothing in `apps/chat` wires them. This is step 13 of the #7503+ migration roadmap (GitHub #7504), scoped to sharing only; file metadata (#7504 row 42) and archive upload (#7504 row 31) are separate follow-up OpenSpec changes so each stays independently reviewable, per `openspec/config.yaml` task-slicing rules.

`DialFileManagerActionProfile.Full` (`apps/chat/src/types/file-manager-variant.ts`) is defined but has zero production call sites today — `isCopyMoveDuplicateAllowed` in `useDialFileManager` currently treats `Full` identically to `Browse`. This change settles what `Full` means: the legacy-parity action set (Share/Unshare/Remove access, and — in the two follow-up changes — Info and upload-archive) that the standalone page will opt into once every action in the set has a working handler.

## What Changes

- **New BFF endpoints** in `apps/chat-api/src/files/`, all proxying `@epam/ai-dial-typescript-sdk` via the existing `DialClientService`:
  - `POST /api/v1/files/share` → Core `shareResource` (`/v1/ops/resource/share/create`). Creates a `LINK`-type invitation for one or more resources at a chosen permission level (`READ` or `READ+WRITE`) and returns the invitation link. This mirrors the legacy `ShareService.share()` → `/api/share/create` flow (confirmed on `origin/development`: `apps/chat/src/utils/app/data/share-service.ts`), which is also link/invitation based, not a live user/group picker — DIAL Core has no "share directly with a named user" primitive, only invitation links.
  - `POST /api/v1/files/revoke-access` → Core `revokeSharedResources` (`/v1/ops/resource/share/revoke`). Owner removes access to a resource for **all** users it was shared with. Distinct endpoint, distinct SDK operation, distinct request schema (`RevokeResourcesRequest`) from discard.
  - `POST /api/v1/files/discard-shared` → Core `discardSharedResources` (`/v1/ops/resource/share/discard`). Recipient removes a resource that was shared with them from their own view; does not affect the owner's or other recipients' access. Distinct request schema (`ResourceLinkCollection`, URL-only — no permissions needed).
- **`FilesService`** gains `shareFiles`, `revokeAccess`, `discardShared` methods, following the thin-controller / typed-exception / structured-logging conventions already used by `copyFiles`/`moveFiles`/`deleteFiles`.
- **OpenAPI regeneration** — `shareFiles()`, `revokeAccess()`, `discardShared()` added to `@epam/chat-api-client`, with matching thin wrappers in `apps/chat/src/server-api/files.api.ts`.
- **`sharedByMePaths` data source** — a new `FilesService.listSharedByMe(bucket)` method calls Core `getSharedResources` with `{ resourceTypes: ['FILE'], with: 'others', includeUserInfo: false }` (the owner-side counterpart of the existing `with: 'me'` call already used by `listSharedFiles`/shared-with-me listing), reusing the existing `GET /api/v1/files/shared` contract shape rather than mutating `ListFilesItemDto` — `ListFilesItemDto` stays as-is (no `isShared`/`sharedWithMe`/`sharedWith` fields added to ordinary listings).
- **`useDialFileManager` hook**: adds `onManagePermissions(path)` (opens a new host-owned `ShareFileModal`), `onUnshareFiles(files)`, `onRemoveFilesAccess(files)`, and `sharedByMePaths: Set<string>` (fetched alongside the existing `sharedWithMeIds` on the `my_files` tab), following the ui-kit contract confirmed via MCP and the local `.d.ts`.
- **New component** `apps/chat/src/components/DialFileManagerModal/ShareFileModal.tsx` — the host-owned share dialog ui-kit does not provide (confirmed: no `onShareFiles` prop exists, and no reusable `ShareModal`/`ShareDialog` component exists anywhere in current `apps/chat/src` — repo-wide search returned no matches). Lets the user pick a permission level and displays the returned invitation link with copy-to-clipboard, matching the legacy link-based sharing UX.
- **`DialFileManagerShell`** wires `sharedByMePaths`, `onManagePermissions`, `onUnshareFiles`, `onRemoveFilesAccess`, and computes bulk `Remove access` visibility by checking every selected path against `sharedByMePaths` — mirroring the legacy `allSelectedItemsShared` guard in `apps/chat/src/components/FileManager/FileManager.tsx` (`origin/development`, lines 95-119).
- **`file-manager-tabs`** capability: the per-tab action-label table gains `Share` (`ManagePermissions`, `my_files` only, single-item, WRITE-gated), `Unshare` (`shared` tab only, discard-shared-with-me), and `Remove access` (`my_files` only, bulk-capable, gated on `sharedByMePaths`) rows. `DialFileManagerActionProfile.Full` is defined as the profile that additionally exposes these three actions; the standalone page continues to use `Browse` until this change and its two follow-ups (#7504 metadata, #7504 upload-archive) are all complete, at which point a final wiring task flips `DialFileManagerPage` to `Full`.

**Non-breaking**: additive endpoints, hook fields, and component; `Browse`/`Attach` action matrices are untouched. `ListFilesItemDto` and `GET /api/v1/files/shared` response shapes are unchanged.

## Capabilities

### New Capabilities

- `file-manager-sharing`: BFF `POST /api/v1/files/share`, `POST /api/v1/files/revoke-access`, `POST /api/v1/files/discard-shared` contracts (DTOs, Core SDK mapping, partial-failure semantics, rate limiting), the `sharedByMePaths` data source and its cache/invalidation story, hook wiring (`onManagePermissions`, `onUnshareFiles`, `onRemoveFilesAccess`), and the `ShareFileModal` component.

### Modified Capabilities

- `file-manager-tabs`: per-tab action-label table gains `Share`/`Unshare`/`Remove access` rows and defines what `DialFileManagerActionProfile.Full` means and when the standalone page adopts it.

## Impact

- **Backend**: `apps/chat-api/src/files/` — three new controller routes, three new DTO files (`share-files.dto.ts`, `revoke-access.dto.ts`, `discard-shared.dto.ts`), new `FilesService` methods using `DialClientService`'s injected `@epam/ai-dial-typescript-sdk` client (`shareResource`, `revokeSharedResources`, `discardSharedResources`, and a `with: 'others'` variant of the existing `getSharedResources` call for `listSharedByMe`).
- **Generated client**: `libs/chat-api-client/` regenerated after Swagger update (`npm run openapi`, `npm run openapi:check`).
- **Frontend**: `apps/chat/src/server-api/files.api.ts` (new `shareFiles`/`revokeAccess`/`discardShared`/`listSharedByMe` wrappers), `useDialFileManager` hook, `DialFileManagerShell`, a new `ShareFileModal` component under `apps/chat/src/components/DialFileManagerModal/`, i18n keys in `apps/chat/src/i18n/locales/en.json` + `apps/chat/src/constants/translation-keys.ts`.
- **Docs**: OpenSpec capability spec documents the three endpoints and the tab/action-matrix delta; `file-manager-tabs` spec gains the `Full` profile definition.
- **Dependencies**: none new — uses the already-installed `@epam/ai-dial-typescript-sdk` `shareResource`/`revokeSharedResources`/`discardSharedResources`/`getSharedResources` operations (confirmed present in `node_modules/@epam/ai-dial-typescript-sdk/dist/index.d.ts`) and the already-defined ui-kit `onManagePermissions`/`onUnshareFiles`/`onRemoveFilesAccess`/`sharedByMePaths`/`DialFileManagerActions.{ManagePermissions,Unshare,RemoveAccess}` contracts (confirmed via the `ai-dial-ui-kit` MCP server and the installed package's `.d.ts`).
- **Out of scope (tracked as separate follow-up OpenSpec changes)**: file metadata popup (`add-file-manager-metadata-ui`, #7504 row 42) and ZIP archive upload (`add-file-manager-upload-archive`, #7504 row 31). The standalone page's switch from `actionProfile=Browse` to `actionProfile=Full` does not happen in this change alone — it is deferred to whichever of the three #7504 changes lands last, so `Full` is only adopted once every action it exposes has a working handler.
