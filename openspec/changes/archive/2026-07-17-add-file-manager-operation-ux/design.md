## Context

`useDialFileManager.ts` (2307 lines) currently owns thirteen independent busy-state signals: `isLoading`, `isSearching`, `isCreatingFolder`, `isDownloading`, `isDeleting`, `isRenaming`, `isCopying`, `isMoving`, `isSharing`, `isUnsharing`, `isRemovingAccess`, `isFileMetadataLoading`, plus `uploadBatchState` (non-null while an upload batch is active). Verified consumption today:

- `DialFileManagerShell.tsx:536-571` renders **three separately-coded** `absolute inset-0 z-[52] ... bg-blackout` overlay blocks (near-identical JSX, differing only in the boolean condition and the `ariaLabel`) for `isDownloading`, `isDeleting`, and `isRenaming && !isMoving`.
- `DialFileManagerShell.tsx:575-596` renders `UploadProgressModal` when `uploadBatchState != null`, and `OperationLoaderModal` (with an existing cancel button, from #7503) when `isCopying || isMoving`.
- `DialFileManagerShell.tsx:598-613` renders `ShareFileModal` when `shareTarget != null`, passing `isSubmitting={isSharing}`.
- **No overlay, modal, or inline indicator exists for `isUnsharing` or `isRemovingAccess`.** Per `file-manager-sharing`'s existing spec, both `onUnshareFiles`/`onRemoveFilesAccess` "call the BFF immediately — no confirmation dialog is shown before the request is sent," so today the only user-visible feedback is the listing eventually refreshing (or an error toast on failure).
- `DialFileManagerModal.tsx` disables the Attach button with `selectedFiles.length === 0 || isLoading || isOperationInProgress`, where `isOperationInProgress = isDownloading || isDeleting || isRenaming || isCreatingFolder || uploadBatchState != null` is a **separate, locally-recomputed** value, and `isLoading` is checked **independently** — confirming the codebase already treats "content is loading" (read) and "an operation is mutating something" (write) as two distinct concepts, not one flag.
- `OperationLoaderModal`, `UploadProgressModal`, and `ShareFileModal` all render through `@epam/ai-dial-ui-kit`'s `DialPopup` (verified: `OperationLoaderModal.tsx` wraps its content in `<DialPopup open ...>` with its own `footer`/`onClose`, no manual `z-*` class in the component itself). `DialPopup` is a portal-based dialog with its own stacking context and backdrop, so these three never need manual z-index coordination against the shell's inline `z-[52]` overlay — they are structurally always "on top" by virtue of being a portal-rendered modal, and none of these three states ever coincides with `isDownloading`/`isDeleting`/`isRenaming`/`isUnsharing`/`isRemovingAccess` in `useDialFileManager`'s existing per-action state model (each action sets exactly one state slice at a time).
- `cancelCopyMove` (`useDialFileManager.ts:2048-2056`) aborts `copyMoveAbortControllerRef.current`; the aborted request's `finally`/`catch` path (per the existing `file-manager-copy-move` spec's "Cancel aborts the in-flight request" scenario) already clears `isCopying`/`isMoving` back to `false`. Any `isAnyOperationInProgress` derived from those two flags therefore clears automatically on cancel — no new wiring is required, only a test asserting the composition.

Legacy reference (`development:apps/chat/src/components/FileManager/hooks/useFileManager.tsx:276-277`): `isAnyOperationInProgress = useAppSelector(FilesSelectors.selectIsAnyFileOperationInProgress)`, rendered in `FileManager.tsx` as one full-page `bg-overlay` + `DialLoader` blackout, in addition to the dedicated `OperationLoaderModal` (hidden while `isRenaming`) and `FilesUploadingModal`. This confirms the legacy pattern was already "every operation gets *some* feedback; copy/move/upload get a richer dedicated modal instead of the generic blackout" — the current codebase already reproduces that split for every operation except unshare/remove-access, which is the actual, narrow gap.

## Goals / Non-Goals

**Goals:**

- One hook-level `isAnyOperationInProgress` boolean as the single source of truth for "is a mutating file-manager operation in flight," with each inclusion/exclusion explicitly justified below.
- Consolidate the shell's three duplicated overlay blocks into one, and extend it to cover `isUnsharing`/`isRemovingAccess` — closing the concrete UX gap without adding a fourth/fifth near-duplicate JSX block.
- `DialFileManagerModal` reads the shared flag instead of re-deriving a local subset.

**Non-Goals:**

- Redesigning the `OperationLoaderModal`/`UploadProgressModal`/`ShareFileModal` split — those already have dedicated, richer UI (progress, cancel) and are correct as-is; folding them into the generic blackout would be a regression, removing cancel/progress affordances.
- Gating tab switching, search, or the destination-folder popup's own preload-loading (`folderPopupLoadingPaths`) on `isAnyOperationInProgress` — no evidence (legacy or current) that these need to be blocked beyond what already happens structurally (a `DialPopup`-based modal already blocks background interaction while open).
- Introducing per-control (row-button-level) disabled states as an alternative to the blackout overlay — see D4.

## Decisions

**D1 — `isAnyOperationInProgress` is hook-owned as a plain boolean; the shell independently computes its own operation→label mapping from the raw flags it already destructures, for its own overlay.**
Considered exposing an `operationKind`/`ariaLabel` pair from the hook alongside the boolean, so the shell could render generically off it. Rejected: the hook must not depend on i18n (`useDialFileManager`'s established pattern has no `useTranslation` call, and `DialFileManagerShell` itself "SHALL NOT call `useTranslation` internally — every user-visible string it renders SHALL come from the `labels` prop," per the existing `file-manager-shell` spec). The *translated* label can only be resolved where the pre-translated `labels` object lives — the shell, which already destructures every individual raw flag it needs. So `isAnyOperationInProgress` stays a pure, hook-owned, i18n-free `useMemo`'d boolean (consumed by hosts like `DialFileManagerModal` for gating), while the shell's consolidated overlay computes its own label locally from the individual flags it already has — two independent, appropriately-scoped derivations of the same underlying state, not a single shared "kind" abstraction that would need to smuggle i18n concerns into the hook.

**D2 — Consolidate the five blackout-eligible states (`isDownloading`, `isDeleting`, `isRenaming && !isMoving`, `isUnsharing`, `isRemovingAccess`) into one overlay block; keep `OperationLoaderModal`/`UploadProgressModal`/`ShareFileModal` exactly as they are.**
The three existing overlay blocks are visually and structurally identical (`absolute inset-0 z-[52] ... bg-blackout`, `aria-live="polite"`, `Spinner`) — only the boolean condition and label differ. Adding a fourth/fifth copy for `isUnsharing`/`isRemovingAccess` would be the fourth/fifth near-duplicate JSX block; instead, resolve the applicable label via a small helper (if/else chain, not nested ternaries, per this repo's TypeScript conventions — `.claude/rules/all-ts.md`) and render one `{label != null && <div>...</div>}` block. `OperationLoaderModal`/`UploadProgressModal`/`ShareFileModal` are explicitly **not** folded into this consolidation — they carry state (progress, cancel button) the generic blackout has no slot for, and collapsing them would remove existing, spec'd UX (`file-manager-copy-move`'s cancel button, `file-manager-upload-archive`'s progress reporting).

**D3 — No manual z-index coordination is needed between the consolidated blackout and the three `DialPopup`-based modals.**
Verified: `OperationLoaderModal`/`UploadProgressModal`/`ShareFileModal` render through ui-kit's `DialPopup`, a portal-based dialog component with its own stacking context — they are never in the same DOM subtree as the shell's inline `z-[52]` overlay, and `useDialFileManager`'s state model never sets `isSharing`/`isCopying`/`isMoving`/upload-active simultaneously with any of the five blackout-eligible flags (each user action sets exactly one operation's state slice). No z-index value changes in this design.

**D4 — Keep the full-surface blocking-overlay approach; do not introduce targeted per-control disabled states.**
The existing overlay (`absolute inset-0`, no `pointer-events: none`) already blocks all pointer interaction with the grid/toolbar beneath it by DOM stacking, which is how `isDownloading`/`isDeleting`/`isRenaming` already work today with no reported gaps. Introducing per-button `disabled` props instead would require touching every row action and toolbar control's disabled logic individually — a much larger, more error-prone surface for equivalent behavior. This design keeps the proven, minimal-diff mechanism and only widens its trigger condition and consolidates its markup.

**D5 — Four flags are explicitly excluded from `isAnyOperationInProgress`, each for a distinct reason:**

| Flag | Included? | Why |
|------|-----------|-----|
| `isLoading` | **No** | Represents a read (listing fetch), not a mutation. `DialFileManagerModal` already checks it independently of `isOperationInProgress` today, confirming the codebase already treats "content is loading" and "an operation is in flight" as separate concepts. Hosts that want a combined read-or-write gate compose `isLoading \|\| isAnyOperationInProgress` explicitly (documented pattern, not baked into the flag). |
| `isSearching` | **No** | Scoped to ui-kit's own search-progress UI (`searchInProgress` prop); no host currently needs to block anything else while a search is in flight. |
| `isFileMetadataLoading` | **No** | Already has its own `loading` state surfaced through `fileMetadataPopupOptions` (per `file-manager-metadata`); it is a read-only, non-mutating fetch. |
| `isSharing` | **No** | `ShareFileModal` is already a foreground `DialPopup` dialog (own backdrop, own focus trap) that blocks interaction with the underlying grid while open — the exact same structural reason `OperationLoaderModal`/`UploadProgressModal` are excluded (D2). Folding `isSharing` into a page-level flag would be redundant, not additive: nothing outside the already-blocking modal needs a *separate* signal. |

Every remaining flag (`isCreatingFolder`, `isDownloading`, `isDeleting`, `isRenaming`, `isCopying`, `isMoving`, `isUnsharing`, `isRemovingAccess`, `uploadBatchState != null`) is included because each either has no dedicated blocking UI of its own (`isCreatingFolder`, `isDownloading`, `isDeleting`, `isRenaming`, `isUnsharing`, `isRemovingAccess` — covered by the consolidated blackout) or already gates a richer modal whose own presence should still be reflected in the shared flag for hosts like `DialFileManagerModal` that don't render that modal at all (`isCopying`, `isMoving`, `uploadBatchState` — the Attach modal has no copy/move/upload-archive affordance, but if the attach profile is ever widened, `isAnyOperationInProgress` must already account for them without a code change).

## Risks / Trade-offs

- **[Risk] A future host might read `isAnyOperationInProgress` to gate row-level interactions and expect it to also cover `isSharing`, producing a subtle "why didn't this block me" bug if a developer doesn't read D5.** → Mitigation: D5's table is captured as a normative requirement in specs.md (not just this design note), and the hook's field JSDoc explicitly lists the four exclusions with a one-line reason each.
- **[Risk] Consolidating three overlay blocks into one, non-nested-ternary-driven label resolution could be mis-ordered (e.g., if two flags are ever simultaneously true in a future refactor, the wrong label could show).** → Mitigation: the helper uses an explicit if/else chain with a documented precedence order, and a unit test asserts the resolution for every currently-reachable flag combination; `useDialFileManager`'s existing state model guarantees at most one of the five flags is `true` at a time today.
- **[Risk] Renaming `DialFileManagerModal`'s local variable to consume the hook field could regress the Attach-button gating if the hook's `isAnyOperationInProgress` composition ever changes to include a flag that IS reachable in the Attach profile but shouldn't block Attach.** → Mitigation: D5's exclusion table is normative; future changes to the composition must explicitly re-justify against it.

## Migration Plan

Additive + one refactor (consolidating three overlay blocks into one, and `DialFileManagerModal`'s local variable removed in favor of the hook field), confined to three files with no cross-file coupling beyond the shared `UseDialFileManagerResult` field. Rollback is reverting the three files independently; no data migration.
