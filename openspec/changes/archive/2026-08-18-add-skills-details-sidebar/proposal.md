# Enrich the skill details sidebar: parsed manifest, Specification, a hierarchical file selector, read-only file preview, and whole-skill archive download

## Why

The skill details sidebar already exists — `libs/catalog/src/components/Details/DetailsPanel.tsx` is a right-side slide-in panel (`desktop:w-[540px]`), and `CONTENT_FIRST_ENTITY_TYPES` at `DetailsPanel.tsx:61-64` already opens a skill on **Content** with an **Overview** beside it. What it shows is thin, and in two places wrong:

1. **The manifest is dumped raw.** `CatalogView.tsx:441-450` reads `SKILL.md` and hands the whole file to `ContentTab`, which renders it through `MarkdownRenderer`. That renderer registers only `remarkGfm` (`libs/chat-shared/src/components/MarkdownRenderer/MarkdownRenderer.tsx:144-145`) — no `remark-frontmatter` — so a skill's YAML frontmatter is rendered as body content. Under CommonMark the closing `---` turns the last frontmatter line into a setext `<h2>`, so a user opening any skill sees `name: …` / `description: …` as a heading before the actual instructions begin.

2. **The typed manifest model is dead code.** `SkillAboutDetails` (`apps/chat/src/types/entity-details.ts:256-261`) already declares exactly the fields a skill manifest carries — `whenToUse`, `allowedTools`, `bundledResources`, `skillPrompt` — and `mapSkillDetails` (`apps/chat/src/utils/map-entity-details-to-catalog.ts:480-508`) already maps them into a "Specification" Overview section. Nothing reaches either one: `EntitySpecificDetails` is built only by `mapDeploymentDetailsDtoToEntityDetails`, and the skill branch returns at `CatalogView.tsx:435-464` before any deployment path. A grep for `type: 'SKILL'` finds one hit — the union declaration itself.

3. **Only the manifest is readable.** A skill ships a whole directory, but the panel reads exactly one file. `buildSkillOverview` (`apps/chat/src/utils/map-skill-to-catalog-item.ts:83-119`) lists the rest as inert `label: <full path>` / `value: <last updated>` rows in the Overview — you can see that `analyzer.md` exists and never see what is in it.

4. **A simplified preview is still not Skill Builder parity.** The hierarchical selector and generic typed-preview revision made Markdown, code, images, and unsupported files readable, but detailed sidebar rendered those types through its own `MarkdownWithPlaceholders`/`MarkdownCodeBlock`/`img` switch. Skill Builder renders the same files through `useSkillFilePreviewSync` and `AttachmentCanvasBody`, which also owns structured JSON, HTML, PDF, audio, visualizers, theme, loading, and error states. Sharing classification helpers therefore did not make the UI or behavior the same. This correction reuses the actual Skill Builder renderer without widening `libs/catalog`'s dependency footprint.

5. **A skill can be read file-by-file but never taken as a whole, and the one action that would let a user do that is buried.** `Header.tsx`'s Manage (ellipsis) menu already carries a generic "Download" entry (`shouldShowDownloadAction`, `onDownload`, `isDownloadVisible`, `Header.tsx:247-248,300-313`), but nothing wires it for a skill today — `CatalogView.tsx`'s `handleDownload`/`isDownloadVisible` (`CatalogView.tsx:824-853`) restrict it to `CatalogEntityType.Prompt` only. Meanwhile the whole-skill archive endpoint a Download action would need already exists end to end and is already exercised in production code: `apps/chat/src/server-api/skills.api.ts`'s `downloadSkill(bucket, path)` wraps the generated `SkillsApi.downloadSkillRaw` (`GET /api/v1/skills/download`, `operationId: downloadSkill`), and `apps/chat/src/pages/SkillEditor/hooks/useSkillEditorLoad.ts:53-68` already calls it today to load a skill for editing. Even once wired, a skill's primary action would land in the same secondary, three-dot Manage menu every other entity's Download uses — for the one entity type whose defining "use" action *is* getting its files, that placement undersells it: `Header.tsx`'s primary-action slot (the same prominent position `PrimaryButton`/"Use in chat" occupies for a Model) is reserved for `Model`/`Agent`/`Prompt` (`shouldShowPrimaryAction`, `Header.tsx:233-238`) and a Toolset-only credentials swap (`isCredentialsActionPrimary`, `Header.tsx:396-397`); a `Skill` gets no primary action at all today.

## What Changes

- **`apps/chat`: a skill-manifest parser.** A new `apps/chat/src/utils/skill-manifest.ts` splits a `SKILL.md` string into its YAML frontmatter and its body, and maps recognised frontmatter keys onto the existing `SkillAboutDetails` shape. Both `snake_case` / `kebab-case` and `camelCase` spellings are accepted for each key, list values are accepted in flow (`[a, b]`) and block (`- a`) form, and unrecognised keys are ignored rather than surfaced. A file with no frontmatter, or with malformed YAML, degrades to "body only" — the panel never loses the manifest text because its header failed to parse.
- **`yaml` moves from `devDependencies` to `dependencies`** in the root `package.json` (currently `2.8.3`, dev-only). Hand-rolling YAML for the frontmatter subset is the alternative and is rejected below.
- **`apps/chat`: the Content tab shows prose, not frontmatter.** The skill branch of `onFetchDetails` passes the parsed **body** as `promptContent.content` and the frontmatter `description` as a new `promptContent.description`. `ContentTab` already renders a summary above a divider (`Content.tsx:33-42`); today it is fed `item.description`, which the skill list mapper hard-codes to `''` (`map-skill-to-catalog-item.ts:56`).
- **`libs/catalog`: `CatalogItemPromptContent` gains an optional `description`**, and `DetailsPanel` prefers it over `item.description` when rendering `ContentTab`. This is the only way a host can attach a summary that is discovered by the details fetch rather than by the list request; it is additive and prompts are unaffected.
- **`apps/chat`: the Overview tab gains a Specification section.** `buildSkillOverview` splits its single "Skill" section into **Specification** (when to use, allowed tools, bundled resources — each row omitted when absent) followed by **Details** (author, last updated, file count). The per-file rows leave the Overview: the picker below enumerates the same files and makes each one readable, so keeping inert copies would be the list twice.
- **`libs/catalog`: a hierarchical file selector in the Content tab. BREAKING.** `CatalogItemPromptContent.files` changes shape from a flat `CatalogContentFile[]` to a nested `CatalogContentTreeNode[]` (a `CatalogContentFileNode | CatalogContentFolderNode` union, folders carrying their own nested `items`), and the flat `CatalogContentFile` export is removed. The tab's picker is no longer `InlineSelect`: it is now a `Dropdown` (from `@epam/ai-dial-ui-kit`, already used elsewhere in this lib for `ShareButton`'s popover) anchored by a trigger built from `InlineSelectTrigger`, with `renderOverlay` rendering a small tree of folder and file rows the lib owns and draws itself — expand/collapse per folder, a persistent selected-row highlight, and full keyboard/ARIA tree semantics. **The picker appears only when the tree contains two or more files across any depth**; a single file, at any depth, is the body itself. Picking a file calls the existing `onLoadContentFile(fileId)` unchanged and renders whatever text it resolves; reselecting the base file still restores the original body with no request. The lib learns nothing about buckets, skills, folders-as-a-backend-concept, or endpoints — it receives a resolved tree of names and calls back with an opaque id, exactly as the flat version did.
- **Why this replaces, rather than extends, the flat picker.** The flat picker disambiguated same-named files in different folders by showing each option's full path (`scripts/run.py` instead of `run.py`) — workable for a short list, unreadable once a skill ships more than a handful of files across a few folders, and it gave the user no sense of the skill's actual file layout. A hierarchical view removes the need for path-qualified labels (position in the tree disambiguates instead) and lets the user scan a skill's structure at a glance.
- **`apps/chat`: `onLoadContentFile` resolves through `downloadSkillFile`.** `CatalogView` maps the callback onto the existing wrapper (`apps/chat/src/server-api/skills.api.ts:59`), converting Core listing ids such as `{skillPath}/files/openai.yaml` to the endpoint's file-relative `openai.yaml` while leaving already-relative ids unchanged. It reuses `readSkillManifest` so the same size cap applies to every file, and strips frontmatter only when the normalized path is `SKILL.md`. No new endpoint and no new `base.ts` helper.
- **File selection and file preview are now two separate concerns.** *Selection* is unchanged: the hierarchical tree from the previous revision still decides which file id the user picked, still lives entirely in `libs/catalog`, and still knows nothing about buckets or skills. *Preview* is new: it decides how the picked file's bytes are turned into something on screen — Markdown, plain text, syntax-highlighted code, an image, or an explicit "can't preview this" state — and it is the subject of every bullet below.
- **`libs/catalog`: a new, additive, generic preview contract, alongside the existing one. NON-BREAKING.** `DetailsPanelProps` and `CatalogProps` gain `onLoadContentFilePreview?: (fileId: string) => Promise<CatalogContentFilePreview | undefined>`, where `CatalogContentFilePreview` is a small discriminated union — `{ type: 'markdown', text }`, `{ type: 'text', text, language? }`, `{ type: 'image', url }`, or `{ type: 'unsupported' }` — added to `libs/catalog/src/models/item-details-data.ts` and exported from `index.ts`. The existing `onLoadContentFile?: (fileId: string) => Promise<string | undefined>` is **retained, not deprecated**: a host that supplies only `onLoadContentFile` keeps today's exact behavior (its result is treated as `{ type: 'markdown', text }`, matching what `MarkdownWithPlaceholders` already rendered before this change). A host supplying both SHALL have `onLoadContentFilePreview` take precedence per pick. Every id stays opaque either way — the new callback receives the identical `fileId` the old one did.
- **`libs/catalog`: a host-owned render slot provides full preview parity without a new dependency. NON-BREAKING.** `renderContentFilePreview?: (fileId, fileName) => ReactNode` takes precedence over both loading callbacks for supporting files. The lib still owns selection and passes only the opaque id plus basename; the app owns downloading, attachment state, and rendering. The base manifest bypasses the slot and remains parsed instructions. The generic typed-preview contract stays available for other consumers.
- **`libs/catalog`: `ContentTab`'s body dispatches on the resolved preview type.** For the base file (`SKILL.md`'s parsed instructions, or a prompt's body) nothing changes — `promptContent.content` keeps rendering through `MarkdownWithPlaceholders` exactly as today, since that text has always been Markdown. For a *picked* file, the panel now renders `MarkdownWithPlaceholders` for `markdown`, the existing `MarkdownCodeBlock` (from `@epam/ai-dial-chat-shared`, already this lib's peer dependency — no new one) for `text`, a plain `<img>` for `image` (`alt` derived from the file's tree name, sized to fit the panel without distortion), and a small accessible "preview not available" state for `unsupported`. **No new dependency**: `MarkdownWithPlaceholders` and `MarkdownCodeBlock` are both already exported from `@epam/ai-dial-chat-shared`, which `libs/catalog` already peer-depends on and already uses for the body; `@epam/ai-dial-attachment-canvas` (the Skill Builder's rendering library) is deliberately **not** added to `libs/catalog` — see the alternatives below.
- **`libs/catalog`: object-URL cleanup follows the same `blob:`-prefix convention `@epam/ai-dial-attachment-canvas`'s own context provider already uses.** `DetailsPanel` revokes a previous `image` preview's `url` via `URL.revokeObjectURL` whenever it is about to be replaced or the panel unmounts, but only when the url string starts with `blob:` — a host that hands back a permanent, non-blob URL (e.g. a public CDN link) is never revoked out from under it. This is a generic browser-API check, not skill- or bucket-specific knowledge, so it does not widen what the lib knows about any host.
- **`libs/catalog`: stale preview requests are now guarded.** `handleSelectContentFile` gains a per-selection request token so that picking file B while file A's `onLoadContentFilePreview` call is still pending, then having A resolve after B, cannot clobber B's already-displayed content. The same token guards the item-switch effect: a preview request in flight when the panel switches to a different catalog item is discarded on arrival rather than applied.
- **`apps/chat`: supporting files use the actual Skill Builder pipeline.** `SkillFilePreview` and `useSkillFilePreviewSync` move to shared app-level locations consumed by both Skill Builder and a new `SkillDetailsFilePreview`. `CatalogView` lazily downloads the selected file's bytes, normalizes Core listing ids, applies the existing size guard, and hands the same `{ bytes, mimeType? }` shape to the shared hook. Both surfaces therefore render through the same `AttachmentCanvasBody`, including JSON/HTML/PDF/audio/visualizer and shared loading/error/theme behavior. The obsolete simplified app classifier is removed.
- **`apps/chat`: the Skill Builder's *other*, stricter manifest parser is explicitly not reused.** `apps/chat/src/utils/skill.ts` already exports a second, differently-shaped `parseSkillManifest` (`ParsedSkillManifest`, throws on a manifest with no frontmatter, keeps the whole frontmatter object for edit-mode round-tripping via `buildSkillManifestFromFrontmatter`). The details panel keeps using the original, lenient `apps/chat/src/utils/skill-manifest.ts::parseSkillManifest` this change already introduced — the one built for read-only rendering, which degrades instead of throwing. The two parsers solve different problems (read-only display vs. editable round-trip) and this change does not merge them.
- **`apps/chat`: the dead deployment-shaped skill path is removed.** `mapSkillDetails` and the `{ type: 'SKILL' }` member of `EntitySpecificDetails` are deleted; `SkillAboutDetails` and `SkillEntityDetails` survive as the parser's output type, moved next to the other skill types in `apps/chat/src/types/skill.ts`. Deleting a mapper nothing calls is not scope creep — leaving two skill-detail mappers, one live and one unreachable, is how the next reader wires the wrong one.
- **`SKILL.md` renders instructions only — reconfirmed, not newly built.** `promptContent.content` is already the manifest's parsed `body` (D2/D1, shipped) — the text left over after `parseSkillManifest` removes the leading `---`-delimited frontmatter block — never the raw file. The parsed `name` and `description` fields are never concatenated into `content`; `description` only ever reaches the separate `promptContent.description` summary slot, and `name` reaches nothing in the Content tab at all (the item's own display name comes from `item.name`, set by `mapSkillToCatalogItem` from the skill's metadata, not from the manifest). This revision changes nothing about that split; it adds explicit acceptance scenarios and a spec requirement so the behavior is a documented contract rather than an implicit side effect of D1/D2. No Skill Builder form field, frontmatter editor, or Skill Builder action (save, validate, upload) is rendered anywhere in the details panel — the panel has never had any of those and this change does not add them.
- **The tab row for a skill stays stable.** No About tab is restored, and no tab is added: the parsed description arrives only after `onFetchDetails` settles, so an About tab derived from it would appear mid-interaction and shift the tab the user is looking at. `Skill` stays in `CONTENT_FIRST_ENTITY_TYPES`, the description lands in Content's summary slot, and the files land in a picker inside the tab the user is already on.
- **i18n**: roughly seven new keys from the earlier revisions (the Specification section and its three rows, plus the picker's aria-label, file count, loading and error strings), plus one new key this revision adds — `catalog.details.contentFileUnsupported` — and one new prop this revision adds to `ItemDetailsTexts` for it (`contentFileUnsupportedLabel`). No duplicate string is declared: `apps/chat` supplies this new prop's value by reusing the existing `attachmentCanvas.unsupportedLabel` string (`'Preview is not supported for this file'`, `en.json:834`) already declared for the chat product's own attachment canvas, per the duplicate-value rule this change already follows for its other keys. Existing `catalog.details.skill.*` and `catalog.details.contentFile*` keys are otherwise unchanged.
- **API capability gate: verified, not assumed.** A whole-skill archive endpoint already exists end to end, and it already ships a full round trip in production code today (see design.md D10 for full evidence): `GET /api/v1/skills/download` (`SkillsController.downloadSkill`, `apps/chat-api/src/skills/skills.controller.ts:169-244`, `operationId: 'downloadSkill'`, `@ApiProduces('application/zip')`) → `SkillsDownloadService.downloadSkill` (`apps/chat-api/src/skills/download/skills-download.service.ts:62-115`), which proxies DIAL Core's `downloadSkillFolder` and streams the ZIP, forwarding `content-type`, `content-disposition`, and `etag` through an explicit safe-header allowlist → the generated `SkillsApi.downloadSkillRaw`/`downloadSkill` (`libs/chat-api-client/src/generated/src/apis/SkillsApi.ts:502-559`) → the app-level wrapper `downloadSkill(bucket, path, signal?): Promise<Response>` (`apps/chat/src/server-api/skills.api.ts:47-57`, already using the `Raw` variant to preserve the native `Response` and its headers/stream). **This wrapper is already called in production** by `apps/chat/src/pages/SkillEditor/hooks/useSkillEditorLoad.ts:53-68` to load a skill for editing. No backend, DTO, OpenAPI, or generated-client change is required or proposed by this revision — the entire gap is that nothing in the catalog details panel calls the already-existing `downloadSkill` wrapper.
- **`apps/chat`: `handleDownload`/`isDownloadVisible` gain a Skill branch, alongside the existing Prompt-only one.** `CatalogView.tsx`'s existing `handleDownload` (`CatalogView.tsx:824-847`) returns early for anything but `CatalogEntityType.Prompt`; it gains a second branch for `CatalogEntityType.Skill` that resolves `{ bucket, path }` from `openSkillRef.current` (the same ref `handleLoadContentFile` already populates when the panel opens on a skill), calls `downloadSkill(bucket, path)`, and hands the response to a small new `saveSkillArchive` helper (see the Archive Handling decision in design.md D11) that resolves the save filename from `Content-Disposition` with a sanitized, deterministic fallback, triggers the browser download, and reports success/failure through the existing `useOperationNotification`/`showErrorNotification` mechanism this same handler already uses for prompts. `isDownloadVisible` gains the matching `CatalogEntityType.Skill` branch. **Prompt's existing branch, wording, and behavior are untouched.**
- **`libs/catalog`: Download becomes a first-class, promotable primary action — a new, additive `isDownloadPrimary` predicate, not a hardcoded Skill branch buried in app-only config.** `DetailsPanelProps`/`CatalogProps` gain `isDownloadPrimary?: (item: CatalogItem) => boolean`, following the exact optional-predicate idiom every other Header visibility rule already uses (`isPrimaryActionVisible`, `isDownloadVisible`, `isShareVisible`, …). `Header.tsx` computes a default — `item.type === CatalogEntityType.Skill` — exactly the way it already defaults `shouldShowPrimaryAction` to `Model`/`Agent`/`Prompt` and already special-cases `CatalogEntityType.Toolset` for the credentials-as-primary swap (`Header.tsx:396-397`, existing, unmodified precedent for a third-type primary-action branch). When the resolved predicate is `true`, `Header` renders a third `PrimaryButton` variant — label `texts?.downloadActionLabel ?? 'Download'` (the **same** key the Manage-menu entry already uses, not a new one), `IconDownload`, wired to `onDownload` — in the same prominent slot `PrimaryButton`/"Use in chat" occupies for a Model, and the Manage-menu's own Download entry is **excluded** for that item (never duplicated). No entity-type name beyond the already-lib-known `CatalogEntityType` enum is hardcoded; the app can override the default for any type through `isDownloadPrimary`, same as every sibling predicate.
- **`libs/catalog`: the promoted Download action gets a real pending state — something the Manage-menu entry has never had and still does not get.** `onDownload`'s existing contract (`Promise<void> | void`, "fire-and-forget: the result is not awaited") is **preserved unchanged for the Manage-menu path** — Prompt's behavior is bit-for-bit identical after this change. Only the new, separate primary-Download button awaits the same `onDownload` call, tracks its own `isDownloading` boolean local to `Header` (mirroring the existing `recipientsCountStatus` local-state pattern in the same file), disables the button and marks it `aria-busy` while pending, ignores a click while already pending (no concurrent downloads), and announces progress through a new `role="status"` region. This state is reset — not raced — when `item.id` changes: since the only transition an in-flight promise's `finally` can ever make is "downloading → not downloading," a stale settle from a superseded item can never re-arm a spinner for the new one (see design.md D11 for the full argument).
- **`libs/catalog`: no Blob, object URL, or archive byte ever exists inside the lib.** `onDownload`'s signature is unchanged; the lib calls it and awaits it, nothing more. Every byte of the archive, the `Response`/`Blob` handling, the `Content-Disposition` parse, the filename sanitization, and the `URL.createObjectURL`/`revokeObjectURL` pair live in `apps/chat`, reusing two already-shipped utilities rather than adding new ones: `apps/chat/src/utils/file-download.ts::triggerBrowserDownload(response, fallbackName)` (already extracts a `Content-Disposition` filename with a fallback, and already calls the object-URL-safe `triggerBlobDownload` from `@epam/ai-dial-chat-shared`) and `apps/chat/src/utils/file-name.ts::sanitizeFileName` (already strips forbidden filename characters for uploads, reused here for the download fallback name). Both are proven, already-tested code paths — `apps/chat/src/hooks/files/useDialFileMutations.ts`'s existing "download files/folder as ZIP" flow (`onDownloadFiles`) already composes them exactly this way, and this revision reuses that same composition for a skill archive rather than inventing a second one.
- **i18n, this revision:** one new title/message pair for the success toast, `entityNotifications.skill.downloadedTitle` (`'Skill downloaded successfully'`) / `entityNotifications.skill.downloaded` (`'Skill "{{name}}" is saved on your device.'`), added to `NotifiableEntity.Skill`'s entry in `ENTITY_OPERATION_NOTIFICATIONS` under the existing `EntityOperation.Downloaded` — following, word-for-word in structure, the pattern already established for `Prompt`/`File`/`Folder`'s own `downloaded`/`downloadedTitle` pairs; and one new failure key, `catalog.details.skillDownloadError` (`"Couldn't download this skill. Please try again."`), mirroring the existing `catalog.details.promptDownloadError` wording exactly with the noun swapped. The primary button's own label reuses the existing `downloadActionLabel` text prop — no new label string. A new `downloadingStatusLabel` text prop (default `'Downloading'`) is added to `ItemDetailsTexts` for the `aria-live` progress announcement, following the same naming convention as the file's existing `deletingStatusLabel`/`unsharingStatusLabel`/`revokingShareStatusLabel`/`loggingOutStatusLabel` props.
- **Non-breaking.** Every lib addition is an optional field, an optional predicate, or reuses an existing callback's exact signature; every app change is inside the skill branch of an already-branching handler. `onLoadContentFile` and `onLoadContentFilePreview` keep working unmodified for hosts that do not adopt `renderContentFilePreview`. Download's Manage-menu behavior is pixel-for-pixel unchanged for every entity type that does not opt into `isDownloadPrimary`. `OverlayFeature.Skills` still switches the whole surface off.

### Non-goals

- ~~**No file download.**~~ **Superseded by this revision.** Whole-skill archive download is now the point of this revision; see the Why and What Changes sections above. This non-goal originally referred to per-file download inside the preview, which stays out of scope (see below) — it never covered the whole-skill case this revision adds.
- ~~**No syntax highlighting per file type.**~~ **Superseded by an earlier revision.** A picked text/source file now renders through `MarkdownCodeBlock` with syntax highlighting keyed off its extension, matching the Skill Builder. This was design.md's open question 3, now resolved.
- ~~**No PDF, HTML-as-page, structured-JSON-tree, audio, or visualizer preview.**~~ **Superseded by the renderer-parity correction.** Supporting files now use Skill Builder's actual `AttachmentCanvasBody`, so every format it supports is supported here too. Video remains governed by that shared pipeline rather than a details-specific implementation.
- **No per-file download inside the preview.** A single supporting file is still read in the panel, not saved to disk — `MarkdownCodeBlock`'s own download control stays hidden (per the `catalog-content-file-preview` capability). Only the *whole skill* is downloadable, and only from the primary action.
- **No skill mutations.** Upload, delete, and grouping-folder writes stay uncalled, and `isEditable` stays `false` for every skill.
- **No backend, DTO, OpenAPI, or generated-client change for archive download.** The whole-skill ZIP endpoint, its generated client method, and its response-header contract all already exist and are already exercised in production by the Skill Builder; this revision only adds a frontend call site. (Unrelated: `apps/chat-api/src/skills/` already exposes listing, file listing, and per-file download for the earlier revisions' own needs; the frontmatter is parsed client-side from the file the panel already fetches.)
- **No promotion of Download to primary-action status for any entity type other than Skill.** `isDownloadPrimary`'s default covers `CatalogEntityType.Skill` only; Prompt's Download stays exactly where and how it is today — a Manage-menu entry, fire-and-forget, no pending state.
- **No cancel button and no progress percentage.** The primary Download button shows an indeterminate busy/disabled state and an `aria-live` status announcement while the archive request is in flight; it does not expose a cancel affordance or a byte-level progress bar. The existing whole-skill download endpoint streams but this revision does not surface stream progress in the UI — worth revisiting if archives are observed to be large enough that an indeterminate spinner reads as a hang.
- **No frontmatter for prompts.** Prompt content keeps rendering exactly as it does today.
- **No skills tab outside the catalog**, no `/skills` route, and no "use in chat" for a skill.
- **No search or filter box inside the tree.** The dropdown lists the whole hierarchy; nothing narrows it by typed text. Worth revisiting if real skills routinely ship enough files that scrolling becomes the bottleneck.
- **No per-folder lazy loading.** `listSkillFiles({ recursive: true })` already returns the skill's entire file inventory, folders included, in one call; the tree is built once from that array and expand/collapse is a pure client-side view over it — no folder ever issues its own request.
- **No drag-drop, rename, upload, or create-folder inside the tree.** It is a read-only selector, not a file-manager surface; `isEditable` stays `false` for every skill regardless of this change.

### Alternatives considered

1. **Hand-roll a frontmatter parser instead of shipping `yaml`.** Rejected. The frontmatter is authored by users, and the failure mode of a hand-rolled parser is silently wrong values (a quoted string containing `:`, a multi-line block scalar, an escaped list item) rather than a clean parse error. `yaml` is already vendored in the lockfile and only loads inside the catalog chunk. If the bundle cost measures badly in task 6.1, the fallback is a dynamic `import('yaml')` inside the skill branch, not a bespoke parser.
2. **Parse the manifest on the backend and return a typed DTO.** Rejected for this change: it adds a skills-details endpoint plus an OpenAPI regeneration cycle to save a parse of a file the frontend already downloads. Worth revisiting if a second consumer needs the parsed manifest.
3. **Restore the About tab for skills now that a description exists.** Rejected: see the tab-stability point above. The summary slot in `ContentTab` shows the same text without moving the tab row.
4. **A dedicated Files tab with per-file download.** Built first, then removed. It cost a new tab, a new lib component, a new tab-derivation branch, and a download callback — and still left every file unreadable in the panel. A picker inside the tab the user is already on adds no tab-row surface and makes the files readable, which is the thing that was missing.
5. **Keep the file rows in Overview as they are.** Rejected: a flat `label: path` list with no action is a list of filenames, not access to them.
6. **Add a generic `remark-frontmatter` plugin to `MarkdownRenderer` instead of stripping the fence in the app.** Rejected: that hides the frontmatter from every markdown surface in the product, including assistant output where a leading `---` is legitimately a rule. The strip belongs to the skill branch that knows the file is a manifest.
7. **Keep the flat `InlineSelect` picker, with full paths as labels.** Rejected — this is the shipped implementation this change now replaces. It scales poorly past a handful of files: every option's label grows to a full path the moment two files share a name, and the list carries no sense of the skill's actual folder structure. See design.md D3 for the full comparison against the two alternatives below.
8. **Render `DialFoldersTree` (from `@epam/ai-dial-react-file-manager`) inside a `Dropdown`.** Rejected. `DialFoldersTree` is a 1.0 component built for a full, mutable file manager — rename, create-folder, drag-and-drop, per-item context menus, lazy per-folder loading via `loadingPaths`/`loadedPaths` — none of which this read-only selector needs, and its `DialFile` item shape (`bucket`, `folderId`, `permissions`, …) is a much larger model than the two or three fields a selector needs. `libs/catalog` does not currently depend on `@epam/ai-dial-react-file-manager` at all; adopting it here would add that package (and its own `ag-grid-community`/`ag-grid-react` peer contract) as a new dependency of a lib that today has none of them, solely to render a static, single-select list.
9. **Build a small tree renderer directly on top of the generic 2.0 `Dropdown`'s `renderOverlay`.** Selected. `Dropdown` already supports fully custom overlay content and is already imported in this exact lib (`ShareButton`'s popover). Composing it with `InlineSelectTrigger` (the same trigger `InlineSelect` itself wraps) keeps the trigger's look identical to today's picker while the overlay becomes a small, purpose-built, read-only tree the lib owns end-to-end — full control over ARIA tree semantics, no new dependency, and a data model sized to exactly what a selector needs.
10. **Keep rendering every picked file as Markdown (today's behavior).** Rejected: it is the problem statement (Why, point 4) — code loses its whitespace, images render as garbage text, and there is no way to say "this can't be shown."
11. **Duplicate the Skill Builder's preview logic inside `libs/catalog` or inside a second copy in `apps/chat`.** Rejected. `libs/attachment-canvas`'s extension tables (`TEXT_EXTENSIONS`, `HTML_EXTENSIONS`, `EXTENSION_TO_LANGUAGE`) and `libs/chat-shared`'s MIME table (`EXTENSION_TO_MIME_TYPE`) already encode this product's answer to "what kind of file is this." A second, hand-maintained copy would drift the moment one table gains an extension the other doesn't, and the details panel and the Skill Builder would silently disagree about the same file.
12. **Add `@epam/ai-dial-attachment-canvas` as a new `libs/catalog` peer dependency and render `AttachmentCanvasBody` directly.** Rejected. `AttachmentCanvasBody` is host-agnostic, but its peer surface includes sidebar, PDF, visualizer, highlighter, and JSON-view packages that `libs/catalog` does not otherwise need. Exact parity is still required, so the selected D9a design mounts the renderer at the app edge through `renderContentFilePreview` instead of widening the catalog library's dependency graph.
13. **Extract a smaller preview library for both surfaces.** Considered and deferred. Skill Builder already has the required production renderer; extracting a new package would duplicate migration work and still require the app to adapt bytes and attachment context. D9a instead shares the existing app component and synchronization hook between Skill Builder and skill details.
14. **Keep file-type resolution inside `libs/catalog`.** Rejected. MIME/extension classification and attachment state are product concerns. The generic four-type fallback accepts an already-classified value, while skill details use the app-owned `AttachmentCanvasBody` render slot and keep all classification outside the catalog lib.
15. **Build a frontend-only archive from the files the panel already lists, zipping them client-side.** Rejected before it was seriously considered, because it is unnecessary: a whole-skill archive endpoint already exists, is already proxying the correct DIAL Core operation, and is already exercised in production by the Skill Builder (design.md D10). Client-side zipping would also silently diverge from whatever DIAL Core actually packages (byte-for-byte identical to what an admin or the Skill Builder downloads), pull in a zip-writing dependency neither `apps/chat` nor `libs/catalog` currently has, and require fetching every file individually instead of one streamed response.
16. **Keep Download in the Manage menu for Skill, just make the menu itself more prominent.** Rejected: the task is explicit that Download must be the primary action in the same prominent position "Use in chat" uses for a Model, and must not be hidden inside the ellipsis menu at all — a more prominent menu is still a menu, not a primary action.
17. **Add a generic `primaryAction` descriptor prop (label/icon/onClick/loading) that fully replaces the hardcoded "Use in chat" and credentials-swap branches.** Considered and deferred, not rejected outright. It would be a cleaner long-term shape — one generic slot instead of three special-cased branches — but it means also refactoring the already-shipped, working `isCredentialsActionPrimary` Toolset branch and the `shouldShowPrimaryAction`/"Use in chat" branch to fit the same descriptor, which is a wider refactor of `Header.tsx`'s existing, tested behavior than this change's stated scope (promote Skill's Download; leave every other entity type's primary action untouched). **Selected instead:** add a fourth branch (Download-as-primary) using the same per-branch pattern the file already has for Toolset, gated by a new `isDownloadPrimary` predicate that follows the established optional-override idiom. Revisit a unified descriptor if a fourth or fifth entity type needs its own distinct primary action.
18. **Give `onDownload` a new, richer signature (e.g. returning progress or accepting an `AbortSignal`) instead of reusing it unchanged for the primary action.** Rejected for this change. The task's required behavior (disabled while pending, no concurrent clicks, an `aria-live` announcement, cleanup on item switch) is fully achievable by having `Header` await the existing `Promise<void> | void` and manage its own local pending state — exactly as it already does for `onFetchRecipientsCount`. Widening the callback's signature would also change the Manage-menu path's contract for every other entity type using `onDownload` today (Prompt), which the task explicitly requires to stay unchanged.
19. **Have `apps/chat` decide download-button placement (primary vs. Manage) by never rendering the Manage-menu entry for Skill in the first place, rather than adding an `isDownloadPrimary` predicate to the lib.** Rejected: `Header.tsx` — not the host — owns the decision of *where* an item's actions render (primary slot vs. `manageItems`); that placement logic (`shouldShowDownloadAction`, `manageItems`) is entirely internal to the component today, with no seam for a host to suppress one placement while keeping the callback wired for the other. Introducing `isDownloadPrimary` is the minimal, additive seam that lets the host influence placement without duplicating or forking `Header`'s existing menu-assembly logic.

### Rollback / backward-compat

Every piece is additive and independently revertible, with one exception. Reverting the `libs/catalog` commit leaves the app passing a `description` and a file tree the lib ignores — degraded, not broken. Reverting the app commit leaves the lib with optional fields no host populates, so no picker is derived. Turning `OverlayFeature.Skills` off removes the whole surface as it does today. The one non-additive step is deleting `mapSkillDetails`, which no code path reaches.

**This revision's rollback.** `onLoadContentFilePreview` is purely additive: reverting the `libs/catalog` commit that adds it leaves `onLoadContentFile` as the only contract, and every picked file renders as Markdown exactly as it does immediately before this revision — a degrade, not a break. Reverting the `apps/chat` commit that supplies `onLoadContentFilePreview` leaves the new prop unpopulated, so `DetailsPanel` falls back to `onLoadContentFile`, again a degrade to the prior revision's behavior, not a break. No version of this change removes `onLoadContentFile` or makes `onLoadContentFilePreview` required.

**The renderer-parity correction's rollback.** Reverting only the app adoption of `renderContentFilePreview` restores the generic typed-preview fallback; reverting the optional lib render slot requires reverting the corresponding app prop in the same change. Skill Builder continues to use the extracted shared component and hook either way.

**This revision's own rollback.** `CatalogContentFile` → `CatalogContentTreeNode` is a breaking change to an interface this same change already shipped (see tasks.md's task 1.2/history). Because the change has not yet been archived, there is no external consumer of the flat shape to migrate — reverting to the flat picker means reverting this revision's commits on top of the original flat-picker commits, not maintaining both shapes side by side. No version of this change ships both a flat and a hierarchical picker at once.

**This (archive-download) revision's rollback.** Purely additive and independently revertible: reverting the `libs/catalog` commit removes `isDownloadPrimary` and the third `PrimaryButton` branch, so Skill's Download reverts to living only in the Manage menu (assuming `apps/chat` already wired `onDownload`/`isDownloadVisible` for Skill) — degraded prominence, not broken functionality. Reverting the `apps/chat` commit that adds the Skill branch to `handleDownload`/`isDownloadVisible` leaves `isDownloadPrimary`'s default predicate matching `CatalogEntityType.Skill` but with no `onDownload` populated for that item, so `shouldShowDownloadAction`/the primary-Download branch both resolve `false` and no Download affordance renders anywhere for a skill — the exact pre-this-revision state. No backend rollback is needed or possible, since no backend change is made.

## Capabilities

### New Capabilities

- `skill-manifest-parsing`: the `SKILL.md` frontmatter/body split — accepted keys and their alias spellings, list value forms, the size guard's interaction with the parse, and the degradation contract for a missing, malformed, or frontmatter-only manifest.
- `catalog-content-file-picker`: the lib's `CatalogContentTreeNode` model (a folder/file union, folders nesting further nodes), when the picker renders (two or more files across the tree), the tree's rendering and interaction contract (expand/collapse, selection, keyboard, focus), the `onLoadContentFile` callback contract including base-file restore and failure handling, and the picker's i18n, RTL, and accessibility requirements. Kept under its original name: the capability is still "let the host's Content tab switch between multiple files" — only the shape of the options and the picker's rendering deepen from flat to hierarchical, not the capability's purpose.
- `catalog-content-file-preview`: the generic typed-preview fallback plus the optional `renderContentFilePreview(fileId, fileName)` host-renderer contract, whose returned node takes precedence without exposing host integration details to the lib. Kept separate from `catalog-content-file-picker`: that capability decides *which* file id was picked; this one decides *what renders* once it has been.
- `catalog-primary-action`: the generic, entity-agnostic contract for `Header.tsx`'s primary-action slot — the existing `Model`/`Agent`/`Prompt` "Use in chat" default and the existing `Toolset` credentials-swap are both restated here as the established precedent this capability's new `isDownloadPrimary` predicate follows; mutual exclusivity with the Manage-menu Download entry; the pending/disabled/`aria-busy`/`aria-live` contract for an awaited `onDownload` call; and per-entity-type precedence documentation (Skill → Download; Model/Agent/Prompt → Use in chat; Toolset → credentials; everything else → no primary action, all unchanged).
- `skill-archive-download`: the skill-specific application-edge wiring — resolving `{ bucket, path }` for the open skill, calling the already-existing `downloadSkill` server-api wrapper, filename resolution from `Content-Disposition` with a sanitized fallback, triggering the browser save, success/failure notification, and the verified evidence that no backend or generated-client change is required.

### Modified Capabilities

- `skill-details-panel`: the skill branch parses the manifest, feeds Content a body plus description plus hierarchical tree, and splits Overview into Specification and Details. Supporting files now mount `SkillDetailsFilePreview` through the generic host render slot and reuse Skill Builder's actual synchronization and `AttachmentCanvasBody`; `SKILL.md` explicitly bypasses that renderer and remains instructions-only. The change also adds the Skill archive-download wiring and primary action.

## Impact

**Libraries**

- `libs/catalog`: retains the generic tree and typed-preview APIs and adds optional `renderContentFilePreview` forwarding through `Catalog`/`DetailsPanel` into `ContentTab`. The returned host node takes precedence and receives an overflow-contained body. No new tab or dependency; no skill/API/context knowledge enters the lib.

**Application**

- `apps/chat`: extracts `SkillFilePreview` and `useSkillFilePreviewSync` from the Skill Editor page to shared app component/hook locations; adds `SkillDetailsFilePreview`; changes `CatalogView` to load raw supporting-file bytes and supply the host render slot; removes the superseded `skill-content-preview.ts` classifier. Manifest parsing/tree mapping/path normalization/archive download remain app-owned.

**Dependencies**

- Root `package.json`: `yaml@2.8.3` moves `devDependencies` → `dependencies` (unaffected by this revision).
- No new dependency for the tree: it is composed from `Dropdown` and `InlineSelectTrigger`, both already part of `@epam/ai-dial-ui-kit`, already a peer dependency of `libs/catalog`. `@epam/ai-dial-react-file-manager` is explicitly **not** added.
- **No new dependency for preview.** `libs/catalog` receives a `ReactNode` and does not import attachment canvas. `apps/chat` reuses its existing `@epam/ai-dial-attachment-canvas` dependency through the same shared component/hook as Skill Builder.
- **No new dependency for archive download.** `apps/chat` reuses its own already-shipped `triggerBrowserDownload`/`sanitizeFileName`; `libs/catalog` gains one new optional predicate prop and one new text prop, no new package.

**Backend**

- None for this revision either. `GET /api/v1/skills/download`, its generated client method, and its response-header contract already exist and are unchanged by this proposal; `npm run openapi:check` stays green because nothing in the OpenAPI surface is touched.

## Acceptance criteria

1. Opening a skill whose `SKILL.md` starts with a `---` fence shows the description as the Content tab's summary line and the body below it, with no `name:` / `description:` text and no stray heading or rule from the fence.
2. Opening a skill whose `SKILL.md` has no frontmatter shows the whole file as the body and no summary line — unchanged from today apart from the absent summary.
3. A manifest with malformed YAML in its fence still renders its body; the panel logs nothing user-visible and shows no Specification rows.
4. The Overview tab shows a **Specification** section listing only the frontmatter fields that are present, followed by a **Details** section with author (omitted when absent), last updated, and file count. No file rows remain in Overview.
5. A skill with two or more files (at any depth) shows a file selector above the Content body: a trigger showing the open file's basename, opened on `SKILL.md`, with the file count beside it. Opening the selector shows every folder and file the listing returned, hierarchically, with grouping folders that carry no files still shown as empty, expandable (but childless) rows. A skill with exactly one file anywhere in its tree, and a skill whose listing failed, show no selector.
6. Every folder in the tree starts expanded the first time the selector opens for a given skill; collapsing or expanding a folder persists across closing and reopening the selector for that same skill, and resets back to fully expanded when a different item opens.
7. Two files with the same name in different folders both appear, each under its own folder, and picking either one loads that specific file's content — the tree's structure, not the display name, disambiguates them.
8. Picking a supporting file uses `renderContentFilePreview` when supplied, otherwise the typed or legacy loading callback in precedence order. The render slot receives the opaque id and basename; reselecting `SKILL.md` restores the manifest body without mounting the host renderer or issuing another request.
9. The selector is fully operable by keyboard: arrow keys move between visible rows and expand/collapse folders, Enter/Space picks a file or toggles a folder, Escape and outside-click close it without changing the selection, and focus returns to the trigger every time it closes.
10. The selector renders without horizontal overflow at a 360px viewport width, mirrors its folder-expansion chevron in RTL, and every row meets the minimum touch-target size on mobile.
11. The tab the panel opens on does not change as details resolve, for a skill or for a prompt, and no new tab is added to the row.
12. `npm exec nx lint` and the vitest suites for `@epam/ai-dial-catalog` and the skill-touching `@epam/chat` specs all pass; `mapSkillDetails`, `type: 'SKILL'`, `CatalogContentFile`, and `buildSkillContentFiles` no longer appear anywhere in `apps/chat/src` or `libs/catalog/src`; `libs/catalog/package.json` gains no new dependency.
13. `SKILL.md`'s preview never contains its YAML frontmatter, the `name:` field, or the `description:` field as body text, and renders no Skill Builder form control or action; a `SKILL.md` that is nothing but frontmatter shows an empty-instructions state, not an error.
14. Markdown, code/plain text, structured JSON, HTML, PDF, image, audio, visualizer, unsupported, loading, and error supporting-file states render through the same `AttachmentCanvasBody` pipeline, theme, and labels as Skill Builder.
15. A Core `application/octet-stream` response falls back to Skill Builder's extension inference, while a specific MIME such as `image/png` is preserved.
16. A supporting-file HTTP 403 renders the shared forbidden state; other non-OK/network/oversize failures render the shared load-error state and leave the detailed sidebar open.
17. Picking file B while file A is pending cannot display A under B: the app component's cancellation plus shared attachment-id reconciliation keeps the active selection authoritative. Switching catalog items has the same guarantee.
18. Object URLs produced by the shared pipeline are revoked by the existing `AttachmentCanvasContext` ownership rules when content changes or the preview unmounts.
19. The host-rendered preview fills the Content body's `min-h-0 flex-1 overflow-hidden` area, works at 360px and the 769px boundary without panel-level horizontal overflow, inherits document direction, and exposes the same accessible group name and loading/error behavior as Skill Builder.
20. `onLoadContentFile` and `onLoadContentFilePreview` continue to work unmodified for hosts that do not supply `renderContentFilePreview`; the new render slot is optional and additive.
21. A skill's details panel shows Download as its primary action, in the same slot and with the same visual prominence a Model's "Use in chat" button uses, and shows no "Use in chat" button.
22. A skill's Manage (ellipsis) menu contains no "Download" entry — the action exists exactly once, in the primary slot.
23. A Model's details panel still shows "Use in chat" as its primary action, unchanged in label, icon, visibility rule, and behavior; a Model's Manage menu is unaffected.
24. A Prompt's Download action still appears only in the Manage menu, fire-and-forget, with no pending/disabled state added to it by this revision; a Toolset's credentials-as-primary behavior is unaffected; an Agent's "Use in chat" is unaffected.
25. Activating a skill's Download button calls the existing `downloadSkill(bucket, path)` server-api wrapper with the bucket and path of the currently open skill, resolved the same way `onLoadContentFile` already resolves them.
26. A successful download triggers a browser save whose filename comes from the response's `Content-Disposition` header when present, or a sanitized `<skill-name>.zip` fallback when it is absent; a filename containing Unicode characters saves correctly; a filename containing path separators or other unsafe characters is sanitized before being handed to the browser.
27. The Download button is disabled and marked busy for the duration of the archive request; a second click while it is pending starts no second request; progress is announced through an `aria-live` region; the button returns to its normal, enabled state once the request settles, whether it succeeded or failed.
28. A failed archive request (unauthorized, forbidden, missing skill, or a server error) keeps the details panel open, shows the existing operation-notification failure UI, and leaves the Download button enabled again — no stale "downloading" state survives the failure.
29. Switching to a different catalog item, or closing the details panel, while an archive request is in flight leaves no visible "downloading" indicator on the new item or after reopening, and creates no dangling object URL.
30. No `fetch` call appears directly inside any `libs/catalog` or `apps/chat` UI component for the archive download — the request goes through the generated client via the existing `server-api/skills.api.ts` wrapper.
31. `libs/catalog/src/**` contains no reference to buckets, skill resource paths, `downloadSkill`, `Content-Disposition`, or any other backend/API-shaped identifier for this feature — it receives only `isDownloadPrimary`'s boolean result and an `onDownload` promise to await.
32. `npm run openapi:check` passes with no diff, confirming this revision changed no backend contract or generated client.
