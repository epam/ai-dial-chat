## Slicing strategy

Vertical slices, risk-first inside the order: the smallest slice (picker, no new lib code) proves the adapter pattern and the entry/peer checks first; the largest (conversation data source) comes last, after the smaller slices have exercised the packaging checks. Each slice adds its lib code with tests written first, adopts it in `apps/chat`, keeps host page/component specs unchanged in meaning, and updates its README section and spec path references in the same slice. Slices 1, 2, 3, 7 and 8 are independent of each other (slice 2 is app-only and comes early so that the page edits of the later slices work on the final import shapes); slice 4 needs slice 3, slice 5 needs slice 4 (the pages compose the draft with the preview controller's `closeIfRemoved`), slice 9 needs slice 8, slice 6 is dropped (see design D5) and slice 10 is droppable (P3), recorded in the closing report if skipped.

Conventions for every slice: relative imports have no `.js`/`.ts` extension; every exported symbol and interface field has JSDoc; new lib code goes under `libs/chat-hooks/src/<module>/` with tests in the sibling `tests/` folder; no new peer on any entry; the lib contains no `/api` path, generated-client instance, `server-api` import, app context, auth/session/cookie/env access, feature flag, routing, analytics, storage key or i18n call. Run `npm run test:file -- <path>` for the named specs, `npm run verify:changed` once when the slice is done, and `npm run build:quiet` only in slices that add exports (bundling is affected).
