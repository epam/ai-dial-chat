## Context

`DeploymentsService` (1038 lines) backs `DeploymentsController` for bulk listing, single-item lookup (used right after a share-invitation accept), rich per-deployment details (model/application/toolset detail shapes), configuration schema, and limits. `ToolsetsService` (1107 lines) backs `ToolsetsController` for listing/retrieval, CRUD mutation, and OAuth/API-key sign-in/sign-out, and additionally injects `DeploymentsService` for one call (`invalidateDetailsCache`, to keep the details panel's cached auth status in sync after a toolset login/logout).

Both files carry a large block of module-level pure mapping/DTO-conversion helpers ahead of the class body — roughly 300 lines in `deployments.service.ts` (`mapToDeploymentItem`, `mapDeploymentFeatures`, `mapToolsetAuthSettings`, `mapConversationStarters`, `redactToolsetAuthSettings`, plus generic `isRecord`/`getBoolean`/`getNumber`/`getString`/`getStringArray`/`toAdditionalProperties`) and roughly 480 lines in `toolsets.service.ts` (`toDialCredentialsLevel`, `parseDialToolsetResource`, `toDialAuthSettings`, `preserveHiddenAuthSettings`, `toDialToolsetBody`, `resolveToolsetLoginUrl`, `toDialToolsetSigninBody`, `toDialToolsetSignoutBody`, `isVisibleToolset`, `isMyToolset`, `getRawAuthSettings`, `mapAuthSettings`, `mapToolsetFeatures`, `mapDialToolsetToDto`, `mergeCustomToolsetDetails`, plus generic record helpers).

The backend already has two precedents for this exact kind of split: `2026-07-16-split-files-service` and `2026-08-07-split-conversation-service` (both archived), which decomposed similarly-sized services into a thin facade plus focused sub-services. This design reuses that pattern for deployments and toolsets, doing both in one change because `ToolsetsService` already depends on `DeploymentsService` — splitting them separately would leave one change's sub-service referencing a method that moved out from under it in the other, not-yet-applied change.

A separate, still-open PR (#8226, `fix/deployment-accept-ownership-enrichment`) is independently extracting a shared `apps/chat-api/src/common/utils/resource-ownership.ts` (`computeItemOwnershipFlags`, `splitResourcesByPermission`) to fix a duplicated-and-subtly-buggy ownership check that exists in both files today (`ToolsetsService`'s `isMyToolset` and `DeploymentsService.listDeployments`'s inline check). This design treats that as an external dependency: the split should consume it if merged, not re-solve it.

## Goals / Non-Goals

**Goals:**
- Break `DeploymentsService` into `DeploymentsListingService`, `DeploymentsLookupService`, `DeploymentsDetailsService`, each independently unit-testable, plus a facade under ~200 lines.
- Break `ToolsetsService` into `ToolsetsListingService`, `ToolsetsMutationService`, `ToolsetsAuthService`, each independently unit-testable, plus a facade under ~200 lines.
- Move each domain's module-level pure mapping/DTO helpers into a dedicated `utils/*.util.ts` file, removing ~780 combined lines of non-class logic from sitting inside the two monoliths.
- Rewire the one cross-domain call (`ToolsetsService` → `DeploymentsService.invalidateDetailsCache`) to the new `DeploymentsDetailsService` directly.
- Split the corresponding oversized spec files into per-sub-service spec files, mirroring the new folder structure.

**Non-Goals:**
- No REST contract, DTO, or OpenAPI changes — identical request/response shapes, status codes, cache keys, TTLs, and structured logging.
- No frontend changes.
- No fix for the `isMyToolset`/`listDeployments` ownership-check duplication or its bucket-segment bug — that is PR #8226's scope. If #8226 has merged by implementation time, the new listing services should import `computeItemOwnershipFlags`/`splitResourcesByPermission` instead of re-inlining the check; if not yet merged, carry the existing (duplicated) logic forward unchanged and note it as a known follow-up.

## Decisions

**Facade + bound-property delegates, matching `ConversationService`'s pattern.** Both `DeploymentsService` and `ToolsetsService` keep their current public method names/signatures and delegate via bound property references for pure 1:1 forwards (`listDeployments = this.listingService.listDeployments.bind(this.listingService)`), with explicit method bodies only where a call needs actual glue. This was the exact approach validated in `2026-08-07-split-conversation-service`'s facade (110 lines, 18 delegated methods) and keeps both controllers' constructor injection and every call site unchanged.

**Deployments boundaries follow the three distinct call shapes, not raw line count.** `listDeployments` (bulk, cached, ownership-enriched) and `resolveDeploymentItem` (single id, used only for the post-share-accept race) look superficially similar (both map `RawDeploymentDto` → `DeploymentItemDto`) but have different callers, different cache keys, and `resolveDeploymentItem` never touches the bulk-list cache at all — keeping them separate (`DeploymentsListingService` vs `DeploymentsLookupService`) avoids coupling their cache lifecycles. `getDeploymentDetails` and its three `build*Details` branches are a third, clearly separate concern (per-type detail shape assembly, its own cache namespace, its own in-flight-request dedup map) — `DeploymentsDetailsService`. `getDeploymentConfiguration`/`getDeploymentLimits` are small, standalone reads with no shared state with the other three; they stay in `DeploymentsDetailsService` since they're the same kind of "fetch and cache one deployment-scoped fact" as details, rather than justifying a fourth tiny service.

**Toolsets boundaries follow HTTP-verb-adjacent responsibility.** `listToolsets`/`getToolset`/`resolveToolsetItem` are all reads with shared ownership-enrichment and cache-invalidation machinery (`ToolsetsListingService`). `createToolset`/`updateToolset`/`deleteToolset` are mutations sharing `resolveToolsetResource`/bucket-resolution logic (`ToolsetsMutationService`). `loginToolset`/`logoutToolset` are a third, self-contained concern — DIAL Core sign-in/sign-out protocol translation — with no read/write-path logic of their own (`ToolsetsAuthService`). This mirrors the natural verb groupings already used by the controller's own route grouping.

**Pure module-level helpers move to `utils/*.util.ts`, not into any one sub-service.** Both files' pre-class helper blocks are pure functions with no `this` dependency — they belong to the domain, not to any single responsibility slice, and multiple new sub-services need them (e.g. `mapToDeploymentItem` is needed by both `DeploymentsListingService` and `DeploymentsLookupService`; `mapDialToolsetToDto` is needed by `ToolsetsListingService` and (for the create/update response mapping) `ToolsetsMutationService`). Extracting them first, before splitting the class bodies, means every subsequent extraction step imports from one already-stable file instead of guessing which sub-service "owns" a given mapper.

**`DeploymentsDetailsService`'s `build*Details` methods stay class methods, not free functions.** Each already depends on `this.dialClient`/`this.logger`/`encodeDialResourcePath` and calls sibling methods (`buildUnprefixedDeploymentDetails` calls `buildModelDetails`/`buildApplicationDetails`/`buildToolsetDetails` in sequence); converting them to free functions would mean threading `dialClient`/`logger` through every call as parameters for no isolation benefit, since they're only ever called from within this one service.

**Cross-domain call is rewired to the concrete sub-service, not left pointed at the deployments facade.** `ToolsetsService`'s `invalidateCaches` only ever calls one deployments method (`invalidateDetailsCache`). Routing that through the full `DeploymentsService` facade would work, but injecting `DeploymentsDetailsService` directly into whichever toolsets sub-service needs it (`ToolsetsMutationService`/`ToolsetsAuthService`, wherever `invalidateCaches` ends up) is one hop shorter and makes the actual dependency (details-cache invalidation, not the whole deployments surface) explicit at the injection site.

**Migrate helpers-first, then service-by-service, monolith intact until the last step.** Order: extract pure helpers to `utils/` (zero behavior risk, pure move) → split `ToolsetsService` → split `DeploymentsService` → rewire the cross-domain call → facade cleanup. Toolsets before deployments because deployments has no inbound dependency from toolsets' *class* logic (only the one cross-domain call, which is rewired last, after both facades exist), so splitting it first doesn't unblock anything; starting with toolsets means the rewire step at the end touches already-stable code on both sides. Each step is verified with `npm exec nx test chat-api` before the next, matching the incremental-slice policy in `AGENTS.md`.

## Risks / Trade-offs

- [Spec relocation drops or duplicates assertions] Moving `describe` blocks from two large spec files into per-sub-service files risks silently losing setup/mocks. → Mitigate by relocating blocks verbatim first (no test-logic changes in the same step as the move), running the full suite immediately after each relocation, and only refactoring test structure in a later, separate pass.
- [Hidden coupling between "sections" inside each monolith] Some private helpers may be used across the proposed boundaries in ways not obvious from a single read-through (e.g. a cache-key format string reused by both listing and details). → Mitigate by grepping every private method/field name across the whole file before assigning it to a sub-service, and promoting any genuinely cross-boundary helper to the shared `utils/*.util.ts` file rather than duplicating it.
- [DI wiring gaps at module registration] Missing a provider registration for a new sub-service, or forgetting to update the cross-domain injection, throws at Nest bootstrap rather than at a call site. → Mitigate by running `npm exec nx build chat-api` (fails fast on DI resolution errors) after each provider-registration change.
- [Sequencing risk with the still-open PR #8226] If #8226 merges mid-implementation, the ownership-check duplication this design deliberately left untouched could conflict with this change's file moves. → Mitigate by checking PR #8226's merge status before starting the `ToolsetsListingService`/`DeploymentsListingService` extraction steps specifically (the only ones touching ownership-flag code), and rebasing onto its shared utility if it has landed, per the Constraints in proposal.md.

## Migration Plan

Same order as `proposal.md`'s "What Changes"/this design's Decisions: extract pure mapping helpers to `utils/` for both domains → split `ToolsetsService` → split `DeploymentsService` → rewire the `ToolsetsService`→`DeploymentsService` cross-dependency to `DeploymentsDetailsService` → facade cleanup/dead-code removal → verification. Each step is a separate commit/slice gated on `npm exec nx test chat-api`, `npm exec nx lint chat-api`, and (for DI/module changes) `npm exec nx build chat-api`. No feature flag or staged rollout is needed since there is no external behavior change — rollback is a straight revert of the offending slice's commit.

## Open Questions

- Should `DeploymentsDetailsService`'s cache (`pendingDetailsRequests` in-flight-request map) stay a private instance field on that one service, or would a shared small "in-flight request dedup" utility be worth extracting given `ConversationGenerationService` has a similar (though not identical) in-memory registry pattern? Default to keeping it local to `DeploymentsDetailsService` unless implementation reveals a second concrete consumer — a one-off shared abstraction for a single caller would be premature.
