## Context

The `publish-share` branch ships a working UI prototype of the catalog publish flow entirely inside `libs/catalog` and `apps/chat/src/components/CatalogView`:

- `PublishPanel` / `PublishFooter` / `PublishHistoryList` render the publish UI and are driven by `usePublishFlow` + `derivePublishState` (pure state machine in `libs/catalog/src/utils/publish-state.ts`).
- `PublishFolderPicker` (`libs/catalog/src/components/PublishFolderPicker/PublishFolderPicker.tsx`) is a **bespoke** folder tree — not built on ui-kit — with its own search filtering (`publish-folder-tree.ts`), expand/collapse, and inline create-folder row.
- `CatalogView.tsx` wires everything to static mocks: `MOCK_PUBLISH_FOLDERS`, `MOCK_PUBLISH_HISTORY`, and a fake `handlePublish` (`setTimeout` no-op), clearly marked `/* TODO: temporary mock wiring for the Publish flow */`.

Investigation for this design confirmed two load-bearing facts:

1. `@epam/ai-dial-ui-kit` is already pinned to `0.12.0-dev.25` in `package.json`, and `DialFoldersTree` **already exists** in the installed package (`node_modules/@epam/ai-dial-ui-kit/dist/src/components/FileManager/components/FoldersTree/FoldersTree.d.ts`). No version bump is required to start Slice 1 — only re-verify pinned-vs-latest at implementation time in case a newer dev build changes the props surface.
2. `useDialFileManager` (`apps/chat/src/hooks/files/useDialFileManager.ts`) already implements the exact lazy-load pattern this change needs: a per-folder `cache` keyed by API path, host-owned `expandedPaths`, a derived `loadedPaths`, and `onExpandedPathsChange` to trigger fetches on demand. It calls `listPublicFiles` / `createFolder` from `apps/chat/src/server-api/files.api.ts` against `GET /api/v1/files/public` (the Organization/public bucket) and merges newly created folders into the cache optimistically.

This change closes the gap between the prototype and a shippable feature without redesigning the already-validated UX.

## Goals / Non-Goals

**Goals:**
- Replace the bespoke `PublishFolderPicker` with a thin `libs/catalog` wrapper around ui-kit's `DialFoldersTree`, preserving current visual/interaction parity (single-folder select, inline create, search-above-tree, RTL).
- Feed the wrapper with real Organization/public-bucket folder data via a new app-level hook, reusing the `useDialFileManager` lazy-load pattern rather than inventing a new one.
- Define and implement the minimum backend surface needed to publish an entity and read its publish history, following `apps/chat-api/AGENTS.md` conventions (thin controller, versioned route, DTOs, Swagger, typed exceptions).
- Wire `CatalogView` to the real hook/API and delete all publish-related mock data and handlers.

**Non-Goals:**
- No `FolderAccess` audience picker, no Shared-vs-Organization scope tabs, no `PublishCalloutKind.Info` — all explicitly deferred by the prototype and not reopened here.
- No redesign of `PublishPanel`/`PublishFooter`/`PublishHistoryList` visuals or `derivePublishState` state machine — only their data sources change.
- No multi-folder or multi-select publish target — the picker remains single-selection.
- Not designing a general-purpose "publish any entity type" abstraction beyond what Model/Toolset/Application already need; extending to further entity types is a follow-up.

## Decisions

### D1: Wrap `DialFoldersTree` instead of extending the bespoke tree
`libs/catalog` gets a new `PublishFoldersTree` component (replacing `PublishFolderPicker`) that renders `<DialFoldersTree items={...} showFiles={false} selectedPath={...} onItemClick={...} onCreateFolderSave={...} onCreateFolderCancel={...} createdFolderPath={...} />`. No `getContextMenuItems` is passed (defaults to no context menu), matching the "folder-only, no row menu" pattern already established for `DialDestinationFolderPopup` in `openspec/specs/file-manager-folder-picker/spec.md`.
- **Alternative considered**: keep the bespoke tree and only swap its internals for ui-kit primitives incrementally. Rejected — it duplicates behavior (expand/collapse, selection, inline-create) that `DialFoldersTree` already implements and tests, doubling maintenance for no UX gain.
- **Mapping**: the lib's existing `PublishFolderNode` (`{ path: string[]; name: string; children?: PublishFolderNode[] }`) is converted to ui-kit `DialFile[]` (string `path`, `nodeType: FOLDER`) at the wrapper boundary inside `libs/catalog`, so `usePublishFlow` and `derivePublishState` keep working against the lib's own model and only the picker/tree layer talks `DialFile`.
- Search stays host-owned: the existing `SearchInput` above the tree filters the `PublishFolderNode[]` tree client-side (reusing `filterFolderTree` from `publish-folder-tree.ts`, kept and adapted) before it is converted to `DialFile[]` and handed to `DialFoldersTree`. `DialFoldersTree` has no built-in search prop today; if a future ui-kit release adds one, this filtering step is removed and delegated.
- **Bug fixed post-implementation**: `PublishFoldersTree` originally managed `expandedPaths` entirely as internal state, with no way for a host to observe expand events and lazily fetch a folder's children — clicking a folder never fetched its subfolders. Fixed by making `expandedPaths`/`onExpandedPathsChange`/`loadingPaths` optional **controlled** props (falls back to internal state when omitted), threaded all the way through `PublishPanelProps` → `DetailsPanelProps` (as `publishExpandedPaths`/`onPublishExpandedPathsChange`/`publishLoadingPaths`) → `CatalogProps` → `CatalogView`, which now forwards `useCatalogPublishFolders`'s own `expandedPaths`/`onExpandedPathsChange`/`loadingPaths`. A second, related bug was fixed alongside it: `usePublishFlow` snapshotted the `folderItems` prop into local state only once on mount (`useState(initialFolderItems)`), so even after wiring the expand callback, newly-fetched children would never reach the tree — fixed by adding a `useEffect` that re-syncs local `folderItems` whenever the `folderItems` prop changes.
- **Bug fixed post-implementation (root selection)**: `selectedFolderPath: []` was originally overloaded to mean "nothing selected" (every consumer used `Boolean(selectedFolderPath?.length)`), so the bucket root itself — a valid publish destination per D3's bare `public/` case — had no way to be chosen. Redesigned the sentinel so `undefined` means nothing selected and `[]` means the root is explicitly selected, and replaced every length-based truthiness check with `selectedFolderPath != null` in `PublishPanel`/`DetailsPanel`. `usePublishFlow`'s existing `hasExistingVersionInFolder`/`hasWriteAccess`/`handleSubmit` logic needed no changes since JS already treats `[]` as truthy — only `undefined` short-circuited them. First attempt rendered the root as a separate `<button>` above `DialFoldersTree`; per user feedback this was corrected to match the file manager's own pattern (`useDialFileManager.ts`'s root `DialFile` node) — the root is now a real top-level node *inside* the tree (`path: ''`, wrapping the actual folders as its children), always rendered expanded, with its path key stripped before reaching the host's `onExpandedPathsChange` (the host has no `''` folder to fetch). Default label renamed `'Organization root'` → `'Organization'` to match the file manager's tab label exactly. `PublishFooter`'s submit label was also simplified in the same pass: it previously interpolated the destination name (`'Publish to {folder}'`), which overflowed the button for long names — it now always reads plain `'Publish'` (or `'Update version {version}'`), and the `folderName`/`publishLabel` prop was removed from `PublishFooter` entirely.

### D2: New app-level hook, not an extension of `useDialFileManager`
`apps/chat/src/hooks/catalog/useCatalogPublishFolders.ts` is a **new, catalog-scoped** hook rather than a generalization of `useDialFileManager`.
- **Alternative considered**: generalize `useDialFileManager` to serve both the file manager and the publish picker. Rejected for this change — `useDialFileManager` also owns file listing, rename, copy/move, and upload concerns that the publish picker does not need (`showFiles={false}`), and coupling the two would risk regressions in the file manager for an unrelated feature. The new hook copies the proven caching/lazy-expand shape (`cache`, `expandedPaths`, derived `loadedPaths`, `onExpandedPathsChange`) but is scoped to folders-only, Organization/public bucket, read + create.
- The hook calls `listPublicFiles` (already used by `useDialFileManager`) for folder listing and a create-folder call for `onCreatePublishFolder`, both through `apps/chat/src/server-api/files.api.ts` — no new server-api surface needed for folder data itself.
- `hasPublishWriteAccess(folderPath)` is defined as a callback contract in this hook; initial implementation is heuristic (mirrors today's mock: deny under specific restricted subtrees) with a documented seam to swap in a real DIAL Core bucket-permission check once that endpoint/contract is confirmed (see Open Questions).

### D3: New `apps/chat-api` domain module — proxies DIAL Core's Publication API, no chat-api persistence
A new domain `apps/chat-api/src/publish/` (controller + service + DTOs + module, no `modules/` wrapper, per `AGENTS.md`) exposes:
- `POST /api/v1/catalog/{entityType}/{entityId}/publish` — body `{ folderPath: string, version: string }` (`version` is required — Core has no way to derive it) → `PublishResultDto`.
- `GET /api/v1/catalog/{entityType}/{entityId}/publish-history` → `PublishHistoryEntryDto[]`.

**Revised after investigation (superseding the original draft of this decision):** `apps/chat-api` has no database/ORM anywhere in the stack (confirmed: no Prisma/TypeORM/Mongoose/pg/mysql/sqlite in `package.json`), and the only "storage" primitives are `@nestjs/cache-manager` (in-memory, lost on restart) and DIAL Core itself. Publish history must survive restarts (it drives the replace-warning UX), so `apps/chat-api` **must not** own `PublishHistoryEntry` persistence itself. Instead, `publish.service.ts` proxies **DIAL Core's Publication API**, already fully typed in `@epam/ai-dial-typescript-sdk` (`createPublication`, `getPublications`, `getPublication`, `approvePublication`, `rejectPublication`, `deletePublication`, `getPublicationRules`, with `Publication`/`PublicationResource`/`PublicationStatus` DTOs) — the same Core capability the legacy (pre-BFF) frontend publication feature used directly, now proxied through the BFF the way `ShareService` (`apps/chat-api/src/share/share.service.ts`) already proxies DIAL Core's resource-sharing API. This mirrors the established `DialClientService` pattern: inject `DialClientService`, call `this.dialClient.client.createPublication({...})`, map SDK errors with `mapDialHttpStatus` from `common/dial/dial-error.mapper.ts` (this service does not use `handleDialSdkError`, unlike some other domains — it only ever hits the fetch-shaped `result.error` case, mapped via `mapDialHttpStatus`, plus a hardcoded `BadGatewayException` for unexpected thrown errors).

Concrete mapping — **confirmed against DIAL Core's own published OpenAPI spec** (https://dialx.ai/dial_api#tag/Publications/operation/createPublication, `/v1/ops/publication/create`'s documented example) after three rounds of trial-and-error (see the bug notes below):
```yaml
targetFolder: public/folder/                              # trailing slash required
resources:
  - action: ADD
    sourceUrl: conversations/{bucket}/my/folder/conversation
    targetUrl: conversations/public/folder/conversation    # resourceTypePrefix + targetFolder + resourceName, no trailing slash
```
- **Publish** → `createPublication` with `targetFolder: 'public/{folderPath}/'` (always trailing-slashed; bare `'public/'` when `folderPath` is empty) and `resources: [{ action: 'ADD', sourceUrl: entityId, targetUrl: '{resourceTypePrefix}/public/{folderPath}/{resourceName}' }]`, where `resourceTypePrefix` is `entityId`'s first path segment (e.g. `applications`) and `resourceName` is its last segment. `entityId` is treated as already being the entity's DIAL Core resource path, the same assumption `ShareService.createShareLink` already makes for its `itemId` — only user-owned/editable entities (Toolset, Application; see D4) are resource-backed in Core and therefore publishable, which is consistent with `isPublishVisible` already being scoped to editable entities.
- **Publish history** → `getPublications` with a `ResourceLink` body scoped to `entityId` itself (the entity's own resource url — history spans every folder the entity was ever published to; folder-scoping happens client-side in `PublishPanel`), filtered to publications whose `resources[].sourceUrl` reference this `entityId`, mapped to `PublishHistoryEntryDto[]`. `Publication.targetFolder` comes back `public/{folderPath}/`-qualified (trailing slash) and has both the `public/` prefix and the trailing slash stripped back off before being returned to the frontend, so `selectedFolderPath` comparisons in `PublishPanel` keep working against plain names. Since Core's schema has no version field, `version` is recovered from `entityId`'s own `{name}__{version}` suffix (catalog entity IDs are always shaped this way — see `applications.service.ts`/`toolsets.service.ts`), not from `Publication.name` (see Bug #4 below for why the latter was tried first and rejected). The SDK has no "history for one entity" endpoint directly — this list-and-filter approach is the closest fit and should be revisited if Core exposes a narrower query later.
- **Folder tree** stays on `GET /api/v1/files/public` (unchanged from the original D2 plan) unless Core's permission semantics for `/v1/metadata/{entityType}/{path}?permissions=true` (the legacy metadata-proxy path) turn out to differ meaningfully from the files listing already in use.
- **Bug #1 fixed post-implementation**: the first implementation built `targetUrl` as `` `${folderPath}/${entityId}` `` — but `entityId` is the entity's *full* DIAL Core resource path (e.g. `applications/{bucket}/{name}`), not a bare name, so this nested the entire source path inside the destination folder (e.g. `DK Test with nested/Level 1/applications/{bucket}/{name}`) and Core rejected it with 400.
- **Bug #2 fixed post-implementation**: even after fixing #1, publishing still failed — `targetFolder`/`targetUrl` were built from the plain `folderPath` with no bucket identity at all, so Core had no way to resolve which bucket the destination lived in ("we lost the public bucket id"). Confirmed via the legacy pre-BFF frontend's publication feature on `origin/development` (`PUBLIC_URL_PREFIX = 'public'` in `apps/chat/src/constants/publication.ts`) that the shared area is addressed by the literal segment `public`, not an opaque bucket-id hash. The `targetFolder` value added at this point (`public/{folderPath}`, **no trailing slash**) was the actual cause of the next 400.
- **Bug #3 fixed post-implementation, confirmed against a live DIAL Core instance then against Core's own OpenAPI spec**: Core's exact 400 message was `` Publication "targetUrl" must start with: public and ends with: / ``. This was initially (incorrectly) read as "`targetUrl` must be folder-shaped with no resource-type prefix or name" — that fix produced a *different* 400 (`Bad resource url: public/{folderPath}`), which prompted checking DIAL Core's published OpenAPI spec directly. The spec's own documented example shows `targetFolder` **requires a trailing slash** and `targetUrl` **is** a full file path (`resourceTypePrefix/targetFolder/resourceName`, no trailing slash) — the original "must start with public and ends with /" error was actually about the missing trailing slash on `targetFolder`, not a folder-shaped `targetUrl`. Final fix: `targetFolder` always trailing-slashed; `targetUrl` restored to `{resourceTypePrefix}/{targetFolder}{resourceName}`, matching the spec example exactly. Temporary debug logging (request body + Core's actual error body) is left in place, marked for removal once verified end-to-end.

- **Bug #4 fixed post-implementation, found via a live debug log comparing our request against the legacy frontend's publication form**: publish requests were succeeding (`201`), but `createPublication`'s `name` field was set to the bare version string (e.g. `"0.0.1"`) — this service had misread D3's "Core has no version field" note as license to stash the version *anywhere*, including `name`, which is actually the free-text **request title** shown in DIAL Core's admin UI (comparable to the legacy pre-BFF frontend's `CreatePublicationHandler.tsx`/`translatePublicationName.ts` on `origin/development`, which default it to `"New request by {author}"` and send `displayAuthor`/`rules` as separate fields this service's request body was missing entirely). A first fix matched that legacy convention literally; per follow-up feedback the title should instead read `"{entity name} {version}"` (e.g. `"My App Name 0.0.1"`) with **no author** in the title — `displayAuthor` already carries that separately. Both the entity name and version are now recovered from `entityId`'s own `{name}__{version}` suffix (`splitEntityNameAndVersion`, URL-decoding the name) rather than being passed through `Publication.name`, which also fixed the publish-history `version` field (previously read from `publication.name`, now from the same `entityId`-derived value). `author` (a human display name) is sourced from the session's allowlisted OIDC claims via a new `getUserDisplayName` util (`name` → `preferred_username` → email local-part → `'Unknown Author'` fallback), passed from `PublishController` down to the service.
- **Bug #5 fixed post-implementation, found via a live debug log**: publishing to a folder name containing a space (`"test 14.04"`) 400'd with Core's `` Bad resource url: public/test 14.04/ ``. `folderPath` arrives as plain, unencoded text from the request body, but `getPublicTargetFolder` interpolated it straight into `targetFolder`/`targetUrl` with no percent-encoding — unlike `entityId`, which the generated client always already URL-encodes. Fixed by running `folderPath` through the existing `encodeDialResourcePath` helper (decode-then-encode per segment, idempotent regardless of input encoding), the same one `toolsets.service.ts`/`conversation.service.ts` already use for user-supplied path text. `stripPublicTargetFolder` now decodes symmetrically when reading `Publication.targetFolder` back for history, so it round-trips to the exact plain folder path the frontend sent.
- **Alternatives considered and rejected**: (1) `apps/chat-api` owning `PublishHistoryEntry` persistence via a new sidecar file in the target bucket, or (2) via a new datastore dependency — both rejected as not matching how publishing already works on this platform (Core-side Publication API), and (2) is also a standalone infra decision out of scope for this feature. (An in-memory-stub interim fallback was considered in case Core wiring proved blocked mid-implementation, but Core integration succeeded directly — no such stub was ever built.)
- Folder-tree data is **not** re-exposed under `/api/v1/catalog/publish-folders` unless `GET /api/v1/files/public` proves insufficient for Organization-bucket scoping (see Open Questions) — reusing the existing files endpoint avoids a duplicate contract.
- `entityType`/`entityId`/`folderPath` are validated with `class-validator`, reusing the existing `IsValidFilePath` decorator (`apps/chat-api/src/files/dto/file-path.validator.ts`) already used by `ShareService`'s `itemId`, to prevent path traversal into arbitrary buckets.
- Errors map to typed exceptions via `handleDialSdkError`/`mapDialHttpStatus`: `NotFoundException` (unknown entity/publication), `ForbiddenException` (no write access to target folder), `BadGatewayException` (upstream DIAL Core failure) — never a bare `null`/200-with-error-body.

### D4: `isPublishVisible` rule
Publish is shown only when the catalog item is user-owned/editable (reusing the entity's existing `isEditable`-equivalent flag from the catalog item model) — this is a UI-only gating rule in `CatalogView`, not a new backend authorization concern (the backend still independently enforces write access via `hasPublishWriteAccess`/403 on submit, since a client-side flag is not a security boundary).

## Risks / Trade-offs

- **[Risk]** `DialFoldersTree` is on a `-dev` prerelease (`0.12.0-dev.25`); its props surface could change before a stable release. → **Mitigation**: pin the wrapper's usage to the documented stable subset of props (`items`, `showFiles`, `selectedPath`, `onItemClick`, `onCreateFolderSave/Cancel`, `createdFolderPath`, `expandedPaths`/`loadingPaths`/`loadedPaths`/`onExpandedPathsChange`); re-check `CHANGELOG.md`/migration guides per `AGENTS.md` before bumping past the currently pinned dev version.
- **[Risk]** `hasPublishWriteAccess` has no confirmed real backend contract yet (Open Question below); shipping a heuristic could diverge from actual DIAL Core bucket permissions. → **Mitigation**: isolate the heuristic behind the hook's single function boundary so swapping in a real permission check later is a one-file change; the backend still independently 403s on submit regardless of what the client heuristic predicted, so the UI heuristic is UX-only, never a security control.
- **[Risk]** Deleting `PublishFolderPicker`/`publish-folder-tree.ts` before the ui-kit wrapper reaches full parity could regress an already-reviewed prototype UX. → **Mitigation**: land the `DialFoldersTree` wrapper alongside the old picker behind the same `PublishPanel` slot first, verify parity manually against the prototype, then delete the old files in the same slice once confirmed (per tasks.md ordering) rather than deleting up front.
- **[Risk]** Reusing `GET /api/v1/files/public` for the publish-folder tree conflates file-manager and publish-flow read paths; a future change to file-manager pagination/filtering could silently affect publish. → **Mitigation**: the new hook calls the endpoint directly rather than through `useDialFileManager`, so it is not coupled to file-manager-specific state, but the risk is documented as an Open Question in case a dedicated endpoint is warranted later.
- **[Trade-off]** No new `/api/v1/catalog/publish-folders` endpoint means the publish flow's folder scope is implicitly whatever `/api/v1/files/public` returns — simpler now, but any future need to scope publish folders differently from the file manager's public view (e.g. a curated subset) requires a new endpoint at that time.

## Migration Plan

Implemented as independently verifiable slices (see `tasks.md`):
1. Ship the `DialFoldersTree`-based wrapper in `libs/catalog` next to the existing picker (no deletion yet) — verified via updated lib unit tests + manual visual parity check against the prototype.
2. Add the app-level folder-loading hook and swap `CatalogView`'s folder data source from mock to hook, still using the mock `handlePublish`/history — verified via `CatalogView` tests + manual QA in Organization tab context.
3. Add the backend module, regenerate `@epam/chat-api-client`, and swap `handlePublish`/`getPublishHistory` to real API calls — verified via backend unit tests + `npm run openapi:check` + manual end-to-end QA.
4. Delete `PublishFolderPicker`/`publish-folder-tree.ts` and all `MOCK_PUBLISH_*` data once the above are confirmed stable.

Rollback: each slice is behind normal PR review; if a later slice regresses, the prior slice's mock/interim wiring can be restored from git history since mocks are not deleted until slice 4.

## Open Questions

- Is there an existing DIAL Core endpoint/contract for bucket-level write-permission checks that `hasPublishWriteAccess` should call, or does this change need to define a new one? Until confirmed, the hook ships a documented heuristic.
- ~~Does Core have (or plan) a native "publish"/versioning concept for catalog entities...~~ **RESOLVED**: yes — DIAL Core's Publication API (`createPublication`/`getPublications`/`getPublication`, already in `@epam/ai-dial-typescript-sdk`), the same capability the legacy pre-BFF frontend publication feature called directly. `apps/chat-api` has no database of its own (confirmed: no ORM/datastore dependency anywhere in the repo) and must not invent chat-api-side persistence for `PublishHistoryEntry` — see the revised D3. An in-memory stub is acceptable only as a clearly-labeled, temporary interim if Core wiring is blocked mid-implementation, never as the target architecture.
- Should `GET /api/v1/files/public` remain the sole folder-tree data source for publish, or does product want the publish picker scoped to a curated subset of the Organization bucket (motivating a dedicated `/api/v1/catalog/publish-folders` endpoint, or reuse of the legacy `/v1/metadata/{entityType}/{path}?permissions=true` metadata-proxy path instead)?
- `getPublications` has no narrower "history for one entity" query — the current plan lists publications for `folderPath` and filters by `entityId` client-side (service-side). If DIAL Core later exposes a more targeted query, `publish.service.ts`'s history mapping should switch to it. **Known open issue (task 6.8, unresolved)**: `getPublications`'s `url` field is documented by Core as the list *scope* (`publications/{bucket}/` or `publications/public/`), not a resource filter — the current `{ url: entityId }` call likely does not match Core's contract and may return no results in practice, even though publish itself works. This has not been fixed or confirmed against a live Core instance; treat the "Publish history endpoint" requirement in `specs/catalog-publish-api/spec.md` as unverified until it is.
