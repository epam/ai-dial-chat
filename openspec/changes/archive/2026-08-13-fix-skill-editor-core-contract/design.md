## Context

This design was revised after reading DIAL Core's actual shipped implementation (not just the pinned `@epam/ai-dial-typescript-sdk`'s generated `.d.ts`, which is verified here to have a real, specific documentation gap). Sources, all fetched directly from `epam/ai-dial-core` via `gh api repos/epam/ai-dial-core/contents/...`:

- **`storage/src/main/java/.../util/EtagHeader.java`** — the real conditional-request engine. `validateIfMatch(etag)`: if the resource doesn't exist (`etag == null`) and a concrete `If-Match` was sent, throws `412` ("Resource must exist"); if it exists and the sent `If-Match` tag doesn't match, throws `412`. `validateIfNoneMatch(etag)`: if the resource doesn't exist, always passes (create proceeds); if it exists and `If-None-Match` was `*` (parsed to `ifNoneMatchTags == null`) or the sent tag matches, throws `412` ("Resource already exists" / "if-none-match condition failed"). **Critically: if neither header is sent at all, both validations pass unconditionally regardless of whether the resource exists** — parsing absent headers yields `ifMatchTags = null` (no constraint) and `ifNoneMatchTags = Set.of()` (empty set, never `.contains(etag)`, no constraint). This directly contradicts the earlier design's D3, which read the SDK's doc-comment ("omit If-Match to create only if not exists") as authoritative. That comment is **wrong** — verified against the real validation code, omitting both headers is a fully unconditional upsert, identical to the v1 `files`/`prompts` APIs' default behavior. Real create-only requires **sending `If-None-Match: '*'` explicitly**, exactly as the original proposal instructions said before the D3 "correction" in the first draft of this design — that correction is itself retracted here, with the authoritative evidence now in hand.
- **`server/src/main/java/.../controller/ComplexResourceController.java`** — the actual v2 Skills HTTP controller (named `ComplexResourceController`/`ComplexResourceService` in the shipped code, not `FolderResourceController` as the originating epic issue's design sketch called it). Confirms: **one `PUT /v2/skills/{bucket}/{path}` for both create and update** — Core itself has no separate create/update route; create-vs-update is entirely a matter of which conditional headers the caller sends. `EtagHeader etag = ProxyUtil.etag(request)` reads **both** `If-Match` and `If-None-Match` from the real request — the SDK's OpenAPI schema simply never declared the second header, a schema/doc gap on the SDK's side, not a Core capability gap. The whole-resource PUT handler collects multipart uploads into `Map<String, Buffer> uploads` keyed by **`upload.filename()`** — Core does not look at the multipart field name at all, only each part's `filename` attribute, confirming "one part per file, filename = relative path" (matching the epic issue's acceptance criteria) and that the field name every part is sent under is irrelevant to Core.
- **`server/src/main/java/.../service/resource/SkillHandler.java`** — the exact source of the reproduced `400 "Skill must contain a SKILL.md at its root"` error (`parseFrontmatter`: `files.get(MANIFEST) == null` → that literal message). Frontmatter is parsed with a regex delimiting `---`-fenced YAML and Jackson's `YAMLMapper`; only `name`/`description` are required (both blank-checked, both `400` on failure); `version` is read into marker metadata if present but nothing else about extra fields is special-cased — arbitrary other frontmatter keys are simply never touched by Core's own validation, consistent with "preserve unknown fields" being purely a client-side concern.
- **`server/src/main/java/.../service/resource/ComplexResourceService.java`** — `Settings`: `maxFiles = 100`, `maxTotalBytes = 16 MiB`, `maxFileSizeBytes = 1 MiB` (exact defaults, confirmed in code, not just the epic issue's "~" prose). `validateLimits`: file-count-exceeded → **`400 Bad Request`** (not `422` — corrects the earlier draft's assumption); any single file or the aggregate exceeding its byte limit → **`413`** (`REQUEST_ENTITY_TOO_LARGE`). Limits are enforced server-side against the actual received byte arrays, before any write. `409 Conflict` exists in this file **only** for "grouping folder is not empty" on delete — never for a whole-skill create collision. A create collision is signaled the same way any `If-None-Match` failure is: `412`.
- **Conclusion this design commits to**: DIAL Core's real wire contract for whole-skill write is **one endpoint** (`PUT /v2/skills/{bucket}/{path}`, `multipart/form-data`, one part per file, filename = relative path), whose *effective* create-vs-update semantics are chosen entirely by which conditional header the caller sends: `If-None-Match: '*'` for atomic create (rejecting with `412` if it already exists), a concrete `If-Match: "<etag>"` for optimistic update (rejecting with `412` if stale). This design's BFF still exposes **two separate browser-facing routes** (`POST /api/v1/skills` for create, `PUT /api/v1/skills` for update) as a deliberate BFF-level API-shape decision — cleaner for the frontend and OpenAPI consumers than one endpoint whose meaning depends on a header — translating each to the same underlying Core `PUT` with the appropriate conditional header.
- **No ZIP on any write path.** The whole-resource PUT's request body was verified above to be `multipart/form-data` with one part per file; Core never expects or accepts a ZIP for writes. The only place a ZIP legitimately appears in this contract is `GET /v2/skills/{bucket}/{path}` (`downloadArchive`, confirmed in `ComplexResourceController.get`/`downloadArchive`, still streams `application/zip`). This corrects the first draft of this change, which (following `add-skill-authoring-ui`'s original design) kept the frontend building a ZIP and had the BFF explode it into per-file multipart parts server-side. That indirection is unnecessary complexity with no upstream requirement behind it: the frontend already holds `SKILL.md` text and every supporting file's bytes in memory (it built the ZIP from exactly that state) — it can send those directly as multipart parts to the BFF, and the BFF forwards them as multipart parts to Core, with no ZIP construction or extraction anywhere on the write path. `SkillsArchiveService` (introduced in the first draft) and its ZIP-extraction/zip-bomb/encrypted-entry/symlink checks are **removed from the upload path** entirely — those checks matter for arbitrary-ZIP-content safety, which no longer exists once the browser sends discrete files instead of an opaque archive. ZIP handling survives only on the **edit-load** path, where Core's `GET` response is unavoidably a ZIP that the frontend must unpack with `fflate` to populate the editor — that specific, narrower ZIP-safety surface (a small, self-produced-by-Core archive, not arbitrary user upload content) is unaffected by this correction.
- **`libs/openapi-fetch`'s `defaultBodySerializer`** (`node_modules/openapi-fetch/src/index.js`: `if (body instanceof FormData) return body;`) — unaffected by this revision, still the mechanism that lets the BFF's SDK-adapter cast (`buildUploadFormData(...) as unknown as {...}`) send an arbitrarily-shaped multipart `FormData` through the pinned SDK client despite its narrower declared type. Still preferred over raw `fetch` — no evidence found that the SDK client cannot transmit the required request.
- `CatalogEntityType.Skill` still has no producer wired into `CatalogView` — unchanged from the first draft; the Catalog "Edit" entry point remains out of scope, filed as a follow-up, edit mode reachable only via `/skill-editor?id=...`.

## Goals / Non-Goals

**Goals:**
- Ship a whole-skill create/update contract that matches Core's real, verified behavior: no ZIP anywhere on the write path; discrete multipart parts (manifest text + supporting files) sent directly from the browser to the BFF and forwarded to Core unchanged in shape.
- Split the browser-facing contract into `POST /api/v1/skills` (create, atomic via `If-None-Match: '*'`) and `PUT /api/v1/skills` (update, requiring a concrete `If-Match`), translating both to Core's single conditional `PUT`.
- Correct BFF limits/status codes to match Core's verified real defaults and real status choices (`400` for file-count, `413` for byte limits, `412` for any conditional-header failure, translated to `409` only for the create-collision case at the BFF's own translation layer).
- Ship the edit flow: load via the existing ZIP-returning `GET`/`downloadSkill`, unpack with `fflate` (this is the one place ZIP handling remains, and only for reading a Core-produced archive), edit, save via `PUT` with the loaded `If-Match`.
- Keep `libs/skill-editor` host-agnostic.

**Non-Goals:**
- Skill catalog listing/details/edit-entry-point wiring (still blocked on a not-yet-built feature; unchanged from the first draft).
- Any Core-side change.
- A general binary-content editor for supporting files.
- Grouping-folder CRUD changes.

## Decisions

### D1 — Two browser-facing routes, one Core operation

**Decision:** `apps/chat-api/src/skills/skills.controller.ts` gets a new `POST /api/v1/skills` (`operationId: createSkill`) alongside the existing `PUT /api/v1/skills` (`operationId` renamed `updateSkill`). Both consume `multipart/form-data` with the same field shape (task-defined: `bucket`, `path`, `skillManifest`, `filePaths` (JSON array), repeated `files` parts). `createSkill`'s service method calls DIAL Core's `uploadSkillFolder` with `If-None-Match: '*'` and no `If-Match`; `updateSkill`'s service method requires a concrete `If-Match` from the request and rejects with a BFF-only `428 Precondition Required` **before calling Core at all** if it's absent (Core itself has no such requirement — sending neither header to Core would just be an unconditional overwrite, per D-Context; `428` is a deliberate BFF safety rail preventing an accidental unconditional overwrite through *this* API, not a translation of any Core response).
**Rationale:** Core's real contract is header-driven, not route-driven — but a single ambiguous `PUT` whose meaning flips on a header is a worse browser-facing API than two named intents, especially once the create path's `409`-on-collision and the update path's mandatory-`If-Match` become genuinely different validation rules the BFF enforces before ever calling Core.
**Alternatives considered:** Keep one `PUT` for both, as the first draft did — rejected on reflection: the two flows now have materially different pre-Core validation (`428` if `If-Match` missing on update; no such check on create) that reads far more clearly as two operations than as branches inside one.

### D2 — Create-only via `If-None-Match: '*'`; `412`-on-create maps to BFF `409`

**Decision:** `createSkill`'s service method sends `headers: { 'If-None-Match': '*' }` (a narrow, documented type cast at this one call site — the SDK's declared header parameters for `uploadSkillFolder` list only `If-Match`, so this follows the same isolated-cast pattern already used for the `FormData` body itself) and no `If-Match`. A `412` response (Core's real signal per `EtagHeader.validateIfNoneMatch`, verified in D-Context) is caught and re-thrown as `ConflictException` (`409`). `updateSkill` always sends the caller's concrete `If-Match` and never `If-None-Match`; a `412` there is surfaced unchanged (a genuine stale-edit conflict).
**Rationale:** This is now the *verified*, not assumed, mechanism — read directly from `EtagHeader.java`. The first draft's D3 ("omitting `If-Match` is itself the create-only mechanism") is retracted; it was based solely on an SDK doc-comment that this investigation found to be incorrect.
**Alternatives considered:** None remain — the ambiguity that motivated alternatives in the first draft is resolved by direct evidence.

### D3 — No ZIP on the write path: direct multipart from browser to BFF to Core

**Decision:** The frontend keeps `SKILL.md`'s manifest text and every supporting file's bytes in memory (exactly the state it already builds today to construct a ZIP) and sends them as a `multipart/form-data` request directly: `bucket`, `path`, `skillManifest` (the full manifest text, one field), `filePaths` (a JSON-encoded array of the supporting files' relative paths, authoritative — never inferred from a part's filename, since multipart parsers/browsers can lose path separators in a bare `filename`), and `files` (the supporting files' raw bytes, one repeated part per entry, positionally paired with `filePaths` by index). The BFF's new focused component (replacing `SkillsArchiveService`, see D4) parses `filePaths`, validates it 1:1 against the received `files` parts, validates every path (reserved markers, traversal, not equal to `SKILL.md`, duplicates), enforces size/count limits against the actual received byte lengths (matching Core's own enforcement point), and builds the outbound Core `FormData`: one `file` part for `skillManifest` (filename `SKILL.md`) plus one `file` part per supporting file (filename = its `filePaths` entry).
**Rationale:** Removes an entire unnecessary layer (browser ZIPs → BFF unzips → BFF re-multiparts) that existed only because the first draft assumed Core wanted a ZIP. The browser already has every byte it needs in memory; sending them directly is strictly simpler and removes the ZIP-specific attack surface (zip-bomb ratios, encrypted entries, symlinks) from the *upload* path entirely, since there is no longer an archive to decompress there.
**Alternatives considered:** Keep ZIP-to-BFF-then-explode (the first draft) — rejected, solves a problem (Core wants a ZIP) that investigation shows doesn't exist. A JSON-body-with-base64-content alternative — not seriously considered; multipart with real binary parts is the native, size-efficient shape for file bytes and every other file-upload endpoint in this codebase already uses it.

### D4 — Replace `SkillsArchiveService` with a multipart/package validation component; no ZIP concerns on the upload path

**Decision:** Remove `SkillsArchiveService` (and its ZIP-extraction, encrypted-entry, symlink, compression-ratio checks) from the upload path entirely — there is no longer an archive to extract there. Introduce `SkillsPackageService` (or `SkillsMultipartService` — name decided during implementation, whichever reads better once the file exists) owning: parsing/validating the `filePaths` JSON array against the received `files` parts (count match, valid JSON, array-of-strings), path-safety/reserved-marker/duplicate/not-`SKILL.md` validation for each supporting path, size/count-limit enforcement against real received byte lengths, and building the outbound Core `FormData` (`skillManifest` as the `SKILL.md` part, each supporting file at its own part). `SkillsUploadService` keeps orchestration: which conditional header to send (D1/D2), the Core call, ETag extraction, and error mapping. `SkillsController`/`SkillsService` stay thin, matching the pre-existing decomposition precedent.
**Rationale:** The "focused component, not a grown `SkillsUploadService`" architecture requirement still applies — it just now covers multipart/package validation instead of ZIP archive validation, since that's what the corrected upload path actually receives.
**Alternatives considered:** Fold this validation directly into `SkillsUploadService` — rejected for the same reason the first draft split it out: keeps upload orchestration and package-shape validation independently testable.

### D5 — Edit load still unpacks a ZIP (Core's `GET` is unavoidably a ZIP); edit save sends multipart, never rebuilds a ZIP

**Decision:** Unchanged from the first draft's D4 for the *load* half: `downloadSkill()` (already returns the raw `Response`, already forwards the `ETag` header) resolves to a ZIP body; the frontend unpacks it with `fflate`, parses `SKILL.md`'s frontmatter with `yaml`, keeps the whole parsed object (unknown fields survive), and loads every other entry into an in-memory path→bytes map. This is the **only** ZIP-handling code that remains anywhere in this change — Core's `GET` contract genuinely is a ZIP (verified: `downloadArchive` in `ComplexResourceController`), so there is no way to avoid unpacking one to populate the edit form. **Save is corrected**: instead of rebuilding a ZIP from the merged frontmatter + files (the first draft's plan), edit-mode save serializes the merged frontmatter object to `SKILL.md` text directly (via `yaml.stringify`, no ZIP step) and sends it plus the untouched-or-edited supporting files as the same `skillManifest`/`filePaths`/`files` multipart shape `updateSkill` expects (D1/D3), with the loaded `If-Match`.
**Rationale:** Once the write path is multipart-not-ZIP (D3), there is no reason for edit-save to round-trip through a ZIP either — it would be pointless extra work (zip then have the BFF do nothing special with it) with no upstream requirement behind it.
**Alternatives considered:** Rebuild a ZIP on save for symmetry with load — rejected, save and load are not symmetric operations here: load must unpack because Core's `GET` response format is fixed; save has no such constraint, since the BFF write endpoints take multipart directly.

### D6 — `libs/skill-editor` prop additions (unchanged in shape from the first draft)

**Decision:** Same as the first draft's D6 — `mode`, `isNameReadOnly`, `onDirtyChange`, `conflict`/`onReloadLatest`. None of these were ZIP/multipart-shaped to begin with (they're presentational flags/callbacks), so this decision is unaffected by the write-path correction. Additionally confirmed in scope per the latest requirements: an optional supporting-file **replace** callback (distinct from add/remove, for "swap this file's bytes without changing its path") is added only if a concrete UI need for it surfaces during implementation of the edit flow — not speculatively added if the existing add/remove pair already covers every edit-mode interaction the design requires (a user can always remove-then-re-add to replace; a dedicated replace callback is only worth the added API surface if that's a materially worse UX than what the task actually needs).
**Rationale:** No new evidence changes this decision's reasoning from the first draft.

## Risks / Trade-offs

- **[Risk] `If-None-Match: '*'` is not declared in the pinned SDK's `.d.ts` for `uploadSkillFolder`**, so sending it requires the same kind of narrow `as unknown as {...}` type widening already used for the `FormData` body — a second, independent undeclared-parameter cast rather than one. → **Mitigation:** This is now backed by direct evidence (Core's `EtagHeader`/`ComplexResourceController` source, not inference from an SDK comment), so the cast is documented as correcting a known SDK/OpenAPI schema gap, not a speculative workaround. If a future SDK version declares `If-None-Match` for this operation, the cast should be removed in that version bump.
- **[Risk] `428 Precondition Required` on missing `If-Match` for `updateSkill` is a BFF invention with no Core equivalent** — a client bypassing this BFF (calling Core directly) would get a fully unconditional overwrite instead. → **Mitigation:** Out of scope to change Core; this BFF-only guard protects only callers of *this* BFF's `PUT /api/v1/skills`, which is the only caller this change controls (the Skill Editor page). Documented explicitly in Swagger so API consumers aren't surprised by a status Core itself would never return for this path.
- **[Risk] `filePaths`/`files` positional pairing (by array index) is fragile if either array is ever reordered by an intermediate proxy or multipart parser** that doesn't preserve part order. → **Mitigation:** The BFF SHALL validate `filePaths.length === files.length` before pairing, and multipart parts are read in arrival order by the same Node multipart parser (Multer/`busboy`) already used for every other upload endpoint in this codebase — no evidence this codebase's stack reorders parts; if this proves wrong under test, the fallback is giving each `files` part its own filename field carrying the path directly (already how Core itself keys parts) instead of a side-channel JSON array — flag as an open question to verify with an actual multipart-wire-shape test (per the testing requirements), not asserted as certain here.
- **[Trade-off] Two browser-facing routes instead of one** — slightly more Swagger/DTO surface than the first draft's single `PUT`, accepted per D1's rationale.
