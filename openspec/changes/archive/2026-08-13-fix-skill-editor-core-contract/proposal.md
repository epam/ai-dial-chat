## Why

`add-skill-authoring-ui` (shipped, PR #8315, not yet archived) built Skill creation on a wrong assumption about DIAL Core's wire contract: it forwards the user's ZIP archive to `PUT /v2/skills/{bucket}/{path}` as a single multipart file part. Creating any skill fails live with `400 "Skill must contain a SKILL.md at its root"`. Investigation initially proposed fixing this by having the BFF explode the browser's ZIP into per-file multipart parts server-side. Reading DIAL Core's actual shipped Java implementation (`epam/ai-dial-core`, `ComplexResourceController`/`ComplexResourceService`/`SkillHandler`/`EtagHeader`, not just the pinned SDK's incomplete generated types) shows a simpler, more correct fix is available: Core never wants a ZIP for writes at all, and its real conditional-header engine (`EtagHeader`) already supports atomic create via `If-None-Match: '*'` — a header the SDK's `.d.ts` simply never declared, a documentation gap, not a missing capability. This revision corrects the change's architecture accordingly: no ZIP anywhere on the write path (create or edit-save), a genuine atomic create using the real header, and a split browser-facing `POST`/`PUT` contract.

## What Changes

- **No ZIP upload, ever.** The frontend keeps `SKILL.md`'s manifest text and every supporting file's bytes in memory and sends them directly to the BFF as `multipart/form-data`: `bucket`, `path`, `skillManifest` (full manifest text), `filePaths` (JSON array of supporting-file relative paths, authoritative — not inferred from multipart filenames), and repeated `files` parts paired 1:1 by array index with `filePaths`. ZIP survives only on the edit-*load* path, where DIAL Core's `GET /v2/skills/{bucket}/{path}` genuinely returns `application/zip` and must be unpacked with `fflate` to populate the form — there is no ZIP on any write path (create or edit-save).
- **Split browser-facing endpoints**: `POST /api/v1/skills` (`createSkill`, `201 Created`, atomic — BFF sends `If-None-Match: '*'` to Core, no `If-Match`) and `PUT /api/v1/skills` (`updateSkill`, `200 OK`, requires a concrete `If-Match` from the caller — the BFF returns `428 Precondition Required` without calling Core if it's missing). Both replace the previous single upsert-style `PUT`.
- **Corrected create-collision mapping, using a verified mechanism**: DIAL Core's real `EtagHeader.validateIfNoneMatch` (read directly from source) returns `412` when `If-None-Match: '*'` collides with an existing resource. `createSkill` catches that `412` and re-throws `409 Conflict`. `updateSkill`'s `412` (a stale concrete `If-Match`) is surfaced unchanged as a genuine concurrent-edit conflict. *(This corrects an earlier draft of this same change, which — before this investigation — concluded, based only on the SDK's `.d.ts` doc-comment, that omitting `If-Match` was itself Core's create-only mechanism. Read directly, `EtagHeader.java` shows that omitting **both** conditional headers is a fully unconditional overwrite; the doc-comment was simply wrong.)*
- **BFF package validation replaces ZIP-archive validation**: `SkillsArchiveService` (ZIP extraction, encrypted-entry/symlink/compression-ratio checks — introduced in the previous draft) is removed from the upload path, since there is no longer an archive to extract there. A new focused component (`SkillsPackageService` or similarly named, decided during implementation) parses/validates `filePaths` against the received `files` parts (count match, valid JSON, path safety, no duplicates, not `SKILL.md`), enforces size/count limits against real received byte lengths, and builds the outbound Core `FormData` (one `file` part for the manifest at `SKILL.md`, one per supporting file at its own relative path).
- **Corrected limits, verified against Core's actual `ComplexResourceService.Settings`**: 100 files max (including `SKILL.md`), 1 MiB per file, 16 MiB total content — exact values read from Core's source, not the epic issue's "~" approximations. File-count-exceeded maps to `400` (matching Core's own status for this case, verified in source — not `422`); byte-limit-exceeded maps to `413` (matching Core's `REQUEST_ENTITY_TOO_LARGE`, also verified).
- **Create-mode frontend correction**: no `listSkills` preflight (superseded by the real atomic-create signal); Name/Description required, **Instructions is optional** (correcting a contradiction the first draft's `skill-authoring` requirements had introduced — nothing in Core's or the product's stated contract requires it, and the current UI already treats it as a plain text field with no server-enforced minimum); build `SKILL.md` text via `yaml`, never manual interpolation; call the new `createSkill` wrapper, not `uploadSkill`; `409`/`413`/validation errors mapped inline; field values preserved on every failure; navigate only after `201 Created`.
- **Edit-mode**: unchanged in almost every respect from the previous draft (ETag-gated load, frontmatter-preserving parse/merge, immutable path, read-only Name, non-destructive `412`-conflict "Reload latest", dirty-navigation guard) — corrected only in that *save* sends the same manifest-text/`filePaths`/`files` multipart shape through the new `updateSkill` wrapper, never rebuilding a ZIP.
- **Library (`@epam/ai-dial-skill-editor`)**: same additive props as the previous draft (`mode`, `isNameReadOnly`, `onDirtyChange`, `conflict`/`onReloadLatest`), unaffected by the wire-contract correction since none of them were ZIP/multipart-shaped.
- **OpenAPI**: `createSkill`/`updateSkill` as two distinct, fully documented Swagger operations (request/response examples, all applicable status codes including the new `201`/`428`); `libs/chat-api-client` regenerated via `npm run openapi`, checked via `npm run openapi:check` — never hand-edited. Frontend `apps/chat/src/server-api/skills.api.ts` gets `createSkill`/`updateSkill` wrappers replacing the old single `uploadSkill`.
- **Environment variable migration**: the old `SKILL_UPLOAD_MAX_BYTES` (a compressed-ZIP-ingress Multer limit) has no remaining meaning once no ZIP is ever uploaded — this variable is removed/repurposed; the design documents the exact migration (see `design.md`/`tasks.md`).
- **Explicitly out of scope (unchanged, still a discovered pre-requisite gap)**: Skill catalog listing/details — the Catalog "Edit" entry point still cannot be wired for the same reason as the previous draft (no `CatalogItem`-of-type-`Skill` producer exists). Edit mode is reachable only via `/skill-editor?id=...`.

## Capabilities

### New Capabilities

- `skills-multipart-processing` *(replaces the previous draft's `skills-archive-processing`)*: The BFF's `filePaths`/`files` parity validation, per-path/size/count checks against real received byte lengths, and outbound per-file Core `FormData` construction (`skillManifest` → `SKILL.md` part, each supporting file → its own part) — no ZIP involved anywhere in this capability.
- `skill-editing`: Unchanged in scope from the previous draft — the end-to-end edit flow (id-based route entry, ETag-gated load with ZIP unpack, in-memory supporting-file map, save via multipart with `If-Match`, ETag replacement, `412` conflict handling with non-destructive reload, read-only resource path/Name, dirty-navigation guard) — corrected only so that *save* never rebuilds a ZIP.

### Modified Capabilities

- `skills-bff-api`: Replaces the single `PUT /api/v1/skills` upsert operation with `POST /api/v1/skills` (`createSkill`, atomic via `If-None-Match: '*'`, `201`) and `PUT /api/v1/skills` (`updateSkill`, requires `If-Match`, `428` if absent, `200`); corrects upload limits to Core's verified real defaults and status codes (`400` file-count, `413` byte-limits); corrects create-collision mapping (`412`→`409`, using the verified `If-None-Match` mechanism, not the retracted omit-`If-Match` theory).
- `skills-service-decomposition`: Adds a multipart/package-processing sub-component (final name decided during implementation) in place of the previous draft's `SkillsArchiveService`, owned only by `SkillsUploadService`.
- `skill-authoring` *(capability introduced by the not-yet-archived `add-skill-authoring-ui` change)*: Removes ZIP construction and the `listSkills` preflight; makes Instructions optional; switches the create call from `uploadSkill` to `createSkill`.
- `skill-editor-library` *(capability introduced by the not-yet-archived `add-skill-authoring-ui` change)*: Unchanged from the previous draft of this same change — create/edit-mode props, read-only Name, dirty-change/retry/reload callbacks, conflict state/actions.

## Impact

- **Affected code**: `apps/chat-api/src/skills/**` (new multipart/package sub-service replacing the previous draft's archive service, `upload/skills-upload.service.ts`, `dto/*`, `skills.controller.ts` — new `POST` handler, corrected `PUT` handler and Swagger, `config/environment.config.ts` — corrected/migrated limit variables, `skills.module.ts`), `libs/chat-api-client/` (regenerated), `apps/chat/src/pages/SkillEditor/**`, `apps/chat/src/utils/skill.ts` (drop ZIP-building for writes; keep ZIP-unpacking for edit-load), `apps/chat/src/server-api/skills.api.ts` (`createSkill`/`updateSkill` wrappers), `apps/chat/src/types/skill-editor.ts` (new `Id` query key), `libs/skill-editor/**`.
- **Dependencies**: No new third-party packages. `fflate` is still used, now only for edit-load ZIP unpacking (not for building any ZIP). `yaml` is still used for manifest serialization/parsing.
- **Discovered gap, filed as follow-up, not built here**: Skill catalog listing/details (unchanged from the previous draft).
- **Compatibility (BREAKING at the BFF-endpoint level)**: The browser-facing contract changes shape — the old single `PUT /api/v1/skills` accepting one `file` ZIP part is replaced by `POST`/`PUT` accepting `skillManifest`/`filePaths`/`files`. Since no skill has ever been successfully created against the old (broken) contract, there is no existing on-disk state or external caller depending on the old shape to migrate — this is a pre-launch correction, not a backward-compatibility break against real usage.
- **Environment variable migration**: `SKILL_UPLOAD_MAX_BYTES` (the old compressed-ZIP Multer ingress cap) is retired; its Multer-limit role is superseded by field-level `fileSize`/`fieldSize`/`files`/`parts` limits sized off the corrected per-file/total/file-count limits. Documented explicitly in `design.md`/`tasks.md` so a deployed environment setting the old variable doesn't silently do nothing.
- **Rollback**: Revert; no data migration.
