## Context

`SharedInvitationPage` (`apps/chat/src/pages/SharedInvitation/SharedInvitation.tsx`) accepts a share invitation, refetches deployments/toolsets, then navigates to `` `${ROUTES.Catalog}?itemId=<id>` `` with `replace: true`. `CatalogView` reads that param once per render via `searchParams.get(CatalogQuery.ItemId) ?? undefined` and forwards it to `Catalog` (`libs/catalog/src/components/Catalog/Catalog.tsx`) as `initialDetailsItemId`. `Catalog.tsx` owns an effect that opens the details panel the first time it sees a given `initialDetailsItemId` matched against a loaded `CatalogItem`, guarded by `appliedInitialDetailsItemIdRef` so the panel doesn't reopen every time the `items` array reference changes (e.g. on a background refetch) while the same id is still current.

Nobody ever clears the `itemId` query param. It is set once by `SharedInvitationPage` and then persists in the address bar for the remainder of the `CatalogView` mount's lifetime — including across further in-tab navigations to the same or a different `SharedInvitation` route, since React Router does not remount already-mounted components for a same-path navigation. Combined with `appliedInitialDetailsItemIdRef` never resetting once it records an id, this produced one real bug (fixed, see the first two Decisions below): a later navigation to a shared link for the *same* deployment silently no-ops because the ref still matches.

**That fix alone did not resolve GitHub #7860.** Manual verification against a running instance, with the reporter, established: the actual repro is a *full page navigation* to `/catalog/shared/:invitationId` (not an in-tab SPA transition — Network tab shows a `document` request). On a full reload every piece of frontend state, including the ref above, starts fresh, so the guard fix is a no-op for this path. The reporter confirmed `itemId` **does** appear in the post-redirect URL, but `Catalog`'s `items.find(id)` still fails — `GET /api/v1/deployments`/`GET /api/v1/toolsets`, even immediately after `SharedInvitationPage`'s own `refetchDeployments()`/`refetchToolsets()`, do not yet include the newly-shared resource. `ShareService.acceptInvitation` does call `invalidateListCache` before returning (so the chat-api-level cache isn't the culprit), but nothing guarantees DIAL Core's own `listDeployments`/`getSharedResources` reflects a just-granted share on the very next call — accept and list-visibility are not the same atomic operation upstream.

The legacy pre-rewrite app (`origin/development`, `apps/chat/src/store/share/share.epics.ts:472-660`) never had this race, because it never depended on the bulk list at all: `acceptInvitationEpic`/`acceptInvitationSuccessEpic` resolve the shared application **by id directly** — `ApplicationActions.get({ applicationId: acceptedId, showCard: true })` when the app isn't yet known locally, or `ApplicationService.getDialEntity(applicationFromState.id)` plus a local `ModelsActions.updateLocalModels` patch when it is — and only then dispatch `MarketplaceActions.setDetailsEntity` to open the panel. The bulk list refresh, when it eventually lands, is irrelevant to whether the panel opens. This design ports that same principle forward.

## Goals / Non-Goals

**Goals:**
- Make navigating to a shared-deployment link reliably open the details panel regardless of what was previously viewed in that tab (done — stale-ref/URL-clearing fix).
- Make the panel open reliably on a *fresh* full-page navigation to a shared-deployment link, without depending on DIAL Core's bulk listing endpoints reflecting a just-granted share by the time the frontend's post-accept refetch runs.
- Keep the fix confined to the accept-invitation round trip; no new standalone endpoint, no polling loop, no change to how the bulk deployments/toolsets lists are fetched or cached in the general case.

**Non-Goals:**
- Not changing `SharedInvitationPage`'s invitation-accept/refetch sequencing beyond adding the merge step (`conversation-share`'s existing race-safety work, already covered by `deploymentsRequestIdRef`/`toolsetsRequestIdRef` in `DeploymentsContext`) — that request-sequencing logic is correct and stays as-is.
- Not adding a callback for "details panel closed" or otherwise expanding `Catalog`'s prop surface.
- Not touching the conversation-share equivalent flow (`ConversationSharedInvitationPage` → `/conversations/:id`) — that route fetches the specific conversation by id already (no bulk-list dependency), so it doesn't have this race.
- Not building a generic polling/retry framework for list-consistency races elsewhere in the app — this fixes the one endpoint (`acceptInvitation`) that already knows the specific id it just granted access to and is the natural place to resolve it.

## Decisions

**Decision: Clear the `itemId` search param in `CatalogView` right after reading it, rather than in `SharedInvitationPage` before navigating.**
`CatalogView` is the sole consumer of the param and the one component that knows it's meant to be a one-shot "open this on mount/update" signal. Clearing it in `SharedInvitationPage` before navigating wouldn't work anyway — the param has to be present in the URL for `CatalogView` to read in the first place. Clearing happens via `setSearchParams` with `{ replace: true }` in a `useEffect` keyed on the raw param value, so it fires once per distinct incoming value and doesn't fight the initial render (which still needs to see the param in order to pass it through as `initialDetailsItemId`).

*Alternative considered:* Have `Catalog.tsx` call an `onInitialDetailsItemIdConsumed` callback so the app can clear its own URL state. Rejected — it adds a new prop/callback to a shared lib for a need that's fully satisfiable by the app reading and clearing its own `useSearchParams` state independently; the lib doesn't need to know the app stores this value in the URL at all.

**Decision: Reset `appliedInitialDetailsItemIdRef` in `Catalog.tsx` when `initialDetailsItemId` becomes falsy, in addition to the URL-clearing change.**
Clearing the URL param alone only helps if `Catalog`'s guard treats the id's disappearance as meaningful. Without also resetting the ref, the sequence would be: id `X` applied (ref = `X`) → `CatalogView` clears the param (`initialDetailsItemId` becomes `undefined`, ref still `X`, effect early-returns without touching the ref) → a later navigation sets the param back to `X` → effect sees `ref === X` and still no-ops. Resetting the ref back to `null` whenever the incoming prop is falsy makes the "already applied" memory scoped to the *current* non-empty streak of the prop, matching what "initial" in `initialDetailsItemId` actually implies: each new appearance of a non-empty value is a fresh open request.

*Alternative considered:* Replace the id-based guard with a monotonically increasing nonce/counter passed alongside the id (e.g. `initialDetailsItemId: { id: string; nonce: number }`). Rejected as unnecessary API surface churn — resetting on falsy is a one-line change that fully fixes the observed bug given the URL-clearing change alongside it, and doesn't require touching the prop's shape or any call site other than `Catalog.tsx` itself.

**Decision: Resolve and return the shared item's summary from `ShareService.acceptInvitation` itself, rather than polling/retrying the bulk list refetch.**
`acceptInvitation` already knows the exact `itemId` (resolved from the peek call) before it ever touches the bulk list. It can reuse the same prefix-based type dispatch already implemented for `DeploymentsService.getDeploymentDetails` (`toolsets/` → toolset, `applications/` → application, otherwise try model → application → toolset) to fetch that one resource directly from DIAL Core and map it into the same shape the bulk endpoints already produce (`DeploymentItemDto` for models/applications via the existing `mapToDeploymentItem`, or the toolset SDK shape as-is for toolsets, matching `ToolsetsService.listToolsets`). Returning this summary in `AcceptInvitationResponseDto` lets the frontend inject the item into `DeploymentsContext`'s local state synchronously — no extra request, no dependency on bulk-list timing at all.

*Alternative considered:* Poll/retry `refetchDeployments()`/`refetchToolsets()` in `SharedInvitationPage` with backoff until the id appears (or a retry budget is exhausted) before navigating. Rejected as the primary fix — it's frontend-only and lower effort, but it treats a knowable fact (which single resource was just granted) as an unknown to be rediscovered by re-scanning the whole list, and still has a failure mode (retries exhausted, DIAL Core still hasn't propagated) with no better outcome than today. The single-id resolve is deterministic: if DIAL Core's per-id `getModel`/`getApplication`/`getToolset` doesn't yet reflect the grant either, that's a genuine DIAL Core-side propagation gap no frontend polling would reliably paper over anyway, and it fails no worse than today (falls back to `sharedDeployment`/`sharedToolset: undefined`, and the existing bulk refetch remains as a backstop that a subsequent list load will pick up).

**Decision: Extract the prefix-dispatch/single-item resolution as a reusable method on `DeploymentsService`, not a private duplicate inside `ShareService`.**
`DeploymentsService.fetchDeploymentDetails`'s prefix dispatch (`toolsets/`/`applications/`/ambiguous-fallback) is exactly the logic `ShareService` needs, just mapped to a different output shape (`DeploymentItemDto` list-item vs. `DeploymentDetailsDto` tab-data). Expose a new `DeploymentsService.resolveDeploymentItem(id, accessToken): Promise<DeploymentItemDto | null>` that shares the *type resolution* step (does this id belong to a model/application/toolset) but maps to the list-item shape; `ShareService` calls it for non-toolset ids and calls a small new `ToolsetsService.resolveToolsetItem(id, accessToken)` for `toolsets/`-prefixed ids.

*Alternative considered:* Duplicate the prefix-check logic inside `ShareService`. Rejected — the resolution rule (`toolsets/` / `applications/` / ambiguous fallback chain) is a DIAL Core id-convention fact that already has one owner (`DeploymentsService`); duplicating it risks the two copies drifting when the convention changes.

**Decision: `DeploymentsContext.mergeSharedItem` upserts into local state synchronously; it does not itself call the network.**
`SharedInvitationPage` already has the resolved item from `acceptInvitation`'s response body — no second round trip is needed. `mergeSharedItem(item: DeploymentItemDto | DialToolsetDto)` sets `rawDeployments`/`toolsets` via the existing `setRawDeployments`/`setToolsets` setters, replacing any existing entry with the same id or prepending a new one. This keeps `DeploymentsContext`'s existing request-id-guarded `refetchDeployments`/`refetchToolsets` untouched — `mergeSharedItem` is a separate, synchronous code path, not a variant of the refetch flow.

*Alternative considered:* Have `mergeSharedItem` trigger its own `getDeploymentDetails`-style re-fetch by id to "confirm" the item before merging. Rejected — the item comes from `acceptInvitation`'s own response, which already reflects a real grant that DIAL Core just processed; re-verifying it via a second call reintroduces the same kind of race this design exists to avoid, for no benefit.

## Risks / Trade-offs

- [Risk] Clearing the `itemId` param immediately could race with `Catalog`'s own effect reading it, if `setSearchParams` synchronously changes props before the open-detail effect runs → Mitigation: `setSearchParams` triggers a React Router state update that re-renders on the next tick, same as any other state setter; the open-detail effect reads the `initialDetailsItemId` value that was current for that render pass (React batches props/state within a commit), so the panel still opens using the value seen at the time the param was present. This mirrors the existing pattern already used for `pendingItemIdRef`/`appliedInitialDetailsItemIdRef` guarding against re-render churn.
- [Risk] A user could bookmark or manually retype a `?itemId=...` URL expecting it to stay in the address bar → Mitigation: this was never a documented/supported use case (the param is only ever produced by `SharedInvitationPage`'s one-time redirect); clearing it does not remove the ability to open details by id, only the URL's reflection of "which id was last opened."
- [Risk] Resetting the ref on every falsy `initialDetailsItemId` could reopen the panel unexpectedly if some other code path also toggles the prop to falsy and back for unrelated reasons → Mitigation: `initialDetailsItemId` has exactly one producer (`CatalogView`'s read of the `itemId` search param) and, after this change, exactly one place that clears it (the same component, right after consuming it) — there's no other writer that could trigger a false transition.
- [Risk] Resolving the item by id inside `acceptInvitation` adds one more upstream DIAL Core round trip (in addition to the peek + accept calls already made) before the endpoint responds → Mitigation: this replaces a client-side dependency on `refetchDeployments`/`refetchToolsets` succeeding *and* containing the id, which was already a real (if implicit) wait; the added latency is comparable to the single-item `getDeploymentDetails` call the details panel makes anyway once opened, and it removes an entire class of failure (list not yet reflecting the grant) rather than trading one wait for another.
- [Risk] DIAL Core's own per-id `getModel`/`getApplication`/`getToolset` could *itself* not yet reflect a just-granted share (the propagation gap could sit below the list endpoint too) → Mitigation: this is a genuine upstream limit no frontend or chat-api change can fully close; if it happens, `sharedDeployment`/`sharedToolset` comes back `undefined`, `SharedInvitationPage` falls back to today's behavior (bulk refetch, no guaranteed merge), and the user sees the pre-existing (already-reported) failure mode rather than a new one — this design strictly narrows the failure window, it doesn't claim to eliminate every possible DIAL Core propagation delay.
- [Risk] `resolveDeploymentItem`/`resolveToolsetItem` reintroduce the same ambiguous-id fallback chain (model → application → toolset) as `getDeploymentDetails`, meaning up to 3 sequential DIAL Core calls for an unprefixed id → Mitigation: identical to the existing `/details` endpoint's behavior and already accepted there; most shared ids in practice carry the `toolsets/`/`applications/` prefix, so this is the uncommon path.

## Migration Plan

No data migration. Rollout in slices:
1. (Done) Land the `Catalog.tsx` guard-reset change and its unit test.
2. (Done) Land the `CatalogView` URL-clearing change and its test.
3. Extract `DeploymentsService.resolveDeploymentItem` / add `ToolsetsService.resolveToolsetItem`, with unit tests for the prefix-dispatch and ambiguous-fallback paths.
4. Add `sharedDeployment`/`sharedToolset` to `AcceptInvitationResponseDto`; wire `ShareService.acceptInvitation` to populate them. Regenerate the OpenAPI spec (`npm run openapi`, `npm run openapi:check`) and rebuild `chat-api-client`.
5. Add `DeploymentsContext.mergeSharedItem`; wire `SharedInvitationPage` to call it with the response's resolved item before navigating.
6. Verify manually against a running instance: full-page navigation to a fresh shared-deployment link opens the details panel on the very first redirect, with no dependency on a subsequent bulk list load.
7. No feature flag needed — this only fixes an existing broken path; the new response fields are additive/optional, so older frontend builds against a newer backend (or vice versa during a rolling deploy) keep working exactly as before.

Rollback: the new DTO fields are optional and additive, so the backend change alone is safely revertible without a frontend redeploy. The frontend `mergeSharedItem` call is guarded by the field being present (falls through to today's refetch-only behavior when absent), so a frontend rollback while the backend change is still live is also safe.

## Open Questions

None for the stale-ref/URL-clearing fix (root cause and fix are both fully determined by the existing code and comments already in `DeploymentsContext.tsx` and `conversation-share`'s spec). For the list-consistency fix: whether DIAL Core's single-id `getModel`/`getApplication`/`getToolset` reliably reflects a grant faster than its bulk `listDeployments`/`getSharedResources` is an assumption based on the legacy app's working behavior, not something verifiable from this codebase alone — manual verification against a running DIAL Core instance (Migration Plan step 6) is the practical confirmation.
