## Context

Today `ScheduledTaskDto` (`apps/chat-api/src/scheduled-tasks/dto/scheduled-task.dto.ts:17-75`) has no boolean active/paused field. The mapper `fromUpstreamSchedule` (`apps/chat-api/src/scheduled-tasks/scheduled-tasks.mapper.ts:158-182`) maps `next_run_time` → `nextRunTime` and nothing else state-related. `UpstreamScheduleResponse` (`scheduled-tasks.mapper.ts:52-75`) has no `is_active`/`paused`/`status` field, and `libs/chat-api-client/openapi.json` has no `schedules/{id}/pause` or `/resume` path — this repo has never called those upstream actions before. The detail-page header (`ScheduledTaskDetailView.tsx:266-307`) currently renders back+title+conditional Edit only; `scheduled-task-detail-page/spec.md`'s header requirement explicitly excludes an Active-toggle "in this iteration." This design closes that gap: a BFF-owned `isActive` field, two new proxy endpoints, and a header switch wired through the existing host-agnostic `ScheduledTaskDetailView` contract.

Stakeholders: users who want to pause a recurring schedule without a full edit round-trip; the `apps/chat-api` scheduled-tasks domain owner (cache/rate-limit/error-mapping conventions must match `updateScheduledTask`); `libs/scheduled-tasks` owner (library isolation must hold).

## Goals / Non-Goals

**Goals:**
- One-click, reversible pause/resume from the detail-page header, backed by dedicated upstream-proxying endpoints.
- A single, BFF-owned source of truth for "is this schedule active", exposed as `ScheduledTaskDto.isActive`.
- Optimistic UI with rollback, matching the responsiveness of a native switch, without risking a silently wrong displayed state.
- Preserve library isolation (`libs/scheduled-tasks` still takes no API/routing/i18n/feature-flag knowledge) and AAA accessibility for the new control.

**Non-Goals:** (mirrors proposal.md `Non-goals`) Delete, Run-now, editing any other task field via this switch, list-card switches, bulk pause/resume, polling, run-history changes.

## Decisions

### Decision 1: Active-state derivation — BFF-owned, `next_run_time`-based, flagged as an assumption

**Chosen:** Add `isActive?: boolean` to `ScheduledTaskDto`, computed once in `fromUpstreamSchedule` as `upstream.next_run_time != null` when a `trigger_type`/`trigger` is present, and `undefined` when the upstream response gives no basis to decide (e.g. a list item missing both `trigger` and `next_run_time` some other way). This is the only signal any file in this repo has ever observed from DIAL Scheduler for schedule state (see Context). It is **not** confirmed as the upstream's formal definition of "paused" — no `openapi.json`/live-response evidence for `is_active`/`status`/`paused` exists in this codebase.

**Alternatives considered:**
1. **`next_run_time != null` heuristic in the BFF mapper (chosen)** — Pros: single source of truth, matches existing `nextRunTime`-driven UI (the detail page already shows a "Next run" label sourced from the same field), no new upstream call needed beyond what `getScheduledTask`/`listScheduledTasks` already make. Cons: ambiguous for a **completed or expired one-time (`date`) trigger** — such a schedule also has `next_run_time: null` but is not "paused" in the resumable sense; DIAL Scheduler likely cannot resume a one-shot schedule whose single run has already fired. Mitigation (see Decision 4): the switch is only rendered/enabled when `triggerType === 'cron'` OR `nextRunTime` is non-null — i.e., a one-time schedule that has already fired renders no switch at all (nothing to toggle), rather than an enabled-but-nonfunctional one.
2. **Derive independently in React from `Boolean(nextRunTime)`** — rejected per the brief: duplicates the same imperfect heuristic in a second place (frontend), with no BFF-level place to correct it later once the real contract is confirmed. Centralizing in the mapper means only one file changes when the assumption is replaced with a confirmed upstream field.
3. **Block this proposal entirely pending upstream contract confirmation** — rejected: the two pause/resume endpoints and the switch UI are independently valuable and testable against the documented, flagged assumption; blocking the whole feature on an external team confirming an OpenAPI detail is disproportionate given a safe, narrowed rendering rule (Decision 4) contains the risk.

**Action required before this ships to production:** confirm against a live DIAL Scheduler instance or its OpenAPI spec whether an explicit active/paused field exists. If it does, replace the heuristic in `fromUpstreamSchedule` with that field — this is a single-function change isolated by Decision 1's centralization. Tracked as an explicit task in tasks.md, not silently assumed.

### Decision 2: Mutation response shape — return the refreshed `ScheduledTaskDto`

**Chosen:** Both `POST .../pause` and `POST .../resume` return `200 OK` with the full, current `ScheduledTaskDto` (same DTO `getScheduledTask` returns), fetched via **a BFF follow-up `GET`** to `.../schedules/{scheduleId}` after the upstream pause/resume action succeeds — because no evidence in this repo confirms the upstream pause/resume action's response body contains the updated schedule (unlike `createScheduledTask`/`updateScheduledTask`, which DIAL Scheduler confirms return the schedule). Treating the action response as opaque and re-fetching is the only design that doesn't require an unverified assumption about the action endpoint's body.

**Alternatives considered (per the brief's four options):**
1. **`200 ScheduledTaskDto`, assuming the upstream action body already contains it** — rejected: unverified; if the upstream pause/resume action returns `204`/`{}` (common REST convention for action-style endpoints), this design breaks silently in production.
2. **Typed state response `{ isActive, nextRunTime? }`** — rejected as the primary shape: saves one field's worth of payload versus the full DTO, but forces the frontend to maintain two different response shapes for "get a task" vs. "mutate a task's active state," and the full DTO is needed anyway to safely merge into detail-page state without dropping other fields.
3. **`204 No Content` + frontend refetch** — rejected as the endpoint contract: pushes the same follow-up-GET cost onto every caller instead of doing it once in the BFF, and a `204` gives the frontend nothing to optimistically reconcile against on the same round-trip.
4. **Optimistic-only, no refetch at all** — rejected as the *response* design (though optimistic *UI* is still used, see Decision 3): the frontend's optimistic guess could drift from server truth (e.g. concurrent edit, upstream computing a new `next_run_time` on resume) with nothing to correct it.

**Chosen: BFF follow-up GET, not "204 + frontend refetch."** Doing the refetch once, server-side, inside `ScheduledTasksService.pauseScheduledTask`/`resumeScheduledTask`, means: (a) one network round-trip from the frontend's perspective instead of two, (b) the mutation and the freshness read share one code path (the existing `getScheduledTask` proxy call, no new upstream call type introduced), and (c) the guarantee in the "State consistency" requirement — "a failed post-mutation refresh does not incorrectly roll back a mutation already confirmed by the server" — is enforced in exactly one place (see Decision 5).

### Decision 3: Frontend interaction — optimistic switch with rollback on failure

**Chosen:** `ScheduledTaskDetailPage` holds `isActiveUpdating: boolean` alongside `task: ScheduledTaskDto | null`. On toggle: (1) immediately set local `isActive` to the requested value and `isActiveUpdating = true`; (2) disable the switch; (3) call `pauseScheduledTask`/`resumeScheduledTask`; (4) on success, merge the returned `ScheduledTaskDto` into `task` (authoritative `isActive`/`nextRunTime` from the server, not the optimistic guess) and show a success toast; (5) on failure, revert `isActive` to the pre-toggle value, keep the rest of `task` untouched, and show a localized error toast including the request/trace id when available (matching the existing error-notification pattern used elsewhere in the app — no new notification component). A request-token guard (an incrementing ref, mirroring `taskFetchToken` already used for the retry flow at `ScheduledTaskDetailPage.tsx:42,184-185`) ensures a late-resolving pause/resume response cannot apply to a different `scheduleId` after navigation, and a simple in-flight boolean prevents overlapping pause/resume calls (the switch is disabled during the request, so only a race between disable-render and a fast double-click needs the extra guard).

**Alternatives considered:**
1. **Optimistic with rollback (chosen)** — matches the brief's explicit preference; a switch is expected to feel instant, and pause/resume are simple boolean transitions with a well-defined rollback (the value before the click).
2. **Pessimistic (wait for server before flipping the switch)** — rejected: violates the brief's explicit "Prefer optimistic behavior" and reads as unresponsive for a control with no other visible loading affordance besides its own disabled state.

### Decision 4: Switch render/enable conditions — only when state is authoritative and resumable

**Chosen:** `ScheduledTaskDetailPage` passes `isActive={task?.isActive}` to `ScheduledTaskDetailView` only once `task` has loaded successfully (mirrors the existing `onEdit={task ? handleEdit : undefined}` conditional at `ScheduledTaskDetailPage.tsx:203`); the view renders the switch **only when `isActive !== undefined`** (i.e., the mapper had a basis to decide — see Decision 1) — never an unchecked switch while state is unknown, per the brief. On a schedule whose `triggerType` is `date` (one-time) **and** `nextRunTime` is `null` (already fired), `isActive` maps to `false` under Decision 1's heuristic, but DIAL Scheduler cannot resume a completed one-shot run; the switch is rendered **disabled** in that specific case (checked=false, disabled=true) rather than hidden, so the user sees the true state without being offered a resume action that would fail. This is a narrow, explicit rule — not a general heuristic — and is covered by a dedicated task/spec scenario.

**Alternatives considered:** Hiding the switch entirely for completed one-shot schedules was considered but rejected — showing "Active: off, disabled" communicates the actual terminal state, whereas hiding it looks identical to "state unknown" (which the brief also says must not render an unchecked switch), collapsing two different situations into one ambiguous absence.

### Decision 5: Cache invalidation and failed-refresh handling

**Chosen:** `pauseScheduledTask`/`resumeScheduledTask` in `ScheduledTasksService` invalidate the caller's list cache (via the existing `invalidateListCache(userSub)` epoch-bump helper, `scheduled-tasks.service.ts:429-446`) **only after the upstream pause/resume action itself succeeds** — matching `createScheduledTask`/`updateScheduledTask`'s existing ordering. The follow-up `GET` (Decision 2) happens after that action succeeds too; if the follow-up `GET` fails, the action is still treated as successful (list cache already invalidated, `isActive` already flipped), and the service returns the last-known `ScheduledTaskDto` fields it has (the pre-mutation task, with `isActive` corrected to the requested value) rather than throwing — so the frontend's optimistic value is confirmed, not rolled back, and the response simply may not carry a freshly recalculated `nextRunTime` until the next natural refetch (list revisit, or detail-page remount). This satisfies the explicit "State consistency" requirement: a failed post-mutation refresh must not roll back an already-confirmed mutation.

**Alternatives considered:** Treating a failed follow-up `GET` as an overall endpoint failure (500-ing the whole pause/resume call) was rejected — it would falsely tell the frontend the mutation didn't happen when DIAL Scheduler already applied it, causing the optimistic UI to roll back a real state change and confuse the user into re-clicking (which could then legitimately fail with a "no-op" or conflict from Scheduler).

### Decision 6: DTO and endpoint shape

**Chosen:** Reuse `GetScheduledTaskDto` (existing `scheduleId` path-param DTO with the `^[A-Za-z0-9_-]{1,128}$` allowlist) for both new endpoints' `@Param()`. No request body DTO — both endpoints take no body, matching the brief. Response type is the existing `ScheduledTaskDto` — no new response DTO class needed. Both endpoints follow the exact `@UseGuards(FeatureGuard)` + `@RequireFeature(FeatureKey.ScheduledTasksEnabled)` + session `sub`/`at` + `@Throttle` + full `@ApiResponse` pattern already on `updateScheduledTask` (`scheduled-tasks.controller.ts:260-309`), reusing its rate limit (`{ default: { limit: 10, ttl: 60000 } }`) since pause/resume are mutations of comparable sensitivity/cost to update.

**Alternatives considered:** A dedicated `PauseScheduledTaskResponseDto`/`ResumeScheduledTaskResponseDto` pair was considered for documentation clarity but rejected as needless duplication — Decision 2 already settled on returning the same `ScheduledTaskDto` shape `getScheduledTask`/`updateScheduledTask` use, so a same-shape DTO alias would only exist to rename the class, not to add fields.

## Risks / Trade-offs

- **[Risk] The `next_run_time != null` heuristic (Decision 1) is wrong for some trigger type not yet enumerated** (e.g. a future Scheduler trigger kind with different pause semantics) → **Mitigation:** heuristic is isolated to one function (`fromUpstreamSchedule`), documented inline as an assumption, and the switch's disabled-state rule (Decision 4) already handles the one known ambiguous case (completed one-shot). A follow-up task requires manual confirmation against a live Scheduler/its OpenAPI spec before this ships, tracked explicitly in tasks.md.
- **[Risk] BFF follow-up `GET` after pause/resume doubles upstream calls per mutation** → **Mitigation:** matches the already-accepted cost profile of `createScheduledTask`/`updateScheduledTask` (both already are single upstream calls that return the schedule directly per the existing spec — pause/resume's extra `GET` is the cost of the action endpoint's shape being unverified, not a new pattern; still just 2 upstream calls total on the rare user-initiated toggle action, not a hot path).
- **[Risk] Optimistic UI could show `isActive: true` after a resume that failed upstream but succeeded HTTP-wise (unlikely mismatch)** → **Mitigation:** the service only reports `isActive` as the new value once the upstream action call itself returned success (not assumed before the call) — an upstream error throws and maps to the documented HTTP status (400/403/404/409/429/502/503) before the frontend's success branch ever runs, so rollback in Decision 3 still fires correctly.
- **[Risk] Reusing the update endpoint's rate limit for two additional endpoints effectively lets a user issue 3x as many task-mutations/minute (create/update/pause/resume all at 10/60s, but pause+resume are separate buckets from update)** → **Mitigation:** acceptable — pause/resume are cheaper, more contained mutations than update (no upstream body construction, no field validation beyond the path param), and per-route buckets are already how `listScheduledTasks`/`createScheduledTask`/`updateScheduledTask` are independently throttled today.

## Migration Plan

Purely additive: new optional DTO field, two new routes, one new lib prop set, one new i18n namespace. No data migration. Deploy as a single change; no phased rollout required since nothing existing changes shape. **Rollback:** revert the change's commits; `ScheduledTaskDto.isActive` being optional means any already-regenerated client code that ignored it before the revert continues to compile and run unchanged.

## Open Questions

1. **Does DIAL Scheduler expose an explicit active/paused field** (e.g. `status`, `is_active`, `paused`) on its schedule resource, distinct from `next_run_time`? Not confirmed in this repository. If yes, Decision 1's heuristic must be replaced before this heuristic-based version reaches production with real user data at scale.
2. **What does `POST .../schedules/{schedule_id}/pause` and `.../resume` return in their response body** — the updated schedule, a bare state object, or no body (`204`)? Decision 2 assumes "unknown/no body" and designs around a BFF follow-up `GET` specifically so this question doesn't block implementation; confirming it later could simplify the service (drop the follow-up `GET`) without changing the endpoint's external contract.
3. **Can DIAL Scheduler resume a completed/expired one-time (`date`) schedule at all**, or does calling resume on one error? Decision 4 assumes "no" and disables (not hides) the switch for that case; if confirmed otherwise, the disabled condition in `ScheduledTaskDetailView` narrows or is removed.
