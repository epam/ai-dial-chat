## Context

The Skills BFF API and its generated frontend wrapper already exist and are out of scope to change:

- `apps/chat/src/server-api/skills.api.ts:12-146` exports `listSkills`, `listSkillFiles`, `downloadSkill`, `downloadSkillFile`, `uploadSkill`, `uploadSkillFile`, `deleteSkill`, `deleteSkillFile`, `createSkillGroupingFolder`, `deleteSkillGroupingFolder`, all delegating to the generated `skillsApi` singleton (`apps/chat/src/server-api/api-client.ts:184`) — none call `fetch` directly.
- `uploadSkill(bucket, path, file: Blob, ifMatch?, signal?)` (`skills.api.ts:79-89`) maps to `PUT /api/v1/skills` (`apps/chat-api/src/skills/skills.controller.ts:297-373`), an **unconditional upsert**. `UploadSkillRequest`/`UploadSkillFileRequest` (`libs/chat-api-client/src/generated/src/apis/SkillsApi.ts:78-91`) only carry an optional `ifMatch`, forwarded as `If-Match` (`SkillsApi.ts:667-696`); there is no `If-None-Match` anywhere in the contract.
- Path safety is enforced server-side by `isValidSkillRelativePath()` (`apps/chat-api/src/skills/utils/skill-path.util.ts:49-71`): no absolute path, no Windows drive letters/backslashes, no control chars, no empty/`.`/`..` segments, no `.dial-resource`/`.dial-folder` segment, no `files`/`v` first segment. Whole-archive validation additionally requires a root `SKILL.md` (`SKILL_MANIFEST_FILE`, `skill-path.util.ts:10`) and rejects duplicate entry paths and archives over `SKILL_UPLOAD_MAX_FILES` (default 500) or per-file size over `SKILL_FILE_UPLOAD_MAX_BYTES` (default 20 MiB) — `apps/chat-api/src/skills/skills-upload.service.ts:49-58,187-244`.
- **The skill "name" has no dedicated server-side charset/length validator.** The whole-skill `path` query param is validated only by the generic `IsValidFilePath` decorator (`apps/chat-api/src/files/dto/file-path.validator.ts:7-29`: no leading `/`, no `..`, no `:;,={}&\"` chars, no invalid/encoded-separator percent-encoding) plus the reserved-segment checks above. The Figma copy "Lowercase letters and hyphens only, no spaces" is a **frontend UX convention**, not a backend contract — confirmed by reading the validator source, not assumed from the old archived proposal.
- Precedent for the app/library split: `libs/prompt-editor/` (package `@epam/ai-dial-prompt-editor`, `libs/prompt-editor/package.json:2,11-25`) is a pure presentational library — it owns only `PromptEditorValues` field state (`PromptEditor.tsx:68-89`) and a folder-picker sub-state, taking `initialValues`, `errors`, `folderActions`, `labels`, `onSubmit/onCancel/onRetry` as props (`prompt-editor-props.ts:25-150`). `apps/chat/src/pages/PromptEditor/PromptEditor.tsx` owns everything host-specific: feature gate via `useUiFeature(OverlayFeature.Prompts)` (`:57,74-78`), `returnUrl`/`promptId` query params (`:55-62`), i18n (`:53,321-353`), notifications (`:56,215-247`), API calls (`:22-30,168-263`), and post-action navigation (`:160-162,236`).
- Precedent for the Catalog entry point: `CatalogView.tsx`'s `createOptions` memo (`:918-982`) pushes plain `{ key, label, onClick }` items gated by `useUiFeature(OverlayFeature.*)` booleans (`:191-206`), each `onClick` building a `URLSearchParams` with a `ReturnUrl` back to `ROUTES.Catalog` and calling `navigate` (`:965-976` for the Prompt entry, which the new Skill entry mirrors).
- Precedent for a create-form's props-only contract: `libs/scheduled-tasks/src/components/ScheduledTaskCreateForm/ScheduledTaskCreateForm.tsx` explicitly documents (`:40-49`) that it "holds no state of its own and performs no routing, i18n, or network calls" — all `values`/`errors`/`labels` are host-supplied, `isSubmitting` disables both Cancel and Submit (`:80-84`), and the rich editor pane is lazily loaded under `Suspense`/`Spinner` (`:33-36,395-402`).
- Precedent for a Files-pane tree: `libs/publish-panel/src/components/PublishFoldersTree/PublishFoldersTree.tsx` wraps `DialFoldersTree` from `@epam/ai-dial-react-file-manager` rather than building its own tree DOM (`:2-6`), with controlled/uncontrolled `expandedPaths` (`:104-130`) and per-row context menus built as `DropdownItem[]` (`:252-271`) — the same `DropdownItem` model (`children?: DropdownItem[]`) that `CreateButton`'s `ButtonDropdown` already supports for nested menus, confirming no new dropdown component is needed anywhere in this change.
- UI-kit discovery (`mcp__ai-dial-ui-kit__searchEntity`/`getEntityDetails`) confirms: the 2.0 `MarkdownEditor` (loaded via `LazyMarkdownEditor()`) has a built-in toolbar with edit/preview/fullscreen switching, but its documented API exposes only `defaultPreview` (initial mode) — no controlled `mode`/`onPreviewChange`, `disabled`/`readOnly`, or `invalid`/`error` props are documented. `DialFoldersTree` (1.0, `@epam/ai-dial-react-file-manager` / re-exported under `@epam/ai-dial-ui-kit`'s FileManager category) already implements expand/collapse, selection, inline rename+validation, folder creation, and context menus via the shared `DropdownItem` model. `Input`/`Textarea` (2.0) carry `invalid`/`error`/`caption` props; `Dropdown`/`DropdownItem` (2.0) support recursive `children` for nested menus (not used here, since Skill is a direct action) but no documented ARIA attributes; `Button` variants have no documented `loading` prop.
- Mobile design facts (Figma nodes `603:9171` "Create skill - file details" and `604:12020` "Create skill - upload file from the device", file `huBIe1WnVCnB2mAKEnGjMW`, both 320px-wide mobile frames): the Files pane is **not** a drawer or separate route. It is an inline collapsible "Editing file" summary card at the top of the scrolling content — collapsed by default, showing only the selected file's icon/name and a chevron-down; tapping it expands in place (chevron-up) to reveal the "Files" heading, an "Add ▾" button, and the file tree inline, still within the single scrolling column. The page header on mobile has only Back + "Create skill" title (no inline Cancel/Create). Cancel/Create render as a `position: fixed`/sticky bottom bar ("Builder footer") spanning the viewport width, always reachable without scrolling. The "Add" button's dropdown includes an "Upload files from device" action that opens a bottom-sheet with a drag-and-drop zone ("Click here to upload", formats `.md`, `.zip`, `.skill`) — this is scoped to adding **supporting files** to the in-progress skill package (in scope per the proposal), not the Catalog-level "Upload a whole skill" action (out of scope).
- `openspec/changes/archive/2026-08-10-add-skills-bff-api/design.md`'s D1/D2/D4 decisions match the current code exactly (no divergence found) and are cited above directly from source rather than from that document, per the investigation requirement not to trust an old proposal's claims uncritically.

## Goals / Non-Goals

**Goals:**
- Ship a working "Create skill" page reachable from the Catalog's Create menu, using the existing Skills BFF contract unchanged.
- Establish `@epam/ai-dial-skill-editor` as a host-agnostic library with the same isolation guarantees as `libs/prompt-editor`.
- Give the user immediate, client-side feedback for the same path-safety rules the server enforces, without weakening server-side enforcement.
- Cover the full state machine (initial/dirty/submitting/success/failure) and the specific HTTP status codes `uploadSkill` can return.
- Meet WCAG 2.1 AAA and full RTL support for the new surface.

**Non-Goals:**
- Atomic create-only upload semantics (tracked as a backend follow-up, see Risks).
- Any Skill catalog listing/details/favorites/edit/delete/share/publish/"use in chat" UI.
- A general-purpose binary-file content editor for supporting files (users add/remove file and folder entries; they do not edit arbitrary binary content in-browser).
- A new `OverlayFeature.Skills` flag — per product decision, this ships unconditionally.
- The Catalog's "Upload" (whole-skill-from-device) sub-action — per product decision, "Skill" is a single direct Create action opening the instructions editor only.

## Decisions

### D1 — Skill is a direct Create option, not a nested menu
**Decision:** Add one `{ key: 'skill', label: t('catalog.create.skill'), onClick }` entry to `CatalogView.tsx`'s `createOptions` array (same shape as the existing `prompt` entry at `CatalogView.tsx:965-976`), navigating straight to `/skill-editor` with a `ReturnUrl=ROUTES.Catalog` param. No `DropdownItem.children` submenu.
**Rationale:** The Figma screenshot's nested "Write instructions"/"Upload" menu implies a second entry point (whole-skill file/ZIP upload from the Catalog) that this slice does not implement. Shipping a nested menu with only one working child, a disabled child, or a stub route would present a broken or misleading affordance. A single direct action matches the existing Prompt/Toolset/Custom-App entries' shape exactly and needs zero new dropdown-nesting code, since `ButtonDropdown`'s `children` support (already present at the `DropdownItem` model level) simply isn't exercised.
**Alternatives considered:** (a) Ship the nested menu with "Upload" disabled/"coming soon" — rejected, adds UI weight for a feature with no target route yet. (b) Ship "Upload" navigating to a stub — rejected, a stub route has no test surface and would need to be un-shipped later.

### D2 — No new `OverlayFeature` flag
**Decision:** The Skill Catalog entry and `/skill-editor` route are not gated by any `OverlayFeature` member; they render/route unconditionally, the same way `ROUTES.FileManager`'s create-folder action is unconditional today.
**Rationale:** Per product decision. Keeps the initial slice minimal — no enum addition, no `DEFAULT_ENABLED_UI_FEATURES` change, no embedding-host contract to design and document yet. This can be added in a follow-up once real usage patterns for the Skills surface are understood.
**Trade-off:** Embedding hosts that use `OverlayFeature` to compose their own UI (as they do for `Prompts`, `Toolsets`, `CustomApps`) cannot suppress just the Skill entry independently of the rest of the Catalog. Accepted given the low blast radius of one additive dropdown entry and one additive route.

### D3 — Create-vs-replace: preflight-list + accept-the-residual-race
**Decision:** Before calling `uploadSkill`, the `SkillEditor` page calls `listSkills({ bucket, path: <parent-folder-of-normalized-name> })` and checks whether an item with the normalized name already exists at that path. If it does, the page shows an inline "A skill with this name already exists" conflict error and does not call `uploadSkill`. If the preflight is clear, it proceeds to call `uploadSkill` with no `ifMatch` (a true create has no prior ETag to match). If the upload response nonetheless indicates the resource already existed (surfaced by `uploadSkill`'s success response carrying an `etag` for what the caller believed was a new resource — the API does not return a distinguishing status for "created" vs. "replaced" on success), the page cannot distinguish an overwrite after the fact; this is the accepted residual race documented in Risks.
**Rationale:** This is the only mechanism available with today's contract (see Context — no `If-None-Match`). Per product decision, this ships now rather than blocking on a backend change.
**Alternatives considered:** (a) Block this whole change on a backend `If-None-Match` addition — rejected per product decision, tracked as a follow-up API-gap item instead. (b) Skip the preflight entirely and let `uploadSkill` silently overwrite — rejected, worse UX than a best-effort check for the common (non-racing) case.

### D4 — Name normalization lives at the app boundary, not in the library
**Decision:** `libs/skill-editor` treats `name` as an opaque string field with host-supplied validation state (`invalid`/`error` passed in as props, mirroring `prompt-editor-props.ts`'s `errors`/`folderNameError` pattern). `apps/chat/src/pages/SkillEditor/SkillEditor.tsx` owns a `normalizeSkillName(input: string): string` function (lowercase, spaces/invalid-chars → hyphens, collapse repeats, trim leading/trailing hyphens) applied on submit, matching the design copy "We'll reformat automatically if needed." The normalized name is then run through the same **client-side mirror** of `isValidSkillRelativePath` (reimplemented as a small pure function in the app adapter, not imported from `apps/chat-api`) before constructing the upload path, so the user gets immediate feedback for the server's real constraints (no traversal, no reserved segments, etc.) rather than a generic regex the server doesn't actually enforce.
**Rationale:** Per the investigation, there is no authoritative "lowercase-hyphen-only" server contract to encode — only the generic path-safety rules. Normalizing client-side for UX consistency (readable, URL-safe skill folder names) while validating against the server's *actual* constraints (not an invented stricter one) avoids the library baking in a policy the backend doesn't enforce, and keeps `libs/skill-editor` free of any DIAL-specific storage-contract knowledge (library isolation rule).
**Alternatives considered:** Enforce the strict "lowercase + hyphens only" regex as a hard client-side rule — rejected, since it would reject valid server-accepted names (e.g. underscores, digits-first) with no server-side backing for the restriction; the design copy's wording ("we'll reformat automatically") already implies normalization-not-rejection, which the design honors.

### D5 — Files pane wraps `@epam/ai-dial-react-file-manager`'s `DialFoldersTree` directly
**Decision:** `libs/skill-editor`'s Files pane renders `DialFoldersTree` (from `@epam/ai-dial-react-file-manager`, already a workspace dependency) directly, translating the in-memory skill package (root `SKILL.md` + supporting files/folders) into `DialFile[]` items, rather than either (a) depending on `libs/publish-panel`'s `PublishFoldersTree` or (b) building a bespoke tree component.
**Rationale:** The instructions explicitly forbid coupling to `libs/publish-panel` (an app-domain-flavored library) while permitting direct use of `@epam/ai-dial-react-file-manager` "if its verified API and module boundaries make it appropriate." `DialFoldersTree` already ships expand/collapse, selection, inline rename+validation (useful for renaming supporting files, not `SKILL.md`), folder creation, and context menus via `DropdownItem` — exactly the behavior needed, with zero new tree logic to write or test from scratch. `PublishFoldersTree` is a thin app-specific wrapper around the same primitive; reusing it would require importing `libs/publish-panel`, violating the anti-coupling instruction and pulling in publish-domain concepts (`PublicationRule`, publish history) irrelevant here.
**Alternatives considered:** Build a bespoke tree — rejected, pure duplication of `DialFoldersTree`'s already-tested behavior with no benefit. Depend on `PublishFoldersTree` — explicitly disallowed by the proposal's instructions.

### D6 — Mobile: inline collapsible Files summary + sticky action footer, not a drawer
**Decision:** At the `mobile` breakpoint, the Files pane collapses into an "Editing file" summary row (selected file's icon + name + expand/collapse chevron) at the top of a single scrolling column; expanding it reveals the same file-tree content inline, above the Name/Description/Instructions fields, which remain below. The page header keeps only Back + "Create skill" title. Cancel/Create render in a `position: fixed` bottom bar spanning the viewport, so both actions stay reachable without scrolling regardless of scroll position — satisfying the proposal's "Create and Cancel must remain reachable without scrolling" requirement uniformly across breakpoints. At `desktop`, the existing two-pane (Files sidebar + main form) layout applies with Cancel/Create in the page header, per the supplied desktop screenshots.
**Rationale:** This supersedes the drawer/dedicated-view options originally floated before design — the actual Figma mobile frames (nodes `603:9171`, `604:12020`) show neither; they show an inline accordion pattern with a sticky footer. Building to the verified design instead of an invented pattern avoids rework.
**Implementation note:** The collapsible "Editing file" summary and its expand/collapse state belongs in `libs/skill-editor` (pure presentational state, like `PromptEditor`'s folder-picker sub-state); which breakpoint is active is resolved by the app adapter via `useBreakpoint`/`useIsMobile` (`apps/chat/src/hooks/breakpoint/useBreakpoint.ts`) and passed to the library as a `layout: 'stacked' | 'two-pane'` prop — the library itself does not read `window.innerWidth` or any responsive media state directly, since Tailwind's `mobile:`/`desktop:` breakpoint classes handle the visual reflow declaratively wherever possible, and the prop is reserved for the one behavioral difference (sticky footer vs. header-inline actions) that CSS alone can express via `position: fixed` at `mobile:` and static at `desktop:` without any JS branch at all — so in practice no JS `layout` prop may even be needed; confirm during implementation whether pure Tailwind responsive classes suffice before introducing the prop.

### D7 — Supporting-file "Add" scope for this slice
**Decision:** The Add control supports two in-memory operations on the skill package: "New file" (creates an empty supporting file at a user-chosen relative path) and "New folder" (creates an empty grouping folder), both validated against the same client-side path-safety mirror as D4 before being added to the tree. "Upload from device" (seen in the mobile bottom-sheet, node `604:12020`) is **included** in this slice as a third Add action: it reads local file(s) via a native file input, stores their `Blob` content in memory keyed by their validated relative path, and adds them to the tree — no upload to the server happens until the whole-skill `uploadSkill` ZIP call on submit. No in-browser content editor is provided for any supporting file's contents (per proposal Non-Goals) — a supporting file's content is either empty (New file) or exactly the uploaded blob's bytes (Upload from device), and users may remove (with a confirmation prompt, per Accessibility) any added supporting entry before submit.
**Rationale:** The mobile design explicitly renders the "Upload files from device" bottom sheet as part of the same "Add" interaction the desktop design's Add button exposes, so treating it as in-scope keeps both breakpoints' designs implementable as shown, and it requires no new backend capability — it is purely an in-memory addition to the ZIP that gets built on submit.

## Risks / Trade-offs

- **[Risk] The `listSkills`-preflight-then-`uploadSkill` create flow has a residual TOCTOU race** — two concurrent Create attempts for the same name can both pass the preflight and one will silently overwrite the other. → **Mitigation:** Document this explicitly in the Create-skill page's help text is out of scope for a technical mitigation; the functional mitigation is the inline conflict error path (D3) covering the common non-concurrent case, and a tracked backend follow-up item requesting `If-None-Match` support on `uploadSkillFolder`. This is an accepted, product-approved limitation for this slice, not a defect to silently ship.
- **[Risk] `MarkdownEditor`'s documented API has no controlled mode/disabled/invalid/aria props** — the design's requirement to disable the editor during submission and show an inline error cannot be verified against the UI kit's documented contract. → **Mitigation:** During implementation, re-verify the component's actual (not just documented) props via `getEntityDetails`/source before relying on an undocumented prop; if genuinely absent, wrap the editor in a disabled-overlay (pointer-events-none + aria-disabled on a wrapping element) and render the error via a separate `CaptionText`/`role="alert"` element below it rather than inside the editor, and file the missing props as a UI-kit gap rather than forking the component.
- **[Risk] `Button`/variant wrappers have no documented `loading` prop** — the submit button's "submitting" visual state has no confirmed built-in affordance. → **Mitigation:** Compose `Spinner` (confirmed props: `size`, `ariaLabel`) inside the button's `iconBefore` slot and set the native `disabled` attribute during submission (confirmed to work since `Button` renders a native `<button>` and forwards unrecognized props), rather than inventing a custom loading button component.
- **[Risk] `DialFoldersTree` is a 1.0 component with no listed 2.0 replacement** — mirrors this repo's existing choice in `PublishFoldersTree`, so it is not a new risk introduced by this change, but is worth flagging since a future UI-kit migration wave will need to revisit both consumers together.
- **[Trade-off] No feature flag (D2)** — accepted; see D2 rationale above.
