## Context

All chat scroll behavior lives in one place: `apps/chat/src/components/ConversationView/ConversationView.tsx`. It already has a working scroll subsystem — `containerRef`/`endRef`, a `scrollToBottom(instant)` helper (`container.scrollTo({ top: container.scrollHeight, ... })`), a `userScrolledRef` flag that pauses auto-follow once the user scrolls away from the bottom during streaming, an `isProgrammaticRef` guard so programmatic scrolls aren't mistaken for user scrolls, a `NEAR_BOTTOM_THRESHOLD = 80`px check that drives `isScrollButtonVisible`, and a `FabButton` rendered at `bottom-4 left-1/2 -translate-x-1/2` when the user isn't near the bottom. There is no virtualization (`react-virtuoso`/`react-window`) — all messages render inline in a flex column, and `ConversationView` has exactly one consumer, `apps/chat/src/pages/Conversation/Conversation.tsx` (no compare/playback surface reuses it).

Initial static analysis suggested the gap was purely "scrolls to the container's absolute bottom instead of near the top of the new message." That turned out to be a secondary issue. **Live browser debugging (via console diagnostics, since this app requires real DIAL Core auth and can't be driven end-to-end in an automated sandbox) found the actual root cause**: the message-list content div (`contentRef`, className `"mx-auto ... overflow-x-hidden px-6 pt-7"`, nested inside `containerRef`) set only `overflow-x-hidden` and left `overflow-y` unset. Per the CSS Overflow spec, when one axis is a non-`visible` value and the other is left `visible`, the browser computes the other axis as `auto` too — so this inner div silently became its own independent scroll container. Because an element that establishes its own scroll region no longer needs to grow past its allotted flex space (the classic `overflow != visible` fix for the flexbox `min-height: auto` trap), it absorbed all the vertical overflow internally instead of overflowing into its parent. The result: `containerRef` (the div with `role="log"`, explicit `overflow-y-auto`, and the one **all** the scroll code — old and new — calls `.scrollTo()` on) never actually overflowed (`scrollHeight === clientHeight` at every level up to `<html>`), so every `container.scrollTo(...)` call was a silent no-op. This was confirmed live: a capture-phase `scroll` event listener on `window` showed manual mouse-wheel scrolling firing on the inner `contentRef` div, not `containerRef`. This bug **predates this change** — it explains the original report just as much as the "wrong scroll target" issue, since neither the old nor the new code could ever move the real scroll position. Fix: drop `overflow-x-hidden` from the inner div (the outer `containerRef` div already clips horizontal overflow with its own `overflow-x-hidden`), which stops the inner div from computing `overflow-y: auto` and lets `containerRef` become the genuine, real scroll owner again. Verified live: sending a message in a long conversation now anchors near the top, and the scroll-down button now appears/disappears correctly.

The remaining, secondary gap is exactly what the original static analysis found: when the fix above is applied and `containerRef` is genuinely scrollable, the length-changed branch calls `scrollToBottom(false)`, scrolling to the container's absolute bottom rather than to the top of the newly sent message — which the anchoring work below addresses.

**Revision after a second round of live testing**: the first implementation kept a "pinned-to-bottom auto-follow" during streaming (instant `scrollToBottom` on every token, gated by a `userScrolledRef` flag that a `ResizeObserver`-driven check could flip back to `false`). In practice this flip happened almost immediately after every anchor — right after anchoring, the assistant placeholder is still short, so the space below the anchored message looks "near bottom" by the threshold check, which resumed auto-follow before the user could see more than a couple of streamed lines. Since this defeated both the near-top anchoring *and* directly reproduced the literal designer requirement ("does not auto-scroll line-by-line"), the pinned-auto-follow mechanism was removed entirely rather than patched — see revised Decision 2 below. This also removed the need for `userScrolledRef`/`isProgrammaticRef`/the `scrollend` guard entirely, which motivated extracting the whole subsystem into `useConversationScroll` (`apps/chat/src/hooks/conversation/useConversationScroll.ts`) — see Decision 6.

## Goals / Non-Goals

**Goals:**
- On send, scroll so the newly sent user message's top is positioned near the top of the visible viewport (not the container's bottom), leaving room below for the streamed response, and keep it there for the rest of that turn.
- Never force-scroll while a response is streaming, full stop — no pinned/conditional auto-follow of any kind. This is a literal reading of "does not auto-scroll line-by-line," confirmed against a prior implementation that kept a conditional auto-follow and was found (via live testing) to resume within the first couple of streamed lines every time, defeating the near-top anchor.
- Keep/refine the existing scroll-to-bottom button so it is visible whenever the user isn't at the bottom and there is content below (including the case where the user is reading an older message, or where a response has streamed past the fold). Clicking it performs a one-time scroll to the current bottom — it does not start a persistent "follow" mode; if more content streams in afterward, the button reappears once it passes the fold again.
- Apply the same "new message near top" positioning to other flows that restart the active turn the same way `handleSend` does (regenerate, edit-and-resubmit), so behavior is consistent, without over-generalizing into flows the designer didn't ask about (e.g. loading an existing conversation from history should keep landing at the bottom, not near-top).
- Extract all scroll behavior out of `ConversationView` into a dedicated `useConversationScroll` hook, so the component stays focused on rendering and the scroll mechanics are independently readable/testable.

**Non-Goals:**
- No virtualization of the message list (out of scope; current DOM-based rendering is retained).
- No change to the streaming transport/state management (`useConversationStream.ts`) — only how `ConversationView` (via the hook) reacts to the resulting `messages`/`isAssistantTyping` changes.
- No redesign of the `FabButton` visuals — reuse the existing button/aria-label (`ChatI18nKeys.ScrollToBottom`) as-is.
- No changes for conversations opened from history/navigation (initial load keeps scrolling to bottom, since there is no "just sent" message to anchor to).

## Decisions

0. **Fix the pre-existing CSS bug that made `containerRef` non-scrollable, before anything else.**
   The message-list content div (`contentRef`) had only `overflow-x-hidden` set, with `overflow-y` left implicit. Per the CSS Overflow spec, the browser then computes the unset axis as `auto` too, so that div silently became its own scroll container and absorbed all vertical overflow internally — starving the actual intended scroll owner (`containerRef`, `role="log"`, explicit `overflow-y-auto`) of any overflow to scroll. Every `.scrollTo()` call anywhere in this file (old code and this change's new code alike) was therefore a no-op in a sufficiently long conversation. Fix: drop `overflow-x-hidden` from `contentRef`'s div; `containerRef`'s own `overflow-x-hidden` already clips horizontal overflow one level up, so no horizontal-clipping behavior is lost.
   - Found via live debugging, not static reading — an earlier version of this change shipped without this fix and was verified only via `nx lint/test/build`, which cannot catch a real-browser layout bug (jsdom has no layout engine, so a unit test wouldn't have caught this either). Confirmed with three console diagnostics: (1) `scrollHeight === clientHeight` at every DOM level from `containerRef` up to `<html>`, (2) manual scroll left `containerRef.scrollTop` at `0`, (3) a capture-phase `window.addEventListener('scroll', ..., true)` showed the `contentRef` div, not `containerRef`, as the actual event target during manual scrolling.

1. **Scroll target on send = top of the new user message element, not container bottom.**
   Each rendered message is wrapped in a plain `<div ref={...}>` (needed because `ConversationMessageItem` isn't `forwardRef`-wrapped) tracked in a `Map<number, HTMLDivElement>` keyed by index. `handleSend`/`handleRegenerateMessage`/`handleEditMessage` are wrapped in `ConversationView` (`handleSendWithAnchor`, `handleRegenerateMessageWithAnchor`, `handleEditMessageWithAnchor`) to record the target index in a `pendingAnchorIndexRef` *before* calling through to the real handler — this is more robust than inferring "was this a fresh send" from `messages.length`/`isAssistantTyping` timing, since the component that knows user intent is the one that sets the anchor. The messages-effect checks and consumes this ref first, before its existing `isAssistantTyping`/`lengthChanged` branches. The scroll target itself is computed via `element.getBoundingClientRect().top - container.getBoundingClientRect().top` (relative to current `scrollTop`), not `offsetTop` — `offsetTop` resolves against the nearest *positioned* ancestor, which is unreliable here since message bubbles commonly use `position: relative` internally for absolutely-positioned action buttons.
   - *Rejected-then-adopted*: this decision originally rejected reserving bottom padding equal to the viewport height ("adds a large empty scroll region... complicates `scrollHeight`-based bottom detection"). Live testing proved that rejection wrong — see Decision 7, which reinstates a version of it as a hard requirement, not an optional nicety.
   - *Alternative considered*: infer "this is a fresh send" purely from `messages.length` changing while not yet streaming. Rejected after tracing `handleSend`'s state updates — `setConversation` (append) and the stream hook's `isStreaming` flip happen synchronously in the same handler with no `await` between them, so React 18 batches them into one render; by the time the effect runs, `isAssistantTyping` is already `true`, so a length-based heuristic can't reliably distinguish "just sent" from "mid-stream" without also special-casing regenerate/edit (which don't change `messages.length` the same way). Explicit anchor-setting at the call site sidesteps this entirely.

2. **Revised: remove pinned-to-bottom auto-follow during streaming entirely — never force-scroll while a response is generating.**
   The first implementation kept an instant `scrollToBottom(true)` on token arrival, gated by a `userScrolledRef` flag, reasoning that "pinned while at bottom" is standard mainstream chat behavior and satisfies "no forced line-by-line scroll" as long as it doesn't fight a user who scrolled away. Live testing disproved this: right after the near-top anchor, the still-short assistant placeholder made the position look "near bottom" by the `NEAR_BOTTOM_THRESHOLD` check, so the self-correcting logic (Decision 5, now removed) flipped `userScrolledRef` back to `false` within the first couple of streamed tokens — resuming forced auto-scroll almost immediately and defeating the anchor. The designer's rule ("does not auto-scroll line-by-line") is now implemented literally: the scroll position never moves once set, for the entire duration of a stream, regardless of where it happens to sit relative to the bottom.
   - *Alternative considered*: keep pinned auto-follow but stop the self-correction from re-triggering it for some cooldown window after anchoring. Rejected — a timing-based workaround is fragile (wrong for both very short and very long responses) and still contradicts the literal requirement; removing the mechanism entirely is simpler and matches what was actually asked for.

3. **Reuse the existing `NEAR_BOTTOM_THRESHOLD`/`isScrollButtonVisible` mechanism for "unseen content" instead of adding a separate unseen-content flag.**
   Because the container only grows at the bottom (new tokens append to the last message), "not near bottom" and "there is unseen content below" are equivalent for this UI — a separate dirty/unseen flag would be redundant state to keep in sync.
   - *Alternative considered*: track an explicit `hasUnseenContent` boolean toggled by the streaming effect. Rejected — duplicates what the scroll-position threshold already expresses and risks drifting out of sync with actual scroll position.

4. **Apply near-top anchoring to `handleRegenerateMessage` and `handleEditMessage` as well as `handleSend`, but not to initial conversation load.**
   Regenerate and edit-and-resubmit both restart the current turn's content and re-stream, the same shape as a fresh send; anchoring the associated user message near the top mirrors the send case and keeps behavior predictable across all three "start a new assistant turn" entry points. Initial load (opening a conversation from history) has no "just acted on" message to anchor to, so it keeps the current jump-to-bottom-on-load behavior. All three wrappers skip setting the anchor when `isAssistantTyping` is already `true`, mirroring the underlying handlers' own in-flight-generation guards — this avoids arming a stale anchor that would otherwise be consumed by an unrelated, later message update if the user clicks regenerate/edit while a different generation is already streaming (a no-op in the underlying handler).

5. **Removed** — superseded by Decision 2. There is no more "user scrolled away" state to track: the messages-effect only ever does two things — consume an armed anchor (one-time), or scroll to bottom on a non-streaming length change (conversation load / delete). Streaming never triggers a scroll on its own. The scroll-to-bottom button's visibility is now computed purely from current scroll position vs. content size (`updateScrollButtonVisibility`), independent of streaming state, via both a `scroll` listener and a `ResizeObserver` on the content box.

6. **Extract the scroll subsystem into `useConversationScroll` (`apps/chat/src/hooks/conversation/useConversationScroll.ts`).**
   Once auto-follow was removed, the remaining logic (anchor arming/consumption, `performScroll`, button-visibility tracking, the message-ref map) had no more dependencies on `ConversationView`'s other concerns (attachments, deployments, chat settings, etc.) beyond `messages`/`isAssistantTyping`, making it a clean extraction. The hook takes `{ messages, isAssistantTyping }` and returns the two refs to attach (`containerRef`, `contentRef`), a `setMessageRef` callback ref, `isScrollButtonVisible`, a one-time `scrollToBottom()`, and `armAnchor(index)`. `ConversationView` still owns *which* index to arm for each of send/regenerate/edit (that mapping is action-specific business logic, not scroll mechanics) and calls `armAnchor` from its own thin wrapper handlers before delegating to the real `onSend`/`onRegenerateMessage`/`onEditMessage`.
   - The `handleEditMessageWithAnchor` wrapper additionally guards with `isMessageChanged` (`apps/chat/src/utils/message-utils.ts`, the same check `handleEditMessage` uses internally) before arming — `handleEditMessage` is a no-op when the submitted text/attachments are unchanged, and arming unconditionally left a stale anchor index that would later fire on an unrelated messages update (e.g. a delete or a rating change), since no messages update ever arrives to consume it from the no-op edit itself. Regenerate doesn't need the equivalent check: it has no "nothing changed" no-op path — it always re-triggers generation once its structural guards pass.

7. **Reserve just enough scroll room to make the anchor reachable, via a frozen `min-height` on a wrapper — not a JS-driven "shrinking spacer".**
   Live testing after Decision 6 found the near-top anchor still landing near the *bottom* of the viewport in a long conversation. Root cause: `container.scrollTo({ top })` clamps to `scrollHeight - clientHeight`. Right after sending, the assistant placeholder is empty, so `scrollHeight` barely exceeds "everything up to and including the new user message" — the computed target (which assumes there's room to push that message all the way to the top) exceeds the clamp ceiling, and the browser silently scrolls to its maximum instead, which sits close to the bottom.
   - **First attempt, reverted**: an always-present spacer element, kept at `containerRef`'s `clientHeight` via a `ResizeObserver` for the container's whole lifetime. Worked functionally, but live testing immediately flagged a UX regression — a fully-scrolled, idle conversation always showed a large empty gap below the last message.
   - **Second attempt, reverted**: a temporary spacer element sized only at anchor time, then explicitly shrunk in a separate `ResizeObserver` callback (`shrinkSpacerForGrowth`) by however much `contentRef` had grown since. This reintroduced a *different*, worse bug: because the content-growing DOM mutation and the spacer-shrinking JS callback happen in two separate steps (`ResizeObserver` callbacks run asynchronously, after the browser has already applied and laid out the DOM change that triggered them), `scrollHeight` transiently *increased* (content grew, spacer hadn't shrunk yet) and then *decreased* (spacer caught up) on every content update. Whenever the second step dropped `scrollHeight` below the already-scrolled position, the browser clamped `scrollTop` down to fit — visibly yanking the anchored message away from the top mid-stream, repeatedly, as the response continued generating.
   - **Third attempt, reverted**: `contentRef` nested inside a `wrapperRef` div, with `wrapperRef.style.minHeight` frozen at anchor time (`contentRef`'s height then + `container.clientHeight`), relying on CSS flex layout to shrink the gap as `contentRef` grew, with no JS shrink step. This *should* have been race-free in principle, but shipped with a latent bug — `contentRef` had been left with a stray `flex-1` class from the pre-refactor structure, which (combined with `wrapperRef`'s frozen `min-height` and `contentRef` being its only child) caused `contentRef` itself to be flex-*stretched* to fill the reserved height, corrupting its own measured size. Live testing still showed a jump, roughly once the response passed one viewport's worth of text — evidence that this corner of flexbox (an auto-height flex container with `min-height` plus a single `flex-grow` child whose own content need can exceed that minimum) doesn't resolve as cleanly/predictably across engines as a clean model would suggest, and is not worth continuing to reason about blind.
   - **Fourth attempt, shipped with a regression**: dropped the CSS-flex approach entirely in favor of something verifiable by direct inspection — a plain spacer element, sibling of `contentRef` (both direct children of `containerRef`, `contentRef` with no `flex-1`), with an *explicit* pixel height computed and applied in a `useLayoutEffect` keyed on `messages` (not a `ResizeObserver`) — synchronous, before paint, in the same commit that rendered the content growth. This eliminated the race from attempt 2. But live testing found the anchor itself broken again (message landing at the bottom, no reserved space at all) — worse than attempt 3. Root cause, found via a real isolated reproduction (a temporary route mounting the actual hook with fake data, since a simplified test harness that didn't mirror the container's `display:flex` structure passed cleanly and gave false confidence): `containerRef` is `flex flex-col`, so the spacer — despite having no explicit `flex-*` class, meaning the CSS default `flex: 0 1 auto` — was subject to flex-shrink. Once `contentRef`'s real content (which has no explicit height cap and is protected from shrinking below its own content size) already exceeded `containerRef`'s own determined height by thousands of pixels — the normal, expected state for a long conversation — the flexbox algorithm had a large shrink deficit to distribute. `contentRef` refused to shrink (protected by its content), so *all* of it landed on the spacer, collapsing its rendered height to `0` regardless of its explicit inline `style.height`. Confirmed directly: `spacer.style.height` read back as the correct value, but `getComputedStyle(spacer).height` and `getBoundingClientRect().height` were both `0`.
   - **Final design**: identical to the fourth attempt, plus `shrink-0` (`flex-shrink: 0`) on the spacer, so it can never be forced to shrink below its explicitly-set height regardless of how large a deficit the flex algorithm needs to distribute elsewhere. Added `shrink-0` to `contentRef` too, for the same protection made explicit rather than relying solely on its content-based automatic minimum. Re-verified with the same live isolated-hook reproduction: spacer's actual rendered height now matches its inline style exactly through the full lifecycle (anchor → shrink → fully consumed → reset), and `scrollTop` never moves on its own at any point.
   - `scrollToBottom()` and `updateScrollButtonVisibility()` measure against `contentRef`'s own bounding rect (never inflated, since it has no `flex-grow`), so neither is affected by the spacer's current size.
   - This is a version of the alternative rejected in Decision 1 ("reserve bottom padding equal to the viewport height") — that rejection was wrong in substance (some reserved room is unavoidable given how `scrollTo` clamping works) but right that a *permanent* reservation is undesirable; the fix is to make the reservation temporary, self-consuming, and computed synchronously within the same commit as the content change that necessitates recomputing it.
   - **Process note**: this bug specifically evaded a same-round isolated test because that test's harness used plain inline styles without `display: flex` on the scroll container, omitting the exact structural detail (`containerRef` being a flex column) that triggered the flex-shrink behavior. When reproducing a layout bug in isolation, mirror the real component's actual CSS display/layout mode, not just its visual appearance — a simplified equivalent can silently drop the specific mechanism causing the bug.

8. **Move the message column's `max-w-[760px] mx-auto` from `contentRef` to `containerRef` (the actual scroll element).**
   Before the Decision 0 CSS fix, the buggy inner scroll container happened to be the narrow, centered content column, so its native scrollbar visually hugged the message text. After fixing the real scroll owner to be `containerRef` (which spans the full chat panel width), the scrollbar moved to the panel's edge — flagged by live testing as a regression from the (accidentally narrow) prior look. Moving the width constraint up to `containerRef` restores a scrollbar that hugs the message column, which is also how Claude.ai's own scrollbar behaves (vs. e.g. ChatGPT's, which spans the full pane) — a legitimate, common pattern either way. `contentRef` keeps its internal padding/gap classes but no longer needs its own width constraint, since it now simply fills `containerRef`'s (now-narrower) width.

## Risks / Trade-offs

- [Risk] Computing the scroll target right after a state update can race with layout if the DOM hasn't painted the new message yet → [Mitigation] Perform the scroll in the same `useEffect` keyed off `messages` (post-commit, as today), where `containerRef`/message refs already reflect the latest DOM, consistent with how `scrollToBottom` already reads `scrollHeight` after commit.
- [Risk] Very short first message: anchoring the user message near the top could push the (nearly empty) assistant placeholder off-screen below the fold, leaving a sparse view until content streams in → [Mitigation] Acceptable per design brief ("as the response streams in below it"); no auto-follow means the sparseness is temporary and resolves as content renders in place, without ever moving the scroll position out from under the user.
- [Risk] Because nothing ever auto-scrolls during streaming, `scrollTop` never changes on its own as content grows, so no native `scroll` event fires to recompute the scroll-down button's visibility → [Mitigation] A `ResizeObserver` on the message-list content box (`contentRef`) calls the same `updateScrollButtonVisibility()` used by the `scroll` listener whenever the content's size changes, independent of whether an actual scroll occurred.
- [Risk] Arming an anchor for an action that turns out to be a no-op (edit-and-resubmit with unchanged text, or regenerate/edit while another generation is already in flight) leaves a stale index that could be consumed by a later, unrelated `messages` update (e.g. a delete or a rating change) → [Mitigation] `handleEditMessageWithAnchor` checks `isMessageChanged` before arming (mirroring `handleEditMessage`'s own no-op condition); all three wrappers already skip arming when `isAssistantTyping` is `true`, matching the underlying handlers' in-flight-generation guards.
- [Risk] Setting the spacer's height imperatively via a DOM ref (bypassing React state) is an unusual pattern that could drift out of sync if some other code path also touches `spacerRef.current.style` → [Mitigation] Only the anchoring/shrink `useLayoutEffect` (set/recompute) and the `isAssistantTyping → false` `useLayoutEffect` (clear) ever write to it; the element has no other purpose and is `aria-hidden`.
- [Risk] Reacting to content growth with a separate, *deferred* size adjustment causes a visible scroll jump: if the growth and the compensating shrink happen in two distinguishable steps, the browser can observe (and clamp `scrollTop` against) the intermediate, transiently-too-tall state → [Mitigation] Confirmed via two failed attempts (a `ResizeObserver`-driven shrink, and a CSS `min-height`+`flex-grow` combination that turned out to depend on flexbox resolution behavior that isn't reliably predictable across engines for this specific shape). Final fix: recompute the spacer's explicit pixel height synchronously in a `useLayoutEffect` keyed on `messages`, which is guaranteed by React to run before paint, in the same commit that rendered the content growth — there is no separate step for the browser to observe an intermediate state in.
- [Risk] A stray `flex-1` class left on `contentRef` during the third attempt (Decision 7) caused it to be flex-stretched to fill the reserved space, corrupting the measurement used by `updateScrollButtonVisibility`/`scrollToBottom` → [Mitigation] Removed in the final design; `contentRef` now has no flex-grow of its own and sizes purely to its real content, verified by re-running the full quality-gate suite after the change.
- [Risk] Any bare flex item without an explicit `flex-shrink` is subject to being compressed when its siblings' combined natural size exceeds the flex container's own determined size — for `containerRef` (a scroll container whose content routinely, and correctly, exceeds its own height), this is the *normal* state, not an edge case, so the spacer needs `flex-shrink: 0` unconditionally, not just "when it matters" → [Mitigation] `shrink-0` applied to both the spacer and `contentRef`; confirmed via live reproduction that the spacer's `getBoundingClientRect().height` now matches its explicit inline `style.height` at every stage of the anchor/shrink/reset lifecycle, not just that the style attribute was set correctly (which can silently diverge from the actual rendered size under flex-shrink).

## Migration Plan

Purely additive/behavioral change confined to `ConversationView.tsx`; no data migration. Roll out as a normal frontend change; rollback is a straight revert since no persisted state or API contract changes.
