## Context

`PromptService` (866 lines) backs `PromptController` for four distinct concerns: low-level DIAL Core prompt-resource I/O (`getPromptMetadataItem`, `savePromptResource`, `readPromptByPath`, `listPromptMetadataItems` — all `private`, and all used across the other three concerns), personal-bucket prompt CRUD + listing (`listPrompts`, `getSharedPrompts`, `getPrompt`, `createPrompt`, `updatePrompt`, `deletePrompt`), organisation/public-bucket reads (`listPublicPrompts`, `getPublicPrompt`), and folder lifecycle + single-prompt moves (`createFolder`, `renameFolder`, `deleteFolder`, `movePrompt`). It also carries ~130 lines of module-level pure path/mapping helpers (`folderIdFromId`, `nameFromId`, `isSentinelPath`, `urlToPromptPath`, `metadataItemToPromptPath`, `mapPromptToResponse`, `deriveFolders`) and several internal-only types.

The backend already has three precedents for this kind of split: `2026-07-16-split-files-service`, `2026-08-07-split-conversation-service`, and `2026-08-07-split-deployments-toolsets-services` (all archived). This design reuses that facade + focused-sub-services pattern, with one structural difference from the deployments/toolsets precedent: there, the module-level helpers needed by multiple sub-services were pure functions with no `this` dependency, so they moved straight into a stateless `utils/*.util.ts` file. Here, the equivalent shared logic (`getPromptMetadataItem`, `savePromptResource`, `readPromptByPath`, `listPromptMetadataItems`) is **not** pure — every one of those four helpers calls `this.dialClient`/`this.logger` — so it cannot become free functions without threading those two dependencies through every call site as parameters. This design instead promotes them to a fourth injectable sub-service (`PromptsResourceService`) that the other three depend on, the same way `ToolsetsMutationService`/`ToolsetsAuthService` already depend on `ToolsetsListingService` for `getUserBucket`/`invalidateCaches` in the prior split.

## Goals / Non-Goals

**Goals:**
- Break `PromptService` into `PromptsResourceService` (shared DIAL Core resource I/O), `PromptsPersonalService` (personal CRUD/listing), `PromptsPublicService` (organisation/public reads), `PromptsFolderService` (folder lifecycle + move), each independently unit-testable, plus a facade under ~200 lines.
- Move the module-level pure path/mapping helpers and shared internal types into a dedicated `utils/prompt-mapper.util.ts`.
- Split the corresponding 762-line spec file into per-sub-service spec files, mirroring the new folder structure.

**Non-Goals:**
- No REST contract, DTO, or OpenAPI changes — identical request/response shapes, status codes, and structured logging.
- No frontend changes.
- No behavior changes to any of the four concerns (e.g. `renameFolder`'s serial-conflict-check-then-parallel-move sequence, `movePrompt`'s read-write-delete sequence) — this is a pure structural move.

## Decisions

**Facade + bound-property delegates, matching the prior three splits.** `PromptService` keeps its current public method names/signatures and delegates via bound property references for pure 1:1 forwards (`listPrompts = this.personalService.listPrompts.bind(this.personalService)`), with explicit method bodies only where genuine glue is needed (none are expected here — every controller-facing method maps 1:1 onto exactly one sub-service). This keeps `PromptController`'s constructor injection and every call site unchanged.

**A fourth "resource" sub-service, not a stateless util, for the shared low-level helpers.** Unlike the deployments/toolsets split, `getPromptMetadataItem`/`savePromptResource`/`readPromptByPath`/`listPromptMetadataItems` are impure (DIAL Core calls via `this.dialClient`, logging via `this.logger`) and are each called from at least two of the other three concerns (e.g. `listPromptMetadataItems` is used by `listPrompts`, `listPublicPrompts`, `renameFolder`, and `deleteFolder`). Promoting them to `PromptsResourceService` — injected by `PromptsPersonalService`, `PromptsPublicService`, and `PromptsFolderService` — avoids either duplicating DIAL Core I/O three times or forcing an artificial "which one owns it" choice. The four methods become `public` on `PromptsResourceService` since they are now called cross-service.

**Boundaries follow the four call shapes already implied by the source file's own section comments.** The source already groups its methods under `/* Personal prompt CRUD */`, `/* Organisation (public bucket) prompts */`, and `/* Folder operations */` block comments, with the low-level helpers in an unlabeled `/* private helpers */` block above them — this design formalizes those four groups as the sub-service boundaries rather than inventing a new grouping. `movePrompt` stays in `PromptsFolderService` (not `PromptsPersonalService`) because it is grouped there in the source and its `targetFolderId` semantics are folder-relative, matching `renameFolder`/`deleteFolder`'s folder-path-driven logic more closely than personal-bucket CRUD's per-prompt logic.

**Pure module-level helpers and shared types move to `utils/prompt-mapper.util.ts`.** `folderIdFromId`, `nameFromId`, `isSentinelPath`, `urlToPromptPath`, `metadataItemToPromptPath`, `mapPromptToResponse`, and `deriveFolders` have no `this` dependency and are needed by multiple sub-services (e.g. `mapPromptToResponse` is needed by `PromptsResourceService.readPromptByPath` and directly by `PromptsPersonalService.getPrompt`/`PromptsFolderService.movePrompt`). The `PUBLIC_BUCKET` constant and the internal result-shape types (`PromptPayload`, `PromptMetadataListResult`, `PromptReadResult`, `PromptWriteResult`, `SharedResourceItem`, `SharedResourcesResult`) move alongside them since they are referenced by the same call sites.

**Migrate helpers-first, then service-by-service.** Order: extract pure mapping helpers/types to `utils/` (zero behavior risk, pure move) → create `PromptsResourceService` from the four private I/O helpers → split `PromptsPersonalService`/`PromptsPublicService`/`PromptsFolderService` out of the remaining class body, each injecting `PromptsResourceService` → reduce `PromptService` to a facade → facade cleanup. This mirrors the deployments/toolsets design's "helpers-first" sequencing, adjusted for the fact that here the shared piece is a sub-service (created second) rather than a util (created first and never revisited). Each step is verified with `npm exec nx test chat-api` before the next.

## Risks / Trade-offs

- [Spec relocation drops or duplicates assertions] Moving `describe` blocks from the single 762-line spec file into four per-sub-service files risks silently losing setup/mocks. → Mitigate by relocating blocks verbatim first (no test-logic changes in the same step as the move), running the full suite immediately after each relocation, and only refactoring test structure in a later, separate pass.
- [Over-widening `PromptsResourceService`'s public surface] Making all four low-level helpers `public` (from `private`) slightly widens what `PromptsPersonalService`/`PromptsPublicService`/`PromptsFolderService` can call, compared to the monolith where they were only reachable from sibling methods on the same class. → Accept this: it is the same trade-off already made for `ToolsetsListingService.getUserBucket`/`invalidateCaches` in the prior split, and the alternative (four private duplicates) is strictly worse for maintainability.
- [DI wiring gaps at module registration] Missing a provider registration for a new sub-service throws at Nest bootstrap rather than at a call site. → Mitigate by running `npm exec nx build chat-api` (fails fast on DI resolution errors) after each provider-registration change.
- [Hidden coupling not obvious from the four documented sections] A private helper might be used across the proposed boundaries in a way not obvious from the source file's own section comments. → Mitigate by grepping every private method/field name across the whole file before assigning it to a sub-service.

## Migration Plan

Same order as `proposal.md`'s "What Changes"/this design's Decisions: extract pure mapping helpers and shared types to `utils/prompt-mapper.util.ts` → create `PromptsResourceService` → split `PromptsPersonalService` → split `PromptsPublicService` → split `PromptsFolderService` → reduce `PromptService` to a facade → facade cleanup/dead-code removal → verification. Each step is a separate commit/slice gated on `npm exec nx test chat-api`, `npm exec nx lint chat-api`, and (for DI/module changes) `npm exec nx build chat-api`. No feature flag or staged rollout is needed since there is no external behavior change — rollback is a straight revert of the offending slice's commit.

## Open Questions

- Should `PromptsResourceService`'s four methods be renamed now that they're public API surface for three other services (e.g. `getPromptMetadataItem` → `getMetadataItem`), or keep their current names unchanged to minimize diff noise? Default to keeping current names — renaming is a separate, optional cleanup that doesn't need to block this split.
