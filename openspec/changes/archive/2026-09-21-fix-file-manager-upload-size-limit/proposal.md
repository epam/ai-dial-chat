## Why

GitHub issue [#6083](https://github.com/epam/ai-dial-chat/issues/6083): a file larger than 512 MB selected in **File Manager → New → Upload files** is reported as uploading "successfully," where the maintainer expects the same rejection the Clip-icon **Upload from device** flow gives ("Max file size up to 512 Mb...").

Investigation found the picture is more specific than "no size check exists":

- The backend already enforces a configurable limit: `FILE_UPLOAD_MAX_BYTES` (`apps/chat-api/src/config/environment.config.ts:545`, default `536_870_912` = 512 MB) is wired into `MulterModule` for `POST /api/v1/files` (`apps/chat-api/src/files/files.module.ts:25`), which correctly returns `413 Payload Too Large` for an oversized file. A separate `ARCHIVE_UPLOAD_MAX_BYTES` covers the archive-extraction upload endpoint. So the maintainer's ask ("add env variable for max file size in bytes since it is configurable") is **already partially met on the backend** — it just isn't surfaced to the frontend or reused consistently.
- The client-side handling of that 413 in the shared upload path (`useDialFileUploadBatch`, used by both the standalone File Manager page and the attach modal) is also already correct: `createUploadFileWithProgress` (`libs/chat-hooks/src/files/create-upload-file-with-progress.ts:67-93`) rejects on any non-2xx status, and the batch worker (`useDialFileUploadBatch.ts:271-304`) only marks a file `Completed` inside the `try` block after a successful `await` — a rejected upload always lands in `Failed`, never `Completed`. No swallowed-error path was found.
- What genuinely does not exist anywhere is a **client-side pre-upload size check**. Neither `useDialFileUploadBatch`'s `onValidateUpload` (unconditionally returns `{ valid: true }`, `useDialFileUploadBatch.ts:356-368`) nor the Clip-icon native `<input type="file">` path (`libs/conversation-input/src/components/Input/Input.tsx` → `useAttachments` → `useAttachmentUpload`, no size-related code at all) reject an oversized file before sending it. Today, an oversized file always attempts the full upload over the wire and only fails after the transfer, relying entirely on the eventual 413. For a 512 MB+ file this is slow, and the exact "Max file size up to 512 Mb..." message the issue describes does not exist anywhere in current source or in `node_modules/@epam/ai-dial-react-file-manager` — it is not a real, currently-shipping message this fix can "restore."
- The only existing client-side size gate, `isRowSelectable` in `apps/chat/src/components/DialFileManagerModal/DialFileManagerModal.tsx:254-260`, blocks selecting an **already-listed** file from storage using a hardcoded `MAX_SELECTABLE_FILE_SIZE_BYTES` constant (`apps/chat/src/constants/files.ts:1-2`, also 512 MB) — it never runs against a freshly-picked local file, and `DialFileManagerPage.tsx` (the standalone page) doesn't pass this limit at all, so existing-file selection there is entirely unrestricted.

Given this, the fix is: add a proactive pre-upload size check to every upload entry point, driven by the backend's already-configurable `FILE_UPLOAD_MAX_BYTES` (exposed to the frontend via client-config, replacing the separate hardcoded constant so the two never drift apart), and close the standalone-page gap in existing-file selection.

## What Changes

- Surface the existing `FILE_UPLOAD_MAX_BYTES` backend value to the frontend, following the `TRANSCRIBE_SIZE_LIMIT_BYTES` → `transcribeSizeLimitBytes` precedent (`config-registry-and-env-provider`, `client-config-endpoint`, `app-config-context`):
  - Register `attachments.maxFileSizeBytes`: `type='config'`, `valueType='number'`, `visibility='client'`, `envVar='FILE_UPLOAD_MAX_BYTES'` (reusing the variable that already gates the Multer limit — no new env var).
  - `GET /api/v1/client-config` returns it as `config.maxAttachmentFileSizeBytes`.
  - `AppConfigContext` exposes `maxAttachmentFileSizeBytes` (default 512 MB before the config loads, matching Multer's own default).
- Wire the pre-upload size check for the File Manager path through the `@epam/ai-dial-react-file-manager` ui-kit component's own **existing, built-in** `maxFileSize`/`uploadValidationMessages.oversizedFiles` mechanism — discovered during implementation to already exist and already do exactly this, just never connected. `DialFileManagerShell` and `FileManagerAttachModal` (`libs/chat-shared`) gain two new pass-through props (`maxFileSize`/reusing the existing `maxSelectableFileSize` value, and a translated `oversizedUploadMessage` string) forwarded to `<DialFileManager>`. No change to `useDialFileUploadBatch`/`onValidateUpload`/`useDialFileManager` is needed — an oversized file is rejected by the ui-kit before either is ever called.
- Add an equivalent pre-upload size check to `useAttachmentValidation` (`libs/chat-hooks`) for the Clip-icon / drag-and-drop / paste path, mirroring its existing MIME-type check shape (new `AttachmentValidationErrorReason.FileTooLarge`, structured event, no translated text inside the lib).
- Wire both checks at the app level (`apps/chat`) to new i18n-driven notifications: a new `attachments.fileTooLarge.*` pair for the Clip-icon path (following the existing `attachments.unsupportedType.*` pattern) and a new `dialFileManager.*` notification pair for the File Manager path (following the existing `dialFileManager.uploadFailed` pattern).
- Fix `DialFileManagerPage` (`apps/chat/src/pages/DialFileManagerPage/DialFileManagerPage.tsx`) to forward the size limit to `DialFileManagerShell`, matching what `DialFileManagerModal` already does for existing-file selection — today the standalone page passes no size context at all.
- Replace `MAX_SELECTABLE_FILE_SIZE_BYTES`'s role as the source of truth with the `AppConfig`-sourced `maxAttachmentFileSizeBytes` everywhere it's currently used; the constant becomes only the pre-config-load default.

**Non-goal:** Making the separate archive-extraction limit (`ARCHIVE_UPLOAD_MAX_BYTES`) frontend-configurable or pre-checked. A file destined for archive extraction is only classified as such after upload begins (by content, not by pre-selection), so it cannot be pre-checked against a different threshold without first reading the file; this proposal pre-checks against the plain-file limit only, matching the issue's concrete repro (a single oversized file, not a zip).

**BREAKING**: None. Uploads under the configured limit are unaffected. The default pre-check value matches today's already-enforced backend default, so behavior changes only for previously-unvalidated oversized uploads (the bug) and for deployments that set `FILE_UPLOAD_MAX_BYTES` to a non-default value (those deployments' frontends now correctly reflect that value instead of the hardcoded 512 MB constant).

## Capabilities

### New Capabilities

- `attachment-file-too-large-error`: Validates the Clip-icon / drag-and-drop / paste attachment flow's file size against a configurable maximum and shows one notification per batch, mirroring the existing `attachment-unsupported-type-error` capability's structure (structured reason in the lib, translated notification at the app level, no upload request for the rejected file).

### Modified Capabilities

- `config-registry-and-env-provider`: add an `attachments.maxFileSizeBytes` registry entry (`type='config'`, `valueType='number'`, `visibility='client'`, `envVar='FILE_UPLOAD_MAX_BYTES'`, `defaultValue=536870912`) — reusing the existing backend env var, not introducing a new one.
- `client-config-endpoint`: `GET /api/v1/client-config` response gains `config.maxAttachmentFileSizeBytes`.
- `app-config-context`: `AppConfigState.config` gains `maxAttachmentFileSizeBytes: number`, following the `transcribeSizeLimitBytes` field's default/loading/error semantics.
- `chat-hooks-attachment-validation`: `useAttachmentValidation` accepts an optional `maxFileSizeBytes` and checks the attachment's file size against it, emitting `AttachmentValidationErrorReason.FileTooLarge` through the existing `onValidationError` callback shape.
- `file-manager-upload`: validation section and the "File size exceeded" scenario rewritten to describe pre-upload rejection happening inside the ui-kit's own `maxFileSize` check, ahead of `onValidateUpload`/`onUploadFiles` — which themselves require no code change — with the pre-existing server-side 413 enforcement remaining as the backing safety net for any file that bypasses it.
- `file-manager-standalone-page`: `DialFileManagerPage` forwards `maxSelectableFileSize` and a translated oversized-upload message (sourced from `AppConfig`) into `DialFileManagerShell`, closing the gap where the standalone page passed no size context at all for existing-file selection, and newly engaging the ui-kit's own pre-upload check for new uploads.
- `dial-file-manager-attach-validation`: the "File-size cap in grid selection" requirement's `maxSelectableFileSize` source changes from the hardcoded `MAX_SELECTABLE_FILE_SIZE_BYTES` constant to the `AppConfig`-sourced `maxAttachmentFileSizeBytes` (constant retained only as the pre-load default); a new requirement adds the same value, plus a translated message, as the ui-kit's `maxFileSize`/`uploadValidationMessages.oversizedFiles` props for new uploads.

## Impact

- **Backend** (`apps/chat-api`): `config-registry.constants.ts` (new registry entry reusing the existing `FILE_UPLOAD_MAX_BYTES` env var — `environment.config.ts` itself is unchanged, since that variable is already declared), `AppConfigService`/client-config DTO (new response field). No new endpoint, no DB/storage change, no new env var.
- **Frontend context** (`apps/chat`): `AppConfigContext.tsx` (new config field + default), `ConversationView.tsx` / `NewConversationComposer.tsx` (source `maxSelectableFileSize` from `AppConfig` instead of the constant), `DialFileManagerPage.tsx` (forward the new prop), `apps/chat/src/i18n/locales/en.json` (new `attachments.fileTooLarge.*` keys and a File-Manager-side notification key pair), `apps/chat/src/components/DialFileManagerModal/*` (notification wiring for the new `onNotification` reason).
- **Libs**: `libs/chat-shared/src/file-manager/DialFileManagerShell/DialFileManagerShell.tsx` and `libs/chat-shared/src/file-manager/FileManagerAttachModal/FileManagerAttachModal.tsx` (two new pass-through props forwarded to `<DialFileManager>`'s existing `maxFileSize`/`uploadValidationMessages`), `libs/chat-hooks/src/attachment/useAttachmentValidation/useAttachmentValidation.ts`, `libs/chat-shared/src/types/attachment.ts` (new `AttachmentValidationErrorReason` member). All lib changes accept the byte limit and translated strings as caller-supplied parameters — no lib reads env vars, `ConfigService`, or app config directly, per the library isolation rule in `AGENTS.md`.
- **i18n**: new user-visible strings for both the Clip-icon rejection notification and the File Manager upload-rejection notification (English key/value pairs at minimum, following existing locale-file conventions).
- **No breaking API/DTO removal.** Purely additive fields and an additive, opt-in validation parameter; omitting `maxFileSizeBytes` anywhere preserves today's pre-check-free (but still server-enforced) behavior, so a partial rollout degrades to the current state rather than to a new failure mode.

**Alternatives considered:** (a) Add a brand-new `MAX_ATTACHMENT_FILE_SIZE_BYTES` env var as the maintainer's comment literally suggests — rejected because `FILE_UPLOAD_MAX_BYTES` already exists, already backs the real server-side enforcement, and a second independently-configured limit would let the frontend pre-check and the backend's actual cap silently diverge. (b) Fix only the File Manager path and leave the Clip-icon path as-is, matching the issue's literal title — rejected because the issue's own "Expected" section demands parity with the Clip-icon flow, and that flow turns out to have the identical gap (no pre-check at all); leaving it would reopen an equivalent bug report immediately. (c) Rely solely on the existing server-side 413 and add no client-side pre-check — rejected because it does not fix the reported UX (a multi-hundred-MB upload attempt that fails only after fully transferring is indistinguishable from "hanging" to a user, and doesn't match the Clip-icon-flow expectation of an immediate rejection).
