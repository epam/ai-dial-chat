Slicing strategy: **risk-first**. The kit bump (slice 1) and token parity (slice 2) are proven before any project switches engine. After that, each consumer path (app → libs → tooling) is its own slice. Every slice is one commit that leaves `development` green. Slices 3–5 depend on 2. Slice 1 is independent.

Architecture guard (applies to every task touching `libs/*`): the move changes only build config. No lib gains imports from `apps/*`, `server-api`, the generated client, app contexts, env, routing or storage keys. The shared theme lives in `tools/tailwind/`, not in a lib, so no lib depends on another's styling.

## 3. Engine switch: everything that resolves `tailwindcss`, in one commit

Slices 3 and 4 of the original plan, and most of slice 5, turned out to be one slice. `apps/chat` compiles every `libs/*/src` class, and the `outline-hidden` rename does not exist in v3, so the app and the lib `dist` builds must change engine together. Once the root `tailwindcss` package is v4, every remaining v3 consumer breaks at once: the root and per-project `postcss.config.js` (Vite picks them up for any CSS, including libs with no config of their own such as `attachment-canvas` and `mcp-apps`), `eslint-plugin-tailwindcss@3`, `prettier-plugin-tailwindcss`, the overlay sandbox, the celebrations Storybook, `apps/chat/browser-tests/text-refinement.browser.spec.mjs` and the agent-config validator's breakpoint check. The planned temporary `tailwindcss-v3` alias therefore has no consumer left and was dropped.

Sass cannot pass v4's `@import … theme(…)` / `@source` through, so Tailwind no longer goes through `styles.scss`, which keeps only `mcp-app-ui-vars`. The `html, body, #root` block keeps its `@apply` in `apps/chat/src/styles/base.css`, imported by `tailwind.css` between preflight and the utilities (where v3's `@layer base` put it). **Deviation from design D4:** nothing is in a cascade layer.
