# Design

## Context

Facts below were checked against `origin/development` at `e54ba186c` (2026-11-16) and, for Core, against `ai-dial-core` and `ai-dial-admin-frontend` sources read on the same day (not run against a live Core). See `proposal.md` for motivation.

**Chat today**
- `GET /api/v1/org-units` (`apps/chat-api/src/org-units/org-units.service.ts`) reads `getOrgUnit('public', { recursive: true })`, cached 60 s per user under `org-units:list:<userSub>`, flag-gated by `FeatureGuard`. `useOrgUnits` and `OrgUnitsProvider` only answer "is this exact folder a unit". Nothing consumes `isOrgUnitFolder` yet (no UI renders units differently).
- Nothing calls `role-assignments` (`apps/chat-api`, `libs/chat-api-client`). Nothing consumes the first change's `isOrgUnitFolder`, `toOrgUnitFolderSet` or the context's `isOrgUnitFolder` either: `OrgUnitsProvider` is mounted but no panel calls `ensureUnits()`.
- The only write-permission check is the placeholder `hasPublishFolderWriteAccess` (`Production` segment) in `usePublishFolders`, used by `PublishConversationPanelContainer`, `PublishProjectPanelContainer` and `CatalogView` through `libs/catalog` into `usePublishFlow` / `derivePublishState`. The Save panel (`useResourceSavePanel`) does not check rights; its `organizationFolders` is simply omitted when the item cannot be published.
- `PublishFoldersTree` has only a whole-tree `disabled` prop.
- Saving into `public/` does not exist: for an Organization destination `runResourceSave` saves in place (own bucket) and then calls `publishCatalogEntity` (a publication request). The BFF fork/commit/move endpoints act on the caller's own bucket.
- SDK: `apps/chat-api/package.json` pins `@epam/ai-dial-typescript-sdk` `0.3.0-dev.4`. The pinned SDK exposes `getUserRoleAssignments` (`operations['getUserRoleAssignments']`, schema `UserOrgUnits { adminAccess?: 'FULL' | 'NONE'; items?: UserOrgUnitsUnit[] }`, `UserOrgUnitsUnit { displayName?, folder?, id?, name?, path?, permissions?: MapStringSet, roles?: string[] }`). All fields are optional in the typings.

**Core contract (read, not run)**
- `GET /v1/user/role-assignments`: any authenticated caller; 404 when org units are off; admin (`adminAccess` FULL) gets every unit with read+write on every namespace; others get the union of their roles' grants as `permissions` (namespace → actions); a unit seen only through `read org-units/**` at its parent has no roles and an empty or absent `permissions`; apps and API keys get no units. Roles can be replaced in Core's dynamic config, so the client trusts `permissions`, never role names.
- Owner of a folder = nearest unit above it, type-independent; roles do not inherit to child units. Core enforces this on every request, so the chat check is advice only.
- Namespaces equal Core's resource groups: `files, conversations, prompts, applications, toolsets, skills, projects` (+ `publications`).

### Rights per resource type (what the groups implement)

| Type (namespace) | Save into a unit folder directly | Publish into a unit | Needs, in the owning unit |
| --- | --- | --- | --- |
| Quick App and other applications (`applications`) | allowed | request | save: `write`; publish request: `read` |
| Toolsets (`toolsets`) | allowed | request | same |
| Prompts (`prompts`) | allowed | request | same |
| Skills (`skills`) | allowed, except a name equal to a unit folder (409) | request, same 409 | same |
| Projects (`projects`) | allowed, same 409 | request, same 409 | same |
| Conversations (`conversations`) | allowed | request | same |
| Any type, plain `public/` | not for non-admins | request, only a DIAL admin decides | unchanged |

A publication request is approved by someone with `read` and `write` on `publications` in every touched unit (by default the unit `admin` role) or a DIAL admin; the chat never calls approve. Core has no publish-without-approval, and a user with only `write` has no path to one: for such a user a publication stays a request. That is a constraint, not a task.

## Goals / Non-Goals

**Goals**
- One rule source for "what may this user do in this folder", usable by every panel and every future surface.
- Group 1 shippable on its own with no visible change: with the flag off, nothing changes (the `Production` heuristic stays); with the flag on and rights `Ready`, the unit rights replace it.
- Disabled rows and direct save that follow Core's own rules, with Core still the authority.

**Non-Goals**
- Unit admin create-then-approve publishing (see proposal; to be decided later).
- File manager, org-unit icons, plain `public/` changes, any ai-dial-core change.
- Showing the user's roles or role names anywhere.

## Decisions

### D1. One endpoint: `GET /api/v1/org-units` reads `getUserRoleAssignments` and carries the rights
The existing handler keeps its URL, guards, cache key (`org-units:list:<userSub>`, 60 s, TTL-only) and `operationId: listOrgUnits`, but its Core source changes from `getOrgUnit('public', { recursive: true })` to `getUserRoleAssignments()`, and its response gains `hasAdminAccess` and a per-unit `permissions` map (delta spec `org-units-api`). There is no `/access` endpoint, no second DTO set, no second cache key and no second hook. Core's `roles` are not returned.
- *Why this is safe (read in Core `origin/development`, 2026-11-16):* `OrgUnitService.unitsOf` keeps every unit that is shown to the caller (a role there, or `read org-units/**` at the parent; every unit for a DIAL admin), while the old list route also requires every ancestor to be shown. So role-assignments `items` is a superset of the old list for the same caller; fields `id`, `name`, `displayName`, `path`, `folder` are the same; both are parents-first. Extra units are those the caller holds a role in whose parent they do not see. `displayName` can be empty: keep the `|| name` fallback.
- *Alternative: a sibling `/access` endpoint.* Rejected: it leaves the first change's endpoint and hook dead and runs two Core calls for one answer.
- Authorization: any authenticated session while `features.orgUnitsEnabled` is on; Core scopes the answer to the caller. Telemetry: only the existing `MetricsInterceptor`. Logs never carry token, cookies or the body above `debug`.
- Generated client: `npm run openapi`, `npm run openapi:check`, build and lint `chat-api-client` (regenerate, never hand-edit); the `permissions` map needs an explicit Swagger `additionalProperties` schema (array of string) so the generated type is `{ [key: string]: string[] }`. Follows `apps/chat-api/AGENTS.md`.
- Accepted risk: a Core without the `role-assignments` route answers 404, which the chat reads as "org units off" and the whole feature disables silently; the old list route would have worked there. The admin panel already uses the route, so supported deployments have it.

### D2. Pure helpers live in `libs/chat-shared`, reusing what is there
`libs/chat-shared/src/utils/org-unit.ts` keeps `normalizeOrgUnitFolder` and the `OrgUnit` type (gains `permissions`); `isOrgUnitFolder` and `toOrgUnitFolderSet` are removed (dead). New helpers `findOwningOrgUnit`, `canAccessAt`, `canWriteAt`, `canSaveToFolderAt` (admin, or no owner, or `write`: the Save panel's rule, so plain public folders stay usable), `canReadAt`, `canRequestPublicationAt` and the enums `OrgUnitNamespace`, `OrgUnitAction` go next to it. Matching is the admin panel's rule (`ai-dial-admin-frontend` `utils/org-units/units.ts` `getOwningUnit`): longest folder prefix at a segment boundary. Complexity: sort units by folder length once (memoised by the hook), then a linear scan. Admin short-circuit first; no owner → `false`; owner → `permissions[namespace]?.includes(action)`. Libs stay isolated: the helpers take resolved data and know no endpoint, flag, context or storage. No new path converter is written: folder arrays are joined with the existing `resolveDialFolderPath` (`libs/chat-hooks/src/files/dial-file.ts`) and `normalizeOrgUnitFolder`.

### D3. One hook `useOrgUnits`, with an "unknown means allowed" rule
The existing `useOrgUnits` (`libs/chat-hooks/src/org-units/useOrgUnits/`) becomes the one hook: `listOrgUnits` resolves `{ enabled, hasAdminAccess, units }`, it keeps `OrgUnitsStatus`, lazy `ensureUnits`, cancelled flag, silent failure and retry, and gains `refreshUnits` and `canWriteAt` / `canSaveAt` / `canReadAt` / `canPublishAt` (replacing `isOrgUnitFolder`). While the status is not `Ready` (Idle, Loading, Disabled, Error) every check returns `true`.
- *Why:* disabling on missing data would break today's working flows when the flag is off, Core has org units off, or the read fails; Core's 403 then remains the guard. Only a `Ready` answer can disable a folder.
- Direct save (Group 3) is the opposite: it needs a proven right, so it requires `Ready`, an owner and `write`; it is never chosen on unknown rights. Group 3 code reads the status, not only the boolean.
- `getOrgUnitNamespace(entityType)` (chat-hooks) maps `CatalogPublishEntityType` (`libs/chat-hooks/src/catalog/publish.ts`) to a namespace; an existing mapping in the libs is reused or extended before a new one is written. Quick App, schema-form and custom apps are all `applications`.
- `refreshUnits()` lets a panel re-read when it opens (Group 2); the BFF cache keeps the refresh cheap (60 s).

### D4. Context: extend `OrgUnitsContext`, no second provider
`useOrgUnitsContext()` returns the hook's result (`status`, `ensureUnits`, `refreshUnits`, `canWriteAt`, `canSaveAt`, `canSaveDirectlyAt`, `canReadAt`, `canPublishAt`); `isOrgUnitFolder` is removed. One provider and one flag read keep the "one rule source" promise; the value stays in `useMemo`; `ensureUnits` gets a new identity when the flag resolves. No new context file, no new flag, no cache outside the BFF.

### D5. Replace the `Production` heuristic by an injected callback, only with the flag on and rights `Ready`
`usePublishFolders` takes `canPublishTo(folderPath: string[]) => boolean` and keeps `hasPublishFolderWriteAccess` (the `Production` placeholder, `RESTRICTED_FOLDER_SEGMENT`) as the fallback when no callback is given; the app wrapper `apps/chat/src/hooks/publish/usePublishFolders.ts` forwards an optional `canPublishTo`. The containers pass it (built from `canPublishAt` and the type's namespace) only when `features.orgUnitsEnabled` is on and the status is `Ready`, otherwise `undefined` so the heuristic applies. The placeholder was added in `fc02d9555` (2026-06-18, "support catalog", #7304) with a TODO to replace it with a real Core check. Because a path outside units is never blocked by the new check, publish panels keep today's behaviour there. Existing tests that assert the `Production` rule stay; new cases cover the callback taking over.
- Where the logic lives (thin app): the decision "flag on and `Ready` → callbacks, else none", the namespace, the path and the reason text injected as a callback is one function in `libs/chat-hooks` (for example `buildFolderGuards`), returning `{ canPublishTo, getDisabledReason }`; the containers only pass `t()` strings.

### D6. Group 2: the tree takes `getDisabledReason`, hosts own the rule and the text
`PublishFoldersTree` gets `getDisabledReason(destination) => string | undefined`; `SaveToFolderPanel`, `StandaloneSaveToFolderPanel` and `PublishPanel` forward it. The host builds it with `useOrgUnitFolderGuards` (`usePublishFolderGuards` for publish) from `canSaveAt` (save) or `canPublishAt` (publish) and a translated typed string chosen by `getOrgUnitAccessReasonKey(purpose, namespace, isQuickApp)`; the Save tree is multi-root, so the guard takes the destination's root and judges only Organization. This keeps libs free of rights and strings (isolation, `i18n-strings`). Tooltip uses the kit tooltip (discover the exact component with the `@epam/ai-dial-ui-kit` MCP tools during the slice, never by grepping the package) and follows how the file manager already shows a disabled row (`getDisabledTooltip` in `DialFileManagerShell`). Disabled rows keep focus and carry `aria-describedby`; a disabled folder still expands, so children with rights stay reachable. A committed destination that becomes disabled after `refreshUnits()` disables Save.
- Phone behaviour is owned by the folder tree component: we pass the disabled state and the reason and add no phone-specific layout. Slice 2.1 only verifies that the tree supports a per-row disabled state with a reason; if it does not, stop and report.
- RTL: logical Tailwind classes, tooltip placed by start/end; no directional icon is added.
- A11y: WCAG 2.1 AAA target; disabled state not conveyed by opacity alone; reason announced on focus. Any dynamic message goes through the kit `LiveRegion`, mounted before its text.
- i18n: new keys, one per resource type for save and publish texts, in a `*I18nKeys` enum in `apps/chat/src/constants/translation-keys.ts` and `apps/chat/src/i18n/locales/en.json`; lib defaults are English in the `*Labels` props.

### D7. Group 3: direct write through an adapter method, QuickApp first
`ResourceEditSaveAdapter` / `ResourceCreateSaveAdapter` (`libs/chat-hooks/src/catalog/resource-save-adapter.ts`) gain an optional `saveIntoOrgUnit(folderPath)`; `runResourceSave` takes the direct-write row for a unit destination (delta in `resource-save-panel`). The BFF write is one of: (a) the per-type controllers accept a unit target and call Core `copyResource` (own bucket → unit folder) or PUT; (b) one generic BFF operation that copies by id for every type. Core allows both for a holder of `write` (copy: destination `write`, source `read`, and for applications/toolsets also `write` on the source, which the owner of an own-bucket copy has; a move into a unit from the own bucket is not blocked by `requireSameUnit`'s early return, which nobody has exercised).
- *Order:* the QuickApp slice goes end to end first as the template (BFF write, adapter, editor wiring); the other types follow as later slices inside this change. Groups 1 and 2 do not depend on Group 3.
- *Check before code:* Core's own tests for an own-bucket to unit copy by a writer are read first. The QuickApp slice starts with a short check, and its first manual run on two accounts (a role with `write` in a unit, and a read-only one) is the verification. If Core refuses the copy, stop at Groups 1 and 2 and come back to the user.
- *What Core's own tests prove and do not (read in `ai-dial-core` `origin/development` at `accba3d1`, after a fetch on 2026-11-16, task 3.1; tests under `server/src/test/java/com/epam/aidial/core/server/`).* Proves:
  - A unit editor writes, reads and deletes in the unit with `PUT` (files and prompts: `OrgUnitEditApiTest.testEditorsCreateChangeAndDeleteInTheirUnit`); a caller with no role there, and one with a read-only role (`auditor`), is refused 403 on write (`testNothingOutsideTheUnit`, `testConfiguredRolesGrantWhatTheySay`).
  - An editor creates and edits an application in the unit with `PUT`; a new app gets `forward_auth_token: false`, an edit keeps the stored value, and interceptors set in the shared space are kept (`testApplicationsKeepTheirPlatformFields`, `testUnitWritesKeepInterceptors`).
  - An editor's own-bucket application is copied into an existing unit application with `overwrite: true`: 200, and the replaced app keeps its interceptors (`testInterceptorsComeOnlyFromTheSharedSpace`, last assertion). This is the nearest proof of "own bucket to unit copy by a writer".
  - Copy and move inside one unit by an editor: 200; to another unit or out to plain `public/`: 403 (`testMovesAndCopiesStayInsideTheUnit`). Copies and moves drop `forward_auth_token`, in and out of a unit (`testCopiesAndMovesDontForwardTokens`, `testCopiesAndMovesOutOfTheUnitDontForwardTokens`). A copy duplicates only files the caller reads and is refused 403 otherwise (`testCopiesDuplicateOnlyFilesTheCallerReads`, `testCopiesDontDuplicateFoldersReadOnlyThroughRoles`).
  - A copy from another user's bucket into a unit is refused 403 (`testPrivateSourcesAnswerAtOnce`); a skill cannot take a unit folder's name, 409 on upload and on copy (`OrgUnitSkillApiTest.testSkillsCantTakeUnitFolders`).
  - An own-bucket file *moves* into a unit with 200, by a DIAL admin (`OrgUnitApiTest.testMovesStayInsideTheirUnit`, last lines); a move of a plain `public/` file into a unit is 409 (`belongs to no unit`, "Copy or publish it instead").
  - An editor's endpoint change on an application with declared `resource_dependencies` drops the admin approval (`ResourceDependencyOrgUnitApiTest`).
  Does not prove: no test has a non-admin unit writer *copy a plain own-bucket application without interceptors into a new unit path* (the closest cases are the overwrite copy above and the 403 on `back`, which fails because the app carries interceptors); no test copies an own-bucket Quick App declaring `resource_dependencies`, a toolset, a prompt or a project into a unit; none shows the response body the chat must display for a refusal; own-bucket move/copy of a non-file by a non-admin is untested. So the first manual run on two accounts (QuickApp slice, 3.4) stays the acceptance check; nothing here contradicts the direct path, so 3.2 proceeds.
- *Decision (tasks 3.2 and 3.4b): one generic operation next to publication, not one endpoint per type.* `POST /api/v1/catalog/:entityType/:entityId/copy-to-org-unit` (`operationId: copyCatalogEntityToOrgUnit`, in the `publish` module, `@RequireFeature(OrgUnitsEnabled)`) copies the caller's own entity into `folderPath` of the `public` bucket (non-empty, so the public root is never targeted) under the same leaf name, with optional `overwrite`, and returns the id of the copy. Precedent: everything that puts something into the public bucket (publish, unpublish, version statuses) is generic by `entityType` in `apps/chat-api/src/publish`; only operations inside the personal bucket are per type. It is built on the same helpers as the personal-bucket operations: `transferDialResource` (the 400-to-409 mapping, now with an `overwrite` option) and the owning service's `resolveOwnApplication` / `invalidateAfterWrite`. Per-type differences are declared in one place, `OrgUnitCopyService.getType` (`apps/chat-api/src/publish/org-unit-copy.service.ts`): the Core resource type, how `entityId` resolves to the caller's own copy, and which caches to clear. Applications, toolsets, prompts and skills have an entry so far (skill: the id parsed with `parseSkillResourceUrl`, own-bucket check, `DialResourceType.Skills` with `listSkillMetadata` for the 409 probe, nothing cached; Core's own 409 for a name equal to a unit folder name reaches the caller unchanged, with no client rule; prompt: the id parsed with `parsePromptId`, checked against the caller's bucket, `DialResourceType.Prompts` with `getPromptMetadata` for the 409 probe, no cache to clear because chat-api caches no prompts; the copy is Core's `copyResource`, not the read-write-delete `movePrompt` uses, and has not been run against real Core for prompts; toolset: `ToolsetsListingService.resolveToolsetResource` plus an own-bucket check, `invalidateCaches`; the `copyResource` call and the 400-to-409 probe are the shared helper's, with `DialResourceType.Toolsets`); any other type answers 501 until its entry is added in 3.5, so the endpoint shape does not change for them. Not proven for prompts and skills: Core's tests show only the 409 on a unit-folder name for skills, and nothing for prompt copies; a skill is a folder with files, so that a whole-skill `copyResource` into a unit works as it does for a single-file resource is confirmed only by the first real run. Projects and conversations have no Save panel (projects save through `useSaveProject` with no folder choice; conversations have only a publish panel), so they get no direct save. Core's 403 (no `write`, or a per-type rule such as the interceptor case above) and 409 are returned as they are; the BFF adds no rule of its own. The save adapters call `PublishApiClient.copyCatalogEntityToOrgUnit(entityType, id, { folderPath })` through `createOrgUnitWriter`.
  - *What 3.5 must add per type (read from the code in 3.4b):* `resolveOwn` for toolsets (`listingService.resolveToolsetResource` plus `assertOwnBucket`), prompts, skills and projects (each service resolves its own bucket and path today); the caches each service clears after a write (applications: `applications:list:{sub}`, the deployments list and the details cache per id; the others differ); and an existence probe for the 400-to-409 mapping, because `transferDialResource` reads metadata through the application and toolset clients only. DIAL Core's copy is the same call for every type (`POST /v1/ops/resource/copy`, source and destination of one type); applications and toolsets also need `write` on the source, which an own-bucket owner has, and skills and projects are refused 409 on a unit folder's name.
- *Alternative: keep publish-with-request and only disable folders (Groups 1 and 2 alone).* The fallback if Core refuses.
- Rules and the admin-approval banner do not apply to a direct write (Core stores no rules in units), so the panel hides both for that destination. A DIAL admin writes directly only inside units; plain `public/` is unchanged.
- *Known risk (Core, not handled by the chat):* a non-admin copy into a unit makes Core reset `forward_auth_token` on the copy, keep interceptors but not add new ones, and drop admin consent of declared `resource_dependencies`; referenced files are duplicated and need `read` (no folders). Today the chat never copies into the shared space directly, so users meet this for the first time with direct save. Other limits stay Core's: skills and projects cannot use a unit-folder name (409, shown on the name field), no move between units, a non-own source is refused.

## Risks / Trade-offs

- [Parents missing in `role-assignments.items`] Core omits parents the caller cannot see; the first change's list did not show such units at all, so this is new for them. A user who holds a role in unit A but cannot see a nested unit B (only with custom roles lacking `read org-units`; the built-in roles all have it) gets owner A for a folder in B, so the client may enable a folder Core will refuse. → Core's 403/409 keeps its existing error path; the client check is advice. The case is covered by a unit test that documents the limitation. Not measured in real tenants.
- [Stale rights during a session] Roles can change after the load. → `refreshUnits()` on panel open, BFF cache 60 s, Core authoritative.
- [Unknown rights enable folders] By design (D3); a failed read never makes things worse than today.
- [Core without the `role-assignments` route] Its 404 reads as "org units off" and the feature disables silently (the old list route would still have worked). Accepted; the admin panel already uses the route, so supported deployments have it.
- [Save disables a read-only unit, Publish does not] A user with `read` but not `write` in a unit cannot save there but can still send a publication request there. Decided: Save disables the row (the mockup), Publish disables only without `read`.
- [Direct save has per-type gaps] A copy into a unit by a non-admin resets `forward_auth_token`, keeps interceptors, and drops admin consent of declared `resource_dependencies` (known risk, D7); the chat neither prevents nor handles it. Whether Quick App declares dependencies is checked in the QuickApp slice.
- [Not proven, read from source only] Own-bucket → unit move is not blocked; who may request a publication into a plain `public/` folder with no read rules for them; complex-resource sub-file routes use the same owner rule; whether `permissions` for a parent-only unit is `{}` or omitted (both treated as no right). None changes Group 1.
- [Library isolation] The new hook and helpers in `libs/chat-hooks` and `libs/chat-shared` take callbacks and resolved data; the BFF read, flag and context stay in `apps/chat-api` and `apps/chat`. Nothing in `libs/publish-panel` or `libs/catalog` learns units, rights or the endpoint.

## Migration Plan

No data or schema migration. Deploy order for Group 1: BFF endpoint, regenerated client, app wrapper, helpers, hook, context, conditional heuristic replacement. All behind `ORG_UNITS_ENABLED` (off by default). Rollback: set the flag off, or revert the slice commits; with the flag off the old `Production` heuristic applies again.

## Open Questions

1. At the end of the work, decide whether to remove the `Production` placeholder for good (it stays while the flag is off).
2. Which BFF mechanism Group 3 uses (per-type endpoints or one generic copy) and whether Quick App declares `resource_dependencies`: fixed in the QuickApp slice after the Core-tests read.
3. Editing in a unit (follow-up, not decided): should a user with `write` in the owning unit be able to edit a unit item from the catalog, and should Save then write in place? Today `isEditable` ignores unit rights, so such an item offers only "Use in chat"; seen on a real Core after a direct save. Out of scope for this change; to be raised with the team.
