# Design

See `proposal.md` for motivation, scope and the departures from the issue, and `specs/` for the requirements.

## Context

Verified on `origin/development` of this repo and of ai-dial-core (read-only, 2026-11-12):

- **Save panel today.** `SaveToFolderPanel` (`libs/publish-panel/src/components/SaveToFolderPanel/SaveToFolderPanel.tsx`) renders the Keep/New `RadioGroup` (`Keep version {version}`, `Version` input, placeholder `Enter new version`), an inline error and a `LiveRegion`. `useResourceSavePanel` (`libs/chat-hooks/src/catalog/useResourceSavePanel/useResourceSavePanel.ts`) starts `newVersion` as `''`, rejects invalid, unchanged and conflicted versions, and maps a 409 to the "exists" error. The summary row already shows the current version inline after the name. These match mockups 2 and 3; the issue's "Keep current version" and "New version" labels (mockup 1) are not adopted, by the author's decision to keep the source as it is.
- **Publish panel today.** `PublishPanel` has no version input: it publishes `item.version` and warns when the folder already has it. It renders the Dependencies list. `PublishHistoryList` is exported but rendered by no panel. For applications and toolsets the panel is hosted by the catalog Details panel (`libs/catalog/src/components/Details/DetailsPublishContent.tsx`, props in `libs/catalog/src/models/item-details-props.ts`, state built in `libs/chat-hooks/src/catalog/publish.ts`); the `apps/chat` publish containers (`PublishConversationPanelContainer`, `PublishProjectPanelContainer`) serve conversations and projects only.
- **Save panel host.** The Save panel opens only for resources the user owns; for a shared one Save keeps saving in place (`resource-save-panel`).
- **Seven version patterns.** UI: `SEMVER_VERSION_PATTERN` and the default `VERSION_PATTERN` in `libs/builder-form/src/utils/validate-deployment-creation-fields.ts`; the toolset editor passes `validateVersionPattern: true` (`libs/toolset-editor/src/utils/toolsets.ts`, `ToolsetEditor.tsx`). API: `create-application.dto.ts`, `update-application.dto.ts`, `application-version.dto.ts`, `toolset-body.dto.ts`, `publish-target.util.ts`. The issue lists four; `update-application.dto.ts`, the fork DTO and the `builder-form` default are additions.
- **Boundaries.** `eslint.config.mjs` lets `type:backend` depend only on `type:backend`, and `apps/chat-api` imports no internal lib. The repo already mirrors the entity limits in `apps/chat-api/src/common/validators/entity-field-limits.ts` and `libs/chat-shared/src/utils/entity-field-limits.ts`, each commenting on the other, with a spec in chat-shared.
- **Listings.** `DeploymentItemDto` and `DialToolsetDto` carry `id`, `displayVersion`, `updatedAt`, `owner` and `isMy`. `DeploymentsListingService` drops toolsets, which are served only by the toolsets listing. Cache keys of the deployments listing vary by `interface_type`. The BFF flattens both lists in `toResourceIdentityEntries`.
- **Cache invalidation after Save as new version.** Applications: fork, commit and create-only clear the lists through `invalidateAfterWrite`. Toolsets: `ToolsetsMutationService` clears them through `ToolsetsListingService.invalidateCaches` (a different name from `invalidateListCache`). Both already satisfy "appears at once"; this change adds tests.
- **Publications.** `getPublishHistory` scans the caller's bucket list and re-reads each candidate with `getPublication`, because the list carries no `resources`. `isDetailCandidate` accepts `Approved` and status-less publications, skips `Pending` and `Rejected` on purpose, and has two callers. Its cache entry (key `publish-history:{entityType}:{entityId}`, 60 s) is cleared on publish and unpublish.
- **DIAL Core facts.** A path segment may contain `+` (kept as is); the whole path is limited to 900 UTF-8 bytes, and chat-api additionally limits a display name to 255 UTF-8 bytes (`DIAL_ENTITY_NAME_MAX_BYTES`); a PUT whose name or folder ends with `.` is answered `400`. Core never parses the `__` suffix or checks it against `display_version`, so grouping is a client convention. A listing returns one item per stored path; `owner` is the resource's original author. A non-admin gets `403` for any publication outside the caller's own bucket, and sharing does not extend that, so status for a resource that is not the caller's own is unknowable. A folder share exposes every version in it; an item share exposes only that item.

## Goals / Non-Goals

**Goals:**
- One version rule, kept identical on both surfaces and proven by one shared corpus.
- A Versions history section in the Save and Publish panels that costs no extra listing work and one bucket read when a panel opens.
- Keep the libs isolated: the section and the hook receive data and callbacks, never paths or app knowledge.

**Non-Goals:**
- Changing the listings' shape, ordering versions, aliases, restore/delete/compare/open, catalog grouping, a Dependencies block in Save, a version input in Publish.
- Changing `isDetailCandidate` or `publish-history` behavior.

## Decisions

1. **Version rule: two mirrored constants.** `^(?!.*\.$)[\w.+-]{1,64}$` in `apps/chat-api` and as `RESOURCE_VERSION_PATTERN` in `@epam/ai-dial-chat-shared` (`libs/builder-form` re-exports it as its default `VERSION_PATTERN` and drops `SEMVER_VERSION_PATTERN`), one shared corpus test on each side, each comment pointing at the other. Alternatives: a shared lib (rejected, `type:backend` cannot import it), a new `type:backend`-tagged lib with a boundary change (rejected, a boundary change for one regex). The trailing dot is rejected on top of the issue's pattern because of Core's `400`. The API changes first.
2. **`versionGroupId` is a pure function applied when listing items are mapped.** The decoded folder path plus the base name split at the last `RESOURCE_VERSION_SEPARATOR` (`__`). An id without the suffix gets no group (a single-version resource). Ids are percent-encoded, so the function decodes segments before comparing. The same separator constant replaces the private copies in `publish-target.util.ts` and `publish-dependency.util.ts` and the bare `'__'` in `publish.service.ts`. Alternatives: a `displayName` key (rejected, it changes on rename), clients parsing ids (rejected by the issue). A rename or a move of a single version splits the group; accepted.
3. **Rows come from the listing; statuses come from an endpoint.** The hook filters the already-loaded listing by `versionGroupId` and `isMy === true` (as in the issue; the Save panel opens only for the user's own resources), sorts by `updatedAt` descending, marks Current by the edited id and joins statuses by `id`. Rows render first; statuses load in the background when a panel opens.
4. **Statuses endpoint reads once and resolves the group from the listing.** The BFF takes the group from the cached deployments or toolsets listing (the unfiltered one, so an interface filter cannot shorten the history), reads the caller's publication list once, expands candidates (including `Pending`) with the existing bounded-concurrency lookups and matches every version's source url in one pass. A new predicate admits `Pending`; `isDetailCandidate` is untouched. Doing this in one pass needs `resolvePublicationDetails` (which hardcodes `isDetailCandidate`) and the per-source narrowing in `resolvePublicationsForSource` / `listSourcePublications` to be split, with a test that `publish-history` output is unchanged. The detail lookups are bucket-wide (every Approved and, now, Pending publication), not group-wide. The endpoint depends on the `versionGroupId` group of tasks. A resource that is not in the caller's bucket answers unknown (a defensive path; the Save panel never opens for one). `publishedBy` is the publication's display author. Wire values: `published`, `in-review`, `not-published`, `unknown`. When both a Pending and an Approved publication exist for a version, Published wins.
5. **Cache the publications, not the response.** `publish:bucket-publications:{bucket}` holds the resolved own-bucket publications for 60 s (the same TTL as `publish-history`, whose key has no bucket); publish and unpublish clear it (both receive `bucket`). The group join is done on every call from that cache and the cached listing, so a version saved or deleted since the last call shows at once. Alternatives: a response cache per group (rejected, a save or delete would leave it stale), per entity id (rejected, a sibling's publish would leave it stale).
6. **History is a section, not a view.** One section component in `libs/publish-panel`, rendered by `SaveToFolderPanel` and `PublishPanel` when the host passes its props. Row anatomy: version + Current tag, status, folder (`Personal` or the full path, formatted like the Save destination), date, author line ("Published by {publisher}" for a Published version, otherwise "by {owner}"). The row has no action. Statuses are text (a `Tag`), never color alone.
7. **Ownership and hosts.** Grouping and the statuses request live in a `libs/chat-hooks` hook that takes the listing items and a configured client (the narrow `chat-hooks` exception); it returns the folder as segments and the host supplies the translated root label. The Save panel is wired in `apps/chat` (`ResourceSavePanelContainer`). The Publish panel for applications and toolsets is hosted by `libs/catalog`, which cannot import `chat-hooks`, so the Details publish state builder in `libs/chat-hooks/src/catalog/publish.ts` and the catalog props (`libs/catalog/src/models/item-details-props.ts`, `DetailsPublishContent.tsx`) carry the rows through props. No new context is needed: the existing deployments and toolsets contexts feed the hook.
8. **Generated client.** The endpoint is `getCatalogVersionStatuses` in `libs/chat-api-client/openapi.json`, used through a thin wrapper in `apps/chat/src/server-api/`.

Library-isolation guard for every lib task: no `/api` path, generated-client import, app context, route or storage key inside `libs/publish-panel`; `libs/chat-hooks` only calls operations on the client it is given.

## Risks / Trade-offs

- [New 64-character cap, `+` and trailing-dot rule reject some inputs on apps and toolsets] → validation applies only to a supplied `version`; an update that omits it keeps the stored one. Check for stored versions over 64 characters or ending with a dot before release.
- [Whole path limit of 900 bytes in Core can be reached by a long folder, name and a 64-character version] → Core answers 400; the Save panel shows the server error through its existing submit-error path; add a test for the error mapping.
- [Statuses cost one bucket scan plus candidate lookups every time a panel opens] → loaded in the background, cached 60 s per group, bounded concurrency; rows never wait for it.
- [The client listing may be filtered or partial] → the BFF resolves the group from the unfiltered listing; the hook needs the same, so check which listing the editors load (open task 4.1).
- [Mirrored constants can drift] → shared corpus test on both sides.
- [Statuses endpoint merged without its consumer] → additive and safe; end to end it is verified only when the hook and the section land, so keep groups 3 and 4 close.
- [An administrator's decision (Pending to Approved or Rejected) does not pass through publish or unpublish] → In review or Published can lag by up to 60 s; accepted and stated in the spec.
- [`+` in an application version reaches ids that `DEPLOYMENT_ID_PATTERN` validates (it allows `%2B` but no raw `+`), and Core may return a raw `+` in an `id`] → group 1 adds tests that feed ids with a raw `+` and with `%2B` through the id validators, `versionGroupId` and the publish target; if one rejects, fix that validator, and if that is not possible keep `+` out of application versions only.
- [A 64-character version plus `__` plus a long name can exceed the 255-byte display-name or the 900-byte path limit] → Core or the DTO answers 400; add tests for both and make sure the Save panel shows the server error.

## Migration Plan

Groups 1–3 are backend-additive and independently releasable (group 1 changes validation, API before UI; group 3 depends on group 2). Group 4 depends on 3. Everything can ship as one PR or several. Rollback: revert a group; nothing is stored or migrated.

## Decided with the user (2026-11-12)

No open questions remain. These were decided in conversation with the user, who also talked to the issue author; this section is the record for any later session. Anything that departs from the issue text is listed in `proposal.md` under "Departures from the issue"; once the work is done, compare the result with the issue again, find what does not match, understand why, and post the comment drafted in task 5.1 (the issue itself is not edited by us).

- **History placement.** Inline Versions history section at the bottom of the Save and Publish panels, as in the mockups; no separate view, link or Open action (the mockups have none).
- **Save panel labels.** Keep the source as it is (`Keep version {version}`, `Version`, empty at start); mockup 1's "Keep current version" and "New version" are not adopted.
- **Publish panel.** No version input (it has none today); the Dependencies list stays as is; the Save panel gets no Dependencies block.
- **Row content.** Version with a Current marker, status, folder (`Personal` at the root, otherwise the path like the Save destination), last modified date and author. Author: the publisher for a Published version, otherwise the listing `owner`. Current and status styling is left to implementation (the mockups show neither).
- **"Draft" on mockups 2 and 3.** An ordinary version name like `beta-2`, not a status.
- **Version rule.** `^(?!.*\.$)[\w.+-]{1,64}$`: the issue's pattern plus a trailing-dot ban, already discussed with the issue author; the API changes first; two mirrored constants; the 64-character cap and `+` for applications are accepted side effects (tests in group 1).
- **Shared resources.** Rows use `isMy === true`, as in the issue; the Save panel opens only for the user's own resources.
- **Statuses cache.** The resolved own-bucket publications are cached for 60 s and cleared on publish and unpublish; an administrator's decision can lag by up to the TTL.
- **Delivery.** One PR or several, decided later; the groups in `tasks.md` are only an order of work.
