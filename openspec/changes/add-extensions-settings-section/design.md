# Design: add-extensions-settings-section

## Context

The #9108 change delivered the full signout chain: `POST /api/v1/offline-credentials/signout` (BFF), the generated `signOutOfflineCredentials` operation, the `signOutOfflineCredentials()` wrapper, the gate's `connected` boolean, the lib's optional `onDisconnectClick` header action, and the page-level confirmation dialog on `ScheduledTasksPage`. This change relocates the user-facing half of that chain into a new Extensions section in Settings and removes the page-header affordance. The Settings machinery is data-driven: `SettingsTabs` (`apps/chat/src/types/settings-tabs.ts`) + one `useSettingsTabConfig` entry (`apps/chat/src/hooks/useSettingsTabConfig.tsx:29-61`) — `SettingsPage` resolves the active tab from the URL segment, so no route-table change is needed. The table pattern to mirror is `libs/usage-dashboard`'s `ModelLimitsSection` (div-based ARIA table; grid-template columns; hidden-on-mobile header row; avatar + name cell in `ModelLimitsRow`).

## Goals / Non-Goals

**Goals:**
- A Settings surface that lists the connected external Scheduler auth service with a per-row logout, replacing the Scheduled Tasks page header button as the single logout surface.
- The revoke stays refetch-authoritative and confirmed — identical semantics to the #9108 flow, new location.

**Non-Goals:**
- Login from the Extensions section (banner on the Scheduled Tasks page remains the login surface — Open Questions).
- Any BFF/generated-client change; new services; auto-signout; changes to the banner, gate-check timing, or the 403 disambiguation toast.

## Decisions

### D1 — Tab registration, feature-gated like the domain it exposes
`SettingsTabs.Extensions = 'extensions'` + a `useSettingsTabConfig` entry (`item` with `t(SettingsI18nKeys.Extensions)` label and `IconPlugConnected` — Tabler, symmetric, `aria-hidden`, `DIAL_KIT_ICON_STROKE`; `Component: ExtensionsTab`). The entry list becomes conditionally filtered: the Extensions entry renders only when `useFeatureFlag('scheduledTasksEnabled')` is `true` — the same flag that gates `ScheduledTasksPage` and (with `liveChatInteraction`) the BFF domain; a tab that always renders but whose status check always 403s is a dead surface. `SettingsPage`'s "default to first configured item" logic already handles a reduced entry list unchanged.
*Alternative rejected:* always-render the tab and show an "unavailable" empty state inside — one extra settings entry for every user without the feature, for no capability.

### D2 — Section composition is app-level; the table copies the pattern, not the component
`apps/chat/src/pages/SettingsPage/ExtensionsTab/ExtensionsTab.tsx` owns the section: page heading `<h2 className="dial-h1-text …">` + description `<p className="dial-small-text …">` (the exact `UsageTab.tsx:239-244` pattern), then a `ModelLimitsSection`-shaped table built from divs with `role="table"`/`role="row"`/`role="columnheader"`/`role="cell"`: column headers via `dial-caption-lead-semi-text` (the `ModelLimitsSection` header class), header row hidden below the `desktop:` breakpoint, grid-template columns `desktop:grid-cols-[minmax(12rem,1.25fr)_minmax(0,1fr)_auto]` (Name / Description / action), rows stacking on mobile. The row component (`ExtensionRow` inside the tab folder) renders the Name cell as `InitialsAvatar` + display name (the `ModelLimitsRow.tsx:108-114` avatar pattern), the Description cell, and the trailing logout button. No new lib: host knowledge (gate, signout, confirmation) dominates, so an app-level section respects library isolation where a lib would fight it.
*Alternative rejected:* generalize `libs/usage-dashboard`'s section — its props model is usage-specific; an unrelated extensions concept would widen a published lib for one consumer.

### D3 — Row identity derives from the Core-reported client identity
The tab uses the existing `useOfflineCredentialsGate` (it is route-scoped and fires on mount; `/settings/extensions` is a fresh route entry). The row renders while the check reports the service is available; the display name derives from `connect.clientId` — the BFF mapper passes `connect` through whenever Core returns a complete object, including while connected (`offline-credentials.mapper.ts:26-45`), so `clientId` is the only identity signal that exists on both sides of a revoke. Display name = `clientId` humanized (kebab/camel → Title Case, e.g. `dial-apps` → `Dial Apps`); avatar initials = `extractInitials(displayName)` (`@epam/ai-dial-chat-shared`) in a square `InitialsAvatar` — `DA` for `Dial Apps`. When Core omits `connect`, the row falls back to a localized default display name (`settings.extensions.service.defaultName`, value `DIAL Apps`). The row description is a localized constant for this service (`settings.extensions.schedulerService.description`, value "Provides access to built-in apps within the platform.") — Core exposes no per-service description.
*Alternative rejected:* a hardcoded single row (name and description as literals, no identity derivation) — rejected by user decision: the identity comes from the service/client the status check reports.

### D4 — Action cell is a state-dependent Log in / Log out pair; refetch stays authoritative on both sides
The row's action cell switches on the gate's resolved state: **Log out** while `connected: true` (and status ≠ `Error` — the same stale-affordance guard the header button had), **Log in** while `available: true && connected: false`, empty while the check is in flight or errored. The Log out button carries `IconLogout` as its icon-before — the same glyph the removed Disconnect header action used (symmetric → no RTL mirror, `aria-hidden`, `DIAL_KIT_ICON_STROKE`); the button's label is the accessible name. **Logout:** activating Log out opens the existing ui-kit 2.0 `ConfirmationPopup` (`Danger` variant, `isDisconnecting` re-entry guard, failure swaps the description to the failed message) — the exact `ScheduledTasksPage` dialog relocated. Confirm: `await signOutOfflineCredentials()` → `await refetchCredentials()` → close the dialog and announce success only when the fresh check reports `connected: false`; any other outcome keeps the dialog open with the failed message. **Login:** activating Log in drives the existing `useOfflineCredentialsLogin` flow with the gate's `connect` settings (the same `handleLogIn` shape the page uses, minus the banner's retry-state machine — the tab has no banner, so popup-blocked/cancelled/timeout/failure outcomes surface as polite `aria-live` announcements using the existing banner outcome message keys where the wording fits, new keys otherwise; resolved by grep during the i18n slice). The button is disabled (label → "Logging in…") while the flow is in flight; a fresh `refetchCredentials()` decides the row's next state. Announcements go through a tab-level `sr-only` polite `aria-live` region.
*Alternative rejected:* logout-only with an empty action cell on a disconnected row — rejected by user decision: the row switches to a Log in action.
*Alternative rejected:* relocating the banner's retry-state machinery wholesale — the banner is a persistent inline surface that swaps its own body text; the row's cell is a button, so outcomes map to announcements, not banner states.

### D5 — Disconnected avatar carries a warning corner badge with a tooltip
While the last resolved state is disconnected (`available: true && connected: false`), the avatar renders a small warning badge overlaid at its **bottom-inline-start** corner: a relatively-positioned avatar wrapper with an absolutely-positioned `IconAlertTriangleFilled` (the login banner's warning glyph — filled, ignores the stroke prop) in a warning-colored rounded chip. No existing avatar corner-badge component exists to reuse (`DeploymentIcon` has no status overlay; `ModelLimitsRow` renders its status as a separate pill), so the overlay is hand-rolled inside the row component. Hover **and keyboard focus** on the badge show a ui-kit `Tooltip` with the localized text "Authorize to use this extension" (keyboard parity per `.claude/rules/a11y.md`); the icon itself is `aria-hidden` — the tooltip text and the Log in button's label carry the signal, so the state is never communicated by color alone. The badge disappears when the row reports connected; it does not render while the check is in flight or errored (no state asserted).
*Alternative rejected:* a separate warning column/cell — rejected by user decision: the badge sits on the avatar's corner.

### D9 — Auth-session 403 on save auto-invokes login, retries the submit once, falls back to a toast
The #9046 path (`isScheduledTaskAuthSessionError` + the create/edit pages' `handleSubmitError`) upgrades from a toast to an auto-login: the shared check util is extended to return the disambiguation result **including the response's `connect` settings** (one fetch, no second client-settings request) instead of a bare boolean; a new shared app-level hook (e.g. `useScheduledTaskAuthAutoLogin`, alongside the existing util) wraps `useOfflineCredentialsLogin` and exposes an async `autoLogin(connect)` that resolves the outcome — both pages drive it from their `handleSubmitError`, so the orchestration cannot drift between create and edit (the single-shared-owner rule the existing capability already pins). The hook's refetch parameter is a plain fresh `getOfflineCredentials` call — the create/edit routes mount no gate hook, so no extra status request is issued outside the 403 path. Flow per **Save activation**: 403 → check → attributed + usable `connect` → `autoLogin` (Save stays disabled; no toast yet) → on success the page re-submits the **same prepared body** (re-prepared from the unchanged values, so a mid-flow edit is impossible while the form's inputs are still disabled by `isSubmitting`) → success behaves like a normal save; a failed retry keeps today's generic error handling with **no second auto-login in the same activation** (loop guard — a login that succeeded but left the grant ineffective must not ping-pong). On blocked/cancelled/timeout/failure: a login-failed toast (`scheduledTasks.autoLoginFailedNotification`), `isSubmitting` cleared so Save is operable again, form untouched — the next Save re-runs the whole path including a fresh auto-login (per user decision: "allow user to save again and invoke login again"). The old `scheduledTasks.authSessionExpiredNotification` toast and key are removed from this path (the login-failed toast replaces them); the generic error toast still covers genuine denials, failed checks, and missing `connect`.
*Alternative rejected:* keep the toast and add a manual "Log in" action — rejected by user decision: the login invokes automatically.
*Alternative rejected:* replay the captured body object instead of re-preparing — the values are frozen by the disabled form for the flow's duration, and re-preparing reuses one tested path (validation re-runs harmlessly on unchanged values).

### D6 — Lib removal: revert the three props, keep the shared collapse class
`libs/scheduled-tasks` loses `onDisconnectClick`, `disconnectButtonLabel`, and `disconnectAriaLabel` (props model, component render branch, tests, README). The shared `.actionButton`/`.actionButtonLabel` mobile-collapse pair in `ScheduledTasks.module.scss` stays (applied to the one remaining header button) — reverting it would churn SCSS to re-widen a rule that is still correct for any future second action; the comment's "applied to both header buttons" wording is updated to match the single-button reality. `ScheduledTasksPage` drops the disconnect state/handlers/labels and renders `ScheduledTasks` with no disconnect props; `resolveBannerState`, the login banner, and the login flow are untouched. The gate's `connected` boolean stays on the hook — it now feeds the Extensions tab.
*Alternative rejected:* keep the props as unused public API "for future hosts" — a documented prop that nothing renders behind is the exact dead-prop defect the lib rules call out.

### D7 — i18n: new settings-namespace keys, disconnect keys removed
New keys in `en.json` under `settings.extensions.*` (exact placement follows the grep of `translation-keys.ts` during the i18n slice, mirroring the namespace `SettingsI18nKeys`/`BasicI18nKeys.Usage` already use): tab label, section heading, section description, Name/Description column headers, the action column's `sr-only` header label, service default name, service description, warning-badge tooltip text ("Authorize to use this extension" — grep `en.json` first), logout button label + aria label, confirm title/description/failed message, success announcement. Generic values reuse `ButtonsI18nKeys`: the dialog cancel (`Cancel`), the logout label (`LogOut`), and the login label (`LogIn`, the same key the login banner's button uses). The login flow's in-flight label and outcome announcements reuse the banner's existing message keys verbatim (the wording fits the same flow in the new location), and the logout dialog's confirm title/description/failed message/success announcement reuse the existing `scheduledTasks.disconnect.*` keys verbatim (same operation, same wording — re-declaring identical values under a new namespace would violate the duplicate-value rule). Only the two keys that lost their consumer with the header button are removed: `scheduledTasks.disconnect.buttonLabel`/`ariaLabel` and their `ScheduledTasksI18nKeys` members, together with the last consumer.

### D8 — A11y: the action column header is visually empty, not informationally empty
The user-specified design has an empty action-column header; a `columnheader` with no accessible name is a hole for screen-reader users browsing the header row. The header renders no visible text but carries an `sr-only` localized label ("Actions") — visually empty, still announced. The table keeps `role="table"`/`row`/`columnheader`/`cell` semantics, the header row hides below `desktop:` (rows then stack, and each stacked cell is self-describing via its visible content), the logout button is keyboard-operable with a localized accessible name, the confirm dialog traps focus, and outcomes are announced through the polite live region. RTL: logical utilities only; `IconPlugConnected`/`IconLogout` are symmetric — no mirroring.

## Risks / Trade-offs

- [Core omits `connect` while connected] → the row shows the localized fallback name instead of a Core-derived one; identity is best-effort, the logout function is not affected.
- [Public API removal from `libs/scheduled-tasks`] → any external consumer passing the removed props fails typecheck; accepted because the props shipped in the same unreleased train as this removal and had exactly one consumer.
- [Two status checks in one navigation (page banner + settings tab)] → each is route-scoped to its own route; no double-fetch within a route.
- [Two login entry points (task-list banner + Extensions row)] → both drive the same `useOfflineCredentialsLogin` flow with the same gate/refetch machinery; the banner remains the indication surface on the task list, the row the account-level control.
- [Small warning badge as a tooltip trigger] → the badge overlay is smaller than a 44px target; the tooltip trigger gets a padded hit area (and the tooltip opens on focus, not hover only) so keyboard and touch users are not excluded.
- [Auto-login popup blocked by the environment] → the login flow already distinguishes popup-blocked from cancelled/timed-out/failed; all four land on the login-failed toast with the form preserved, so a popup-hostile browser degrades to the #9046-style manual path (Save again re-invokes).
- [Login succeeded but grant not yet effective → retried submit 403s again] → the loop guard stops the same activation from re-invoking login; the retry's failure keeps the generic error handling, and the user's next Save starts a fresh activation.
- [Mobile stacked rows] → the action column header disappears with the header row; the button remains labeled and operable in the stacked layout.

## Migration Plan

Frontend-only; implementation slices (each verified before the next): 1 — tab registration + gating + i18n tab label; 2 — ExtensionsTab section shell (heading/description/table + row identity + warning badge/tooltip) + tests; 3 — action flows (logout dialog relocation + login flow + announcements) + tests; 4 — auto-login on save failure (check-yields-connect, shared hook, retry, fallback toast, key swap) + tests; 5 — removal sweep (page button, lib props, README, tests, `scheduledTasks.disconnect.*` + `authSessionExpiredNotification` keys); 6 — docs sweep + `validate:docs` + five-axis review. Rollback: revert restores the #9108 header-button flow and the #9046 toast unchanged.

## Open Questions

- Surfacing Core's limited-access ("You can't create or edit tasks. Contact your administrator…") message on genuine permission denials is **deferred to a separate change** by user decision: whether Core even sends such a 403 body is unverified (nothing in this repo renders it; the one observed 403 body is bare `{"message": "Forbidden"}`; the BFF deliberately forwards no message on 403). Verify via the chat-api warn log (`DIAL Core error body for …`) with a limited-access account before designing that change.
- Exact key layout for the new strings (settings namespace placement in `translation-keys.ts`) — resolved by grep during the i18n slice.
- Whether the login flow's popup-blocked/cancelled/timeout outcomes reuse the banner's message keys verbatim or get settings-namespace wording — resolved by wording review during the i18n slice.
- Whether the settings side column (`@epam/ai-dial-settings-panel`) needs any panel-level registration beyond the `useSettingsTabConfig` entry — checked during slice 1; no change expected since `Usage` required none.
