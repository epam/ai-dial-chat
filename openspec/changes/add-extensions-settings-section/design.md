# Design: add-extensions-settings-section

## Context

The #9108 change delivered the full signout chain: `POST /api/v1/offline-credentials/signout` (BFF), the generated `signOutOfflineCredentials` operation, the `signOutOfflineCredentials()` wrapper, the gate's `connected` boolean, the lib's optional `onDisconnectClick` header action, and the page-level confirmation dialog on `ScheduledTasksPage`. This change relocates the user-facing half of that chain into a new Extensions section in Settings and removes the page-header affordance. The Settings machinery is data-driven: `SettingsTabs` (`apps/chat/src/types/settings-tabs.ts`) + one `useSettingsTabConfig` entry (`apps/chat/src/hooks/useSettingsTabConfig.tsx:29-61`) — `SettingsPage` resolves the active tab from the URL segment, so no route-table change is needed. The table pattern to mirror is `libs/usage-dashboard`'s `ModelLimitsSection` (div-based ARIA table; grid-template columns; hidden-on-mobile header row; avatar + name cell in `ModelLimitsRow`).

## Goals / Non-Goals

**Goals:**
- A Settings surface that lists the connected external Scheduler auth service with a per-row logout, replacing the Scheduled Tasks page header button as the single logout surface.
- The revoke stays refetch-authoritative and confirmed — identical semantics to the #9108 flow, new location.

**Non-Goals:**
- Login from the Extensions section (banner on the Scheduled Tasks page remains the login surface — Open Questions).
- Any BFF/generated-client change; new services; auto-signout; changes to the banner, gate-check timing, or the 403 disambiguation toast.

## Decisions

### D1 — Tab registration, feature-gated like the domain it exposes
`SettingsTabs.Extensions = 'extensions'` + a `useSettingsTabConfig` entry (`item` with `t(SettingsI18nKeys.Extensions)` label and `IconPlugConnected` — Tabler, symmetric, `aria-hidden`, `DIAL_KIT_ICON_STROKE`; `Component: ExtensionsTab`). The entry list becomes conditionally filtered: the Extensions entry renders only when `useFeatureFlag('scheduledTasksEnabled')` is `true` — the same flag that gates `ScheduledTasksPage` and (with `liveChatInteraction`) the BFF domain; a tab that always renders but whose status check always 403s is a dead surface. `SettingsPage`'s "default to first configured item" logic already handles a reduced entry list unchanged.
*Alternative rejected:* always-render the tab and show an "unavailable" empty state inside — one extra settings entry for every user without the feature, for no capability.

### D2 — Section composition: presentational table shell in `libs/settings-panel`, host knowledge in the tab
`apps/chat/src/pages/SettingsPage/ExtensionsTab/ExtensionsTab.tsx` owns the section: page heading `<h2 className="dial-h1-text …">` + description `<p className="dial-small-text …">` (the exact `UsageTab.tsx:239-244` pattern), then the table shell rendered through `ExtensionsSection` from `@epam/ai-dial-settings-panel` (table container, header row with the Name / Description column headers and the `sr-only` Actions header, the shared desktop grid template with a bounded action track, and one row per service — the `ModelLimitsSection` pattern, props-driven: `labels` for the shell, per-row fields for the display name, description, warning flag, `authorizeLabel`, and the trailing `action` node, plus `styles` color/typography overrides). The row renders the Name cell as `InitialsAvatar` + display name (the `ModelLimitsRow.tsx:108-114` avatar pattern), the Description cell, and the host's action. The lib holds no i18n, no gate/signout/confirmation knowledge — that stays in the tab, which passes translated labels and state-derived rows as props. The lib declares `@tabler/icons-react` as a dependency (the warning badge glyph); its peers stay `react` + `@epam/ai-dial-chat-shared` + `@epam/ai-dial-ui-kit`, which it already declared for `SettingsPanel`, so the extraction adds no new peer.
*Alternative rejected (the original D2, reversed on review of this change — the row and header only stay aligned through the shared grid template, and another DIAL chat wanting the same Extensions section would have to copy the whole shell):* keep the whole section app-level ("host knowledge dominates, so an app-level section respects library isolation where a lib would fight it") — true for what stayed in the tab, but the table shell itself is host-agnostic presentational markup; the reviewer-requested extraction splits exactly along that line.
*Alternative rejected:* generalize `libs/usage-dashboard`'s section — its props model is usage-specific; an unrelated extensions concept would widen a published lib for one consumer. `libs/settings-panel` was extended instead: it is the settings-surface lib, already publishes, and already declares exactly the peers the table needs.
*Alternative rejected:* a new standalone lib for the extensions table — one consumer today; extending the existing `libs/settings-panel` keeps the settings surfaces in one package with no new scaffolding.

### D3 — The row is the fixed service with the localized default name
The tab uses the existing `useOfflineCredentialsGate` (route-scoped, fires on mount; `/settings/extensions` is a fresh route entry). The row renders while the deployment has the service configured (gate `Available` — configured and disconnected — or `Hidden` — connected); a Spinner stands in for the table while the check is in flight, and no row renders while the service is unconfigured or the check errored. The row is the fixed Dial native service: its display name is the localized default (`settings.extensions.service.defaultName`), never derived from the OAuth client id Core happens to report for the connected grant — a client id is a stable technical identifier, not a product name, so it is not shown to the user; avatar initials = `extractInitials(displayName)` (`@epam/ai-dial-chat-shared`) from that same default name in a square `InitialsAvatar`. The row description is a localized constant for this service (`settings.extensions.schedulerService.description`, value "Provides access to built-in apps within the platform.") — Core exposes no per-service description.
*Alternative rejected (the original D3, reversed during implementation by user decision — keep the localized default name, see the implementation note in `ExtensionsTab`):* derive the display name from `connect.clientId` humanized (`dial-apps` → `Dial Apps`) — the gate's `connect` is set only while a login is possible (`available && !connected`), so a connected row would always have fallen back anyway, and a client id is not a product name.

### D4 — Action cell is a state-dependent Log in / Log out pair; refetch stays authoritative on both sides
The row's action cell switches on the gate's resolved state: **Log out** while `connected: true`, **Log in** while the gate's `connect` settings are present (a login is possible), empty when the row renders but Core sent no usable `connect` settings — while the check is in flight the section shows a Spinner with no table, and while the check errored no row renders at all. The Log out button carries `IconLogout` as its icon-before — the same glyph the removed Disconnect header action used (symmetric → no RTL mirror, `aria-hidden`, `DIAL_KIT_ICON_STROKE`); the button's label is the accessible name. **Logout:** activating Log out opens the existing ui-kit 2.0 `ConfirmationPopup` (`Danger` variant, `isDisconnecting` re-entry guard, failure swaps the description to the failed message) — the exact `ScheduledTasksPage` dialog relocated. Confirm: `await signOutOfflineCredentials()` → `await refetchCredentials()` → close the dialog and announce success only when the fresh check reports `connected: false`; any other outcome keeps the dialog open with the failed message. **Login:** activating Log in drives the existing `useOfflineCredentialsLogin` flow with the gate's `connect` settings (the same `handleLogIn` shape the page uses, minus the banner's retry-state machine — the tab has no banner, so popup-blocked/cancelled/timeout/failure outcomes surface as polite `aria-live` announcements using the existing banner outcome message keys where the wording fits, new keys otherwise; resolved by grep during the i18n slice). The button is disabled (label → "Logging in…") while the flow is in flight; a fresh `refetchCredentials()` decides the row's next state. Announcements go through a tab-level `sr-only` polite `aria-live` region.
*Alternative rejected:* logout-only with an empty action cell on a disconnected row — rejected by user decision: the row switches to a Log in action.
*Alternative rejected:* relocating the banner's retry-state machinery wholesale — the banner is a persistent inline surface that swaps its own body text; the row's cell is a button, so outcomes map to announcements, not banner states.

### D5 — Disconnected avatar carries a warning corner badge with a hover tooltip
While the last resolved state is disconnected (`available: true && connected: false`), the avatar renders a small warning badge overlaid at its **bottom-inline-end** corner: a relatively-positioned avatar wrapper with an absolutely-positioned `IconAlertTriangleFilled` (the login banner's warning glyph — filled, ignores the stroke prop) in a warning color. No existing avatar corner-badge component exists to reuse (`DeploymentIcon` has no status overlay; `ModelLimitsRow` renders its status as a separate pill), so the overlay is hand-rolled inside the row component. The badge is informational, not an affordance: a ui-kit `Tooltip` on the badge shows the localized text "Authorize to use this extension" on **hover** — the tooltip's own trigger carries the badge position so the hover reference has the glyph's real size (positioning a child instead leaves the reference zero-sized and the tooltip flickering, per the implementation note in `ExtensionServiceRow`). The badge is not focusable, so the tooltip opens on hover only; the state's a11y channel is the badge's own accessible name — the span is `role="img"` with the localized authorize text, the underlying svg `aria-hidden` — plus the Log in button's label, so the state is never communicated by color alone. The badge disappears when the row reports connected; it does not render while the check is in flight or errored (no state asserted).
*Alternative rejected (the original D5, reversed during implementation — see the comment in `ExtensionServiceRow`):* a keyboard-focusable tooltip trigger with a padded AAA hit area — the badge is informational and not an action; its accessible name already carries the text to assistive tech.
*Alternative rejected:* a separate warning column/cell — rejected by user decision: the badge sits on the avatar's corner.

### D9 — Auth-session 403 on save offers a user-consented login through the login-required toast, which retries the submit once
The #9046 path (`isScheduledTaskAuthSessionError` + the create/edit pages' `handleSubmitError`) upgrades from a toast-only indication to a login-and-retry flow driven by the login-required toast's action. The shared check util returns the disambiguation result **including the response's `connect` settings** (one fetch, no second client-settings request); the shared app-level hook (`useScheduledTaskAuthAutoLogin`) wraps `useOfflineCredentialsLogin` and exposes an async `autoLogin(connect)` — both pages drive it, so the orchestration cannot drift between create and edit (the single-shared-owner rule). The hook's refetch parameter is a plain fresh `getOfflineCredentials` call — the create/edit routes mount no gate hook, so no extra status request is issued outside the 403 path. Flow per **Save activation**: 403 → check → attributed + usable `connect` → the login-required error toast (`scheduledTasks.loginRequiredNotification`, carrying the trace ID and a **"Log in and retry"** action button) → the user clicks the action → the OAuth popup opens inside that fresh user activation → on success the page re-submits the body **re-prepared from the form's current values** (an edit made while the toast sat open is included; the form stays frozen via `isSubmitting` while the login runs) → success behaves like a normal save; a failed retry keeps today's generic error handling with **no second login toast in the same activation** (loop guard — a login that succeeded but left the grant ineffective must not ping-pong). On blocked/timeout/failure: the login-failed toast (`scheduledTasks.autoLoginFailedNotification`), form untouched, `isSubmitting` cleared so Save is operable again — the next Save re-runs the whole path. A user-cancelled login (the OAuth popup closed by the user) stays silent — the dismissal is deliberate, so no toast is shown beyond the dismissed login-required one. The old `scheduledTasks.authSessionExpiredNotification` toast and key are removed from this path; the generic error toast still covers genuine denials, failed checks, and missing `connect`.
Support changes: the whole submit orchestration (in-flight state, every failure branch, the login-required toast, the login-and-retry handshake) lives in one shared app-level hook, `useScheduledTaskSubmit` — the ~110 lines that were near-duplicates across the two pages (identical except the edit page's 404 branch and the fallback i18n key) now have one owner, so the consent short-circuit, the login outcome handling, and the retry-once guard cannot drift between create and edit. Each page supplies only its own pieces as component-level handlers (body preparation, the save request, the success path, `setErrors` as the field-error sink, the generic failure key; the edit page adds its not-found branch through `handleExtraError`) plus the login-and-retry action's rendering through a `renderLoginAndRetryAction?: (onAction: () => void) => ReactNode` option — the pages (components) render the Neutral/Outlined/Small `Button` (the kit's own retry-action doc example shape) with their own translated label, the hook (logic) holds no JSX and no kit imports; a host that omits the renderer gets the login-required toast without the retry action. `NotificationItem` gains `action?: ReactNode` and actionable toasts are manually dismissed (they must not vanish after 5s while the user is deciding); `showNotification` accepts a caller-supplied notification id (defaulting to a generated one) so the action's handler dismisses its own toast with an id computed before the action is built — no mutable binding assigned after the closure that reads it; a stale actionable toast left behind after a completed or failed login-and-retry would invite a second, duplicate save.
*Reversal:* the first implementation of this slice auto-invoked the login through a popup reserved synchronously at Save-click time (the reserved-popup pattern `useExternalServiceLogin.loginWithDialNative` uses), which opened an `about:blank` window on **every** save — a window flash on desktop and a tab switch away from the form on mobile, for a login that almost never runs. Reversed by user decision (2026-10-12): the login is user-consented through the toast action's click — the same gesture the Scheduled Tasks banner and the Extensions row use — which is itself the fresh user activation that lets the OAuth popup open without any reservation.
*Alternative rejected (superseded by the reversal):* auto-invoke the login with no intermediate toast — the earlier user decision "the login invokes automatically"; the unconditional reservation it required is the defect the reversal fixes.
*Alternative rejected:* prefetch the offline-credentials status when the form mounts and reserve the popup only when it reports `available && !connected` — one extra status GET per form visit, contradicting the no-status-request-outside-the-403-path rule, and a stale "connected" prefetch would still miss a mid-session logout.
*Alternative rejected:* replay the captured body object instead of re-preparing — re-preparing reuses one tested path, and the form is editable while the toast sits open, so the retried save must pick up any edit made since.

### D6 — Lib removal: revert the three props and the speculative generalization
`libs/scheduled-tasks` loses `onDisconnectClick`, `disconnectButtonLabel`, and `disconnectAriaLabel` (props model, component render branch, tests, README). The speculative generalization the #9108 disconnect work introduced for its second header button is reverted with them: the header's wrapper div (which existed only to hold two buttons) is removed, the `.actionButton`/`.actionButtonLabel` mobile-collapse pair reverts to its original `.createButton`/`.createButtonLabel` names with the original single-button comments, and the README's "any future header action button" sentence describes only the create button. A published lib carries no scaffolding for a hypothetical second action (reverses the earlier "keep the shared pair" decision — speculative generality flagged on review). `ScheduledTasksPage` drops the disconnect state/handlers/labels and renders `ScheduledTasks` with no disconnect props; `resolveBannerState`, the login banner, and the login flow are untouched. The gate's `connected` boolean stays on the hook — it now feeds the Extensions tab.
*Alternative rejected:* keep the props as unused public API "for future hosts" — a documented prop that nothing renders behind is the exact dead-prop defect the lib rules call out.
*Alternative rejected (the original D6, reversed on review):* keep the renamed shared collapse pair "still correct for any future second action" — speculative generality in a published lib for an action this change removes.

### D7 — i18n: new settings-namespace keys, disconnect keys removed
New keys in `en.json` under `settings.extensions.*` (exact placement follows the grep of `translation-keys.ts` during the i18n slice, mirroring the namespace `SettingsI18nKeys`/`BasicI18nKeys.Usage` already use): tab label, section heading, section description, Name/Description column headers, the action column's `sr-only` header label, service default name, service description, warning-badge tooltip text ("Authorize to use this extension" — grep `en.json` first), logout button label + aria label, confirm title/description/failed message, success announcement. Generic values reuse `ButtonsI18nKeys`: the dialog cancel (`Cancel`), the logout label (`LogOut`), and the login label (`LogIn`, the same key the login banner's button uses). The login flow's in-flight label and outcome announcements reuse the banner's existing message keys verbatim (the wording fits the same flow in the new location), and the logout dialog's confirm title/description/failed message/success announcement reuse the existing `scheduledTasks.disconnect.*` keys verbatim (same operation, same wording — re-declaring identical values under a new namespace would violate the duplicate-value rule). Only the two keys that lost their consumer with the header button are removed: `scheduledTasks.disconnect.buttonLabel`/`ariaLabel` and their `ScheduledTasksI18nKeys` members, together with the last consumer.

### D8 — A11y: the action column header is visually empty, not informationally empty
The user-specified design has an empty action-column header; a `columnheader` with no accessible name is a hole for screen-reader users browsing the header row. The header renders no visible text but carries an `sr-only` localized label ("Actions") — visually empty, still announced. The table keeps `role="table"`/`row`/`columnheader`/`cell` semantics, the header row hides below `desktop:` (rows then stack, and each stacked cell is self-describing via its visible content), the logout button is keyboard-operable with a localized accessible name, the confirm dialog traps focus, and outcomes are announced through the polite live region. RTL: logical utilities only; `IconPlugConnected`/`IconLogout` are symmetric — no mirroring.

### D10 — Offline-credentials hooks extraction to `libs/chat-hooks` (post-review)
The three app hooks — `useOfflineCredentialsGate`, `useOfflineCredentialsLogin`, `useOfflineCredentialsAuth` — move to `libs/chat-hooks/src/offline-credentials/` with every host coupling as a parameter, the `useApplicationCredentials` pattern: the gate and the auth hook take `offlineCredentialsClient: Pick<OfflineCredentialsApi, …>` (already-configured generated client, never constructed inside the lib), and the login flow takes the OAuth `callbackPath` instead of importing `ROUTES.ToolsetSignIn`. `apps/chat` keeps one-line wrappers in `apps/chat/src/hooks/offlineCredentials/` that pre-wire `offlineCredentialsApi` and `ROUTES.ToolsetSignIn`, so every consumer's import path and every spec's mock seam stay stable. The gate drops the pathname-keyed re-fetch: every consumer surface is a route component that remounts per entry, so the mount-fired check + unmount abort already re-check per route entry (also fixes the stale "Route-scoped … for the Scheduled Tasks list route" JSDoc — ExtensionsTab uses the hook too). The auth hook becomes outcome-based: `loginOutcome` plus `logOut` resolving `OfflineCredentialsLogoutOutcomeType` (`Disconnected`/`NotDisconnected`/`Failed`) instead of a boolean, `liveAnnouncement` dropped — the host maps outcomes onto announcement text (`apps/chat/src/utils/offline-credentials-announcements.ts`, the `LOGIN_ANNOUNCEMENT_KEYS` map relocated), so the lib holds no i18n. The login hook's stale timeout-constant comment is repointed at `oauth/handshake.ts`'s `DEFAULT_OAUTH_RESULT_TIMEOUT_MS` (its real home since the handshake extraction).
*Alternative rejected:* keep the hooks app-level — the reviewer's point: they are the reusable part of the feature and almost all host-agnostic; another DIAL chat would otherwise copy them. The isolation line splits cleanly: client instances, callback path, and announcement text parameterize; routing and i18n stay app-side, exactly what the `chat-hooks` exception (thin request/response + configured-client parameters) sanctions.
*Alternative rejected:* parameterized announcement strings on the auth hook (a `Record<outcome, string>` prop) — returning outcomes is cleaner: no string props, no English defaults, no wording knowledge in the lib at all; hosts keep full wording control.

### D11 — One shared response mapper; the 403 check joins the helpers in `libs/chat-hooks` (post-review)
The DTO→`OfflineCredentialsStatusResult` mapping was written in three places — the gate's `fetchStatus`, `checkScheduledTaskAuthSessionError`, and `useScheduledTaskAuthAutoLogin`'s raw-DTO refetch (which worked only by structural-typing luck). One mapper in `libs/chat-hooks/src/offline-credentials/map-offline-credentials-response.ts` now serves all three: `mapOfflineCredentialsResponse` (null-coalesced flags + connect gated on available-and-disconnected) for the gate and the refetch, and `normalizeOfflineCredentialsConnectSettings` (the line-identical connect block) for the gate and the check. The split is deliberate: the check's tested contract returns the connect settings from the same single check **regardless of the connection state** ("so the caller decides from one check") — gating its connect on the mapper's available-and-disconnected rule would break that contract, so the check takes its flags from the mapper and its connect from the normalize. `checkScheduledTaskAuthSessionError` itself moves to `libs/chat-hooks/src/scheduled-task/` beside the other scheduled-task helpers, with the one status call arriving as a passed-in `getOfflineCredentials` operation (the app passes its thin server-api wrapper) — the fourth library-isolation exception's checklist holds: the rule depends only on the DIAL Core response's own shape (the `403` status, `available`/`connected`, `connect` completeness), its test suite relocates with it proven behavior-preserving, and every host consumes it identically with the per-host variance (toasts, wording, retry) staying app-side in `useScheduledTaskSubmit`.
*Alternative rejected:* gate the check's connect through the full mapper — breaks the documented "connect returned even while connected, so the caller decides from one check" contract; the mapper's gating is the gate's rule, not the check's.
*Deferred (follow-up, only if another host adopts the create/edit pages):* extracting `useScheduledTaskSubmit`'s error classification into a pure outcome-enum function (field errors / admin consent / login required / generic) — the hook is genuinely app-level (`useNotification`, `t()`, a rendered `Button` in the toast), and the classifier is speculative until a second host exists. When that host appears, the move's shape is required parameters, not optional ones: the lib hook declares `notifications` (the show/dismiss surface) and `labels` and renders its action through a caller-supplied renderer; the host's scheduled-tasks module pre-wires `useNotification()` and `t()`, exactly the one-line-wrapper pattern the offline-credentials hooks use. The action's rendering is decoupled **now**, not deferred: `useScheduledTaskSubmit` takes `renderLoginAndRetryAction?: (onAction) => ReactNode` and the two pages render their own `Button` (the hook holds no JSX and no kit imports) — the same cut, one layer early, so the remaining deferred surface is only `notifications` + `labels` + the message strings. An optional/null default for the notification surface was rejected — a caller that forgets it would get a hook that swallows every outcome silently; a param that changes behavior on omission must be required. The caller-supplied notification id (`showNotification`'s optional `id`) is the piece that is not deferred either — it is done now (see D9's amended support-changes note), because it removes the `let toastId` temporal coupling the submit hook carried and makes the future notification surface id-transparent for the extraction.

## Risks / Trade-offs

- [Core omits `connect` while connected] → the row shows the localized fallback name instead of a Core-derived one; identity is best-effort, the logout function is not affected.
- [Public API removal from `libs/scheduled-tasks`] → any external consumer passing the removed props fails typecheck; accepted because the props shipped in the same unreleased train as this removal and had exactly one consumer.
- [Two status checks in one navigation (page banner + settings tab)] → each is route-scoped to its own route; no double-fetch within a route.
- [Two login entry points (task-list banner + Extensions row)] → both drive the same `useOfflineCredentialsLogin` flow with the same gate/refetch machinery; the banner remains the indication surface on the task list, the row the account-level control.
- [Small warning badge with a hover-only tooltip] → the badge is informational, not an affordance (see D5's reversal): its localized accessible name (`role="img"`) carries the state to assistive tech and the Log in button's visible label carries the remedy for everyone, so the hover-only tooltip is an enhancement — sighted keyboard users never see the tooltip sentence, but no state or action is hidden from them.
- [Login popup blocked by the environment] → the login flow already distinguishes popup-blocked from cancelled/timed-out/failed; all four land on the login-failed toast with the form preserved, so a popup-hostile browser degrades to the #9046-style manual path (Save again re-offers the login toast).
- [Login succeeded but grant not yet effective → retried submit 403s again] → the loop guard stops the same activation from re-invoking login; the retry's failure keeps the generic error handling, and the user's next Save starts a fresh activation.
- [Mobile stacked rows] → the action column header disappears with the header row; the button remains labeled and operable in the stacked layout.

## Migration Plan

Frontend-only; implementation slices (each verified before the next): 1 — tab registration + gating + i18n tab label; 2 — ExtensionsTab section shell (heading/description/table + row identity + warning badge/tooltip) + tests; 3 — action flows (logout dialog relocation + login flow + announcements) + tests; 4 — login-and-retry on save failure (check-yields-connect, shared hook, login-required toast + action, retry, fallback toast, key swap) + tests; 5 — removal sweep (page button, lib props, README, tests, `scheduledTasks.disconnect.*` + `authSessionExpiredNotification` keys); 6 — docs sweep + `validate:docs` + five-axis review. Rollback: revert restores the #9108 header-button flow and the #9046 toast unchanged.

## Open Questions

- Surfacing Core's limited-access ("You can't create or edit tasks. Contact your administrator…") message on genuine permission denials is **deferred to a separate change** by user decision: whether Core even sends such a 403 body is unverified (nothing in this repo renders it; the one observed 403 body is bare `{"message": "Forbidden"}`; the BFF deliberately forwards no message on 403). Verify via the chat-api warn log (`DIAL Core error body for …`) with a limited-access account before designing that change.
- Exact key layout for the new strings (settings namespace placement in `translation-keys.ts`) — resolved by grep during the i18n slice.
- Whether the login flow's popup-blocked/cancelled/timeout outcomes reuse the banner's message keys verbatim or get settings-namespace wording — resolved by wording review during the i18n slice.
- Whether the settings side column (`@epam/ai-dial-settings-panel`) needs any panel-level registration beyond the `useSettingsTabConfig` entry — checked during slice 1; no change expected since `Usage` required none.
