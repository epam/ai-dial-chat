## 9. Follow-up: reliable tool-discovery contract from DIAL Core (mcp-app-discovery-contract)

Both current tool-discovery paths in `useMcpAppTools` are workarounds, not a proper contract:

- **Direct discovery** requires an admin to explicitly set `features.mcp: true` on the deployment in DIAL Core config. A quick app that is itself the MCP server (e.g. "NT AWS Explore") will never be discovered unless this flag is set.
- **Indirect discovery** prefix-matches tool-call names against the `displayName` of toolsets in the catalog. This is a convention, not a spec: it breaks if the orchestrator does not name delegated tool calls `{toolsetDisplayName}_{toolName}`, if the prefix contains underscores, or if the application is its own MCP server (no separate toolset to match against).

**Confirmed failure case**: "NT AWS Explore" — a quick app whose tools (`NT_AWS_Explore_search_amazon`, `NT_AWS_Explore_present_amazon_products`) are prefixed with the application's own name, not a separate toolset. `availableToolsets` is empty, `features.mcp` is unset, so neither path fires. Canvas never opens.

**Immediate workaround**: set `features.mcp: true` on the deployment in Core config; direct discovery then works via the `application` kind path.

**Required long-term fix (Core-side)**:

- [ ] 9.1 Investigate/propose a Core-side contract that lets the host enumerate MCP-Apps-capable tools for any deployment without requiring explicit `features.mcp` config or name-prefix inference. Candidate approaches:
  - A deployment-agnostic flag or field in `DeploymentItemDto`/`ApplicationDetailsDto` that signals MCP capability without admin configuration.
  - Core returning `_meta.ui.resourceUri` in a deployment-metadata endpoint rather than only via `tools/list` (which today requires a live MCP session, not just catalog metadata).
  - Core enriching `tools/list` responses for quick apps to include the delegated toolsets' tool metadata, so the application's own `tools/list` already contains `_meta.ui.resourceUri`-bearing entries.
- [ ] 9.2 Once Core ships the contract, remove the prefix-guessing path from `useMcpAppTools` and replace both paths with a single reliable lookup. Remove the debug logging added during investigation (`useMcpAppTools.ts` effect log, `listMcpAppTools` log).
- [ ] 9.3 Update `design.md` D9 to replace the current workaround description with the final contract.

## 14. Per-message matching fixed for toolset-backed vs. self-hosted apps (bug reports)

- [x] 14.1 Fixed: the trigger stayed visible under every assistant message for the rest of the conversation once any MCP-capable tool was discovered, even for messages that never called it. `findMcpAppForMessage`'s unconditional `?? mcpAppTools[0]` fallback made every settled message match once `mcpAppTools` was non-empty. Now the fallback only applies while the message is still streaming (`custom_content.state` may not have caught up yet); a settled `kind: 'toolset'` message with no matching call name returns `undefined` and shows nothing.
- [x] 14.2 Fixed: a `kind: 'application'` self-hosting MCP App (the deployment itself is the MCP server — a quick app is the common case) is not an LLM-orchestrated tool-call turn and never populates `custom_content.state`, so it can never win 14.1's real-match check. `findMcpAppForMessage` now always matches a `kind: 'application'` tool when no real call matched, regardless of streaming state, restoring the "always visible" behavior specifically for self-hosted apps (see D9's known discovery gap for the same class of app).
- [x] 14.3 Fixed: `resolveMcpAppToolResult`'s live re-call (D10) required `seed?.toolInput != null`, so a `kind: 'application'` message with no seed (the normal case per 14.2) never got live data — the mounted app showed no initial `toolInput`/`toolResult` at all. The `kind: 'application'` branch now always calls live, passing `seed?.toolInput ?? {}` when no seed exists (the same "give me your current state" call the app's own resource would make on `ui/initialize` if the host didn't pre-seed it) — falling back to `seed?.toolResult` (now optional-chained; the previous unconditional `seed.toolResult` would have thrown once `seed` could be `undefined` here) only if the live call itself fails.
- [x] 14.4 Fixed (confirmed via a real "NT Weather App" turn, `kind: 'toolset'`, indirect discovery): when a tool is retried in the same turn after a failed first attempt (e.g. `weather_get_weather` called with `location: "London,UK"` → `Location not found`, then retried with `location: "London"` → success), `resolveMcpAppToolCallSeed`'s `[...calls.values()].find(...)` returned the **first** matching call by insertion order — the failed attempt's bad args and error text — instead of the retried, successful one, so the inline preview/canvas seeded with wrong/error `toolInput`/`toolResult`. Now uses `.reverse().find(...)` so the last (most recent, authoritative) matching call wins.
- [x] 14.5 Fixed (bug report: a real `kind: 'application'` deployment's `mcp-app-tool-call` endpoint received 3 identical POSTs in a row): `useMcpAppInlinePreview`'s effect started `fetchResourceHtml`/`resolveMcpAppToolResult` directly inside the effect body with only a post-hoc `cancelled` flag guarding the resulting `setState` calls — the flag never stopped the actual network calls from firing. React's dev-only StrictMode double-invokes an effect (mount → cleanup → remount) before the first run's async work settles, so both runs saw a cache miss and both started their own fetch/live-tool-re-call. ## 16. App-initiated container-dimension requests (`ui/notifications/host-context-changed`)

Some apps request their container size by sending `ui/notifications/host-context-changed` **upstream** with `params.containerDimensions` (e.g. `{ width: 670, height: 382 }`) instead of the standard `size-changed` notification. The protocol's `AppNotification` union includes the method in the app→host direction and this repo's sandbox proxy relays it verbatim, but `@mcp-ui/client`'s `AppFrame` registers no handler for it — `AppBridge` dropped it, leaving the iframe at its hardcoded `600px` default height (the observed extra bottom space under such apps). See design.md D13 (revised) and the `mcp-app-canvas` spec requirement.

- [x] 16.1 `McpAppCanvasRenderer` registers a notification handler on its host-owned `AppBridge` via the SDK `Protocol`'s `setNotificationHandler` with `@modelcontextprotocol/ext-apps`' `McpUiHostContextChangedNotificationSchema` (verified exported from the same `./app-bridge` entry the models already import from; the SDK's `zod-compat` `AnyObjectSchema` accepts the zod-v4 schema).
- [x] 16.2 The handler applies `params.containerDimensions` to the sandbox iframe (queried from the renderer's container at invocation time, since `AppFrame` creates the iframe in its own mount effect) with the same inline-style assignment `AppFrame` performs for `size-changed`: fixed `width`/`height` replace the `100%`/`600px` defaults; `maxWidth`/`maxHeight` clamp via `style.maxWidth`/`style.maxHeight`; absent `containerDimensions` is a no-op. The `.fullscreenFrame` `!important` rule keeps the fullscreen canvas immune.
- [x] 16.3 Renderer-internal by design — no new `McpAppCanvasContent` callback (an app sizing itself is mechanics, like `size-changed`, not a host policy decision). `libs/attachment-canvas/README.md`'s renderer section, the `mcp-app-canvas` spec, and design.md D13 updated in the same change.
