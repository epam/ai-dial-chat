## Context

Tool-call activity from an MCP-backed toolset already reaches the frontend as `custom_content.stages` on an assistant message, streamed over SSE from DIAL Core and rendered by `StagesPanel`/`StageItem` (`stage-visualization` capability, `libs/conversation-stages`). Toolsets themselves are MCP servers DIAL Core connects to on the model's behalf (`catalog-toolsets`, `toolset-authoring` — each toolset exposes an MCP endpoint URL, e.g. `buildToolsetMcpUrl`). `AttachmentCanvas` (`libs/attachment-canvas`) already hosts one precedent for "iframe driven by a third-party app": `VisualizerCanvasRenderer`, which speaks a bespoke postMessage protocol (`@epam/ai-dial-visualizer-connector`) to operator-registered visualizer URLs.

MCP Apps is a different, standardized extension: a tool result can carry `_meta.ui.resourceUri` pointing to a `ui://` resource (an HTML/JS/CSS bundle) that a *host* fetches and renders in a sandboxed iframe, then drives via an MCP-Apps-specific JSON-RPC-over-`postMessage` dialect (`ui/initialize`, forwarded `tools/call`, context updates). This is incompatible with `VisualizerConnector`'s wire format — it needs its own content type and renderer, not a branch inside the existing one.

**DIAL Core contract — confirmed.** `epam/ai-dial-core` PR #1745 ("MCP Apps Phase 1 — domain rewrite in tools/list and resource endpoint", merged 2026-07-31) ships the DIAL Core half of this feature:

- A `RewriteMcpUiDomainFn` response function, wired into the existing `tools/list` pipeline, rewrites `_meta.ui.domain` on every tool in the response — but only for deployments where an admin has set `mcp_apps.domain_override` in the `Application.Mcp` config (JSON key `mcp_apps.domain_override`; Java `Application.Mcp.mcpApps.domainOverride`). The `_meta.ui.resourceUri` field itself is declared by the upstream MCP server per the MCP Apps spec — Core only rewrites the `domain` sub-field of whatever `ui` object the tool already returned. If a deployment has no `mcp_apps` config, tool metadata passes through byte-for-byte unchanged (no `ui` rewriting, no new route overhead).
- A new endpoint, `GET /v1/deployments/{deployment_name}/mcp/resources?uri={ui://...}` (`McpResourceController`), fetches the resource via `resources/read` against the upstream MCP session and returns the raw resource body directly — `Content-Type` taken from the upstream `mimeType` (validated against a fixed allowlist: `text/html`, `text/plain`, `text/css`, `application/json`, `image/svg+xml`, `image/png`, `image/jpeg`, `image/gif`, `image/webp`), plus `Content-Security-Policy: frame-ancestors 'self'; sandbox allow-scripts; default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src https: data:` and `X-Content-Type-Options: nosniff`. Works for both `Application` and `ToolSet` deployments, reusing existing auth injection (`McpUpstreamAuthInjector`) — no new grant. Errors: `400` (missing/non-`ui://` `uri`), `403` (consent), `404` (unknown deployment / app has no MCP config), `502` (upstream fetch/mimetype/empty-body failure), `500`, and Core's existing rate limiter (`429` with `Retry-After`).
- **No new Core endpoint for app-initiated `tools/call` forwarding.** This PR only consolidated auth injection across Core's *existing* generic MCP JSON-RPC proxy routes (`ApplicationMcpProxyController`, `ToolSetMcpProxyController`, at `/v1/deployments/{id}/mcp`), which already forward arbitrary JSON-RPC — including `tools/call` — to the upstream MCP server. An MCP App's self-initiated tool call reuses that existing proxy; it does not need a Core change.

This resolves the prior open dependency: ai-dial-chat's `chat-api` proxy should mirror Core's raw-passthrough resource endpoint (not synthesize a JSON DTO around it) and forward app-initiated tool calls through Core's existing generic MCP proxy rather than any bespoke Core surface. See "Decisions" and the former "Open Questions" (now resolved, kept below for record) for how this reshapes D3/D4/D6.

## Goals / Non-Goals

**Goals:**

- Render an MCP tool's `ui://` resource inside `AttachmentCanvas` as a new `McpApp` content type, sandboxed and isolated per the MCP Apps security model (no DOM/cookie access to the host page).
- Let the mounted app call tools on its owning MCP session and receive results, via a client library rather than a hand-rolled protocol implementation.
- Surface the app inline, always visible, on the message that produced the UI resource, with a manual action to expand it into the full-width canvas — see D5 (revised) / D11.
- Keep MCP transport/session/auth knowledge entirely in `apps/chat-api` (and `apps/chat/src/server-api` for the client-side call), so `libs/attachment-canvas` and `libs/conversation-stages` only see resolved values and callbacks — per the library isolation rule.

**Non-Goals:**

- Building a general-purpose MCP client/host framework, or a UI for browsing/discovering MCP Apps outside of a tool call result.
- Implementing DIAL Core's side of the MCP Apps contract. If it's missing, this change delivers the ai-dial-chat half and documents the exact shape DIAL Core needs to provide.
- Supporting MCP Apps host capabilities beyond `tools/call` forwarding in v1 (e.g. `sendOpenLink`, device permission grants, context/notification push from host to app) — noted as follow-ups.

## Decisions

### D1: New `AttachmentContentType.McpApp`, not a branch on `Visualizer`

`VisualizerCanvasContent`'s fields (`visualizerName`, `layout`, opaque `data`) are shaped around the `VisualizerConnector` handshake and have no equivalent of a `ui://` resource URI, tool-call forwarding, or the MCP-Apps JSON-RPC envelope. Reusing the type would force irrelevant fields onto both variants. A new content type mirrors how `Visualizer` itself was added as a sibling to `Html`/`Pdf`/etc. — same pattern, new leaf.

**Alternative considered**: extend `VisualizerCanvasContent` with optional MCP-specific fields. Rejected — conflates two incompatible protocols in one type and makes `isDownloadable`/`AttachmentCanvas`'s switch harder to reason about.

### D2: Client library — `@mcp-ui/client` (confirmed via spike, `tasks.md` §2)

`@mcp-ui/client@7.1.1`'s peer deps (`react`/`react-dom` `^18 || ^19`) match this repo. Its `AppRenderer` component accepts pre-fetched `html` directly (`html` prop — "skips all resource fetching") plus custom `onCallTool`/`onReadResource`/etc. handlers in place of a live MCP `client`, which is exactly the "no client, custom handlers" shape this change needs (transport stays server-side). `App Bridge` (`@modelcontextprotocol/ext-apps`) is what `@mcp-ui/client` itself is built on — using `@mcp-ui/client` directly, rather than App Bridge's lower-level primitives, avoids re-implementing the double-iframe sandbox relay and JSON-RPC dialect by hand, which D2 always intended to avoid.

**Spike finding that reshaped D3 below**: `AppRenderer`/`AppFrame` do not take a resource URL to set as a plain iframe `src`. They require either fetched HTML content or a live MCP client, **and** a `sandbox: { url: URL }` pointing at a separate, cross-origin "sandbox proxy" page that the *host* (us) must build and deploy — this is `@mcp-ui/client`'s (and the underlying MCP Apps spec's) double-iframe security architecture: a trusted proxy page on an isolated origin relays postMessage traffic between the host and a further-nested, genuinely sandboxed iframe holding the untrusted tool HTML. Neither `@mcp-ui/client` nor `@modelcontextprotocol/ext-apps` ships this proxy page; `modelcontextprotocol/ext-apps`'s own repo (`examples/basic-host/{sandbox.html,src/sandbox.ts,serve.ts}`) is a reference implementation of one, which `mcp-app-sandbox-proxy` (new capability, below) adapts.

### D3: `McpAppCanvasRenderer` fetches HTML via the app layer and renders through an isolated-origin sandbox proxy

Mirrors `VisualizerCanvasRenderer`'s constraint (no app-level context reads) but goes further: `VisualizerCanvasRenderer` connects straight to an operator-configured third-party URL, because visualizers are static operator config. MCP Apps tool calls need live credentials/session scoped to the toolset that produced them — that must stay server-side.

Core's `mcp/resources` endpoint is still a raw-passthrough GET, exactly as PR #1745 designed it (see Context) — that part of "follow Core" is unchanged. What changes from the earlier draft of this decision is **who consumes that endpoint and how**: since `@mcp-ui/client`'s `AppRenderer` needs HTML content, not a URL, `apps/chat`'s app layer (`useOpenMcpAppCanvas`, `mcp-app-trigger` capability) fetches `chat-api`'s GET endpoint via JS and passes the resulting HTML text into `McpAppCanvasContent`. The renderer receives:

- `html: string` — the fetched resource body, passed straight to `@mcp-ui/client`'s `AppRenderer` (`html` prop — "skips all resource fetching"); the renderer itself makes no network calls.
- `sandboxUrl: string` — the isolated-origin URL of the `mcp-app-sandbox-proxy` deployment (see below), resolved by the app layer from client config, passed as `sandbox: { url: new URL(sandboxUrl) }` to `AppRenderer` (no `permissions` field — the installed `@mcp-ui/client` does not expose one on `SandboxConfig`). The inner iframe's `sandbox` attribute (`allow-scripts allow-same-origin allow-forms`) is hardcoded by `apps/mcp-app-sandbox/src/app/sandbox-page.ts` (see D6); `allow-same-origin` grants the tool HTML the sandbox proxy's own isolated origin, which is bounded to that origin — not the chat app's origin.
- an `onToolCall(name, args): Promise<CallToolResult>` callback wired to `AppRenderer`'s `onCallTool`, forwarding to a `chat-api` endpoint that holds the real MCP session.

This keeps `libs/attachment-canvas` ignorant of toolset IDs, MCP endpoints, auth, and env-configured URLs — it only ever receives resolved `html`/`sandboxUrl`/callback values, consistent with how it already ignores DIAL file URLs and only receives resolved `url`/`blob` values from `apps/chat/src/utils/attachment-canvas.ts`. Importing `CallToolResult` (and other wire types) from `@modelcontextprotocol/sdk/types.js` inside the lib is the protocol's own vocabulary, not a host-specific integration detail — the same tier as `VisualizerCanvasRenderer` already importing `VisualizerConnectorRequests` from `@epam/ai-dial-shared`.

### D7: `mcp-app-sandbox-proxy` — a new, isolated-origin deployable app

Per the user's explicit direction to favor the more effort-intensive, more secure option: the sandbox proxy is a **new Nx app**, `apps/mcp-app-sandbox` (minimal NestJS), deployed at an origin genuinely distinct from `apps/chat`'s — the MCP Apps spec's double-iframe architecture and `@modelcontextprotocol/ext-apps`'s own runtime self-test (in its reference `sandbox.ts`) both assume/require this; reusing `apps/chat-api`'s existing same-origin static-serving pattern (as `chat-overlay-sandbox` does, via `/overlay-sandbox`) would defeat the isolation the architecture exists for.

- One route serves a self-contained HTML response (inline `<script>`, no separate JS bundle/build step) adapted from `modelcontextprotocol/ext-apps`'s `examples/basic-host/{sandbox.html,src/sandbox.ts}`: referrer/origin validation, the double-iframe relay (host ↔ proxy ↔ inner untrusted iframe), and the outer self-test that verifies `sandbox` isolation is actually in effect.
- **Server-side Referer validation, not client-side regex.** The reference implementation validates `document.referrer` client-side against a hardcoded regex. This app instead validates the `Referer` request header server-side against an env-configured allowlist (`MCP_APP_SANDBOX_ALLOWED_HOST_ORIGINS`) before serving anything (403 otherwise), and injects the *validated* origin into the emitted script — a stronger guarantee than trusting the browser-supplied `document.referrer` against a client-embedded pattern.
- **Fixed, maximally-restrictive CSP for v1** (`default-src 'self'`, `frame-src 'none'`, `object-src 'none'`, `base-uri 'none'`, images/styles/fonts limited to `'self' data: blob:`) — no per-tool `csp` query param support yet, unlike the reference implementation's configurable `buildCspHeader`. **Non-goal / follow-up**: tool UIs that need to load external images/fonts/connect to third-party domains beyond same-origin won't render correctly under this default; plumbing per-toolset CSP domain allowlists through is deferred, not silently unsupported forever.
- `Content-Security-Policy` and `Cache-Control: no-store` set as real HTTP response headers (not `<meta>` tags — tamper-proof, matching the reference implementation's own rationale).
- Absence of a deployed+configured sandbox proxy (`MCP_APP_SANDBOX_URL` unset) means the "Open app" trigger simply never appears — same "absence isn't failure" posture already established for `mcp_apps.domain_override` in the Context section.

`apps/chat` learns the sandbox proxy's URL the same way it already learns `dialCoreExternalUrl`/`customVisualizers`: a new client-visible key (`mcpAppSandboxUrl`) in `apps/chat-api`'s existing `AppConfigService`/`ClientConfigResponseDto` pipeline, sourced from a new `MCP_APP_SANDBOX_URL` env var — no new frontend-only env-injection mechanism is introduced.

### D4: `chat-api` proxy is deployment-agnostic for the resource GET; `tools/list`/`tools/call` route by kind

The proxy endpoints are scoped by deployment ID (the same ID already used by `buildToolsetMcpUrl`/`buildApplicationMcpUrl`, and the same identifier Core's `mcp/resources` route calls `deployment_name`) — the backend resolves "deployment ID → MCP endpoint + credentials" using the existing toolset/application lookup, so the frontend never has and never sends a raw MCP server URL. `apps/chat-api` needs two operations:

- **GET, cacheable, raw passthrough**: mirrors Core's `GET /v1/deployments/{deploymentId}/mcp/resources?uri={resourceUri}` — same status codes, same headers, body untouched. No `McpAppResourceDto` JSON wrapper; there's nothing in Core's response to wrap (see D6). Per D3, `apps/chat` consumes this via a JS `fetch` (to obtain the HTML text for `@mcp-ui/client`'s `AppRenderer`), not as a bare iframe `src` — that's a frontend consumption detail and doesn't change this endpoint's shape. This endpoint is deployment-generic: Core's `McpResourceController` works identically for both `ToolSet` and `Application` deployments — no `kind` parameter required.
- **POST, not cached**: accepts `{toolName, arguments, kind}` from the frontend, validates `toolName` against the deployment's exposed tools (same check chat-api's existing invocation path already does), and forwards a `tools/call` JSON-RPC request through Core's *existing* generic MCP proxy — the same route/auth path already used for LLM-driven tool calls, not a new Core surface. **Correction, confirmed via spike**: unlike the GET resource endpoint above (which is deployment-generic), Core's generic MCP JSON-RPC proxy is prefix-specific by deployment kind (`ToolSetMcpProxyController` at `/v1/toolset/{id}/mcp` vs `ApplicationMcpProxyController` at `/v1/deployments/{id}/mcp` — same distinction `apps/chat/src/utils/mcp-endpoint-url.ts`'s `buildToolsetMcpUrl`/`buildApplicationMcpUrl` already encode for the LLM-driven session path). A toolset id against `/v1/deployments/{id}/mcp` 404s. **`kind` must therefore be sent by the frontend and forwarded to `McpAppService.callTool`/`rpcRequestForDeployment`** — it determines which of the two proxy prefixes to use. The `tools/list` validation call inside `callTool` must also use the correct prefix. The JSON-RPC `result`/`error` is unwrapped into `McpAppToolCallResponseDto{result}` / a `502`.
  - **Bug confirmed via end-to-end test** (StatGPT `statgpt-gtdc` application): the original implementation of `McpAppToolCallRequestDto` omitted `kind`, so `callTool` always hardcoded `McpDeploymentKindDto.Toolset` and routed through `/v1/toolset/{id}/mcp`. For an application-type deployment this produced `WARN DIAL Core returned 404 for mcp "tools/list" for toolset "{id}"` and a `404 Resource not found` response to the frontend. Fixed by adding `kind: McpDeploymentKindDto` to `McpAppToolCallRequestDto`, threading it through `McpAppController → McpAppService.callTool → rpcRequestForDeployment`, and propagating it from `McpAppToolRef.kind` through `callMcpAppTool` in `apps/chat/src/server-api/mcp-apps.ts` and `useOpenMcpAppCanvas.ts`.

Both reuse whatever session/consent DIAL Core already establishes for that deployment in the current conversation — no separate MCP-Apps-specific grant exists on the Core side today.

### D5 (revised three times): Trigger lives inside the message body, below the stages, as a normal-size primary "Open App" button, operates on the message directly (no `Stage` involved), and auto-opens for the most recent matched message

**Original decision (superseded).** The first version of this decision put the trigger on `StageItem` as a small, icon-only action, manually clicked, matching every other `AttachmentCanvas` trigger's explicit-action posture — specifically to avoid stealing focus mid-stream.

**First revision (superseded).** Moved the trigger to `libs/conversation-messages`'s `MessageActions` bar (the Like/Dislike/Copy row), rendered as a `PrimaryButton` at `ElementSize.Small`, positioned opposite the icon actions via `justify-between`. **Rejected on review — didn't feel right** placed alongside the hover-revealed, icon-scaled action row.

**Second revision (superseded in part).** Landed the button directly in the message body's `afterContent` (`ConversationMessageItem.tsx`), immediately below the `CollapsedGroup` stages block, as a default-size (`ElementSize.Standard`) `PrimaryButton` labeled "Open App" (`AttachmentCanvasI18nKeys.OpenAppLabel`). Per explicit user direction, this trigger was also made to show *unconditionally* on every assistant message once the deployment has any MCP-Apps-capable tool (`mcpAppTools.length > 0`) — not gated on a real tool-call stage matching. That change is what exposed the problem the third revision fixes below; the placement/sizing/label themselves are unchanged.

**Third revision, per explicit user direction ("the button is not connected to any stage, it's outside of them"):** once the trigger's visibility stopped depending on finding a real tool-call stage, threading a `Stage` through the whole pipeline (`Stage.mcp_app`, `useOpenMcpAppCanvas(stage, ...)`, the `MCP_TOOL_STAGE_NAME_PATTERN` regex used to fake Core's not-yet-real per-stage correlation) became dead weight — the regex only mattered for a code path that rarely determined what the user actually saw. This revision removes `Stage` from the trigger/canvas path entirely:

- **`Stage.mcp_app` is deleted** from `libs/chat-shared`'s `Stage` interface — nothing reads it anywhere in the codebase anymore. If Core ever ships real per-stage correlation, it can be re-added at that time against its real shape, rather than kept as a speculative, now-unread field.
- **Correlation moved to the message level.** `apps/chat/src/utils/mcp-app.ts`'s `findMcpAppForMessage(message, mcpAppTools)` replaces the old `findMcpAppStage`/`attachMcpAppOnStages`/regex pair. It reads `message.custom_content.state.tool_messages` (see the new sub-decision below) for the names of tools actually called this turn, matches against the real `mcpAppTools` list by exact name, and falls back to `mcpAppTools[0]` when no real call matches yet — preserving the "always available once supported" behavior the second revision introduced.
- **`useOpenMcpAppCanvas`'s signature changed** from `(stage: Stage, canvasKey?, toolCall?)` to `(match: McpAppToolRef, canvasKey?, toolCall?)`, reading `match.toolsetId`/`match.resourceUri`/`match.toolName` directly instead of `stage.mcp_app.*`.
- **`mcpAppCanvasKey`** dropped its `stage` parameter (`${messageIndex}:mcp-app:${stage.index}` → `${messageIndex}:mcp-app`) since there's exactly one canvas trigger per message now, not one per stage.
- **Auto-open** (unchanged in spirit from the first revision, updated for the new shape). The canvas still opens automatically, without a click, for the last message with a match. If multiple messages qualify, only the **last** one auto-opens — `findLastMcpAppMessage` scans messages newest-first. `useAutoOpenMcpAppCanvas`'s guard ref is now keyed on `${messageIndex}` alone (no stage index).
- The manual button remains available even after auto-open (e.g. if the user closes the canvas and wants to reopen it, or wants to open an *earlier* message's app instead of the auto-opened last one).

**Fourth revision, reversed per explicit user direction ("the app should show inline in the conversation, not open full-screen in canvas automatically"):** `useAutoOpenMcpAppCanvas` and `findLastMcpAppMessage` are deleted outright — the canvas (full-width, `AttachmentCanvas`) is never opened without an explicit click again. In their place, `apps/chat/src/components/ConversationView/McpAppInlinePreview/McpAppInlinePreview.tsx` (see D11) renders the matched app inline, compact, under every qualifying message unconditionally — taking over the "always visible once supported" role the third revision's unconditional-visibility change gave the trigger button. The message-actions-bar button is gone too, replaced by the inline preview's own overlaid expand-to-canvas icon button. `mcpAppCanvasKey`/`isMcpAppOpenedInCanvas` in `ConversationMessageItem.tsx` are unchanged and still used — they now govern only whether the inline preview or the "Opened in Canvas" placeholder renders for a message whose canvas was manually expanded.

### D11: Inline preview under the message is the default surface; the full-width canvas is manual-only

**Problem this reverses:** the third revision's auto-open (unmodified since the first revision) meant every MCP-Apps-capable turn silently took over the full-width `AttachmentCanvas` the moment a matching message rendered — no click, no per-user opt-in. This is exactly the "steals focus/scroll position" risk called out below (previously accepted), and it also meant the app was an all-or-nothing experience: full canvas or nothing, no lightweight way to just glance at the widget's output.

**Fix**: `McpAppInlinePreview` (`apps/chat/src/components/ConversationView/McpAppInlinePreview/`) mounts the same `McpAppCanvasRenderer` (now exported from `libs/attachment-canvas`, see D10's sibling change) inside a fixed-size (360px-tall) box directly in the message's `afterContent`, seeded via `useMcpAppInlinePreview` — a lighter sibling of `useOpenMcpAppCanvas` that fetches the resource HTML and resolves the tool result without touching `AttachmentCanvas`'s panel/loading-state machinery, so it can render alongside the message instead of taking over a side panel. Its `hostContext` uses `displayMode: 'inline'` (vs. the canvas's `displayMode: 'fullscreen'`, both real values from the MCP Apps spec's `McpUiDisplayModeSchema`), so a well-behaved app can lay itself out differently for the two surfaces.

An overlaid `GhostIconButton` (`IconArrowsMaximize`) on the inline preview calls the same `onOpenApp`/`useOpenMcpAppCanvas` path the old button used, expanding into the full-width canvas on demand — nothing about the canvas's own fetch/seed/error handling changed, only how it gets triggered.

**Bug fix — one-frame flash when the sandbox proxy isn't configured.** `useMcpAppInlinePreview`'s status `useState` originally seeded `Loading` unconditionally; `McpAppInlinePreviewStatus.Unavailable` was only set inside a `useEffect`, which runs after the browser paints. With `MCP_APP_SANDBOX_URL` unset, this meant every qualifying message's preview box (border, header, loading spinner) rendered for one frame before disappearing, instead of never appearing at all. Fixed by lazily initializing `status` from `match`/`mcpAppSandboxUrl` directly, so an unconfigured sandbox renders `Unavailable` (nothing) from the very first render.

**Trade-off, resolved**: the canvas and the inline preview initially each independently fetched the resource HTML and (per D10) could each independently re-call the tool live — expanding to canvas after already viewing the inline preview meant a second `fetchMcpAppResourceHtml` and potentially a second live tool re-call. Fixed by D12's shared per-conversation cache: both surfaces now check it before fetching, so switching between them for the same message only ever fetches/re-calls once.

### D12: Per-conversation response cache; canvas fills its container and reports live resize

**Cache**: `apps/chat/src/hooks/attachment/useMcpAppResponseCache.ts` holds one `Map<mcpAppCanvasKey, {html, toolResult}>` per open conversation (a `useRef` reset whenever `conversationId` changes, so switching conversations never serves another conversation's stale entries). `ConversationView` creates one instance and passes it to both `useOpenMcpAppCanvas` and (via `ConversationMessageItem`) `useMcpAppInlinePreview`, so D11's inline preview and the full canvas reuse the same fetch/live-tool-recall for a given message instead of repeating it on every switch. A manual reload button — next to the expand button on the inline preview's header, and a new header action in `AttachmentCanvas` itself (gated on a new `McpAppCanvasContent.onReload` callback and `labels.mcpAppReloadLabel`) — invalidates the cache entry and re-fetches from scratch.

**Canvas sizing**: confirmed via user report that the canvas rendered the app at a fixed `736×600` — `AppFrame` sizes its sandbox iframe to the *app's own reported content size* (an inline pixel `style.width`/`style.height`, driven by the app's `onsizechange` notifications), which is the right default for D11's compact inline preview but left the full-width canvas looking undersized against its own panel. `McpAppCanvasRenderer` now forces the iframe to `100%`/`100%` via a CSS `!important` override (`.fullscreenFrame :global(iframe)`) whenever `content.hostContext.displayMode === 'fullscreen'` — i.e. only for the canvas, never the inline preview, which still sizes to content per the original ask.

**Live resize reporting**: previously the host never told the mounted app how much space it actually had, beyond whatever `hostContext` was built once at open time — confirmed no `containerDimensions` was ever set. `McpAppCanvasRenderer` now watches its own root element with a `ResizeObserver` and merges the live pixel size into `hostContext.containerDimensions` before passing it to `AppRenderer`; `AppRenderer` already calls the AppBridge's `setHostContext` whenever its `hostContext` prop changes, which sends a real `ui/notifications/host-context-changed` message — so drag-resizing the canvas panel (or a window resize) now reaches a well-behaved app live, not just once at mount.

### D8 (revised): Real tool-call data comes from `custom_content.state`, in one of two confirmed orchestrator-specific shapes — not `stages[].content`'s markdown

**Confirmed via spike** against a real MCP-Apps-capable deployment (StatGPT): the streamed SSE delta carries an orchestrator-specific `custom_content.state` object — gated behind that orchestrator's own `show_debug_stages` flag, **not** a standard DIAL Core or MCP Apps contract — containing `state.tool_messages`, an array of LangChain-style messages: an `'ai'`-typed entry with `tool_calls: [{ name, args, id }]` (the model's real, structured tool-call request) and a matching `'tool'`-typed entry with `tool_call_id`/`name`/`content` (the tool's result, still plain text, not the tool's true `structuredContent`).

**Second shape confirmed via a different deployment/agent.** A second, unrelated app streams the same kind of data under `state.tool_execution_history` instead — OpenAI chat-completion message shape rather than LangChain's: an `{ role: 'assistant', tool_calls: [{ id, type: 'function', function: { name, arguments: <JSON string> } }] }` entry (request) paired with an `{ role: 'tool', tool_call_id, content }` entry (result, plain text, same as the first shape). The two shapes differ in field name (`tool_messages` vs `tool_execution_history`), discriminator (`type` vs `role`), and how the call itself is nested (`tool_calls[].{name,args}` directly vs `tool_calls[].function.{name,arguments}`, the latter's `arguments` being a JSON-encoded string that must be parsed, not an object). `libs/chat-shared`'s `MessageState` declares both fields as independent optionals (`tool_messages?`, `tool_execution_history?`); a given orchestrator is expected to emit at most one. `apps/chat/src/utils/mcp-app.ts`'s `resolveToolCalls(state)` normalizes whichever is present into one internal `Map<id, {name, args, result}>` shape that the rest of the module (`findMcpAppForMessage`, `resolveMcpAppToolCallSeed`) reads uniformly.

This field was previously invisible end-to-end: both `apps/chat-api/src/conversations/utils/apply-chunk.server.ts` (persisted message) and `apps/chat/src/utils/apply-chunk.ts` (live streaming) only ever cherry-picked known `custom_content` fields (`form_schema`, `attachments`, `stages`, `annotations`) and silently dropped anything else — `state` never reached `Message.custom_content` on either path. Fixed by adding `state` (replace-wholesale semantics, since it arrives as one complete snapshot per turn, not token-streamed like `content`) to both merge functions, and adding `ToolCallRequest`/`ToolStateMessage`/`OpenAiToolCall`/`ToolExecutionHistoryMessage`/`MessageState` types to `libs/chat-shared`.

`apps/chat/src/utils/mcp-app.ts`'s `resolveMcpAppToolCallSeed(message, toolName)` (renamed from `mockMcpAppToolCall`, which previously regex-parsed `"> ##### Request:\n\`\`\`json\n{...}\n\`\`\`"` / `"> ##### Response:\n\`\`\`...\n\`\`\`"` out of a stage's hand-formatted `content` markdown) now reads `toolInput` directly as the call's real structured arguments (parsed from JSON for the OpenAI shape) and `toolResult` from the matching result message's `content` (still a lossy plain-text wrap, since the state bag itself carries no `structuredContent` in either shape — this part remains a workaround, not a full fix).

**Confirmed via spike, end-to-end against a real widget** (the "weather" toolset's `get_weather` MCP App): the plumbing works exactly as designed — `AppRenderer`'s own internal debug trace (`[AppFrame] Sending tool input:`/`Sending tool result:`) shows both notifications successfully delivered to the guest iframe after it reports `ui/notifications/initialized`, and the guest acknowledges with a `size-changed` notification (it re-rendered). The widget still shows no visible weather data, though. This is the lossy-`toolResult` limitation above manifesting concretely, not a delivery bug: the widget's own JS almost certainly expects structured fields (temperature, condition, forecast) to draw its UI, but `toolResult.content[0].text` is only ever the orchestrator's flattened prose summary — there is no `structuredContent` anywhere in `custom_content.state` to seed instead. Fixing this at the root would require DIAL Core's orchestrator to preserve the tool's real `structuredContent` in the state bag it streams, which is out of this repo's control (same category as the D8 scope caveat and the correlation gap in Risks below) — see **D10** for the temporary client-side workaround adopted instead.

**Scope caveat, narrowed but not closed:** two orchestrator shapes are now confirmed and handled, but this remains an enumerated allowlist, not a general DIAL Core or MCP Apps spec guarantee — a third orchestrator may emit neither field, or a shape not yet seen. `findMcpAppForMessage`'s fallback to `mcpAppTools[0]` when neither field yields a name match means the trigger still degrades gracefully (shows, but without a name-matched result) rather than breaking for orchestrators outside the two known shapes.

**Why the message level, not per-stage.** A message can carry multiple stages, but only one canvas can be open at a time (existing `AttachmentCanvas` mutual-exclusivity invariant) — surfacing the trigger once per *message* rather than once per *stage* avoids offering multiple simultaneous triggers for outcomes that can only ever open the same single canvas slot.

### D9: Tool discovery also resolves an internally-delegated toolset, not only the selected deployment's own MCP capability

**Confirmed via spike**, using a real quick app ("NT Weather App"): `useMcpAppTools(deployment)` originally gated entirely on the *selected deployment's own* `features.mcp` flag, then called Core's `tools/list` against that same deployment id. This works for a toolset, or an application that is itself an MCP server — but a quick app is neither: it's a plain custom application (`deployment.features.mcp` is `undefined`) that internally calls a separate MCP-capable toolset ("weather", exposing `get_weather`) to do its work. Nothing in `DeploymentItemDto`/`ApplicationDetailsDto` (or `applicationProperties`, a free-form bag) links the application back to that toolset — Core does not expose this relationship to the host. Result: `mcpAppTools` stayed permanently empty for this conversation, and the trigger never appeared, even though the message-level tool-call correlation (D8) already resolved a real call named `weather_get_weather`.

**The only available thread connecting a message's tool call back to a toolset is the naming convention itself.** Confirmed via spike: the orchestrator names a delegated tool call `{toolsetDisplayName}_{toolName}` (`weather_get_weather` = toolset `weather` + tool `get_weather`). A bare toolset id (`weather`) does not resolve on Core (`404` on `tools/list`) — the toolset must be addressed by its real, bucket-qualified resource path (`toolsets/{bucket}/weather__0.0.1`), which is only available via the already-loaded `listToolsets()` catalog (`DialToolsetDto.id`), not derivable from the name alone.

**Fix**: `useMcpAppTools` now merges two independent sources instead of one:
1. **Direct** (unchanged) — the selected deployment's own `features.mcp`-gated `tools/list`.
2. **Indirect** (new) — `apps/chat/src/utils/mcp-app.ts`'s `collectToolCallNames(messages)` collects every real tool-call name seen in the conversation so far; for each toolset in the already-loaded `toolsets` catalog (`useDeployments()`) whose `displayName` prefixes one of those names, `listMcpAppTools(toolset.id, 'toolset')` is called against that toolset's real id, and each returned tool is re-prefixed (`${toolset.displayName}_${toolName}`) so it matches the `{toolset}_{tool}` form already used by D8's name-matching in `findMcpAppForMessage`/`resolveMcpAppToolCallSeed` — no changes needed there.

**Second bug found via the same spike, after tool discovery itself worked**: the canvas opened and `tools/list` resolved correctly, but the mounted app rendered with no seeded `toolInput`/`toolResult` — empty despite a real, matched tool call. Root cause: `McpAppToolRef.toolName` (the *correlation* name, re-prefixed to `weather_get_weather` so it matches the message's tool-call name) was also being passed as `AppRenderer`'s `toolName` prop in `useOpenMcpAppCanvas.ts` — but the mounted widget only recognizes its own real, unprefixed name (`get_weather`) and silently ignores a seed addressed to a name it doesn't know. Fixed by splitting the two concerns: `McpAppToolRef` now carries both `toolName` (correlation name, used by `resolveMcpAppToolCallSeed`/`findMcpAppForMessage`) and `mcpToolName` (the toolset's real declared name, used for `AppRenderer`'s `toolName` prop and by extension the mounted app's own tool-identity checks). For directly-discovered tools the two are identical; only the indirect path's re-prefixing makes them diverge.

**Scope caveat**: prefix-matching against `displayName` is itself an unverified convention (like D8's two orchestrator shapes), not a Core/MCP Apps spec guarantee — a toolset name containing an underscore, two toolsets sharing a name after normalization, or an orchestrator that doesn't follow the `{toolset}_{tool}` convention would not be discovered this way. Indirect discovery only ever adds entries; it never suppresses the direct path, so a toolset/application that already declares `features.mcp` is unaffected.

**Known gap — both discovery paths can fail for a quick app that is itself the MCP server.** Confirmed via end-to-end testing against "NT AWS Explore": a quick app whose tool names are prefixed with the *application's own name* (e.g. `NT_AWS_Explore_search_amazon`) rather than a separate toolset's name will not be discovered by indirect discovery — no toolset in the catalog shares that prefix. Direct discovery also won't fire unless the deployment has `features.mcp: true` set in DIAL Core config. In this scenario the canvas never opens. The immediate workaround is to set `features.mcp: true` on the application deployment in Core config — that enables direct discovery via the `application` kind path (D4). However, both current discovery paths are **workarounds that depend on either admin-set flags or name-guessing conventions**. The proper long-term fix is a Core-side contract by which the host can reliably enumerate the MCP-Apps-capable tools of any deployment it is about to converse with, without needing `features.mcp` to be explicitly configured or inferring toolset membership from call-name prefixes. This likely means Core exposing an explicit mechanism — e.g. a deployment-agnostic `tools/list` endpoint or a dedicated field in `DeploymentItemDto`/`ApplicationDetailsDto` — that returns tool metadata including `_meta.ui.resourceUri` for any deployment that has MCP capabilities, regardless of whether it is classified as a toolset, application, or quick app. Tracked as a follow-up in `tasks.md`.

### D10: Live re-call of the tool as a **temporary** workaround for D8's lossy `toolResult`, gated to `kind === 'application'` only

**Problem, restated from D8/the weather-widget spike above:** `custom_content.state` never carries a tool's real `structuredContent` — only the orchestrator's flattened prose summary in `content`. A widget that expects structured fields to draw its UI (the common case) silently renders empty, exactly as observed end-to-end (D8). This is a DIAL Core orchestrator gap, not fixable from this repo.

**Workaround**: since the original `toolInput` *is* available with full fidelity (D8), and `chat-api`'s `mcp-app-tool-call` endpoint (built for the mounted app's own self-initiated `onToolCall`, D4) can invoke that same tool directly against its live MCP session, `apps/chat/src/utils/mcp-app.ts`'s `resolveMcpAppToolResult(match, seed)` re-calls the tool with its original arguments and seeds the canvas with that live, structured `CallToolResult` instead of the lossy reconstruction — falling back to `seed.toolResult` if the call fails or there's nothing to replay.

**Gated to `match.kind === 'application'` only — not `'toolset'`.** `McpAppToolRef.kind` is `'application'` only for a deployment that is *itself* the MCP server (D4's direct-discovery path when `deployment.type === 'application'`); `'toolset'` covers both a direct toolset deployment and D9's indirect, name-prefix-*guessed* matches. For the indirect path in particular, the tool/toolset identity is inferred from a naming convention (D9's scope caveat), not confirmed — re-calling on a guessed match risks invoking the wrong tool, or re-triggering a non-idempotent side effect (e.g. "send email", "create ticket") for a tool the orchestrator already executed once for real. Direct toolset deployments were left in the same gated-off bucket rather than special-cased, since the risk/benefit didn't warrant the extra branch for this workaround's scope; revisit if toolset-kind MCP Apps turn out to need it too.

**Explicitly temporary.** This re-call is a client-side patch over a Core-side gap, not a fix — it doubles the number of tool invocations for every `kind === 'application'` MCP App canvas open (once by the orchestrator during the actual turn, once again here), costs extra latency (confirmed via testing: a real call took ~38s, prompting `apps/chat-api/src/toolsets/mcp-app.service.ts`'s `TOOL_CALL_TIMEOUT_MS` to be raised from 30s to 60s), and only works at all when the deployment still has a live, callable MCP session outside the original conversation turn (not guaranteed for every deployment/tool). **Remove this workaround once DIAL Core's orchestrator preserves the tool's real `structuredContent` in `custom_content.state`** (the D8 gap) — at that point `resolveMcpAppToolCallSeed` alone becomes sufficient and `resolveMcpAppToolResult`'s live-call branch should be deleted.

### D6: CSP/permission enforcement — layered across Core, the sandbox proxy, and the lib; no tool-declared payload to intersect

Core's `mcp/resources` endpoint sets its own fixed `Content-Security-Policy` on the resource response (`sandbox allow-scripts` without `allow-same-origin`, `frame-ancestors 'self'`, `default-src 'none'`, ...) and `X-Content-Type-Options: nosniff` — `chat-api`'s GET mirrors these headers verbatim (D4). Once `apps/chat` fetches that response body and hands it to `AppRenderer` (D3), the *browser-enforced* isolation shifts to the `mcp-app-sandbox-proxy` app (D7): its fixed response CSP plus the inner iframe's `sandbox` attribute (hardcoded to `allow-scripts allow-same-origin allow-forms` by `apps/mcp-app-sandbox/src/app/sandbox-page.ts`, matching the outer host↔proxy iframe hardcoded by `@mcp-ui/client`'s `AppFrame`; `allow-top-navigation` is never included) are what actually constrain the rendered HTML in the browser, since the HTML is no longer loaded as a direct HTTP response the browser applies Core's header to — it's injected by the proxy's relay script. `allow-same-origin` grants the tool HTML the sandbox proxy's own isolated origin (not the chat origin); chat cookies, localStorage, and DOM remain inaccessible because the sandbox proxy is deployed at a distinct origin from the chat app. There is no `_meta.ui.csp`/`_meta.ui.permissions` JSON payload for `chat-api` or the renderer to read or intersect against a host maximum; Core's Phase 1 doesn't surface one, and `mcp-app-sandbox-proxy`'s v1 CSP is a fixed default rather than per-tool-configurable (see D7's noted follow-up). If a later MCP Apps phase adds tool-declared permissions (mic/camera/etc.), that becomes a new requirement against a real payload shape at that time — not speculatively built now.

## Risks / Trade-offs

- **[Resolved] DIAL Core's MCP Apps Phase 1 (PR #1745, merged 2026-07-31) confirmed the resource-fetch endpoint and tool-metadata rewrite; no Core change is a blocker for this change.** Residual note: `_meta.ui` rewriting only touches the `domain` field and only fires when a deployment's admin has set `mcp_apps.domain_override` — a toolset without that config will never produce a stage with a UI resource, so the inline preview simply won't appear for it (expected, not an error state).
- **[Risk] `@mcp-ui/client`/App Bridge is a young, evolving dependency (extension not yet 1.0) — breaking changes are likely.** → Mitigation: isolate all direct usage inside `McpAppCanvasRenderer`, matching how `VisualizerCanvasRenderer` isolates `@epam/ai-dial-visualizer-connector`; version-pin and document the upgrade path.
- **[Risk, accepted] `mcp-app-sandbox-proxy` (D7) is new deployable infrastructure — a whole app plus an isolated-origin deployment/DNS/cert, not just a library dependency.** → Accepted per explicit direction to prefer the more secure option. Mitigated by treating its deployment exactly like operator-registered visualizer URLs: optional, absence-tolerant (`MCP_APP_SANDBOX_URL` unset ⇒ feature simply doesn't surface), and isolated to its own tiny app so it carries no other app's blast radius.
- **[Risk] A malicious or buggy MCP App could attempt excessive/looping `tools/call` traffic through the proxy.** → Mitigation: rate-limit the `chat-api` proxy endpoint per-conversation/per-toolset with `@nestjs/throttler`, same posture as other chat-api endpoints; the sandbox iframe cannot bypass this since every call is server-relayed through Core's existing generic MCP proxy.
- **[Trade-off, superseded twice] Manual "Open app" action → auto-open → manual-only again.** v1 was manual-only, to preserve `AttachmentCanvas`'s no-stolen-focus invariant. That was reversed (D5, third revision) to auto-open the canvas for the last mcp_app-carrying message. That in turn is reversed again by D5's fourth revision/D11, per explicit user direction: the canvas never auto-opens now — every qualifying message gets an always-visible **inline** preview instead (D11), and the canvas is reached only via that preview's manual expand button. Net effect versus the original v1: still no auto-opened canvas, but now with an always-visible inline surface where v1 had only a button.
- **[Risk, resolved] Auto-open (D5, third revision) could steal focus/scroll position if a new mcp_app message arrived while the user was reading elsewhere in a long conversation — exactly the concern the original manual-only decision was meant to avoid.** Previously accepted as a trade-off; now moot — D5's fourth revision/D11 removed auto-open entirely, so nothing ever takes over the canvas without a click.
- **[Risk, confirmed via spike] Core's `mcp/resources` mimetype allowlist appears to do a strict/exact match against the full `Content-Type` header, rejecting the MCP Apps spec's own `;profile=mcp-app` parameter convention.** Probing a real toolset's `ui://weather/mcp-app.html` resource against a live Core deployment returned `502 Unsupported resource mimeType: text/html;profile=mcp-app` — the upstream MCP server's resource legitimately declared `Content-Type: text/html;profile=mcp-app` (the standard way an MCP App resource signals itself), yet Core's allowlist check (Context, PR #1745) evidently compares the header verbatim against bare types like `text/html` rather than parsing out the base media type before comparing. Any upstream MCP server that follows the MCP Apps spec's `profile` parameter convention will hit this, regardless of what `chat-api`/`apps/chat` do — the rejection happens entirely inside Core, before any response reaches this repo's proxy. → Mitigation: none available from ai-dial-chat's side; this is a Core-side fix (parse/strip parameters before the allowlist comparison in `McpResourceController`). Until fixed, an MCP App resource author can work around it by serving a bare `Content-Type: text/html` (no `;profile=mcp-app`) — confirmed as a viable workaround for a server we control, but loses the spec's intended signal and isn't something we can require of third-party MCP servers. Flag this to the Core team; track separately from the `_meta.ui.resourceUri` field-name risk below, since this one is confirmed and reproducible while that one remains unconfirmed either way.
- **[Risk, confirmed via spike, implementation defects — fixed] Four independent bugs surfaced end-to-end spike testing against a real DIAL Core deployment and a real upstream MCP server, all now fixed in code:**
  1. Frontend double-encoding of an already-percent-encoded deployment/toolset id (`%20` → `%2520`) in `apps/chat/src/server-api/mcp-apps.ts` — fixed with decode-then-encode helpers mirroring `utils/mcp-endpoint-url.ts`'s established pattern.
  2. `chat-api`'s `mcp-app-tool-call` POST 403'd — `apps/chat/src/server-api/mcp-apps.ts` used a raw `fetch` instead of the shared `post()` helper in `base.ts`, so it never attached `X-CSRF-Token`. Fixed by switching to `post()`.
  3. `chat-api`'s `McpAppService.rpcRequest` (`tools/list`/`tools/call`) 404'd against `/v1/deployments/{toolsetId}/mcp` — that generic MCP JSON-RPC proxy is prefix-specific by deployment kind (`/v1/toolset/{id}/mcp` for toolsets vs `/v1/deployments/{id}/mcp` for applications, mirroring `apps/chat/src/utils/mcp-endpoint-url.ts`'s `buildToolsetMcpUrl`/`buildApplicationMcpUrl`), unlike the GET resource-fetch endpoint (which genuinely is deployment-generic, per the Resolved bullet above). Fixed by adding a toolset-only `toolsetMcpProxyUrl` used exclusively for the JSON-RPC proxy.
  4. Same call then 406'd, then 503'd — the MCP Streamable HTTP transport requires `Accept: application/json, text/event-stream` on every POST (missing → 406), and once added, Core's proxy could reply as SSE rather than a bare JSON object, which `rpcRequest` didn't handle (unhandled → parse failure → generic 503). Fixed by adding the header and an SSE-body parser (`parseJsonRpcSseBody`) that activates based on the response's `Content-Type`.
- **[Risk, confirmed via spike] DIAL Core's generic MCP resource-fetch endpoint rejects the MCP Apps spec's own `;profile=mcp-app` `Content-Type` parameter convention** — see the mimetype bullet above (kept separate; already documented in detail).
- **[Risk, confirmed via spike, blocking] `Stage.mcp_app` does not arrive "wire-verbatim" for any tested Application/orchestrator deployment — the correlation between a called tool and its declared `_meta.ui.resourceUri` does not exist anywhere in the chain this change can control.** Full evidence chain, gathered by instrumenting raw-wire logging at three points (frontend SSE delta merge, backend SSE relay before any merge, and the post-stream server-persisted-conversation reload):
  - **Confirmed correct**: the real weather MCP server declares `_meta.ui.resourceUri` (and `_meta['ui/resourceUri']`) exactly per the MCP Apps spec — on the **tool definition** in `tools/list`'s response (`{"_meta":{"ui":{"resourceUri":"ui://weather/mcp-app.html"}}}`), discovered once per session, not re-sent on every `tools/call` result (which carries only `content`/`structuredContent`, confirmed via a direct curl to the MCP server). This supersedes the earlier "field name unconfirmed" framing below — the field name is `resourceUri`, confirmed.
  - **Confirmed broken**: a real conversation against `NT Weather App` (an Application that internally calls the `weather` toolset's `get_weather` tool) produces a stage whose raw wire JSON — logged unmodified at the earliest possible point, `apps/chat-api/src/conversations/conversation.service.ts`'s `relayModelCompletion`, before any merge/typing touches it — contains only `index`/`name`/`content`/`status`. `content` is a hand-formatted human-readable "> ##### Request/Response" markdown block the orchestrator itself generates; nothing from the tool result's declared `_meta` survives into it. The same is true of the post-stream server-persisted reload (`GET /conversations`), so this isn't a streaming-vs-final-state gap either.
  - **Confirmed no client-side workaround exists**: `chat-api`'s own deployment metadata (`RawDeploymentDto`) has no field naming which toolset(s) an Application calls internally — the closest candidates (`mcp` — only populated when the *Application itself* is MCP-capable, which `NT Weather App` isn't per its own `"Application doesn't support MCP protocol"` response tested earlier; `application_properties` — an unstructured bag with no guaranteed schema) cannot generally reconstruct the correlation after the fact.
  - **Conclusion**: the only party that ever holds both halves simultaneously — "I just called toolset X's tool Y" and "tool Y declares `_meta.ui.resourceUri` Z" — is Core's own agent/orchestrator execution engine, at the moment it makes the internal tool call. It does not currently attach that pair to the stage it emits. This is a Core/agent-framework-side gap, not something fixable inside `ai-dial-chat`. → **No mitigation available from this repo.** For continued development, `ConversationMessageItem.tsx`'s `mockMcpAppOnStages` fakes the correlation client-side (matching a stage named `"Calling <tool> via MCP"` and attaching the known-working debug toolset id + resource URI) purely so the real "Open app" trigger (D5), `useOpenMcpAppCanvas`, and `McpAppCanvasRenderer` can be exercised end-to-end while this gap is open — it is explicitly marked spike-only and must be removed once Core's orchestrator sends this correlation for real. Escalate to the Core/agent-framework team as a required Phase 2 addition to PR #1745's work.
